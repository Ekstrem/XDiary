# ADR-032: APIM стоит в пути трафика — этап 2 наступил (меняет ADR-023 в части роли APIM)

- **Статус:** Предложено — ждёт кворума команды и вердикта владельца
- **Дата:** 2026-11-05
- **Источник:** факт, зафиксированный @DO и проверенный снаружи: с `DO-076` (2026-11-05) публичный вход идёт через APIM; расхождение с `ADR-023` найдено @DO, передано @TL (`11:13`), зона — @AR
- **Связанные ADR:** 023 (APIM как контрольная плоскость), 025 (роли APIM/YARP), 026 (маршрутная авторизация), 030 (единственный шлюз — Предложено), 031 (канон измерений — Предложено)
- **Связанные решения:**
  - **ADR-023 → почему меняется:** ADR-023 (Принято, 2026-11-09) описывает **этап 1**: APIM = контрольная плоскость (реестр спецификаций, версии, портал), **вне пути запросов**, трафик идёт `Funnel → YARP`. Факт с 2026-11-05: трафик идёт `Funnel → Caddy:8081 → APIM:18082 → сервис`. То есть утверждение ADR-023 противоречит измерению. **Комплаенс прошлого (§3.3 ADR-023):** не отступает по существу — реестр и контракт-first остаются; меняется **роль APIM** («контрольная плоскость» → «контрольная плоскость **и** путь трафика»). Правка тела ADR-023 **не производится** (правило владельца 2026-11-05: старые ADR меняют только статус).
  - **ADR-025 → согласуется:** ADR-025 уже выбирал «APIM в тракте на этапе 2»; этот ADR фиксирует, что этап 2 **наступил**, и не меняет разделение ролей.
  - **ADR-030 → не дублирует:** ADR-030 — про **единственный** шлюз (вывод YARP). Здесь — про то, что APIM **в пути**; решения независимы, порядок любой.
- **Заменяет:** — (меняет **часть** ADR-023; сам ADR-023 остаётся документом, меняется только его статус после согласования этого ADR)
- **Владелец решения:** @EX — согласование ожидается

## 1. Контекст

`ADR-023` (Принято 2026-11-09) фиксировал: APIM — **контрольная плоскость** (импорт `openapi/*.json`, версии, портал,
drift-check), **вне пути запросов**; трафик — `Funnel → YARP → сервисы`. Это было верно для этапа 1.

2026-11-05 (`DO-076`) публичный вход переключён: `Tailscale Funnel → Caddy :8081 → APIM :18082 → сервисы`. Проверено **снаружи**:

| Проверка | Результат | Что доказывает |
|---|---|---|
| `/api/v1/catalog` | `401` + `x-gravitee-request-id`, `-transaction-id`, `-client-identifier` | ответил APIM |
| несуществующий путь `/api/v1/nonexistent-path-xyz` | `404 No context-path matches the request URI` | маршрутизация APIM (у YARP было бы `401`) |
| `/internal/journal/records` | `404` | внутренний API не опубликован |
| `/health` | `200`, `x-gravitee` = 0 | осознанное исключение: `/health` идёт мимо APIM |

Таким образом **документ утверждает то, чего больше нет**, и на него ссылаются как на норму. Это третий случай за сутки
(до него: `migrations.md` «схему создают пакеты» — опровергнуто кодом; канон измерений, дописанный в принятый `ADR-026`).
Класс один: **норма, не сверенная с замером**.

## 2. Варианты решений

### Вариант A — новый ADR «APIM в пути», ADR-023 получает статус «Пересмотрен»

- **Описание:** этот документ фиксирует наступление этапа 2 и его доказательства; `ADR-023` меняет **только статус**.
- **Плюсы (исчерпывающе):**
  - история ADR-023 сохраняется: видно, что планировали этап 1 и почему перешли;
  - норма соответствует замеру, и ссылка на неё воспроизводима (таблица выше);
  - не нарушает правило владельца (старые ADR не переписываются);
  - хорошо ложится на ADR-025 («APIM в тракте на этапе 2») и ADR-030 (единственный шлюз).
- **Минусы (исчерпывающе):**
  - ещё один документ; два ADR про APIM (023 — план, 032 — факт), и читателю нужна ссылка между ними;
  - статус ADR-023 меняется только после согласования этого ADR — до тех пор есть окно, где `Принято` противоречит факту.
- **Соответствие целям:** да.

### Вариант B — внести правку прямо в ADR-023 («этап 1» → «этап 2»)

- **Плюсы (исчерпывающе):** один документ, ссылки не меняются.
- **Минусы (исчерпывающе):** **прямо нарушает правило владельца** («переписывать старые ADR нельзя»); стирается след о том, что было решено на этапе 1 и почему; следующий автор снова «поправит на месте».
- **Соответствие целям:** нет.

### Вариант C — оставить как есть и полагаться на `ADR-025` («этап 2 в тракте»)

- **Плюсы (исчерпывающе):** ничего не делать.
- **Минусы (исчерпывающе):** `ADR-023 (Принято)` продолжает утверждать «APIM вне пути», и любой, кто читает его первым, получает **ложную норму**; именно это и произошло (вопрос @DO → @TL); тестовые и деплойные проверки ориентируются на статус, а не на факт.
- **Соответствие целям:** нет.

## 3. Выбранное решение

**Вариант A.** Зафиксировать: **APIM стоит в пути трафика с 2026-11-05** — это и есть этап 2 `ADR-023`, наступивший по `ADR-025`.
`ADR-023` получает статус **`Пересмотрен (дата): роль APIM — см. ADR-032`** — **после** согласования владельцем.

**Что остаётся без изменений:** реестр `openapi/*.json` как канон контракта, контракт-first, `api-index.yaml` как источник
`operationId`, этап 1 как исторический план. **Что фиксируется:** APIM в пути; `/health` — исключение (мимо APIM);
периметр держат **сервисы** (`[Authorize]`), а не APIM (JWT-план отложен — `ADR-026`).
