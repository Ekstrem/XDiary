# ADR-024: «Я» — профиль клиента, а не партнёр (минимальный онбординг)

> ✅ **ПРИНЯТО 2026-11-09 (делегировано владельцем).** Владелец: «Реши по ограниченным контекстам сам,
> скажи мне что проверить». Решение принял @AR на основании ответов владельца (они в `03-ddd/01-entity-map.md` §5).
> Что владельцу проверить — в §6 этого ADR (короткий чек-лист, не пересказ модели).
>
> Исходная постановка: «Клиент (аккаунт: PIN, соматика) и Партнёр (участник акта) — два разных контекста;
> я в акте не выбираю себя — я всегда в сексе». Что поменялось против первой редакции:
> (1) **Privacy — часть Client**, отдельный мелкий BC не выделяем;
> (2) **`orgasms` — словарь участник→оргазмы**, ключ `"me"` законен (у «я» тоже бывает оргазм);
> (3) **Partner может стать клиентом** — `partner.clientId` опционален, это база для будущего
> взаимодействия (чаты/фантазии/игры);
> (4) **имя и пол спрашиваем один раз на онбординге** (пол не меняется за пару дней).

- **Дата:** 2026-11-09

## 1. Контекст
Владелец на тесте: на онбординге нужно **создать карточку партнёра**, чтобы обозначить себя, а затем «я» виден во вкладке «Партнёры» («Евгений» на скриншоте). Для продукта это ошибка: во вкладке «Партнёры» должны быть **другие** люди.

Факт из домена: журнал уже хранит участника как `orgasms[].participant = "me" | partnerId`
(`BC-Journal/02-aggregate-canvas.md`), то есть **«я» уже не требует отдельной сущности `Partner`**. Смешение появилось из реализации (BE-048 добавил `Partner.ClientId`, и «эго»-партнёр = запись с `ClientId` = текущий клиент).

## 2. Варианты решений

### Вариант A — Профиль клиента (имя/пол) в BC-Client; «я» — не партнёр
- **Описание:** `Client` получает профиль (`displayName`, `gender`, `photo?`). Онбординг = один экран «имя + пол». `Partner` — только другие люди; список исключает «я» по определению.
- **Плюсы (исчерпывающе):**
  - совпадает с ожиданием владельца: «имя и пол», а не «создай партнёра»;
  - **один** источник правды для «я» (сейчас он размазан: `Client` + эго-партнёр);
  - список партнёров = другие люди, без фильтров в каждом потребителе;
  - журнал уже умеет `participant = "me"` — переделывать не надо;
  - онбординг короче: один экран вместо «создай сущность, чтобы обозначить себя».
- **Минусы (исчерпывающе):**
  - миграция: существующие эго-партнёры → поля профиля клиента;
  - `Client` расширяется профильными полями (агрегат растёт);
  - надо разобрать ссылки истории: журнал (`author`, `participant`), каталог (`partnerId`), аналитика (MV по партнёрам);
  - FE: новый экран онбординга + раздел «Профиль» вместо «я в партнёрах».
- **Соответствие целям:** онбординг в 1 шаг, «партнёры» = люди, без второго источника правды.

### Вариант B — Оставить эго-партнёра, но скрывать его в API (`isSelf`)
- **Описание:** `Partner` остаётся, добавляется признак «я», `GET /partners` его выфильтровывает; онбординг создаёт его неявно.
- **Плюсы (исчерпывающе):**
  - минимальные изменения бэка (признак + фильтр);
  - быстрый фикс UI-симптома.
- **Минусы (исчерпывающе):**
  - концептуальное смешение остаётся (владелец упрётся снова при первой правке профиля);
  - каждый потребитель обязан помнить про фильтр — риск, что «я» снова утечёт;
  - онбординг по-прежнему внутренне «создаёт партнёра», просто этого не видно;
  - две правды про «я» (Client + эго-партнёр) расходятся при редактировании.
- **Соответствие целям:** симптом уходит, причина остаётся.

### Вариант C — Отдельный агрегат `SelfProfile` (третий контекст/сервис)
- **Описание:** «я» живёт в новом агрегате рядом с `Client` и `Partner`.
- **Плюсы (исчерпывающе):**
  - явное разделение понятий на уровне модели;
  - не меняет существующие контракты `Client` и `Partner` (только добавляет новое).
- **Минусы (исчерпывающе):**
  - третий источник данных о клиенте при том, что `Client` уже хранит телефон/OTP/PIN;
  - лишний сервис/агрегат/миграция ради двух полей;
  - выигрыша против A нет, а стоимость выше.
- **Соответствие целям:** избыточно.

## 3. Выбранное решение
**Вариант A.** «Я» = профиль клиента (`displayName`, `gender`, `photo?`), а не партнёр.
`Partner` — только другие люди. Онбординг состоит из одного экрана: имя + пол →

- **Порядок экранов:** вход (телефон + OTP) → **«Кто вы?» (имя + пол, фото опционально)** → Журнал. Партнёр добавляется **позже** и **необязательно**, когда есть кого добавлять.
- **Где «я»:** раздел «Профиль» (аватар в шапке), не вкладка «Партнёры».
- **Вкладка «Партнёры»:** только другие люди (`GET /api/v1/partners` исключает «я»).
- **Журнал:** участник «я» = `participant = "me"` (уже есть), `author` = клиент.
- **Граница BC (не дублировать имена):** `Client` владеет **только моим** профилем (`displayName`, `gender`, `photo?`). Имя **второго человека** остаётся в `Partner` — из профиля клиента **не проецируется** (иначе одно имя живёт в двух местах и расходится). Журнал и каталог ссылаются на `Partner` для других людей и на `participant = "me"` для меня; `Client.displayName` в `Partner` не копируется и наоборот.
- **`gender` — словарь `male` | `female`, не свободная строка** (решение владельца 2026-11-03 16:54: «обойдёмся двумя»; справочник пола — общий для Журнала/Партнёров/Каталога). Контракт **отвечает 400** на любое другое значение; `other` **не добавляется**. Причина не в строгости: на поле держится аналитика по полу и подбор по типам оргазмов, а «любая непустая строка» пропускает `Other`/`other`/`м` мимо UI. Расширение словаря — новое решение владельца (канвас + контракт + тест одним коммитом).
- **Миграция (поэтапно, без удаления до подтверждения):** (1) значения эго-партнёра переносятся в профиль клиента; (2) эго-партнёр **исключается из выдачи** `GET /api/v1/partners`; (3) **записи не удаляются**, пока владелец не подтвердил — сохраняется id-алиас, чтобы история (журнал/каталог/аналитика) читалась без переписывания; (4) удаление — отдельный шаг после подтверждения.

## 6. Что проверить владельцу (короткий чек-лист, не пересказ модели)

1. **Онбординг после входа** спрашивает **имя и пол** — и сразу журнал, без «создай партнёра».
2. **Вкладка «Партнёры»** не содержит вас самого — только других людей.
3. **«Я»** — в «Профиле» (имя/пол), а не в списке партнёров.
4. **Оргазмы**: в записи акта можно указать их **и себе**, и партнёру (у «я» тоже бывает).
5. **Старые записи не пропали**: журнал показывает историю до изменений; удалённых данных нет.
6. **Профиль правится** (имя/пол можно изменить), но онбординг повторно не спрашивает.

## 4. Последствия
- **Плюсы:** онбординг в один экран; один источник правды для «я»; «Партнёры» = другие люди; журналу менять ничего (`participant = "me"` уже есть).
- **Риски:** миграция эго-партнёров и ссылок истории (журнал/каталог/аналитика) — нужен идемпотентный скрипт с бэкапом; FE-объём (новый онбординг + «Профиль»); расширение агрегата `Client` профильными полями.

## 5. Уточнения по ответам владельца (2026-11-09)

Ответы внесены; они правят три пункта первой редакции:

1. **Privacy — часть `Client`.** «Пусть называется Privacy, но по сути это клиентский профиль + база;
   нет смысла сильно мельчить контексты». Значит: профиль, политика приватности и PIN живут в
   контексте `Client`, отдельный мелкий BC не выделяем. Действие — слить при следующей правке
   домена (после ретро), не сейчас.
2. **`orgasms` — словарь участник → оргазмы**, а не коллекция партнёров: ключ может быть `"me"`
   («у меня тоже бывает оргазм»). В `BC-Journal` формулировку уточнить (сейчас `participant`
   уже допускает `"me"`, но описание читается как «по партнёрам»).
3. **Partner может стать клиентом.** «Может, и фишкой приложения станет их взаимодействие —
   чаты/фантазии/игры… то, что мы делаем, — база для такого взаимодействия». Следствие:
   `partner.clientId` — **опциональная** связь (партнёр без аккаунта → `null`); проектировать
   взаимодействие сейчас не начинаем, это отдельная тема после продуктовой постановки.
4. **Профиль:** `name`, `gender` спрашиваем **один раз на онбординге** («пол не поменяется за пару
   дней») — правим редко, в настройках.

**Не решено и не блокирует:** нужны ли в аналитике метрики «я vs партнёры» — продуктовый вопрос,
технически `participant` это уже позволяет.

### 5.1 Отношение к ADR-008 (границы предметов, не «поглощение»)

- **ADR-008 = аутентификация:** JWT (access/refresh), локальный PIN как слой, PIN per-client,
  валидация JWT в каждом сервисе. Он **не устанавливает границы bounded context** — «Приватность
  и доступ» упоминается там как контекст защиты API.
- **Граница контекста** живёт в `03-ddd/00-context-map.md` (+ `BC-Privacy/*`). Именно её меняет
  этот ADR при принятии: Privacy → часть `Client`.
- Поэтому **ADR-008 не помечаем «поглощён»**: предметы разные. При принятии ADR-024 правится
  **context-map**, а ADR-008 остаётся про JWT/PIN-механику (в нём меняется только одна ссылка —
  «на бэке контекст Приватность» → «в `Client`»).
- До принятия ADR-024 действует текущая граница — два владельца одного контекста не возникает,
  пока карта не изменена.
