# ADR-035: Версионирование артефактов — SemVer у сервисов и фронта, версия API в APIM, digest в lock

- **Статус:** Предложено
- **Дата:** 2026-11-06
- **Источник:** прямой вопрос владельца (чат-тред, 2026-11-06): «я хочу пересмотра ADR про lock … каждая версия микросервиса и фронта должна версионироваться. API в APIM должен версионироваться … хотя бы зафиксируй черновик таких решений». Карточки нет — это ответ на прямой запрос, что допускает `adr-template.md` §0 п.3.
- **Связанные ADR:** 027 (релиз — неизimmutable артефакт по digest), 025 (контракты и APIM), 023 (APIM как этап), 022 (деплой по компонентам), 034 (схемы БД)
- **Связанные решения:** ADR-027 → **не меняется, а доводится до исполнения**: он уже требует «деплой по digest из lock», а сегодня lock содержит **теги** `single-<short>`, не digest; SemVer и версия API — **новое** поверх него. Комплаенс ADR-027 §«Комплаенс» (аудит `podman inspect RepoDigests` против lock) **сохраняется и усиливается** — версия без digest не считается доказанной.
- **Сверка с логом (AGENTS §5.2 п.1), результат прогона, а не пересказ:** `git grep -l -i -e "lock" -e "версионир" -e "semver" -e "digest" -- 04-architecture/ADL` → **15 файлов** (`adr-006/008/013/018/020/021/023/025/026/027/030/031/034`, `README.md`, и сам этот файл). Категория «релиз/артефакт» **уже решена**: `ADR-027` «Релиз — неизменяемый артефакт (deploy по digest)»; `ADR-020` (CD, мутабельные теги) им заменён в этой части. ⇒ этот ADR — **уточняющий** к ADR-027, а не новый «с нуля». Шаг 2: тот же `git grep` по `04-architecture/edm-verification.md` и `03-ddd/TECHDEBT.md` → **1 совпадение, и оно ложное**: `03-ddd/TECHDEBT.md:8` содержит слово `RecomputeLocked` (блокировка пересчёта read-модели), а не «lock» в смысле релиза. ⇒ по существу это **не gap в коде**, а новое решение; но факт совпадения записан, чтобы следующий читатель не решил, что проверки не было. Шаг 3: источник — прямой запрос владельца (карточки нет, допускается §0 п.3).
- **Заменяет:** — (не пересмотр; дополняет ADR-027)
- **Владелец решения:** @AR (архитектура версий) + @DO (реализация релиза)

## 1. Контекст

**Что есть сейчас (факты, 2026-11-06):**

| Артефакт | Как помечается сегодня | Проблема |
|---|---|---|
микросервисы | тег `single-<short sha коммита, тронувшего путь>` в `images.lock` | **нет человекочитаемой версии**: `single-766e59e` не отвечает «какая это версия и что в ней»; разные наборы сервисов несравнимы |
фронт | `APP_VERSION = "0.97"` в `8-front/js/app.js` + имя кэша `sw.js` (`xdiary-v97`) | версия живёт **в коде руками**, не связана с коммитом и не попадает в lock |
APIM | 12 API импортированы из `openapi/*.json` | **версии API нет**: Gravitee присваивает свою, контракт в git — без версии; «какая версия API в проде» не отвечает ни один документ |
lock | 13 строк `service single-<sha>` | **нет digest** (хотя ADR-027 требует деплой по digest), нет даты сборки, нет версии |
прод | образ `single-766e59e` при lock `single-0dd2b57` | расхождение «git ≠ прод» — уже случалось и признано дрейфом |

**Почему сейчас:** за один день 2026-11-06 мы трижды не могли ответить на вопрос «что именно запущено» без ручного `podman inspect`, а `images.lock` дважды расходился с реестром. Это цена **отсутствия версии**, а не конкретного бага.

**Рамка (CN & LS):**
- **Cloud Native:** артефакт неизменяем, идентифицируется **digest**; версия — метка для человека; среда поднимается из манифеста, а не «из того, что нашлось в реестре».
- **Left Shifting:** несоответствие версий ловится **на сборке и в PR**, а не на деплое и не в проде. Гейт, который проверяет версию, должен стоять **раньше** деплоя.

**Ограничения:**
- один VPS и podman, без Kubernetes — манифест остаётся файлом в git;
- приватный фид .NET: локальная сборка недоступна, значит версия вычисляется **в CI**;
- фронт публикуется через GitHub Pages, не через GHCR (в реестре его нет — это норма, а не пробел).

## 2. Варианты решений (минимум 3)

### Вариант A — оставить теги, добавить только подписи (labels/annotations)

- **Описание:** lock остаётся списком `service single-<sha>`; к образу добавляются OCI-labels (`org.opencontainers.image.version`, `revision`, `created`). Версия APIM и фронта не вводится.
- **Плюсы (все, исчерпывающе):**
  - нулевая миграция: 13 строк lock и `deploy.sh` не меняются;
  - labels видны через `podman inspect`, то есть аудит возможен без новых файлов;
  - ничего не ломается в существующих гейтах (`lock-published`, `--verify-registry`).
- **Минусы (все, исчерпывающе):**
  - **не решает вопрос владельца**: «какая версия сервиса» по-прежнему не отвечает (`single-766e59e` — не версия);
  - нет сравнения «prod отстаёт от dev на N версий» — сравнение тегов даёт только «разные коммиты»;
  - **версия APIM и фронта остаётся вне модели** — два из трёх требований не выполнены;
  - left shifting не улучшается: расхождение по-прежнему видно только на деплое.
- **Соответствие целям:** частично (CN — да, LS и версионирование — нет).

### Вариант B — SemVer у каждого сервиса и фронта + digest в lock + версия API в APIM (ВЫБРАН)

- **Описание:**
  1. **Сервис** получает версию `MAJOR.MINOR.PATCH` в `6-msa/BC-<X>/src/<X>.Api/<X>.Api.csproj` (`<Version>`), она же попадает в сборку и в OCI-label;
  2. образ публикуется **двумя** метками: `semver-<версия>` и `single-<short sha>`; в lock пишется **строка из четырёх полей**: `service version tag digest`;
  3. **фронт** получает `8-front/version.json` (единственный источник), из него CI генерирует `APP_VERSION` и имя кэша `sw.js`; в lock — `front version commit`;
  4. **API в APIM** версионируется: версия контракта берётся из `04-architecture/api-index.yaml` (`info.version`), Gravitee API создаётся/обновляется с этой версией, `check_apim_drift` сверяет **версию** и состав операций;
  5. **поверхность версии:** каждый сервис отдаёт `GET /version` → `{version, commit, digest, builtAt}`; прод-аудит — сравнение ответа с lock, а не чтение логов.
- **Плюсы (все, исчерпывающе):**
  - «какая версия в проде» отвечается **одним запросом** и сверяется машинно;
  - lock становится **манифестом релиза**: версия + digest + коммит, то есть ADR-027 исполняется, а не только провозглашается;
  - сравнение сред становится арифметикой: «dev 1.4.2, prod 1.4.0» вместо «разные sha»;
  - версия API в APIM делает контракт **версионируемым**: ломающее изменение = MAJOR, и это видно в реестре, а не в переписке;
  - left shifting: `check_version_consistency` (csproj ↔ label ↔ lock) падает **в PR**, а не на деплое.
- **Минусы (все, исчерпывающе):**
  - миграция: 13 сервисов + фронт + APIM + lock v2 (7 задач ниже);
  - нужен **дисциплина подъёма версии**: без неё SemVer превращается в «всегда 1.0.0» (лечится гейтом, но гейт надо написать);
  - digest в lock меняется при каждой пересборке — lock диффы станут шумнее (митигация: lock обновляется ботом, а не руками);
  - два тега на образ = вдвое больше места в реестре (не критично, но факт).
- **Соответствие целям:** полностью (CN — digest + манифест; LS — гейты в PR; версионирование — сервисы, фронт, API).

### Вариант C — только digest, без SemVer (максимальный CN)

- **Описание:** lock = `service digest` (13 строк); версия — только digest; APIM и фронт тоже по digest/коммиту, без SemVer.
- **Плюсы (все, исчерпывающе):**
  - строго неизменяемо: одно поле, нельзя «пометить не тем»;
  - нет дисциплины подъёма версии — нечему расходиться;
  - минимальный гейт: digest в lock ↔ `RepoDigests` в проде.
- **Минусы (все, исчерпывающе):**
  - **человеку версия не читается**: `sha256:ab12…` не отвечает «это фикс утечки или предыдущий релиз»;
  - нельзя сказать «prod отстаёт на 2 релиза» — только «digest другой»;
  - **не выполнено требование владельца** («каждая версия сервиса должна версионироваться»);
  - откат требует знать digest наизусть/искать в истории — SemVer-тег делает это одной строкой.
- **Соответствие целям:** CN — да, версионирование и LS — нет.

### Вариант D — релизные ветки и теги git (`release/2026.11`, `v2026.11.1`), деплой по тегу

- **Описание:** версия — это git-тег на коммит; ветка `release/*` фиксирует набор; lock генерируется с тега; APIM и фронт версионируются тем же тегом.
- **Плюсы (все, исчерпывающе):**
  - «версия» = git-тег, единый для всего набора: один тег отвечает за все 13 сервисов;
  - привычно для аудита: `git describe` даёт версию;
  - не нужно поле версии в csproj — источник один (git).
- **Минусы (все, исчерпывающе):**
  - **смешивает жизнь кода и релиза**: любой фикс требует нового тега, даже если сервис не менялся;
  - «версия одного сервиса» не выражается — только версия набора, то есть требование «каждая версия микросервиса» не выполнено;
  - тег git мутабелен (переписать можно), значит как идентификатор артефакта слабее digest;
  - ветки `release/*` в общем дереве с одним `main` дают ту же проблему конфликтов, что мы весь день лечим.
- **Соответствие целям:** частично (единый номер релиза — да, по-сервисные версии — нет).

## 3. Выбранное решение

**Вариант B** — потому что он единственный отвечает на все три требования владельца одновременно (версия сервиса, версия фронта, версия API), сохраняет digest как **идентичность** (CN) и даёт проверку **до** деплоя (LS). Вариант A оставляет вопрос без ответа, C стирает человекочитаемость, D смешивает релиз набора с версией сервиса.

**Ключевой принцип:** **digest — идентичность, SemVer — метка для человека, lock — манифест, `/version` — способ проверить прод не глядя в логи.**

## 4. Последствия

### Где именно упирается исполнение — замер 2026-11-10 (@AR), а не мнение

Владелец просил «поднять ADR: релиз = immutable SHA-pinned, не `latest`» (`chat/lm.md` 2026-11-12 21:12).
**Отдельный ADR не поднимаю:** этот документ и есть ответ (принцип «digest — идентичность, SemVer — метка»),
и дубль был бы ровно той ошибкой, за которую я сам себя правил в ADR-029. Ниже — почему решение,
будучи принятым, **не исполняется**, с адресами:

| Факт | Замер |
|---|---|
| работа **была** сделана | `e45f95f1a` (2026-11-11 21:28): в `7-deploy/images.lock` **12** строк с `digest=sha256:` |
| и **стёрта** через 3 минуты | `e198a6bb9`, `61f16284c`, `12eb5aa86` — бот `lock-sync`: `sha256:` → **0**, затем и `commit=` → **0** |
| причина | `tools/gen_images_lock.py:517` (путь `--from-registry`) пишет `"%s %s %s"` — **без** `digest=` и **без** `commit=`; `:519` пишет `commit=`, но без `digest=`; `fill_digests()` (`:565-600`) — отдельный шаг `--fill-digests`, в `--write` не вызывается |
| следствие в деплое | `7-deploy/deploy.sh:54` — «digest в lock нет — старый формат» → тянет **по тегу** |

**Вывод:** обязательство `@DO` в §3 («lock v2 …, `--verify-registry` по digest») выполнено **в коде**, но не
**удерживается автоматикой**: любой прогон регенерации возвращает мутабельную форму. Значит к обязательствам
добавляется условие: **`--write` обязан сохранять `digest=`/`commit=`** (или падать `rc=1`), иначе ADR исполняется
до первого бота.

### Что НЕ входит в этот ADR (осознанно)

- **Kubernetes/Helm** — инфраструктура не меняется, манифест остаётся файлом в git.
