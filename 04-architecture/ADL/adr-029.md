# ADR-029: Межсервисная доставка событий — outbox + HTTP (at-least-once), а не шина

- **Статус:** Предложено
- **Дата:** 2026-11-14
- **Связанные ADR:** 002 (профиль Single), 003 (event store), 005 (event bus), 009 (деплой), 026 (внутренний контур)
- **Заменяет:** — (уточняет ADR-005 в части гарантий межсервисной доставки; ADR-003 остаётся в силе)
- **Уточняет (не заменяет):** ADR-005 «Event Bus» — там решено «InMemory, межсервисные связи через HTTP/шлюз»;
  этот ADR фиксирует **как именно** этот HTTP надёжен. **ADR-003** (Event Store как command store) остаётся в силе.
- **Владелец решения:** @AR (архитектура), исполнитель @BE (`6-msa`), инфраструктура @DO
- **Бэклог:** `edm-debt-plan.md` E1/E5/E6; ADR-026 (внутренний контур); `BC-Journal/02` §2.7; `BC-Partners/02` §11

## 1. Контекст

ADR-005 принял: `EventBus = InMemory`, «события не переживают рестарт и не доставляются между сервисами —
для межсервисных связей используется HTTP/шлюз». То есть **транспорт уже выбран**, но **гарантии не описаны**:
какой HTTP, что при падении приёмника, что при дубле, откуда взять историю для пересборки проекции.

Факты (`origin`, 2026-11-14, проверено командами):

| Что | Факт |
|---|---|
| Шина | в `Journal.Api.csproj` — `DigiTFactory.Libraries.EventBus.InMemory`; `IBusAdapter.Publish` у 10 контекстов = `Task.CompletedTask`; вызовов `Publish` нет |
| Event store | Journal: `AddEventStorePostgres` + `AddEventBusInMemory` **зарегистрированы**, `AddReadStorePostgres` закомментирован (`TODO(E1)`) |
| Путь записи | `JournalCommandRepository.SaveAsync` → **`_db.SaveChangesAsync`**; то же в `PartnerCommandRepository` — store **обойдён** |
| Фактическая связь | `HttpJournalEventPublisher`, `HttpDailyMetricsEventPublisher` — fire-and-forget POST в Analytics из команды |
| Partners | ни store, ни bus, ни типов событий |

**Проблема:** «HTTP» из ADR-005 реализован как fire-and-forget из команды: при падении приёмника факт теряется,
при ретрае — дублируется, истории нет. Пока это так, **проекции питать нечем** (`partners_directory` §2.7 пуста),
и replay невозможен.

## 2. Варианты решений

### Вариант A — оставить fire-and-forget HTTP (как сейчас)
- **Описание:** команда сохраняет состояние и сразу POST-ит событие потребителю.
- **Плюсы (исчерпывающе):**
  - ничего не менять, работает сейчас для Analytics;
  - нет новых таблиц и фоновых процессов;
  - задержка минимальна.
- **Минусы (исчерпывающе):**
  - **потеря факта** при недоступности приёмника — молча, без следа;
  - **дубли** при повторе (нет идемпотентности) → двойной учёт в проекциях;
  - **истории нет** → проекцию нельзя пересобрать, дефект данных неисправим;
  - команда зависит от доступности чужого сервиса (связанность во время выполнения).
- **Соответствие целям:** это и есть долг E5, который владелец просил закрыть.

### Вариант B — внешний брокер (RabbitMQ/Kafka)
- **Описание:** события публикуются в брокер, потребители подписаны, брокер хранит до подтверждения.
- **Плюсы (исчерпывающе):**
  - стандартная семантика (ack, redelivery, DLQ);
  - развязка по времени и по адресам;
  - масштабируется на много потребителей.
- **Минусы (исчерпывающе):**
  - **+1 инфраструктурная сущность**: развёртывание, бэкапы, мониторинг, обновления, секреты;
  - новая точка отказа и новая компетенция для двух пользователей и единиц событий в час;
  - порядок и идемпотентность всё равно остаются на потребителе;
  - на VPS добавляет память/диск, конкурируя с уже согласованным бюджетом (ADR-009/027).
- **Соответствие целям:** избыточно для профиля Single (ADR-002).

### Вариант C — outbox + HTTP-диспетчер, at-least-once (ВЫБРАН)
- **Описание:** событие пишется **в outbox-таблицу той же БД в одной транзакции** с изменением состояния;
  фоновый диспетчер (`IHostedService`) читает outbox по порядку и POST-ит в `/internal/events` получателя
  с ретраями; приём идемпотентен (`processed_events(event_id)`).
- **Плюсы (исчерпывающе):**
  - **факт не теряется**: он в БД до отправки (одна транзакция с состоянием);
  - **дубли безвредны**: идемпотентность на приёме;
  - **история есть** → проекции пересобираемы, дефекты данных исправимы;
  - **нет новой инфраструктуры**: та же Postgres, тот же HTTP, тот же мониторинг;
  - команда **не зависит** от доступности потребителя (развязка по времени);
  - **наблюдаемо**: `outbox_lag`, `attempts`, `outbox_dead` — видно, что не доехало.
- **Минусы (исчерпывающе):**
  - новая таблица + фоновый процесс в каждом пишущем BC (объём работы);
  - **at-least-once** ⇒ потребитель **обязан** быть идемпотентным (иначе дубли);
  - порядок гарантирован только внутри агрегата;
  - outbox растёт → нужен retention и чистка (иначе БД пухнет);
  - появляется «второй путь» рядом с существующим fire-and-forget — надо **удалить** старый, иначе два способа.

## 3. Выбранное решение

**Вариант C.** Outbox + HTTP-диспетчер, доставка **at-least-once**, приём идемпотентен.

| Элемент | Правило |
|---|---|
| Запись | insert в `outbox` **в той же транзакции**, что изменение состояния (иначе событие врёт) |
| Доставка | `IHostedService` на сервис; FIFO по `id`; ретраи с backoff (`attempts`, `next_attempt_at`) |
| Приём | `POST /internal/events` (внутренний контур, ADR-026): `processed_events(event_id PK)` + upsert проекции **в одной транзакции** |
| Порядок | внутри агрегата — да; между агрегатами — нет (и не требуется: проекции идемпотентны) |
| Мёртвые | после N попыток → `outbox_dead` + `::error::` в лог; ручной разбор, не «тихо забыли» |
| Retention | outbox ≥ 90 дней (источник для пересборки проекций до появления отдельного event store) |
| Удаление старого пути | `HttpJournalEventPublisher`/`HttpDailyMetricsEventPublisher` **удаляются** в том же пакете работ |

### Конверт события (обязательные поля)

```jsonc
{ "eventId": "uuid", "type": "Partner.Removed", "schemaVersion": 1,
  "aggregateId": "uuid", "version": 7, "clientId": "uuid",
  "occurredAt": "...Z", "correlationToken": "uuid", "payload": { } }
```

`clientId` — обязателен с первого дня (иначе tenant-скоуп Analytics, E6, придётся добавлять миграцией событий).
`payload` — «минимум для получателя»: весь агрегат в событие не кладём, иначе событие станет вторым источником правды.

### Event Sourcing: что делаем и чего не делаем

| Делаем | Не делаем в этой итерации |
|---|---|
| пишем **все** изменения как факты (даже при одном потребителе) | не восстанавливаем агрегат из событий |
| проекции производные и пересобираемые | command-DB остаётся источником истины для агрегата |

Запись фактов включаем сразу: включить позже = потерять историю за прошедший период (уже проходили с легаси-строками
журнала). Цена — таблица и insert в транзакции; цена отсутствия — необратимая дыра.

## 6. Комплаенс
| Что | Значение |
|---|---|
| Признак «сделано» | команда не вызывает `SaveChangesAsync` в command-path; в outbox появляется строка; приёмник получает POST; проекция обновилась |
| Отказной тест 1 | остановить приёмник → команда проходит, `outbox_lag` растёт → поднять → проекция догнала |
| Отказной тест 2 | два одинаковых POST → `200` оба раза, состояние проекции одно (`processed_events`) |
| Отказной тест 3 | событие `version=5` после `7` → проекция не откатывается |
| Отказной тест 4 | битый payload → `outbox_dead`, остальные события идут |
| Кто проверяет | @DO (метрики и два прогона), @BE (тесты), @AR (соответствие ADR), @TL (приёмка) |

## 7. Последствия
- **Плюсы:** факты не теряются; дубли безвредны; проекции пересобираемы; нет новой инфраструктуры; отказ приёмника
  не ломает команду; всё наблюдаемо.
- **Риски:** потребители обязаны быть идемпотентными (иначе дубли прорастают в данные) — закрывается `processed_events`
  и тестами §6; outbox растёт (retention); два пути доставки одновременно — закрывается обязательством «удалить старый
  в том же пакете».
