# ADR-029: Межсервисная доставка событий — из Event Store через Outbound Handler (Saga/HTTP)

- **Статус:** Предложено (⚠️ часть про механизм доставки **не соответствует** EDM-скиллу — см. §0)
- **Дата:** 2026-11-14
- **Связанные ADR:** 003 (Event Store, `FullEventSourcing`), 004 (Read Store), 005 (Event Bus = InMemory), 009 (деплой), 026 (внутренний контур)
- **Заменяет:** — (уточняет ADR-005: каким именно HTTP и с какими гарантиями; **ADR-003 не переопределяет**)
- **Владелец решения:** @AR (архитектура), исполнитель @BE (`6-msa`), инфраструктура @DO
- **Бэклог:** `edm-debt-plan.md` E1/E5/E6; `03-ddd/BC-Analytics/05-materialized-views.md`

## 0. Соответствие EDM-скиллу (проверка по `edm-verification.md` и `0-df-issue/`)

Скилл (`edm-verification.md`, эталон `edm-net.md`) требует: `AddEventStorePostgres` + `SaveEventAsync`
(`FullEventSourcing`, Event Store = источник истины) · `Command → Aggregate.BusinessMethod() → IEventBus.Publish`
(без прямой записи в БД) · `IEventBus → Event Consumer (IHostedService) → SaveEventAsync + UpsertAsync + Outbound Handler`
· проектор `IDomainEventHandler + UpsertAsync` → MV · Command DB ≠ Read Store · **свои инфраструктурные интерфейсы запрещены**.

| # | Требование скилла | Что в этом ADR | Вердикт |
|---|---|---|---|
| 1 | Event Store = источник истины, `FullEventSourcing`, `SaveEventAsync` | «Event Store остаётся единственным источником истины», второго журнала нет | ✅ |
| 2 | Публикация `IEventBus.Publish` из команды, не прямая запись | так и записано | ✅ |
| 3 | Event Consumer (`IHostedService`) с `SaveEventAsync + UpsertAsync` | приём: `SaveEventAsync` (идемпотентность по `eventId`) + `UpsertAsync` в одной транзакции | ✅ |
| 4 | Доставку наружу делает **фреймворковый Outbound Handler** | роль названа верно, но **механизм я придумал свой**: чтение стора по курсору + таблица `delivery_offsets` | ❌ **свой инфраструктурный механизм** — ровно то, что скилл запрещает |
| 5 | Свои `IEventBus`/`IAnemicModelRepository`/`IReadRepository` запрещены | новых интерфейсов не ввожу, но `delivery_offsets` — своя инфраструктура доставки | ⚠️ граница нарушена механизмом из п.4 |
| 6 | MV = прекомпьют, query не считает на лету | ADR про доставку, MV не меняет | — (вне scope; долг E1/п.10 верификации) |

**Вывод: ADR соответствует скиллу по модели (п.1–3) и НЕ соответствует по механизму доставки (п.4–5).**
Механизм должен быть фреймворковым (Outbound Handler из DF), а не самописным курсором. Пока API фреймворка для
исходящей доставки **не подтверждён** (`0-df-issue/edm-own-implementations.md` перечисляет `AggregateProvider`,
`IAnemicModelRepository`, `AddEventStorePostgres`/`AddReadStorePostgres` — про outbound-доставку там ничего),
этот ADR **не может быть принят**: он описывает обход, а не использование скилла.

**Что нужно, чтобы закрыть (до перевода в «Принято»):** подтвердить у DF/в пакете, есть ли штатный механизм
исходящей доставки (Outbound Handler / subscription / outbox внутри стора); если есть — переписать §3 на него;
если нет — зафиксировать gap в `0-df-issue/` и только тогда решать, чем закрывать (и это решение будет
исключением из скилла с обоснованием, а не «новой архитектурой»).

## 1. Контекст

**Что уже решено и этим ADR не пересматривается:**

| Источник | Решение |
|---|---|
| **ADR-003** | **Event Store = источник истины**: `AddEventStorePostgres`, стратегия **`FullEventSourcing`**; агрегат загружается из стора (`AggregateProvider`), `SaveEventAsync` |
| **ADR-005** | шина **InMemory** (внутри процесса); «для межсервисных связей используется HTTP/шлюз» |
| **EDM-скилл** (`edm-verification.md`, эталон `edm-net.md`) | `Command → Aggregate.BusinessMethod() → IEventBus.Publish` (**не** прямая запись в БД); `IEventBus → Event Consumer (IHostedService) → SaveEventAsync + UpsertAsync + **Outbound Handler**`; проектор `IDomainEventHandler` + `UpsertAsync` → MV; **свои инфраструктурные интерфейсы запрещены** |
| `03-ddd/BC-Analytics/05` | «событие = источник истины (Event Store), доставка соседям через **Outbound Handler (Saga/HTTP)**» |

**Дыра, которую закрывает ADR:** «HTTP/шлюз» из ADR-005 не отвечает, что происходит при недоступности приёмника,
при дубле и как пересобрать проекцию. ADR задаёт **контракт доставки**; хранилище событий при этом остаётся одно —
**Event Store**, второй журнал событий не создаётся ни в каком виде.

**Факты (`origin`, 2026-11-14, проверено командами):**

| Что | Факт | Отклонение от скилла |
|---|---|---|
| Путь записи | `JournalCommandRepository.SaveAsync` → `_db.SaveChangesAsync`; то же у Partners | №1: нет ES, `SaveEventAsync` нет |
| Публикация | `IBusAdapter.Publish` у 10 контекстов = `Task.CompletedTask`; вызовов нет | №2: нет `IEventBus.Publish` |
| Потребитель | `IHostedService` — 0 | №3: нет Event Consumer |
| Доставка наружу | `HttpJournalEventPublisher`, `HttpDailyMetricsEventPublisher` — fire-and-forget POST **из команды** | №3: вместо Outbound Handler — ручной вызов из команды |
| Регистрация | Journal: `AddEventStorePostgres` + `AddEventBusInMemory` есть, `AddReadStorePostgres` закомментирован | частично |

## 2. Варианты решений

### Вариант A — оставить fire-and-forget HTTP из команды (как сейчас)
- **Описание:** команда пишет состояние в EF и сразу POST-ит событие потребителю.
- **Плюсы (исчерпывающе):**
  - работает сейчас для Analytics;
  - нет фоновых процессов;
  - минимальная задержка.
- **Минусы (исчерпывающе):**
  - **против скилла:** публикация не через `IEventBus`, уведомление из команды вместо Outbound Handler;
  - потеря факта при недоступности приёмника — молча;
  - дубли при ретрае (идемпотентности нет);
  - истории нет → проекцию не пересобрать;
  - команда зависит от чужого сервиса в момент выполнения.
- **Соответствие целям:** это и есть долг E5.

### Вариант B — внешний брокер (RabbitMQ/Kafka)
- **Описание:** публикация в брокер, подписка потребителей.
- **Плюсы (исчерпывающе):**
  - стандартные ack/redelivery/DLQ;
  - развязка по времени и адресам.
- **Минусы (исчерпывающе):**
  - **против ADR-002/ADR-005**: профиль Single, шина InMemory, брокер не предусмотрен;
  - +1 инфраструктурная сущность (развёртывание, бэкапы, мониторинг, секреты);
  - идемпотентность и порядок всё равно на потребителе;
  - конкурирует за память/диск VPS с уже согласованным бюджетом.
- **Соответствие целям:** избыточно.

### Вариант C — доставка из Event Store через Outbound Handler (ВЫБРАН)
- **Описание:** события durable в **Event Store** (ADR-003). **Outbound Handler** — `IHostedService` в каждом BC:
  держит **курсор доставки на потребителя** и читает из стора события, ещё не доставленные этому потребителю;
  POST-ит их в `/internal/events`; приём идемпотентен; неудачные попытки ретраятся, отравленные — в dead-letter.
- **Плюсы (исчерпывающе):**
  - **соответствует скиллу:** публикация от событий, доставку делает Outbound Handler, а не команда;
  - **единственное хранилище событий** — Event Store; никакого второго журнала;
  - команда не зависит от доступности потребителя;
  - дубли безвредны (идемпотентность на приёме);
  - проекции пересобираемы (источник — Event Store);
  - наблюдаемо: лаг доставки по курсору.
- **Минусы (исчерпывающе):**
  - нужен **курсор доставки** (`delivery_offsets`) — минимальная сущность состояния, не копия событий;
  - at-least-once ⇒ потребитель обязан быть идемпотентным;
  - порядок гарантирован внутри агрегата, между агрегатами — нет;
  - если фреймворковый стор не даёт чтения по диапазону — это gap в `0-df-issue/` (свой стор **не пишем**).

## 3. Выбранное решение

**Вариант C: Outbound Handler поверх Event Store.** Event Store — источник истины (ADR-003), второго журнала нет.

| Элемент | Правило |
|---|---|
| Источник событий | **Event Store** (ADR-003, `FullEventSourcing`); отдельного журнала/таблицы событий **не создаётся** |
| Публикация | `Command → Aggregate.BusinessMethod() → IEventBus.Publish` (скилл); события переживают рестарт, потому что они в сторе |
| Доставка | **Outbound Handler** = `IHostedService`; читает из стора события после `last_delivered_seq` для конкретного потребителя; POST `/internal/events` |
| Состояние доставки | `delivery_offsets(consumer, last_delivered_seq, attempts, next_attempt_at)` — **состояние доставки**, не события |
| Приём | `POST /internal/events`: потребитель делает `SaveEventAsync` (идемпотентность по `eventId`) + `UpsertAsync` проекции **в одной транзакции** |
| Порядок | внутри агрегата — да (по `version`), между агрегатами — нет |
| Мёртвые | после N попыток — dead-letter + `::error::`; ручной разбор |
| Старый путь | `Http*EventPublisher` **удаляются** после перевода потребителей на Outbound Handler |

### Конверт события (обязательные поля)

```jsonc
{ "eventId": "uuid", "type": "Partner.Removed", "schemaVersion": 1,
  "aggregateId": "uuid", "version": 7, "clientId": "uuid",
  "occurredAt": "...Z", "correlationToken": "uuid", "payload": { } }
```

`clientId` — обязателен с первого дня (иначе tenant-скоуп Analytics, E6, придётся добавлять миграцией событий).
`payload` — «минимум для получателя»: весь агрегат в событие не кладём (иначе событие станет вторым источником правды).

### Что этот ADR **не** меняет

Event Sourcing **включён** (ADR-003): Event Store — источник истины, агрегат загружается из стора через
`AggregateProvider`; `SaveEventAsync` пишет событие. Текущее состояние кода (EF + `SaveChangesAsync` + ручной HTTP)
— **отклонение от скилла**, которое закрывает E1, а не альтернативная архитектура.

## 6. Комплаенс
| Что | Значение |
|---|---|
| Соответствие скиллу | `IEventBus.Publish` вызывается из команды; `IHostedService`-потребитель есть; `UpsertAsync` в проекции есть; `SaveEventAsync` пишет событие; **своих** `IEventBus`/`IReadRepository` нет (E3); второго журнала событий нет |
| Признак «сделано» | команда не вызывает `SaveChangesAsync`; событие видно в сторе; Outbound Handler двигает `last_delivered_seq`; проекция обновилась |
| Отказной тест 1 | остановить приёмник → команда проходит, лаг растёт → поднять → проекция догнала |
| Отказной тест 2 | два одинаковых POST → `200` оба раза, состояние проекции одно (идемпотентность `SaveEventAsync`) |
| Отказной тест 3 | событие `version=5` после `7` → проекция не откатывается |
| Отказной тест 4 | битый payload → dead-letter, остальные события идут |
| Кто проверяет | @DO (метрики, два прогона), @BE (тесты), @AR (соответствие скиллу), @TL (приёмка) |

## 7. Последствия
- **Плюсы:** доставка — часть событийной модели, а не побочное действие команды; хранилище событий одно;
  проекции пересобираемы; отказ приёмника не ломает команду; всё наблюдаемо.
- **Риски:** потребители обязаны быть идемпотентными (закрывается `SaveEventAsync` + тесты §6); `delivery_offsets`
  рассинхронизируется при ручных вмешательствах (закрывается метрикой лага и dead-letter); два пути доставки
  одновременно — закрывается обязательством «удалить `Http*EventPublisher` в том же пакете».
