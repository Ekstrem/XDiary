# ADR-026: Маршрутная авторизация — deny-by-default, анонимность по (метод, путь)

- **Статус:** Принято (2026-11-10)
- **Дата:** 2026-11-10
- **Заменяет:** — (уточняет ADR-008 в части «кто решает, что маршрут анонимный»)
- **Владелец решения:** @AR
- **Связанные ADR:** 008 (JWT), 021 (идентификация клиента), 023/025 (APIM и YARP)
- **Бэклог:** BE-053 (инцидент), DO-060 (шлюз), TE-038 (контракт)

## 1. Контекст

2026-11-10 @TE замерил на dev: **`GET /api/v1/clients` без токена → 200** и в теле — **список клиентов с телефонами**.
Приватное приложение, PII (номер телефона) — утечка на чтение анонимом.

Причина не «забыли `[Authorize]`» в одном месте, а **конструкция**: шлюз (`6-msa/ApiGateway/Auth/GatewayRoutes.cs`)
решает анонимность **по пути, без метода**:

```
path.Equals("/api/v1/clients")   // ← сюда же попадает и POST (регистрация), и GET (список)
```

`POST /api/v1/clients` действительно должен быть анонимным (регистрация), а `GET` того же пути — нет.
Один URL, два разных класса доступа — и правило «по пути» склеило их. В сервисе `ListClientsQuery` и
`GET /clients/{id}` тоже без `[Authorize]`, то есть защиты нет и на втором рубеже (шлюз — единственный).
`GET /clients/{id}` анонимом не отдаётся только потому, что не попал в whitelist (путь не совпал).

**Цена решения (факты, не драма):**

| Что | Факт | Кто зафиксировал |
|---|---|---|
| Утечка на dev | `GET /api/v1/clients` без токена → **200**, в теле — список клиентов с `phone` | @TE, 2026-11-10 06:43 |
| Утечка на проде | `GET /api/v1/clients` без токена → **200** + **9 записей** с `phone`, `displayName`, `gender`, `photoUrl`, `verified` | @TL, 2026-11-10 14:50 |
| Дата решения | 2026-11-10 (ADR-026) | — |

Приватное приложение: номер телефона — это PII, а список позволяет **перечислить всех** пользователей, а не прочитать одного.
Именно поэтому решение фиксируется с датой и ценой, как у инцидента `DO-051`: через месяц должно быть видно, что это стоило и когда закрыли.

**Тот же дефект нашёлся ещё в двух местах** (@DO, 2026-11-10 11:10): `POST /api/v1/clients/refresh` и
`POST /api/v1/clients/{id}/verify` были анонимны **любым методом** — то есть «по пути» работало не в одном месте,
а в трёх. Поэтому в реализации deny-by-default стоит **первым**: `if (!HttpMethods.IsPost(method)) return false;`,
и только потом allow-list путей. Порядок принципиален: если сначала проверять путь, а метод проверять потом,
любая новая пара «публичный POST + что-то ещё» снова протечёт.

**Проверено на проде после деплоя** (@DO, 11:10): `GET /clients` → 401, `POST /clients` (пусто) → 400,
`GET /clients/refresh` → 401, `POST /clients/refresh` → 400, `GET /journal/records` → 401,
`GET /swagger/v1/swagger.json` → 401, `/health` → 200.

## 2. Варианты решений

### Вариант A — оставить как есть, точечно закрыть дыру
- **Описание:** в `GatewayRoutes` убрать `"/api/v1/clients"` из анонимных, в `ClientsController` поставить `[Authorize]` на `List`/`Get`.
- **Плюсы (исчерпывающе):**
  - минимальная правка, один коммит, риск сломать мало;
  - быстрый способ убрать утечку **сегодня**.
- **Минусы (исчерпывающе):**
  - правило остаётся **по пути** — следующая пара «публичная команда + приватный GET» на том же URL даст ту же дыру;
  - защита в сервисе появляется «по требованию», а не по умолчанию: новый контроллер снова будет открыт;
  - нет автоматической проверки: узнаем опять замером руками (как сейчас).
- **Соответствие целям:** закрывает симптом, не класс.

### Вариант B — deny-by-default в сервисе + анонимность по (метод, путь) на шлюзе
- **Описание:** шлюз пропускает без токена только явные пары `(POST, /api/v1/clients)`, `(POST, /api/v1/clients/{id}/verify)`, `(POST, /api/v1/clients/refresh)`; всё остальное — 401. В каждом сервисе — fallback-политика «требуется авторизация» (deny-by-default) + `[AllowAnonymous]` только на регистрации/верификации/refresh. Контрактный тест проверяет и «аноним работает», и «аноним получает 401».
- **Плюсы (исчерпывающе):**
  - дыра класса «один URL — два класса доступа» **невозможна**: метод стал частью правила;
  - новые эндпоинты **закрыты по умолчанию** — забыл атрибут, получил 401, а не утечку;
  - два рубежа (шлюз + сервис): обход шлюза напрямую не открывает данные;
  - проверяемо тестом, а не «на глаз»: `GET /clients` без токена → 401/404.
- **Минусы (исчерпывающе):**
  - правка в двух местах (шлюз + каждый сервис) — на 10 BC это не один коммит;
  - fallback-политика может неожиданно закрыть `/health`, `/swagger`, внутренние вызовы — их надо явно перечислить;
  - при этапе 2 (APIM в тракте) правило надо повторить в политиках APIM, иначе поведение разъедется.
- **Соответствие целям:** закрывает класс; совпадает с «deny-by-default» и с будущим APIM.

### Вариант C — убрать список клиентов из клиентского API вообще (только `me`)
- **Описание:** `GET /api/v1/clients` (список) **удаляется** из клиентского контура; админский список — только `/internal/clients` (внутренний контур, не публикуется шлюзом). `GET /clients/{id}` тоже удаляется — клиент читает только `me`.
- **Плюсы (исчерпывающе):**
  - нет поверхности для перечисления клиентов — утечка невозможна by design, а не «закрыта правильно»;
  - согласуется с уже принятым принципом `me` в пути (`BC-Client/03-command-api.md`): клиент не оперирует чужими id;
  - меньше контрактов — меньше дрейфа.
- **Минусы (исчерпывающе):**
  - ломает текущий контракт (если кто-то им пользуется — а им пользуется только dev-замер @TE);
  - если админка понадобится, её надо делать осознанно (отдельный контур + политика), а не «вернуть как было»;
  - не решает класс целиком: другой эндпоинт завтра повторит ошибку (нужен ещё и B).
- **Соответствие целям:** убирает конкретную поверхность, но не правило.

## 3. Выбранное решение

**Вариант B + C.** B — правило (класс ошибок закрыт), C — поверхность (перечисление клиентов убираем совсем):

1. **Разрешённые анонимные маршруты — исчерпывающий allow-list (ключ = метод + путь):**

   | Метод | Путь | Почему анонимен |
   |---|---|---|
   | `POST` | `/api/v1/clients` | регистрация (до токена) |
   | `POST` | `/api/v1/clients/{id}/verify` | подтверждение кода (до токена) |
   | `POST` | `/api/v1/clients/refresh` | обновление пары токенов (access истёк) |
   | `POST` | `/api/v1/privacy/verify-token` | проверка токена (сам является проверкой) |
   | `GET` | `/health` | проба живости |

   **Всё остальное — deny-by-default** (401/403). Список закрыт: новый маршрут попадает внутрь только осознанной правкой ADR.

2. **Deny-by-default в сервисах:** `FallbackPolicy = RequireAuthenticatedUser`; `[AllowAnonymous]` — только на маршруты
   из п.1; `/health` — явное исключение. `GET /api/v1/clients` (список) и `GET /api/v1/clients/{id}` **удаляются** из
   клиентского API: клиент читает только `me`.
   **Решение по каждому маршруту (без «или»):**
   - **`GET /api/v1/clients` (список) — УДАЛИТЬ.** Потребителей нет (фронт не вызывает), именно он отдаёт телефоны. Это и есть источник утечки, а не побочный маршрут.
   - **`GET /api/v1/clients/{id}` — оставить, но `[Authorize]` + только «себя», иначе `403`.** Альтернатива (удалить целиком) допустима, если проверка `id == sub` окажется хрупкой: она легко забывается в новом обработчике, а маршрут без id защитить проще.
   - **Фактические статусы (замер @DO на dev, 2026-11-10 21:30, скрипт `7-deploy/check-pii-scope.sh`) — записываем как норму, а не как «допустимый диапазон»:**

     | Запрос | Статус | Почему так |
     |---|---|---|
     | `GET /clients` **без** токена | **401** | снимает шлюз (deny-by-default), список не отдаётся |
     | `GET /clients` **с** токеном | **405** | на пути остался только `POST` (регистрация) — ASP.NET отвечает «метод не разрешён». Это **не** 404: путь существует, и скрывать этот факт бессмысленно — регистрация публична |
     | `GET /clients/{чужой id}` с токеном | **403** | проверка владельца есть |
     | `GET /clients/{свой id}` с токеном | **200** | — |
     | `GET /clients/{id}` без токена | **401** | шлюз |

     **Инвариант важнее кода ответа:** список **не отдаётся ни в каком случае**. `405` вместо `404` — следствие того, что мы удалили **метод**, а не путь; принудительный 404 потребовал бы лишнего кода ради сокрытия публичного факта, и это было бы хуже: тест начал бы проверять «спрятанность», а не «недоступность данных».
3. **Анонимность на шлюзе — по паре (метод, путь):** реализация — `IsAnonymous(string method, string path)`
   (`6-msa/ApiGateway/Auth/GatewayRoutes.cs`), метод — **часть условия**; `GET`/`PUT`/`DELETE` не анонимны **по умолчанию**
   (проверка `!HttpMethods.IsPost(method) → false`, затем allow-list путей). Путь без метода — **не** основание.
   *Факт:* патч @DO 2026-11-10 закрыл PII именно так — `/api/v1/clients` анонимен только для `POST`, `GET` уходит
   в JWT-ветку и получает **401**.

   **`/swagger` — НЕ исключение** (@DO 10:40): на проде `/swagger*` отдаёт **401**, а внутри сети спеки видит `Analytics`
   (условие `EnvironmentName == "Single"`). Открыть `/swagger` в whitelist = **сделать спеки всех сервисов публичными**.
   CI этого не требует: реестр `openapi/` генерируется **из кода** (`openapi-registry.yml`, `-t:GenerateOpenApi`),
   а не HTTP-запросом к `/swagger`. Публичный доступ допустим **только в Development** отдельной веткой
   `Environment.IsDevelopment()`, без записи в allow-list.
4. **Внутренний контур `/internal/**` — отдельный класс, а не «забытый анонимный».** Default-deny **сломает
   внутренние вызовы**, если их не выделить: `Analytics` обновляет «Тренды» вызовом
   `{journalUrl}/internal/journal/records` (`InternalJournalController`, маршрут `internal/journal` — **без** `api/v1`).
   Правило:
   - `/internal/**` — **`[AllowAnonymous]`**, доступ **только внутри сети**; шлюз его **не публикует**
     (проверено: в `appsettings.json` маршруты только `/api/v1/**`);
   - это **осознанный компромисс**: анонимность внутри сети = доверие периметру. Если сеть скомпрометирована,
     `/internal/**` открыт. Альтернатива (service-to-service: подписанный токен или mTLS) — **отдельный ADR**,
     вводим, когда появится второй потребитель или внешний контур;
   - **обязательный тест «precompute работает»**: после включения default-deny `Analytics` обязан обновить «Тренды» —
     иначе мы вернём ровно тот дефект, который лечили вечером (анонимный/недоступный внутренний вызов).

5. **Контрактный тест в двух направлениях** (иначе «default-deny» нечем проверить):
   - каждый маршрут allow-list **анонимно** → по смыслу (`POST /clients` 200/201 или 400 при невалидном теле,
     `verify` 400/401, `refresh` 401 при пустом теле, `GET /health` 200);
   - **«любой другой» анонимный маршрут** (например `GET /api/v1/clients`, `GET /api/v1/journal/records`) → **401/404**;
     для удалённого списка дополнительно: **с токеном** → **405** (путь остался только для `POST`), и в теле **нет** данных клиентов;
   - **внутренний** `GET /internal/journal/records` анонимно → **200** (Analytics не должен онеметь).
6. **Условие перехода:** dev/E2E не ломаются — онбординг работает без токена, «Тренды» обновляются; проверка
   **прогоном контракта на dev**, а не «на глаз».

### Комплаенс
| Что | Значение |
|---|---|
| Правило | анонимность — только по **(метод, путь)**; всё прочее **deny-by-default**; сервис закрыт по умолчанию |
| **Гейт после включения deny-by-default** | прогон **всех** маршрутов allow-list анонимно + один «посторонний» маршрут анонимно → 401/404 + `GET /internal/journal/records` анонимно → 200. Это и есть проверка, которая ловит следующую такую дыру и одновременно не даёт «закрыть всё» вместе с внутренними вызовами |
| **Где включается** | в **деплойный гейт** (до прода), не только в CI: следующая такая дыра не должна доехать до прода |
| Внутренний контур | `/internal/**` не публикуется шлюзом (маршруты только `/api/v1/**`); проверяется при каждом новом маршруте — «внутренний не попал в публичные» |
| **`/internal/**` — только изнутри сети** | доступ без токена разрешён **исключительно** внутри сети; шлюз публикует лишь `/api/v1/**` — проверка: `git grep` по `6-msa/ApiGateway/appsettings.json` при **каждом** изменении маршрутов + **негативный контроль**: снаружи `/internal/journal/records` → **404/401** |
| **Временное ослабление периметра** | только **решением в ADR**, не строкой в чате: «временно открыли маршрут» = новый/правленый ADR с датой и условием снятия. Сегодняшние два случая (`IsAnonymous` по пути без метода, анонимный `GET /clients`) — ровно цена «договорились в чате» |
| Где проверяется | контрактный тест в CI (два прогона: «allow-list работает» и «посторонний 401») + ревью нового контроллера @AR |
| Кто проверяет | @BE (код) + @DO (факт на dev, прогон) + @AR (контракты) + @TL (приёмка) |
| Что делаем при расхождении | новый маршрут без пары в allow-list → 401 (это норма, не поломка); «нашли маршрут, который должен был быть закрыт, но 200» → дефект, карточка с датой |
| Этап 2 APIM | то же правило дублируется в политиках APIM; расхождение «APIM разрешил, YARP нет» — дефект |

**Уточнение области (важно, иначе ADR требует невозможного).** Формулировка «fallback в **каждом** BC» была
неверной: в 5 контекстах нет auth-стека, и `FallbackPolicy` там закроет всё без разбора. Фактическое правило:

| Где | Что | Почему |
|---|---|---|
| 6 BC с auth (`Client`, `Journal`, `Partners`, `Privacy`, `Garmin`, `AppleHealth`) | `FallbackPolicy = RequireAuthenticatedUser` + явные `[AllowAnonymous]` | есть чем проверить токен; защита в глубину |
| 5 BC без auth (`Catalog`, `SomaticSeries`, `DailyMetrics`, `Portability`, `Analytics`) | **доверие краю** (шлюз валидирует JWT, ADR-008); своих проверок нет | нет auth-стека; добавление = отдельное решение и объём |

**Риск, принимаемый явно (не «забыли»):** эти 5 BC отдают **личные данные** (каталог, соматика, дневные метрики, экспорт)
любому, кто до них дотянется **внутри сети** мимо шлюза — из другого контейнера, при ошибке маршрута, при отладке.
Шлюз закрывает внешний контур, но не является единственной защитой для приватного приложения.
**Как риск минимизируется уже сейчас (и что проверяется машинно):**
- **Внешняя поверхность = только шлюз.** В `7-deploy/podman-compose.yml` `ports:` объявлен **один раз** — у `api-gateway`;
  ни один BC не публикует порт на хост. То есть снаружи хоста BC недоступны, доступны только через шлюз.
  **Гейт:** `tools/check_ports.py` (@DO, 2026-11-13): `ports:` в compose ровно **1** и принадлежит шлюзу;
  любой BC с `ports:` → **rc=1** с именем сервиса и строкой. Приёмка гейта: **дефект** (копия compose с `ports:` у
  `journal`) → `::error::journal (стр.33) публикует порт`, rc=1; **норма** → «объявлений ports: 1, сервисы с портами:
  api-gateway, нарушений 0», rc=0; `--selftest` 4/4. То есть инвариант «внешняя поверхность = только шлюз» теперь
  проверяется машиной, а не строкой в ADR.
- **Внутри сети доступ есть у всех контейнеров** — это остаточный риск, который `ports`-гейт **не** закрывает:
  его закрывает только auth-стек (target ниже). Проверка «кто может дотянуться изнутри» **не имеет смысла как гейт**:
  ответ всегда «все контейнеры в сети `xdiary`», список не меняется и ничего не блокирует — это документация, а не контроль.
  Проверять надо то, что может измениться: **публикацию порта на хост**.

**Целевое состояние (target, по §8):** auth-стек + fallback в этих 5 BC.
**Владелец:** @BE. **Условие снятия (машинно-проверяемое):** `git grep -l 'AddAuthentication' -- 6-msa/BC-<X>` непустой
для каждого из 5 → тогда для них включается fallback, и гейт `DO-064` проверяет уже 11 BC, а не 6.

> **Поправка 2026-11-12:** строка «`PrivacyController` без `[AllowAnonymous]`» была верна на 00:20 и **устарела** —
> @BE добавил атрибуты. Проверять надо `origin`, а не память (правило §3), поэтому таблица выше пересобрана по факту.
> Класс дефекта остаётся тем же, пока нет fallback: **анонимность без deny-by-default — это разрешение, которое
> никто не выдавал**, и следующая правка `Program.cs` может открыть маршрут молча.

## Уточнение 2026-11-10: `401 / 405` на `GET /clients` — что именно доказывает код ответа

**Записано по просьбе @DO и подтверждено замером @TE (2026-11-10 23:32).** Позиция:

| Запрос | Ответ | Что это значит |
|---|---|---|
| `GET /api/v1/clients` **без** токена | **401** | шлюз закрыл до сервиса (allow-list), утечки нет |
| `GET /api/v1/clients` **с** токеном | **405** | на пути остался только `POST`; метод удалён, а не «доступ запрещён» |
| `POST /api/v1/clients` (пусто, с токеном) | **400** | валидация отработала — сервис жив и обрабатывает запрос |

**Почему `405` — не ошибка:** мы удалили **метод**, а не путь. Семантически `405 Method Not Allowed` точнее, чем `404`
(«нет такого пути» — ложь: путь есть) и чем `403` (это про права, а не про набор методов).

**Почему `405` — не доказательство:** как верно сформулировал @TE, `405` можно получить и при полностью сломанном
чтении — он лишь говорит «этот метод здесь не обслуживается». Поэтому **рядом обязаны стоять позитивные проверки**:

- `GET /api/v1/clients/{id}` **своим** токеном → **200** (данные реально отдаются);
- `GET /api/v1/clients/{id}` **чужим** токеном → **403** (скоуп по `sub` работает, а не просто «закрыто»);
- Без токена → **401** (шлюз).

**Правило для контрактных тестов (следствие):** негативный код (`401/403/404/405`) без парной позитивной проверки —
не приёмка. Это тот же класс, что «зелёный прогон без шагов»: код ответа сам по себе не подтверждает поведение.

## Уточнение 2026-11-04 20:54: APIM в пути — авторизация **не переезжает** в APIM, она **дублируется**

**Факт @DO:** APIM отдаёт `200` там, где YARP отдаёт `401` (`catalog`, `analytics/summary`), потому что план — `KEY_LESS`.
Причина: **deny-by-default жил в YARP** (это решение ADR-026), а APIM его не наследует. Значит переключение Funnel
в текущем виде **открывает API без авторизации** — это не «настройка», а регресс безопасности.

**Выбор из трёх вариантов, которые поставил @TL (`chat/tl.md` 20:55) — решение: (а), с узким включением (в):**

| Вариант | Что даёт | Почему не выбран / где уместен |
|---|---|---|
| **(а) план `JWT`/OAuth2** — APIM валидирует токен и пробрасывает | deny-by-default на входе работает **так же, как работал в YARP**; невалидный токен не доходит до сервисов | **выбран.** Ключевой аргумент: **сегодня JWT валидирует YARP** — это и есть место deny-by-default. APIM встаёт на его место, значит обязан выполнять ту же роль. Это не новая дупликация, а **замена того же слоя**; ключ берётся из того же секрета |
| **(б) `KEY_LESS` + проброс `Authorization` без валидации** | одно место валидации (сервисы), без второго секрета | **не выбран для публичного пути.** На входе исчезает allow-list: запрос без токена доходит до сервиса, и защищён он только `[Authorize]` — которого у `catalog`/`analytics` **нет** (факт @DO). Это ровно текущая регрессия, просто «потом починим». Проброс заголовка обязателен **в обоих случаях**, но сам по себе он не защита |
| **(в) `KEY_LESS` только для внутренних вызовов** | `/internal/**` не требует токена | **принят как дополнение, а не альтернатива:** внутренние вызовы идут по сети и не должны тащить JWT. Для **публичного** `/api/v1/**` не годится |

**Решение (архитектура, моя зона):**

1. **APIM приводится к той же норме, что YARP:** план `JWT` с тем же `issuer`/`audience`/ключом подписи, что у сервисов
   (один источник секрета — Secrets, не второй ключ). Не «auth-политика на каждый API» — это второй источник правды.
2. **Allow-list один и тот же и он в индексе:** анонимны ровно операции с `auth: anonymous` в `04-architecture/api-index.yaml`
   (проверка: `python -c "…api-index…"` → **4**: `Client.Register`, `Client.Refresh`, `Client.Verify`, `Privacy.VerifyToken`;
   `GET /health` — **инфраструктурный эндпоинт вне индекса**, анонимность задаётся в APIM вместе с остальными четырьмя,
   но в индексе его нет и быть не должно — он не часть контракта домена).
   **Число 4 — не «на глаз»:** оно совпадает и с `check_api_index` (`anonymous 4`), и с `openapi`-спекой; расхождение = ошибка реестра.
   Всё остальное — **`401` на входе в APIM**, до маршрутизации. Изменение allow-list = правка индекса, а не политики в APIM.
3. **Deny-by-default остаётся и в сервисах** (`[Authorize]` + `sub`-скоуп): APIM — **не** периметр прав, а точка отказа.
   Два слоя — потому что APIM теперь единственный, кто видит трафик; упавший APIM или забытая политика не должны
   означать «API открыт».
4. **Найденный побочный дефект (не про APIM):** `catalog` и `analytics` отвечают `200` **и через YARP-путь**, то есть
   `[Authorize]` в этих сервисах **отсутствует**, и их защищал только шлюз. Это надо закрыть в @BE независимо от APIM
   (иначе после переключения у них останется ровно один слой).
5. **Гейт переключения:** Funnel переключается **только** когда матрица `APIM | YARP` совпадает по коду ответа для **всех
   операций индекса**, а не для 12 выборочных. Команда проверки — та же, что даёт `check_api_index`/`openapi`: список
   операций берётся из `api-index.yaml`, а не из головы. `200|401` в любой строке = **не переключаем**.
6. **Что считается «хуже» для отката** — без изменений (ADR-025: p95/`5xx`/`health`/RSS/контракт), плюс новая строка:
   **любой `2xx` на операции, которая в индексе не `anonymous`** = немедленный откат, независимо от метрик.
**Уточнение по факту 20:56: (а) и (б) — не «или», а «оба», но с разными ролями.** @DO показал, что через `KEY_LESS`-APIM
`/api/v1/catalog` отдаёт `200` **и данные** (`[{…}]`), а через YARP — `401`. Отсюда правило:

- **(а) JWT-план в APIM — блокер переключения.** Без него edge не имеет никакого периметра, и «один хоп» (YARP вне пути)
  означает, что периметра нет **вообще**.
- **(б) `[Authorize]` в сервисах — параллельная работа @BE, не альтернатива (а).** Если сделать только (а), у нас **один**
  слой: упавший APIM, ошибка политики или новый сервис без маршрута = открытый API. Если сделать только (б), edge всё равно
  публикует то, чего нет в индексе (allow-list исчезает). Нужны **оба**, потому что это разные слои: периметр на входе и права в сервисе.

**Дополнительно (гигиена):** фактические записи из прода (даже безобидные, как название костюма) **не цитируются в чат** —
репозиторий публичный (§6). Формат доказательства: «`200` и тело вида `[{id, kind, name}]`», без значений.

## Ревизия 2026-11-04 20:58: авторизация — **в сервисах**, JWT-план APIM **отложен** (ключ симметричный)

**Связанные решения:** ADR-026 (этот же документ, блок 20:54) → **почему меняется:** я выбрал «план `JWT` в APIM
с тем же ключом». **Это оказалось технически невозможным**, и это проверяемый факт, а не мнение: `Jwt__SigningKey` —
**64 символа, без PEM**, то есть **симметричный HMAC**; APIM `JWT`-план проверяет подпись по **публичному** ключу/OAuth2,
а публичного ключа в системе нет (`chat/do.md` 20:58, @DO). **Комплаенс прошлого (§3.3):** отступаю от блока 20:54
в части *механизма*, не в части *принципа*: «APIM — не периметр прав» остаётся, и теперь он следует из природы ключа,
а не из договорённости.

**Решение:**

1. **Авторизация канонически живёт в сервисах:** `[Authorize]` + `sub`-скоуп (ADR-008). Причина прямая: симметричный ключ
   может проверить только тот, у кого он есть; **раздавать ключ подписи в APIM нельзя** — это второй держатель секрета
   и бо́льшая зона поражения (политики APIM меняют чаще, чем код).
2. **APIM остаётся `KEY_LESS` для публичного пути и не является проверкой прав.** Он даёт маршрутизацию, лимиты,
   наблюдаемость; `Authorization` **пробрасывается** как есть.
3. **JWT-план APIM отложен, а не отклонён:** он требует перехода на **асимметричный ключ (RSA) + JWKS** — это изменение
   формата ключа, затрагивающее все 11 сервисов и ротацию, то есть **отдельное решение**, а не шаг деплоя.
4. **Машинный критерий вместо «матрица APIM == YARP»** (он сильнее, потому что проверяет **самого держателя прав**, а не прокси):
   для **каждой** операции из `api-index.yaml`, у которой `auth ≠ anonymous`, прямой запрос **в сервис** без токена обязан
   вернуть **`401`**; `2xx` = дефект. Список операций берётся из индекса (80), а не из выборочных 12.
   «Матрица APIM == YARP» остаётся как **вторая** проверка (согласованность прокси), но приоритет — (4).
5. **Что закрыть до переключения (@BE):** `[Authorize]` в `Catalog`, `Analytics`, `DailyMetrics`, `SomaticSeries`
   (в `Client` есть; `Privacy`/`Partners`/`AppleHealth`/`Garmin` проверены матрицей). Для анонимных операций — явный
   `[AllowAnonymous]`, чтобы «отсутствие атрибута» больше **не** было способом случайно открыть ручку.

**Почему это не «вернулись к (б) из сообщения @TL»:** (б) там звучало как «добавить `[Authorize]` и всё»; здесь —
(б) плюс **машинный критерий на все операции индекса**, плюс требование явного `[AllowAnonymous]`. Без критерия это
снова стало бы «мы посмотрели 12 ручек руками».

**Отдельный факт, который нельзя смешивать с авторизацией:** @DO нашёл `portability/document` → `404` в живом контейнере
при наличии маршрута в коде (`PortabilityController.cs:25`) — на проде **образ старше кода** (класс `DO-050`). Пока это так,
«матрица 1:1» меряет **чужую ошибку выкатки**, а не поведение. Условие переключения дополняется: **`gen_images_lock --check`
= зелёный** (образы в `images.lock` соответствуют коду), только потом матрица.

## Итог 2026-11-04 21:00: JWT-план **снят с предусловия переключения**

@DO проверил эмпирически: схема V4-плана `JWT` в Gravitee 4.4 **отвергает любое значение** `signature`
(`HMAC`/`RSA`/`ECDSA`/`JWT`/`NONE`/`HS256` → `400 "#/signature: X is not a valid enum value"`), схему поля не достать
(`/management/v2/plugins*` → `500`, файла в контейнере нет — в jar). То есть «план `JWT`» сейчас — **не настройка,
а исследование**, и держать на нём путь трафика нельзя.

**Решение (финальное, заменяет предусловие (а) из блоков 20:54/20:58):**

1. **Переключение Funnel не требует JWT-плана.** Условия — только два машинных:
   **(i)** `gen_images_lock --check` зелёный (образы соответствуют коду — закрывает класс `DO-050`, из-за которого
   `portability/document` даёт `404` при наличии маршрута); **(ii)** для **76** из 80 операций индекса (`auth ≠ anonymous`)
   прямой запрос **в сервис** без токена = **`401`**.
2. **RSA-переход не делаем сейчас.** Причина: единственная выгода — валидация на edge, а она **не нужна**, пока авторизация
   живёт в сервисах и проверяется машиной на всех 76 операциях. Цена — смена формата ключа у **11** сервисов + ротация +
   правка `TokenService` — несоразмерна. **Условие возврата к вопросу:** появление внешних клиентов, per-user лимитов
   в APIM или требования «невалидный токен не должен доходить до сервиса» как отдельного (не нашего) комплаенса.
3. **APIM — маршрутизация, лимиты, наблюдаемость.** Не периметр прав. Это не «временно»: это следует из симметричного
   ключа и зафиксировано здесь, чтобы вопрос не поднимался каждый раз с нуля.
4. **Если владелец захочет (а) — нужен один шаг его руками:** создать JWT-план в UI Gravitee и прислать его JSON
   (там видно настоящие имена полей V4). Это **ресурс/доступ**, а не архитектура: без него любая реализация — гадание.

### Условие (ii) — это ДВА разных утверждения, и гейтом является второе

@TL прогнал `9-tests/scripts/check_apim_auth.py` и получил **`76/76 → 401`, `rc=0`** (`REF=0387f955`) — на тесте и на проде.
Но `--base` указывает на **публичный вход (YARP)**, поэтому квитанция доказывает «**прокси** закрывает 76/76». Записываем честно, двумя строками:

| Утверждение | Что измерено | Статус | Чем измеряется |
|---|---|---|---|
| **(ii-a) прокси** | публичный вход (YARP) → `401` на 76/76 неанонимных операциях | **выполнено**, `REF=0387f955`, `rc=0` (тест и прод) | `check_apim_auth.py --base <публичный вход>` |
| **(ii-b) сервис напрямую** | `http://xdiary-<bc>:8080/...` → `401` на 76/76 | **не измерено** (нужен запуск изнутри контура) | `check_apim_auth.py --direct` (режим нужен) / ad-hoc по 5 BC |

**Гейтом переключения является (ii-b), а не (ii-a).** Причина: после переключения трафик идёт `Funnel → Caddy → APIM → сервис`,
**YARP в пути отсутствует** (endpoints APIM смотрят прямо в `xdiary-<bc>:8080`). Значит `76/76 через YARP` не защищает:
APIM пойдёт мимо YARP в тот самый сервис, который в `20:58` отдавал `200` напрямую (`xdiary-catalog`). Засчитывать (ii-a) как
выполнение условия — значит зачесть проверку объекта, которого в новом пути не будет.

**Порядок:** `BE-064` (5 BC × `[Authorize]`) → **(ii-b) 76/76 изнутри** → переключение Funnel. Пока (ii-b) не измерено,
переключение остаётся запрещённым независимо от красоты (ii-a).
**Инструмент для (ii-b) готов (`9-tests/scripts/check_apim_auth.py --direct`, @TE 00:16):** маппинг `BC → xdiary-<service>:8080`
из compose, `--service-map` для переопределения, `--only` для ad-hoc по 5 BC; `--dry-run --direct` → **12 сервисов / 76 целей**
(journal 20, catalog 8, partners 8, analytics 8, privacy 8, clients 5, daily-metrics 5, garmin 4, portability 4, apple-health 3,
somatic-series 2, api-gateway 1).

**И главное — три исхода, а не два.** @TE нашёл у себя дефект того же класса, что мы ловим месяц: из песочницы запрос до
сервисов не доходит, в ответ приходит `502` (прокси), и первая версия зачла бы это как `rc=0` — «нарушений нет = зелено».
Исправлено: `502/503/504` → класс `[infra] unknown`, а если **ни одна** цель не дала измеримого ответа — **`rc=2`**
с текстом «запускать изнутри контура; это не нарушения и не зелено».

| Исход | Значение | Зачитывается как условие |
|---|---|---|
| `rc=0` + `76/76 → 401` | PASS | **да** |
| `rc=1` + список `2xx` | FAIL | нет (и это нарушитель, а не «шум») |
| `rc=2` / `503` / `000` | **UNKNOWN — не проверено** | **нет и не может быть** |

**Норма:** `UNKNOWN` **никогда** не считается выполненным условием, даже если «ошибок не показал». Квитанция для (ii-b):
`REF=<sha> | (ii-b) N/76 → 401 | rc=0`, и запускается **изнутри контура** (`podman exec`/под в сети).
**Квитанция (ii-b) — с обязательным provenance (реализовано @TE 00:46, проверено мной):**

```
REF=<sha> | (ii-b) PASS 76/76 → 401 | rc=0 | where=<чем измерено> | template=<…>|map=<…>
REF=<sha> | (ii-b) FAIL 76/76 → 401 (нарушители выше) | rc=1 | where=…
REF=<sha> | (ii-b) UNKNOWN N/76 измерено (НЕ засчитывается) | rc=2 | where=НЕ УКАЗАНО
```

**Ключевое: `--where` не пожелание, а условие приёма.** Если `--direct` дал `rc=0`, а `--where` пуст, скрипт **не отдаёт PASS**:
печатает `::error::` со ссылкой на ADR-026 / `round-checklist` §3.1 и возвращает **`rc=2` с меткой `UNKNOWN`**
(`9-tests/scripts/check_apim_auth.py:400-404`). То есть норма «UNKNOWN не засчитывается» **вшита в инструмент**, а не живёт в чате.
`--selftest` — **13/13** (новый кейс проверяет оба исхода: `PASS … where=podman exec` и `UNKNOWN … where=НЕ УКАЗАНО`).

**Следствие для приёмки:** квитанция без `where` не является выполнением (ii-b) — принимается только строка, где видно,
**откуда** мерили.
### Измерение (ii-b) 2026-11-05 01:21 — числа и что считается защитой

@DO сделал инструмент `tools/check_service_auth.py` (прямые вызовы в сервисы изнутри контура, 76 операций из индекса).
**Результат и, главное, классификация:**

| Класс ответа | Сколько | Что это значит | Засчитывается |
|---|---|---|---|
| `401`/`403` | **21** (`Client` 5, `Privacy` 8, `Garmin` 4, `AppleHealth` 3, `ApiGateway` 1) | защищено | **PASS**-кандидат |
| `2xx` | **9** (`Analytics` 8/8 + `Catalog.List`) | **ОТКРЫТО**, данные отдаются | **FAIL** |
| `400` (валидация) | **13** (`Catalog` 6, `DailyMetrics` 5, `SomaticSeries` 2) | **не защита:** в ASP.NET `[Authorize]` выполняется **до** валидации модели, значит `400` = запрос **дошёл до бизнес-логики без токена** | **FAIL** (а не «без проверки») |
| нет ответа (`000`) | **32** (`Journal` 20, `Partners` 8, `Portability` 4 — рестарт-петли) | **UNKNOWN** — сервис не ответил, ничего не доказано | **UNKNOWN** (блокирует, но не «провал» конкретной ручки) |

**Ключевое уточнение к классификации @DO:** `400` нельзя держать в отдельной «нейтральной» колонке. `[Authorize]` в ASP.NET
срабатывает **раньше** model binding, поэтому `400` физически означает «авторизация пропустила запрос». Если в сервисе нет
`[Authorize]`, то открытая ручка на невалидном теле ответит `400` — и это ровно тот случай (`Catalog` 6, `DailyMetrics` 5,
`SomaticSeries` 2). Поэтому `400` = **FAIL**, а «неизвестно» остаётся только за `000`.

**Итог (ii-b): НЕ выполнен.** 21 защищено / **22 нарушителя** (`2xx` 9 + `400` 13) / 32 неизвестно. Два независимых замера
сходятся: через APIM `21/76 → 401`, напрямую в сервисы — те же **21**. Это подтверждает, что APIM ничего не обходит:
он просто не периметр, а периметра в сервисах у пяти BC нет.

**Зависимость, которую нельзя обойти:** пока `journal`/`partners`/`portability` в рестарт-петлях (`restarts = 35 / 1037 / 1210`),
32 операции остаются `UNKNOWN`, а значит условие (ii-b) **не может быть выполнено** даже после `BE-064`. Порядок:
поднять три сервиса → `BE-064` → перепроверка (ii-b) → только потом Funnel.
