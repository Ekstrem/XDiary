# ADR-023: Управление API-контрактами и версионирование (полный APIM)

- **Статус:** Принято (2026-11-09; все голоса собраны — реализация по этапу 1)
- **Дата:** 2026-11-08
- **Заменяет:** ADR-023 (редакция «решение C, контракт-first реестр»)
- **Владелец решения:** @AR (архитектура) + владелец PO (выбор APIM)
- **Связанные ADR:** 006 (REST), 007 (шлюз YARP), 013 (версионирование /v1 + OpenAPI)
- **Бэклог:** техническая итерация (владелец 2026-11-08: «нужен полный APIM, API сразу помещать туда»)

## 1. Контекст
ADR-013 декларирует `/api/v1` + OpenAPI, но исполнение не проверяется: контракт (`03-ddd`),
реализация (`6-msa`) и клиент (`8-front`) расходятся. Владелец решил: нужен **полный APIM**,
и OpenAPI-контракты держать **в нём** (нативная модель APIM), а не в рукотворном реестре.
Это отменяет прежнее решение C в пользу B.

## 2. Варианты решений

### Вариант A — Оставить YARP + дисциплина
- **Описание:** усилить ADR-013: версионная политика (breaking → `/v2`), deprecation, CI-валидация OpenAPI.
- **Плюсы (исчерпывающе):**
  - без нового компонента (0 ops);
  - минимальная цена внедрения (только CI-валидация);
  - остаёмся в текущем стеке (YARP, ADR-007).
- **Минусы (исчерпывающе):**
  - нет единого источника правды контрактов (реестр расходится с кодом);
  - версии — ручная дисциплина, легко нарушается;
  - нет портала / аналитики / rate-limiting;
  - контрактный дрейф уже случался (`/verify` token→accessToken, `/partners` [Authorize]).
- **Соответствие целям:** консистентность контрактов — частично, только дисциплиной.

### Вариант B — Полноценный APIM (Gravitee)
- **Описание:** отдельный APIM-слой перед сервисами: OpenAPI-контракты импортируются в APIM (источник правды), версии управляются нативно, политики (JWT, rate limiting), портал.
- **Плюсы (исчерпывающе):**
  - OpenAPI-импорт нативно → единый источник правды контрактов («API помещать туда»);
  - жизненный цикл версий нативно (created → published → deprecated → retired);
  - политики (JWT, rate limiting, преобразования) — нативно, не руками;
  - встроенный портал разработчика (документация + пробы из коробки);
  - аналитика вызовов.
- **Минусы (исчерпывающе):**
  - новый компонент + ops (Java-стек Gravitee + MongoDB + Elasticsearch);
  - вне текущего стека EDM/DF (шлюз = YARP, ADR-007) — роли разведены в **ADR-025** (APIM = control plane, YARP = трафик);
  - обучение/компетенция по продукту.
- **Соответствие целям:** единый источник правды контрактов, версии без поломок, управление API-жизненным циклом.

### Вариант C — Контракт-first реестр (YARP + OpenAPI-реестр + версионные маршруты + CI-гейт)
- **Описание:** YARP остаётся; центральный OpenAPI-реестр (рукотворный) + версионные маршруты + CI-гейт breaking-change.
- **Плюсы (исчерпывающе):**
  - без нового тяжёлого компонента;
  - бьёт в корень (контрактный дрейф) через гейт;
  - в текущем стеке (YARP + CI).
- **Минусы (исчерпывающе):**
  - реестр и гейт строим руками (две задачи: BE-050 + DO-056);
  - нет портала / аналитики / rate-limiting;
  - нужна дисциплина ведения реестра;
  - риск «второго источника правды» (реестр vs код), если не генерировать из кода.
- **Соответствие целям:** консистентность — с ручной поддержкой.

## 3. Выбранное решение
**Вариант B — полный APIM. Продукт: Gravitee (Gravitee.io).**

Обоснование продукта — техническое, не «по вкусу»:
- **Gravitee** — единственный из трёх, кто даёт «полный APIM» нативно: OpenAPI-импорт как
  источник правды, жизненный цикл версий, встроенный портал, политики. Это ровно «API помещать туда».
- **Kong** — легче, но версионирование ручное (отдельный route на версию), портал минимальный
  (Kong Manager), OpenAPI — через плагины/deck, а не как ядро.
- **Tyk** — Go (легче Gravitee), но портал и часть управления — enterprise/платные.

Цена Gravitee — Java + MongoDB (+ Elasticsearch для аналитики) — тяжелее Kong/Tyk; на single-VPS
с встроенными БД управляемо, ES можно не поднимать, пока аналитика не нужна. YARP остаётся
маршрутом и путём деградации; **BFF-агрегация — под мараторием владельца (ADR-007, 2026-11-09)**,
в этом решении её нет.

**Направление: repo → APIM** (условие @LM). Источник правды контракта — **git** (OpenAPI
генерируется из кода, BE-050); APIM — **рантайм** (импортирует спеку по тегу, авторинг не в APIM).
Исключает «артефакт вне git» (инциденты: deploy.sh 33 ч на старом образе, Telegram-OTP как
внешняя точка отказа). Если авторинг в APIM — обязателен экспорт на каждый publish в git +
drift-check + запрет ручных правок в APIM (кроме аварийного хотфикса).

**Внедрение в два этапа** (@TL 2026-11-09) — «в пути» это условие перехода, а не факт:

| Этап | Что | Трафик | Риск простоя |
|---|---|---|---|
| **1. Control plane (сейчас)** | Gravitee CE **вне пути запросов**: импорт `openapi/*.json`, жизненный цикл версий, портал, drift-check | как сейчас: `Funnel → YARP → сервисы` | **нет**: падение APIM не влияет на продукт (деградация по умолчанию, не по команде) |
| **2. APIM в пути — НЕ НАСТУПАЕТ** (решение ADR-025, вариант C) | APIM остаётся control plane; трафик идёт мимо него | `Funnel → YARP → сервисы` без изменений | **нет**: APIM вне пути, механизм деградации не нужен |

Переход к этапу 2 — только при **всех** условиях: Caddy ≥ 2.5 с `health_uri`; **суточный замер RSS
на VPS-1** (не на dev — там 93 МБ без swap) с запасом **≥ 1 ГБ** на пике; Elasticsearch с
`-Xms512m -Xmx512m`. Иначе остаёмся на этапе 1 (контракты и версии уже работают, а прод не зависит
от APIM). Этап 1 ставится **сразу на VPS-1** с `mem_limit` на каждый компонент — не на dev.

### Комплаенс
| Что | Значение |
|---|---|
| Условия пересмотра | если ops-нагрузка Gravitee (Java/Mongo/ES) не оправдается → вернуться к C или Kong |
| Где источник правды | **git** (OpenAPI генерируется из кода); APIM — рантайм, авторинг не в APIM. При авторинге в APIM — экспорт в git на каждый publish + drift-check (@DO-056) |
| Версия и лицензия Gravitee | **пин версии** (фиксированный тег, не `latest`); **CE** (Community) — если функций хватает, **EE** — только по решению владельца (платно) |
| Поведение при падении APIM | **Этап 1 (control plane):** APIM вне пути — падение **не влияет на продукт**, трафик идёт `Funnel → YARP`; деградация не «по команде», а по умолчанию. **Этап 2 (в пути):** режим зависит от версии Caddy (измеряет @DO): **≥ 2.5** → два upstream + `health_uri` → авто-переключение на YARP; **< 2.5** → только пассивные (`max_fails`/`fail_duration`) → **ручное переключение по ранбуку**, «авто» не пишем. Негативный контроль одинаков в обоих этапах: остановить APIM → `GET /api/v1/clients` = **200** |
| Ресурсный бюджет (блокирующее условие) | Замер @DO (2026-11-09): стек **≈1.96 ГБ** — ES 875 + Mongo 99 + Gateway 489 + Management 496; на VPS-1 остаётся **≈2275 МБ** (13 сервисов + ОС, 4 vCPU). **Правило:** при свободной RAM на пике **< 500 МБ** APIM в путь **не вводим**. **PoC на dev не делаем** (там 93 МБ без swap — числа были бы swap-driven): этап 1 идёт сразу на VPS-1 с лимитами, суточный замер RSS — на VPS-1, запас для этапа 2 **≥ 1 ГБ** |
| dev без APIM | **обязателен**: dev поднимается без APIM, E2E идут мимо него (`Funnel → YARP`); APIM — только control plane (этап 1) и позже prod-путь (этап 2); иначе новый компонент останавливает всех |
| Ошибки не переупаковываются (условие @FE, **критичное** — @TL 08:06) | **401/400/409/5xx от сервиса проходят через APIM байт-в-байт по смыслу (код + тело)**; APIM не подменяет их своими. Иначе фронт теряет различие «неверный код / нет связи / 5xx», которое делалось ради диагностики, и владелец снова увидит бесполезное сообщение. **Негативный контроль:** сломали сервис → APIM **не подменяет** 5xx на свой 502, а отдаёт код+тело сервиса. Проверяется на этапе 2 (этап 1 трафик не трогает) |
| Как проверяется дрейф APIM↔git | ежедневный drift-check: экспорт APIM ↔ git-спека, расхождение → красный гейт |
| Как проверяется | контракт в APIM синхронизирован с кодом (генерация → импорт); версии без поломок |
| Кто проверяет | @AR (контракты) + @DO (APIM ops) |

## 4. Последствия
- **Плюсы:** нативные контракты/версии/портал/политики; OpenAPI в APIM = единый источник правды; «API помещать туда».
- **Риски:** новый компонент (Java + MongoDB + ES) + ops; вне стека EDM/DF (шлюз YARP); обучение Gravitee.
- **Роли с YARP разведены в ADR-025** (вариант C): APIM — только control plane, `YARP` — единственный шлюз трафика;
  трактовые функции APIM (rate-limit, аналитика вызовов) не используются — если понадобятся, это новый ADR.
- **Риски (D-19, @LM):** APIM как новый компонент в path-деплое (DO-052); локальная разработка без APIM (dev-режим должен работать без него); APIM как единая точка отказа; лицензия Gravitee (CE vs EE).
- **Снято этапностью:** риск «APIM — единая точка отказа» действует **только для этапа 2**; на этапе 1 APIM вне пути и продукт от него не зависит.
- **Не куплено на этапе 1:** APIM-политики в тракте (rate-limit, аналитика вызовов) — это функциональность этапа 2, её отсутствие не блокирует контракты и версии.
