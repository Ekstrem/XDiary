# ADR-001: Разбиение на микросервисы

- **Статус:** Принято
- **Дата:** 2026-10-29
- **Связанные ADR:** 002, 006, 007, 009
- **Бэклог:** Инк 1..9 (TOBE «микросервисы на основе DDD»)

## Контекст
Сейчас — монолитная PWA (IndexedDB + локальный Python-прокси для Garmin). Цель — микросервисы на .NET (EDM/CEQRS). В `03-ddd` выделено 10 ограниченных контекстов. Базовое условие: два пользователя, минимальная нагрузка.

## Решение
Разбить на **3 микросервиса** по доменным группам (не 10, чтобы не переусложнять):

| Сервис | Контексты (из 03-ddd) | Агрегаты | Роль |
|---|---|---|---|
| `journal-svc` | Журнал, Партнёры, Каталог | Record, Partner, CatalogItem | Core (Execution) |
| `somatics-svc` | Соматика (минутные точки), Дневные метрики, Шлюз Garmin, Шлюз Apple Health | SomaticPoint, DailyMetrics, GarminSync, AppleImport | Execution + Gateway |
| `analytics-svc` | Аналитика | — (read-only) | Analysis |

- **Приватность и доступ** — сквозной модуль (JWT + локальный PIN), не отдельный сервис.
- **Переносимость данных** — внутри каждого сервиса (CSV-экспорт/импорт), не отдельный сервис.

**Обоснование:** 10 контекстов не обязаны быть 10 сервисами при 2 пользователях. Три сервиса — минимально-осмысленное разбиение с путём роста (можно дробить дальше).

## Последствия
- **Плюсы:** читаемое разбиение по доменам; независимая деплойность; аналитика изолирована (read-only).
- **Риски:** межсервисные связи (журнал↔соматика↔аналитика) через события/API; нужен шлюз (ADR-007).
