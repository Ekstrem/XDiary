# ADR-028: Тесты — часть изолированного жизненного цикла компонента

- **Статус:** Принято (2026-11-13)
- **Дата:** 2026-11-13
- **Владелец решения:** @AR (архитектура). Направление задано владельцем 2026-11-13: «микросервисы должны обладать
  изолированным жизненным циклом — тестирование, деплой и кодовая база изолированы». Обоснование ниже —
  архитектурное: изоляция жизненных циклов, независимая доставляемость, радиус поражения, стоимость CI.
- **Связанные ADR:** 022 (деплой по компонентам), 027 (immutable артефакты), 025 (контракт-first)
- **Заменяет:** — (уточняет границы зон из `AGENTS.md` §1 в части тестов)

## 1. Контекст

Требование владельца: **у микросервиса изолированный жизненный цикл** — своя кодовая база, свои тесты, свой деплой.
Из этого следует критерий, который обычно упускают: **тест, который нельзя собрать и прогнать вместе с сервисом,
не является тестом сервиса** — он часть другого жизненного цикла.

Факты (`origin`, 2026-11-13):

- **изоляция кода уже соблюдается:** в `6-msa` у 9 BC есть свои `*.Domain.Tests` и `*.IntegrationTests`,
  и **ни один** тестовый проект `6-msa` не ссылается на чужой `BC-*` (проверено: межBC-ссылок **0**);
- **деплой изолирован:** 12 `Dockerfile` в `6-msa` → отдельный образ на сервис (тег `:single` мутабелен — отдельный
  дефект, ADR-027);
- **тесты — нет:** в `9-tests` лежат **9 проектов, 0 браузеров** (`Contract.ClientJournal`, `E2E`, `Gateways`,
  `Gateways.Api`, `Journal`, `Partners.Catalog`, `Portability.Gateway`, `Somatic.Daily`, `Analytics.Privacy`).
  Они **black-box по HTTP** (ни одной `ProjectReference` на код сервисов), то есть код не связывают, но связывают
  **жизненные циклы**: чтобы их прогнать, нужен поднятый контур из нескольких сервисов;
- единственное, что требует фронта, — `9-tests/RnD/front-e2e` (node + Playwright).

**Почему текущее положение — дефект архитектуры, а не «другая папка»:**
1. **Сервис нельзя проверить сам по себе:** его поведение частично «проверяется» в чужой папке, которая к нему
   не относится и без него не собирается.
2. **Независимая доставляемость ломается:** правка `BC-Journal` не может быть проверена и выпущена силами его
   жизненного цикла — часть проверок живёт вне его.
3. **Радиус поражения:** падение общего набора тестов останавливает всех, даже если виноват один сервис.
4. **Владение размывается:** тест в `9-tests` не имеет владельца-сервиса; «чей это тест» уже случалось.
5. **Стоимость CI:** нельзя гонять «тесты затронутого сервиса» — гоняется всё.

## 1.1. Термины — сначала договориться, потом раскладывать (правка владельца 2026-11-13)

Владелец поймал ошибку терминологии в первой редакции: я назвал `6-msa/E2E` набор, который **фронта не касается**.
**E2E (end-to-end) — это проверка системы через пользовательский интерфейс**, то есть через фронт. Всё остальное —
не E2E, и называть так нельзя: имя папки становится утверждением о содержимом (класс «`9-tests/Gateways` — это Garmin»).

| Уровень | Что проверяет | Стенд | Где живёт | Как называется |
|---|---|---|---|---|
| **Unit / domain** | агрегат, инварианты, VO | нет стенда | `6-msa/BC-<X>/src/<S>.Domain.Tests` | `DomainTests` |
| **Integration** | сервис + его БД/хранилище | нет (EF InMemory / контейнер БД) | `6-msa/BC-<X>/src/<S>.IntegrationTests` | `IntegrationTests` |
| **Contract** | ожидания потребителя (A→B) и соответствие провайдера | HTTP к одному сервису или двойнику | у потребителя и у провайдера | `ContractTests` |
| **API / scenario** | несколько сервисов по HTTP, **без фронта** | поднятый контур | **`6-msa/ApiTests/**`** | `ApiTests` (не «E2E»!) |
| **E2E** | сценарий пользователя **через фронт** | фронт + контур | **`9-tests/**`** + `front-e2e.md` | `E2E` |

**Следствие, которое надо поправить в уже написанном коде:** атрибут `[E2EFact]` у тестов, которые ходят в API без
браузера, — **неверное имя**; его надо переименовать в `[ApiFact]` (или `[ScenarioFact]`) при переносе, иначе
человек читает «E2E» и думает «через фронт». Имена файлов `*E2ETests.cs` при переносе тоже лучше назвать `*ApiTests.cs`
— но это косметика, приоритет у атрибута: он попадает в отчёты.

## 2. Варианты решений

### Вариант A — все тесты в `9-tests`, у сервисов только код
- **Описание:** единая папка тестов, включая доменные и интеграционные; сервис собирается без тестов.
- **Плюсы (исчерпывающе):**
  - одна точка запуска «все тесты»;
  - единый инструментарий и шаблон проекта;
  - не нужно решать, где живёт тест.
- **Минусы (исчерпывающе):**
  - **нарушает изоляцию жизненного цикла:** сервис нельзя проверить без чужой папки;
  - доменный тест вне сервиса отстаёт от кода и не попадает в ревью того, кто менял агрегат;
  - сервис удалён/вынесен — тесты остаются сиротами и «проверяют» то, чего нет;
  - нельзя гонять по зоне (CI всегда весь набор);
  - падение любого теста блокирует всех.
- **Соответствие целям:** прямо противоречит требованию изолированного жизненного цикла.

### Вариант B — всё в папке сервиса, включая межсервисные сценарии
- **Описание:** любой тест кладём в папку одного из сервисов-участников (например, сквозной — в папку «ведущего»).
- **Плюсы (исчерпывающе):**
  - формально «всё рядом с кодом», одна папка на сервис;
  - нет отдельной папки тестов, значит нет спора «где искать».
- **Минусы (исчерпывающе):**
  - **ломает изоляцию с другой стороны:** сборка сервиса начинает зависеть от чужих сервисов;
  - «ведущий» сервис назначается произвольно → при падении виноват он, хотя причина в другом;
  - при удалении «ведущего» уезжает тест, проверявший связку;
  - выпуск одного сервиса блокируется тестом, который к нему не относится.
- **Соответствие целям:** выполняет «рядом с кодом», но нарушает изолированную доставляемость.

### Вариант C — изолированный жизненный цикл: тест принадлежит компоненту, который проверяет (ВЫБРАН)
- **Описание:** у каждого компонента (сервиса, фронта, E2E-набора) — **свой** жизненный цикл: код, тесты, сборка,
  деплой. Тест живёт там, чей жизненный цикл он проверяет.
- **Плюсы (исчерпывающе):**
  - сервис **собирается, тестируется и деплоится сам** — требование владельца выполнено буквально;
  - доменный тест меняется в том же коммите, что и агрегат, и попадает в ревью владельца сервиса;
  - CI гоняет по зоне (затронут `BC-Journal` → его тесты), стоимость прогона падает;
  - радиус поражения: падение доменного теста останавливает один сервис, а не всех;
  - владение однозначно: тест принадлежит компоненту, на который ссылается или который поднимает;
  - межсервисный набор не «висит в воздухе»: у него есть владелец и пайплайн, но он не ломает изоляцию сервисов.
- **Минусы (исчерпывающе):**
  - нужна **разовая миграция** 9 проектов и правка CI-путей;
  - появляется **второй вид** тестов (per-service и E2E-набор) — нужно правило, куда относить новый;
  - контрактные тесты «пара A↔B» больше не существуют как папка-пара: делим на потребительские и провайдерские;
  - `6-msa/ApiTests` формально «не сервис» — надо зафиксировать, что у него свой lifecycle и свои правила.

## 3. Выбранное решение

**Вариант C. Критерий размещения — чей жизненный цикл тест проверяет, а не «какая папка ближе».**

| Тест проверяет | Где живёт | Часть чьей сборки |
|---|---|---|
| домен/агрегат/валидаторы сервиса | `6-msa/BC-<X>/src/<Service>.Domain.Tests` | **сборка сервиса** (блокирует его выпуск) |
| интеграцию сервиса с его БД/API | `6-msa/BC-<X>/src/<Service>.IntegrationTests` | **сборка сервиса** |
| шлюз (маршруты, авторизация) | `6-msa/ApiGateway.Tests` | **сборка шлюза** |
| контрактные ожидания **потребителя** (A ждёт от B) | `6-msa/BC-A/src/A.IntegrationTests`, HTTP-двойник B, **без ссылки на код B** | **сборка A** |
| соответствие **провайдера** контракту | `6-msa/BC-B/src/B.IntegrationTests` | **сборка B** |
| межсервисный сценарий (несколько сервисов, black-box, **без фронта**) | `6-msa/ApiTests/<scenario>` | **отдельный набор**, gate релиза |
| браузерный E2E (с фронтом) | `9-tests/<project>` + `front-e2e.md` | lifecycle фронтовой проверки |
| гейт/скрипт | `tools/`, `7-deploy/` | рядом со своим кодом |
| поведение, требующее **состояния БД** (легаси-строки, миграции, NULL-поля) | `6-msa/BC-<X>/src/<Service>.IntegrationTests` (EF InMemory/контейнер — прямой сев строки) | **сборка сервиса**: HTTP его не проверит, а слой БД — только здесь |

**Временное состояние при миграции (по §8, иначе «потом» станет «всегда»).** Пока перенос не выполнен, уже
написанные тесты могут оставаться в `9-tests` **с явным маркером** `[pending:ADR-028-move]`, владельцем (@BE) и
условием снятия: маркер исчезает в том же коммите, который выполняет `git mv`. Тест без маркера в `9-tests` —
нарушение; маркер без даты/владельца — тоже.

**Правила (проверяемые):**
1. **Тест не может быть зависимостью чужой сборки.** Сборка сервиса запускает только тесты из своей папки.
2. **Per-service тестовый проект не ссылается на код другого `BC-*`** (сегодня 0 нарушений — держим).
3. **`6-msa/ApiTests` не входит в сборку ни одного сервиса** (это API-уровень, не E2E) и блокирует только релиз контура, не выпуск сервиса.
4. **`9-tests` содержит только фронтовые тесты:** у каждого проекта `front-e2e.md` и браузерная зависимость.
5. **Контракт — ожидание потребителя, а не папка-пара.** Общая папка `Contract.A_B` **запрещена**: она не собирается
   без обоих сервисов и превращается в «общий тест ни за кем».

**3.1. Допустимые адреса — единственные (не собирать по памяти).** Запрещённая форма `Contract.<A>_<B>` вне `E2E`
трижды всплывала в указаниях, поэтому адреса фиксируются здесь и только здесь; любой другой путь — ошибка, которую
поймает приёмка (`9-tests/scripts/check-adr028-move.sh`, проверка 6).

| Проект сегодня | Допустимый адрес после переноса | Владелец |
|---|---|---|
| `9-tests/Contract.ClientJournal` | `6-msa/ApiTests/Contract.Client_Journal` | @BE |
| `9-tests/Partners.Catalog` | `6-msa/ApiTests/Contract.Catalog_Partners` | @BE |
| `9-tests/Somatic.Daily` | `6-msa/ApiTests/Contract.DailyMetrics_SomaticSeries` | @BE |
| `9-tests/Portability.Gateway` | `6-msa/ApiTests/Contract.Gateway_Portability` | @BE |
| `9-tests/Analytics.Privacy` | `6-msa/ApiTests/Contract.Analytics_Privacy` | @BE |
| `9-tests/E2E` | `6-msa/ApiTests` (сам набор) | @BE |
| `9-tests/Gateways`, `9-tests/Gateways.Api` | `6-msa/ApiGateway.Tests` (или `6-msa/ApiTests/Gateways`) | @BE |
| `9-tests/Journal` | `6-msa/BC-Journal/src/Journal.IntegrationTests` | @BE |
| `9-tests/RnD/front-e2e` | **не переносится** (браузер) | @TE |

**Порядок миграции (механический, `git mv`, код не переписывается):**

| Сейчас в `9-tests` | Куда | Почему |
|---|---|---|
| `E2E` | `6-msa/ApiTests` | black-box сценарий нескольких сервисов, без фронта |
| `Contract.ClientJournal` | `6-msa/ApiTests/Contract.Client_Journal`, далее разделить: ожидания в `BC-Client`, проверку в `BC-Journal` | цепочка идёт через оба сервиса |
| `Partners.Catalog`, `Somatic.Daily`, `Portability.Gateway`, `Analytics.Privacy` | `6-msa/ApiTests/<pair>` по тому же принципу | межсервисные цепочки |
| `Gateways`, `Gateways.Api` | `6-msa/ApiGateway.Tests` (или `6-msa/ApiTests/Gateways`, если нужен контур) | проверяют шлюз |
| `Journal` | `6-msa/BC-Journal/src/Journal.IntegrationTests` (или `6-msa/ApiTests`) | зависит от того, один ли сервис поднимается |
| `RnD/front-e2e` | **остаётся** в `9-tests` | браузер есть |

## 7. Последствия
- **Плюсы:** у сервиса появляется **настоящий** изолированный жизненный цикл (сборка, тесты, образ, деплой);
  CI гоняет по зоне и дешевле; владение тестами однозначно; межсервисные проверки перестают блокировать
  выпуск отдельного сервиса; спор «чей тест» закрывается правилом, а не перепиской.
- **Риски:** миграция 9 проектов может сломать пути в CI (закрывается `git mv` + сборка + два прогона по §5.4);
  `9-tests` может снова начать принимать API-тесты (закрывается гейтом с маркером);
  контрактные пары временно останутся в `6-msa/ApiTests` как сквозные (цель в §5, не блокер);
  `6-msa/ApiTests` может «расползтись» в свалку (правило: один сценарий = один проект с владельцем).
