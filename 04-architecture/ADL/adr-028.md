# ADR-028: Тест живёт рядом с тем, что проверяет — микросервисные тесты в `6-msa`, `9-tests` только с фронтом

- **Статус:** Предложено
- **Дата:** 2026-11-13
- **Владелец решения:** владелец продукта (прямое указание 2026-11-13: «Тесты микросервисов (без фронта) должны быть
  в папке с микросервисами»), исполнение — @AR (правило) + @TE (миграция) + @DO (CI)
- **Связанные ADR:** 022 (деплой по компонентам), 027 (immutable артефакты), 026 (маршрутная авторизация)
- **Заменяет:** — (уточняет границы зон из `AGENTS.md` §1 в части тестов)

## 1. Контекст

Владелец зафиксировал правило: **тесты микросервисов (без фронта) должны лежать в папке с микросервисами**.
Сегодня это не так, и это видно по фактам (`origin`, 2026-11-13):

- в `6-msa` **уже** есть тесты рядом с кодом: `*.Domain.Tests` и `*.IntegrationTests` у 9 BC + `ApiGateway.Tests`;
- в `9-tests` лежат проекты, которые **фронта не касаются**: `Contract.ClientJournal`, `E2E` (C#-тесты против API:
  `AuthE2ETests`, `JournalE2ETests`, `SomaticAnalyticsE2ETests`), `Gateways`, `Gateways.Api`, `Journal`,
  `Partners.Catalog`, `Portability.Gateway`, `Somatic.Daily`, `Analytics.Privacy` — **9 проектов, 0 браузеров**;
- единственное, что действительно требует фронта, — `9-tests/RnD/front-e2e` (node + Playwright).

**Почему это плохо, а не «просто другая папка»:**
1. **Связь теста и кода теряется:** меняешь `Journal.Aggregate` — тест, который это ловит, лежит в другой зоне и его
   не видно ни в диффе, ни в ревью, ни в карточке владельца сервиса.
2. **Нельзя гонять по зоне:** CI не может запустить «тесты только Journal», потому что они размазаны между
   `6-msa` и `9-tests`; в итоге гоняем всё или ничего.
3. **Сироты:** сервис удалён/вынесен — тесты в `9-tests` остаются и продолжают «проверять» то, чего нет.
4. **Зоны ответственности размываются:** `9-tests` — зона @TE, `6-msa` — зона @BE; тест падает, и непонятно,
   чья это правка: сервиса или теста. Агентская петля уже спотыкалась об это (спор «чей тест» 2026-11-13).

## 2. Варианты решений

### Вариант A — всё в `9-tests` (как фактически сложилось для API-тестов)
- **Описание:** любой тест, включая контрактные и API-E2E, кладём в `9-tests/`; `6-msa` — только код.
- **Плюсы (исчерпывающе):** одна точка запуска «все тесты»; единый инструментарий; не надо решать, где тест живёт;
  удобно гонять «чёрный ящик» против задеплоенного контура.
- **Минусы (исчерпывающе):** тест отделён от кода, который проверяет; нельзя гонять по зоне; при выносе/удалении
  сервиса тесты остаются сиротами; правка кода и правка теста — разные зоны, значит нет «одного коммита на изменение»;
  нарушает указание владельца.
- **Соответствие целям:** прямо противоречит правилу владельца.

### Вариант B — всё рядом с кодом, `9-tests` удалить
- **Описание:** `9-tests` не существует; браузерные E2E тоже распихиваем по «своим» папкам.
- **Плюсы (исчерпывающе):**
  - «тест рядом с кодом» без исключений;
  - одна зона на сервис, нет двусмысленности;
  - дифф всегда полон.
- **Минусы (исчерпывающе):**
  - браузерный E2E **не принадлежит ни сервису, ни фронту** — проверяет их связку, значит попадёт в произвольную папку;
  - сквозные сценарии (онбординг → запись → аналитика) нельзя приписать одному сервису;
  - `8-front` (зона @FE) получит тесты, которые правят бэкендеры, и наоборот.
- **Соответствие целям:** выполняет «рядом с кодом», но ломает «у сквозного теста есть хозяин».

### Вариант C — по признаку «нужен ли фронт» (ВЫБРАН, указание владельца)
- **Описание:** критерий ровно один и проверяемый: **участвует ли фронт/браузер**.
  - **нет фронта** (unit, domain, integration с БД, контрактные между сервисами, API-E2E, тесты шлюза) → **`6-msa/**`**;
  - **есть фронт** (браузерный E2E, UI-сценарии) → **`9-tests/**`**;
  - инфраструктура, которая не микросервис (гейты, скрипты) → рядом со своим кодом: `tools/**`, `7-deploy/**`.
- **Плюсы (исчерпывающе):**
  - правило владельца выполнено буквально;
  - один признак → нет споров (фронт есть или нет);
  - тест и код в одном диффе, одна зона, один владелец;
  - CI гоняет по зоне (затронут `BC-Journal` → его тесты);
  - сквозной сценарий с фронтом остаётся там, где живёт фронтовая проверка;
  - механически проверяемо гейтом.
- **Минусы (исчерпывающе):**
  - нужна **разовая миграция** 9 проектов (`git mv`, без переписывания кода);
  - часть CI-путей и карточек надо поправить;
  - в `6-msa` появятся тесты, которым нужны **два** сервиса — нужны папки `Contract.<A>_<B>` (см. §3);
  - фронтовые E2E внутри `9-tests` потребуют маркера, иначе `9-tests` снова начнёт принимать API-тесты «по привычке».

## 3. Выбранное решение

**Вариант C.** Тест живёт рядом с тем, что проверяет; `9-tests` — только фронт.

Правила размещения:

| Что проверяет тест | Где живёт | Пример |
|---|---|---|
| Один сервис: домен, агрегат, валидатор, его БД/API | `6-msa/BC-<X>/src/<Service>.*Tests/` | `Journal.Domain.Tests`, `Journal.IntegrationTests` |
| Шлюз (маршруты, авторизация, проксирование) | `6-msa/ApiGateway.Tests/` | уже так |
| Контракт **двух** сервисов (без фронта) | `6-msa/Contract.<A>_<B>/` (A, B — по алфавиту) | `6-msa/Contract.Client_Journal/` |
| Сквозной сценарий **нескольких** сервисов через API (без фронта) | `6-msa/E2E/` | `AuthE2ETests`, `JournalE2ETests` |
| **С фронтом**: браузерный E2E, UI-сценарии | `9-tests/<project>/` + обязательный `front-e2e.md` | `9-tests/front-e2e/` |
| Гейт/скрипт (не сервис) | рядом с кодом: `tools/`, `7-deploy/` | `tools/check_*.py` |

**Правило-комментарий (почему не в папке конкретного сервиса):** контрактный тест пары и сквозной API-E2E
**не принадлежат одному** сервису — если положить их в папку `A`, то при падении теста виноватым выглядит `A`,
а при удалении `A` тест уедет вместе с ним, хотя проверял связку. Поэтому папки на уровне `6-msa`, а не внутри `BC-*`.

**Миграция (разовая, механическая):** из `9-tests` в `6-msa` переносятся **9 проектов**, код **не переписывается**:

| Сейчас | Куда | Как |
|---|---|---|
| `9-tests/Contract.ClientJournal` | `6-msa/Contract.Client_Journal` | `git mv` |
| `9-tests/Partners.Catalog` | `6-msa/Contract.Catalog_Partners` | `git mv` |
| `9-tests/Somatic.Daily` | `6-msa/Contract.DailyMetrics_SomaticSeries` | `git mv` |
| `9-tests/Portability.Gateway` | `6-msa/Contract.Gateway_Portability` | `git mv` |
| `9-tests/Analytics.Privacy` | `6-msa/Contract.Analytics_Privacy` | `git mv` |
| `9-tests/E2E` | `6-msa/E2E` | `git mv` |
| `9-tests/Gateways`, `9-tests/Gateways.Api` | `6-msa/ApiGateway.Tests` (или `6-msa/Gateways`) | `git mv` |
| `9-tests/Journal` | `6-msa/BC-Journal/src/Journal.IntegrationTests` (или `6-msa/E2E`) | `git mv` |
| `9-tests/RnD/front-e2e` | **остаётся** в `9-tests` | браузер есть — правило выполнено |

**Обязательный маркер для `9-tests`:** у каждого проекта в `9-tests/` есть `front-e2e.md` со списком экранов/маршрутов,
которые он реально проверяет, и проект **использует браузер** (Playwright/аналог). Нет маркера или нет браузера →
проект там находиться не должен.

## 6. Комплаенс
| Что | Значение |
|---|---|
| Где тест должен лежать | по таблице §3: без фронта — `6-msa/**`; с фронтом — `9-tests/**` |
| Как проверяется | гейт: (а) ни один проект в `9-tests/**` не существует без `front-e2e.md` и браузерной зависимости → иначе rc=1; (б) в `9-tests/**` нет C#-проекта, который не поднимает браузер; (в) `6-msa/**/*.Tests` собираются |
| Кто проверяет | @DO (гейт и CI) + @TE (перенос) + @TL (приёмка) + @AR (соответствие правилу) |
| Когда пересматриваем | если появится «интеграционный» тест, которому нужен фронт и сервисы одновременно (тогда он живёт в `9-tests`, маркер обязателен) |

## 7. Последствия
- **Плюсы:** тест и код в одном диффе и одной зоне; CI гоняет по зоне; нет сирот при выносе сервиса; правило владельца
  выполнено буквально; спор «чей тест» закрыт (у пары — своя папка, у сквозного API — `6-msa/E2E`, у браузерного — `9-tests`).
- **Риски:** перенос 9 проектов может сломать пути в CI/скриптах (закрывается тем, что `git mv` + сборка + прогон
  по §5.4); `9-tests` может снова начать «принимать» API-тесты без маркера (закрывается гейтом);
  `6-msa` вырастет в объёме (приемлемо: тесты рядом с кодом и так уже там у 9 сервисов).
