# ADR-007: API Gateway (YARP)

- **Статус:** Принято
- **Дата:** 2026-10-29
- **Связанные ADR:** 001, 006, 008
- **Бэклог:** Инк 2 (PWA); ST-01 (сводка аналитики, агрегация)

## Контекст
Вопрос: нужен ли шлюз между PWA и тремя сервисами. Задачи: единая точка входа, аутентификация (ADR-008), агрегация (например, сводка аналитики собирает данные из journal + somatics), CORS/HTTPS.

## Решение
**API Gateway (YARP)** как единая точка входа + **BFF-агрегация** для составных экранов (сводка аналитики).

**Обоснование:** три сервиса — уже нужно единое место для маршрутизации и аутентификации; BFF скрывает сложность от PWA.

## Последствия
- **Плюсы:** один внешний адрес, централизованная аутентификация, агрегация на стороне бэка.
- **Риски:** шлюз — дополнительная точка отказа; следить за его конфигурацией.

## Проверки
- Кросс-ссылка: агрегируемые экраны — сводка/топы/корреляции из `03-ddd/BC-Analytics/*`.
- Согласовано с ADR-001 (3 сервиса), ADR-006 (REST), ADR-008 (JWT на шлюзе).

## ⛔ Мораторий владельца на BFF (2026-11-09)

**Владелец: «на BFF я ввожу мараторий».** Раздел «Решение» выше (BFF-агрегация) **не действует**: новых
агрегирующих эндпоинтов не добавляем, BFF не развиваем.

**Что фактически есть (проверено 2026-11-09):**
- код: `6-msa/ApiGateway/Controllers/BffController.cs` — один эндпоинт `GET /api/v1/bff/analytics-summary`
  (склеивает `journal` + `daily-metrics`);
- **потребителей нет:** ни `8-front`, ни `9-tests` не обращаются к `/api/v1/bff` — фронт берёт
  `/api/v1/analytics/summary` напрямую. То есть это **мёртвый код**, а не работающая функция;
- упоминания: только этот ADR и комментарии в коде.

**Решение:** BFF — под мараторием. Существующий эндпоинт — **кандидат на удаление** (задача @BE, если владелец
подтвердит); до удаления он не трогается. Агрегация для экранов делается **в контексте-владельце** данных
(например, сводка — в `BC-Analytics` на MV), а не склейкой чужих ответов на шлюзе.

## Уточнение (2026-11-09, AR-014): YARP = маршрут и резерв, маршрутизация уходит в APIM

После ADR-023 (полный APIM) и с учётом маратория на BFF:

- **YARP — маршрутизация + резервный путь.** BFF-роли у него нет (мараторий выше).
- **Маршрутизация и контракты** — на APIM: на **этапе 1** APIM стоит вне пути (control plane), трафик идёт
  `Funnel → YARP → сервисы`; на **этапе 2** APIM встаёт в путь (`Funnel → Caddy → APIM → YARP`).
- **Условие вывода YARP из пути** (не решено): маршрутизация полностью на краю, YARP не нужен как отдельный контейнер.
  До этого YARP **остаётся** — он же путь деградации при падении APIM (ADR-023 §комплаенс).
- «Единая точка входа» больше не свойство YARP: это свойство **края** (Caddy/APIM). YARP — внутренний сервис.
