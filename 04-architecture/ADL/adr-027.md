# ADR-027: Релиз — неизменяемый артефакт (deploy по digest), а не мутабельный тег

- **Статус:** Принято (2026-11-13)
- **Дата:** 2026-11-12
- **Заменяет:** — (уточняет ADR-022 «деплой по компонентам» в части «что именно деплоим»)
- **Владелец решения:** @AR (архитектура релиза) + @DO (реализация деплоя)
- **Связанные ADR:** 022 (деплой по компонентам), 023/025 (APIM и контракты), 013 (заменён)
- **Бэклог:** AR-010 (дом «архитектура деплоя»), `ITERATION-PLAN.md` §11

## 1. Контекст

Владелец флагует P0-долг (через @LM, 2026-11-12 21:12): **«деплой берёт мутабельный тег, а не pinned SHA →
пуш бэка пересобирает образ, и мы тестируем не то, что деплоим»**.

**Факт (проверено в `origin`, не по слухам):** в `7-deploy/podman-compose.yml` все 11 сервисов и шлюз
ссылаются на **`ghcr.io/ekstrem/xdiary-*:single`** — один мутабельный тег. То есть дело не в слове `latest`:
**`:single` — тот же мутабельный указатель**, меняющий смысл на каждом пуше в `main`. CI пересобирает его,
и «какой образ сейчас в проде» знает только `podman inspect`, а не git.

**Симптомы, которые это уже дало:**
- инцидент «33 часа на старом образе» (DO-050 — пост-проверка digest появилась как заплатка);
- «@TE проверяет не те теги» — прямой конфликт «пушнул бэк → CI пересобрал `:single` → проверяем другое»;
- правило `ITERATION-PLAN.md` §11 / `AGENTS.md` §5.1 «**не пушить `6-msa/**` во время выкатки**» — это
  **костыль на дефект**, а не дисциплина: если бы артефакт был неизменяемым, пушить было бы безопасно.

## 2. Варианты решений

### Вариант A — оставить как есть (`:single`, мутабельный тег)
- **Описание:** ничего не менять: CI публикует `:single`, compose тянет `:single`, «что запущено» выясняем на сервере.
- **Плюсы (исчерпывающе):**
  - нулевая стоимость: работает сейчас, ничего не надо делать;
  - одна строка в compose на сервис — просто читать;
  - не нужен lock-файл и процедура откатa.
- **Минусы (исчерпывающе):**
  - **прод невоспроизводим:** один и тот же commit/тег даёт разные образы в разное время;
  - **откат невозможен по факту** — «предыдущий `:single`» уже перезаписан, откатывать нечем;
  - **аудит невозможен:** нельзя ответить «какой код работает в проде» без сервера;
  - **тест ≠ прод:** @TE проверяет не тот артефакт, который деплоится (уже случалось);
  - порождает костыльные правила («не пушить во время выкатки»), которые никто не сможет снять.
- **Соответствие целям:** прямо противоречит требованию владельца «не тестировать не то, что деплоим».

### Вариант B — версионирование semver-тегами (`v1.4.2`) по тегу git
- **Описание:** руками (или по git-тегу) ставить `v1.4.2` на 12 образов, compose ссылается на версию.
- **Плюсы (исчерпывающе):**
  - человеку понятно «какая версия в проде»;
  - версия видна в compose без инструментов;
  - можно собрать список изменений между версиями.
- **Минусы (исчерпывающе):**
  - **тег остаётся мутабельным**: его можно переставить на другой образ, и это никто не заметит;
  - **12 сервисов × ручное версионирование** = дрейф: где-то `v1.4.2`, где-то забыли поднять;
  - семантика semver для внутренних сервисов ничего не значит (совместимость держится контрактом, ADR-025);
  - нужна дисциплина «не переиспользовать версию» — то есть снова правило вместо конструкции.
- **Соответствие целям:** частично (видно версию), но не решает «артефакт неизменяем».

### Вариант C — immutable `sha-<short>` + деплой по digest из lock-файла (ВЫБРАН)
- **Описание:** CI публикует **`sha-<short>`** на каждый коммит (immutable по построению: новое содержимое —
  новый тег). Прод-деплой идёт **по digest** (`ghcr.io/…@sha256:…`) из **lock-файла в git**
  (`7-deploy/images.lock.md`/`images.lock`), который обновляется **отдельным коммитом**. `:single`
  остаётся **только для dev** (быстрый контур).
- **Плюсы (исчерпывающе):**
  - **артефакт неизменяем:** тег `sha-<short>` привязан к коммиту, digest привязан к байтам;
  - **деплой воспроизводим:** что в lock — то и запущено, независимо от того, что пушнули после;
  - **откат — это строка в lock** (предыдущий digest), а не поиск «предыдущего тега»;
  - **аудит:** `podman inspect RepoDigests` сверяется с lock, расхождение = дефект выкатки;
  - **тест = прод:** @TE гоняет тот же digest, который в lock (и может его назвать в отчёте);
  - **снимает костыль:** «не пушить во время выкатки» становится ненужным — пуш не меняет деплой;
  - работает при любом registry и не мешает APIM-реестру контрактов (ADR-025).
- **Минусы (исчерпывающе):**
  - **появляется lock-файл** и процедура его обновления (кто, когда, чем) — новая дисциплина;
  - **нужна чистка registry**: тегов `sha-*` много, старые надо вычищать (иначе распухает);
  - **digest в compose читать неудобно** (длинные строки) — нужен генератор из lock;
  - **digest между registry-ами не переносится** (если сменим GHCR — lock перегенерировать);
  - dev-контур с `:single` сохраняет мутабельность — значит «на dev проверили» всё ещё не равно «в проде то же», если dev тянет `:single`.

## 3. Выбранное решение

**Вариант C — immutable `sha-<short>` + деплой по digest из lock-файла.**

**Статус реализации: целевая схема, файла ещё нет.** Проверено 2026-11-13: `git ls-tree -r --name-only origin/main -- 7-deploy | grep -i lock` → **пусто**,
`7-deploy/images.lock` **не создан**, деплой по-прежнему берёт `:single`. То есть этот ADR описывает **куда идём**, а не то, что уже работает.
**Порядок (обязательный, иначе получим «lock есть, а деплой его не читает» — то есть снова два источника правды):**
1) сначала `images.lock` + **гейт, который его проверяет** (два прогона по §5.4: дефект → rc=1, норма → rc=0);
2) потом переключение деплоя на digest из lock;
3) только после зелёного прод-деплоя по digest — снятие костыля «не пушить при выкатке».

Правила:

1. **CI публикует на каждый коммит в `main`:** `xdiary-<service>:sha-<7>` (immutable) **и** `:single` — **только для dev**.
   Прод-путь `:single` **не использует**. В образ вшиваются labels:
   `org.opencontainers.image.revision=<git sha>`, `org.opencontainers.image.created=<build ts>`,
   `org.opencontainers.image.source=<repo url>` — чтобы происхождение читалось с образа, а не только из lock.
2. **Источник правды для прода — `7-deploy/images.lock`** (по строке на сервис: `service`, `sha-<7>`, `digest`).
   Обновляется **только явным коммитом** (не автоматом из CI), чтобы смена прод-артефакта была видима в истории.
3. **Деплой по digest:** compose/скрипты получают `image: <repo>@sha256:…` из lock (генерация, не руками).
4. **Проверка после выкатки (обязательная, две сверки):**
   - **digest:** `podman inspect --format '{{.RepoDigests}}' <container>` == `digest` из lock;
   - **происхождение:** label образа `org.opencontainers.image.revision` == `sha` из lock
     (ставится при сборке). Это отвечает на вопрос «из какого коммита собран этот байт», а не только «какой байт»;
   - плюс `/health` 200. Любое расхождение = выкатка не закрыта.

   **Почему нужны оба идентификатора (ответ на «а зачем SHA, если есть digest»):** digest — это **идентичность байта**
   (что именно запущено), SHA — **происхождение** (из какого коммита). Для аудита и откатa нужны оба: по digest
   мы знаем, что не подменили артефакт, по SHA — какой код в нём. И наоборот: `--is-ancestor` для деплоя
   действительно не нужен (SHA в lock точен), но **без label** пришлось бы верить lock'у на слово — а lock
   обновляется человеком. Label делает проверку самодостаточной: образ сам говорит, из чего он собран.
5. **Откат = предыдущая строка lock** (коммит «rollback: <service> → <digest>»), а не «пересобрать заново».
6. **Снятие костыля:** правило «не пушить `6-msa/**` во время выкатки» (`AGENTS.md` §5.1, `ITERATION-PLAN.md` §11)
   **удаляется**, когда (2)+(4) работают в проде. Условие машинно-проверяемое: **деплой читает только lock**, значит
   пуш в `main` не влияет на прод. До этого момента правило остаётся (target_owner: @DO, условие: первый прод-деплой по digest с зелёной сверкой).
7. **Retention (иначе откат умрёт именно тогда, когда нужен).** Хранить **не менее 10 последних** `sha-*` на каждый сервис
   и **никогда** не удалять digest, который: (а) указан в текущем `images.lock`; (б) встречается в **последних 10** коммитах
   lock-файла (история откатов). Чистка — отдельная джоба с проверкой этих двух условий **до** удаления: retention,
   который не смотрит в lock, — это отложенная потеря способности откатиться.
8. **Гейт «прод деплоится только по lock» (машинно-проверяемый, заменяет костыль).** Деплой-скрипт (`update.sh`/`deploy.sh`)
   **отказывается** работать, если хотя бы один образ задан **тегом**, а не `@sha256:…` из lock; и **не принимает** образ
   «из аргумента» — только из `7-deploy/images.lock`. Проверка: подложить в вызов тег → скрипт завершается с **rc≠0**
   и текстом «деплой только по digest из images.lock»; норма — прод-деплой по lock. Это тот самый гейт, который делает
   пуш бэка безопасным (пуш физически не влияет на то, что деплоится).

## 3.2. Аудит существующих путей деплоя (2026-11-14) — чего этот ADR не покрывал

При проектировании я описал **идентичность артефакта**, но **не проверил существующие ручные пути**. Они есть, и
каждый обходит и версионирование, и гейты:

| # | Путь | Факт | Чем плох |
|---|---|---|---|
| 1 | **Ручной запуск деплоя с произвольным тегом** | `.github/workflows/deploy.yml`: `workflow_dispatch.inputs.tag`, описание «Image tag (empty = single/latest)»; шаг `TAG=${TAG_INPUT:-single}` | по умолчанию **мутабельный `single`**; тег вводится руками |
| 2 | **Ручной деплой на сервере** | `7-deploy/deploy.sh:15`: `TAG="${1:-single}"`, далее `podman run … :$TAG` для 11 сервисов | тот же мутабельный тег, минуя CI и lock |
| 3 | **«Откат» руками на проде** | `7-deploy/runbooks/release-gate.md:90`: `ssh <прод> "sudo podman tag <предыдущий-digest> …:single"` | откат нигде не фиксируется: «что в проде» снова знает только сервер |
| 4 | **Прод при красном фронтовом гейте** | условие `deploy-prod`: `always() && smoke-api=='success' && (smoke-front=='success' \|\| front!='true')` (DO-035) | осознанное исключение, но **не оформлено по §8** (нет владельца и условия снятия) |

**Следствие:** правила §3 (digest из lock, отказ при теге) **не выполняются ни одним из путей 1–3**. Пока они
существуют, «деплой по lock» — декларация.

## 3.3. Релиз-менеджмент — что ещё не спроектировано (честно)

Этот ADR отвечает на «**что** деплоится и **как проверить, что доехало именно оно**». Он **не отвечает** на:

| Вопрос релиз-менеджмента | Состояние | Решение |
|---|---|---|
| Как релиз попадает на прод (промоушен dev→prod) | пуш в `main` → dev → smoke → прод | оставить автопромоушен, но прод берёт **digest из lock** |
| Кто имеет право на прод | `environment: prod` (approval настраивается в UI, в репо не видно) | зафиксировать в ранбуке: прод — только по зелёным `smoke-api`+`smoke-front`; исключение — **только ADR**, не `always()` |
| Нумерация релизов | нет | semver **не вводим**: идентификатор релиза = `lock@<sha>`, плюс git-тег `release-YYYY.MM.DD.N` для читаемости |
| Release notes | нет | генерировать из `git log --oneline <prev-lock>..<next-lock>` в CHANGELOG при обновлении lock |
| Hotfix | не описан | hotfix = коммит в `main` → тот же конвейер; **ручной деплой hotfix запрещён** |
| Freeze-окно | не описано | заморозка = lock не меняется; код пушить можно (это и снимает костыль «не пушить при выкатке») |
| Владелец релиза | не назначен | @DO — исполнение, @TL — приёмка, @AR — правила |

**Вывод:** релиз-менеджмент **не спроектирован**; сделана только идентичность артефакта. Следующий шаг не требует
нового ADR — достаточно дополнить §3 (промоушен по lock, релиз = lock-коммит, release notes из диффа, hotfix через
тот же конвейер).

## 4. Последствия
- **Плюсы:** прод воспроизводим; откат возможен; аудит «какой код в проде» — по git; тест и прод на одном артефакте;
  снимается костыльное правило про пуш во время выкатки.
- **Риски:** lock-файл станет «второй правдой», если его начнут менять вручную без коммита (закрывается проверкой §3 п.4);
  **retention без проверки lock ломает откат** (закрывается правилом §3 п.7 — чистка смотрит в lock и его историю);
  распухание registry от `sha-*` (нужен retention); digest не переносится между registry (перегенерировать lock при переезде);
  dev на `:single` остаётся мутабельным — «на dev проверили» не гарантирует «в проде тот же байт» (осознанно: dev — быстрый контур).
