# ADR-022: Архитектура деплоя — по изменённым образам (не монолит, не полный компонентный)

- **Статус:** Предложено
- **Дата:** 2026-11-08
- **Связанные ADR:** 020 (CD pipeline), 002 (профиль Single)
- **Бэклог:** AR-010

## Контекст
`update.sh` тянет **все** образы и считает **один** агрегатный хеш; любое изменение → `deploy.sh`
пересоздаёт **все 12** контейнеров (`podman rm -f` всех + `podman run` по hardcoded IP).
Владелец спросил: не делить ли деплой по компонентам.

## Решение
**Деплой по изменённым образам** (path-based), а не полный компонентный:
- **Граница компонента = образ** (1 сервис = 1 образ = 1 компонент).
- `update.sh` считает хеш **по-образно**; изменённые → `deploy.sh` пересоздаёт **только их** (`podman compose up -d <svc>`).
- **Миграции — per-service:** БД изолированы по сервису (отдельная база на каждый), кросс-сервисных миграций нет → частичный деплой безопасен.
- **Откат по компоненту:** `podman run <svc>:single-<SHA>` (иммутаб. тег) или compose с зафиксированным тегом.

## Обоснование (почему не монолит и не 12 скриптов)
- **Монолит** — нет изоляции (любой чих → весь стек); но при 12 сервисах + 1 паре передеплой быстрый, и инцидент «33 часа на старом образе» был от `|| true`, а не от монолитности.
- **Полный компонентный** (12 скриптов/профилей, health-цепочки, порядок) — преждевременное усложнение для текущего размера.
- **Path-based** — даёт изоляцию (только изменённые) при одном скрипте; это ровно то, что уже наполовину есть (CI собирает по-сервисно, `gen-hosts.py` даёт список).

## Последствия
- **Риск порядка:** при изменении шлюза (маршруты / `--add-host`) — пересоздавать шлюз вместе с затронутыми сервисами.
- **JWT-ключ (ADR-021) — общий для всех:** при ротации ключа — передеплой **всех** (это редкое исключение, не рутина).

## Проверки
- AR-010 → задачи @DO: `update.sh` по-образный хеш + `deploy.sh` пересоздание только изменённых (через compose, без hardcoded IP).
