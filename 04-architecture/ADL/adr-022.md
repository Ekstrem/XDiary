# ADR-022: Архитектура деплоя — каждый микросервис = независимая единица деплоя

- **Статус:** Принято (2026-11-11) — до 2026-11-11 стоял `Предложено (пересмотрено 2026-11-08)`, хотя решение реализовано
- **Дата:** 2026-11-08
- **Связанные ADR:** 001 (контексты), 002 (профиль Single), 020 (CD pipeline)
- **Связанные решения:** ADR-020 (CD) → деплой по компонентам остаётся в силе, уточняется «что именно деплоим»;
  ADR-027 (релиз по digest) → **соответствует**: единица деплоя по-прежнему компонент, меняется только идентичность образа
- **Бэклог:** AR-010

## Контекст
Владелец: **«микросервис по определению деплоится отдельно»**. Текущий `deploy.sh` монолитен — пересоздаёт **все 12** контейнеров. Первая версия ADR-022 предлагала path-based (один скрипт, только изменённые) — это компромисс, который не делает микросервис независимой единицей деплоя. Пересматриваю.

## Варианты (цена / риск)

### A. Монолитный `deploy.sh` (текущий)
- **Цена:** 0 (ничего не менять).
- **Риск:** нет независимого деплоя — изменение одного образа пересоздаёт весь стек; откат тоже «весь стек»; сломанный компонент требует передеплоя всех.
- **Вердикт:** ❌ нарушает базовый принцип EDM (микросервис = независимо деплоимая единица).

### B. Path-based (один скрипт, по изменённым образам)
- **Цена:** малая (по-образный хеш + условное пересоздание).
- **Риск:** «единицей деплоя» остаётся **весь скрипт**, а не сервис: нельзя отдельной командой «задеплой только journal», есть лишь условное пересоздание внутри общего прогона.
- **Вердикт:** ⚠️ компромисс — снимает изоляцию, но не даёт независимую единицу.

### C. Компонентный — каждый BC = независимая единица деплоя
- **Цена:** средняя (12 деплой-единиц + явный порядок).
- **Риск:** порядок миграций и зависимостей — но **БД изолированы по сервису** (кросс-миграций нет), а шлюз статичен (маршруты/`--add-host` меняются только при изменении состава). Риск управляем.
- **Вердикт:** ✅ EDM-канон: 1 BC = 1 контейнер = 1 независимая единица деплоя.

## Решение: C — компонентный деплой

- **Граница компонента = ограниченный контекст (BC):** 1 BC = 1 контейнер = 1 единица деплоя.
- **Единица деплоя:** `podman-compose up -d <service>` — только этот сервис; триггер — по-образный хеш (изменился образ → пересоздан только его сервис). **Команда — `podman-compose` (python, пинованная версия из репозитория):** на VPS podman 3.4.4 нет подкоманды `podman compose` (она с 4.x); после апгрейда podman ≥4.x (DO-054) — нативный `podman compose up -d <service>`.
- **Пинованная версия `podman-compose`:** объявляется в `7-deploy/requirements.txt` (фиксированная версия, напр. `podman-compose==1.0.6`); ставится на VPS шагом деплоя (`pip install -r requirements.txt`); пост-проверка — `podman-compose --version`.
- **Порядок:** миграции (per-service, на старте; БД изолированы) → сервисы → **шлюз последним** (он фронтует всех; пересоздаётся, только если менялся его образ/состав).
- **Откат по компоненту:** иммутаб. тег `single-<SHA>` → `podman-compose up -d <service>` с зафиксированным тегом.
- **Источник правды для состава и порядка:** `podman-compose.yml` (каждый сервис = entry) + манифест порядка (шлюз последним). `deploy.sh` с hardcoded IP/`--add-host` — убрать (он обходит compose, это дрейф).

## Последствия
- **JWT-ключ (ADR-021) общий для всех:** при ротации ключа — передеплой **всех** (редкое исключение, не рутина).
- **Негативный контроль:** фронт-only коммит не перезапускает бэкенд (критерий DO-052).
- **Миграции:** катятся только своим сервисом; зависимость «сервис A ждёт схему B» в текущей модели отсутствует (изолированные базы).

## Окно смешанных версий (ответ на вопрос @TL 2026-11-08 10:20)

**Вопрос:** при частичном деплое образ сервиса с миграциями уехал, а зависимый — ещё нет. Что происходит?

**Про миграции — покрыто и не является проблемой по конструкции.** БД **изолированы по сервису**: миграции катятся стартом
**своего** контейнера, кросс-сервисных миграций нет, поэтому «сервис A ждёт схему B» в этой модели отсутствует. Схема каждого
сервиса меняется ровно тем бинарником, который её знает — версия схемы и версия кода разойтись не могут.

**Чего действительно не хватало — окна смешанных версий по КОНТРАКТУ.** Пока идёт частичный деплой, старый потребитель
(N-1) и новый поставщик (N) работают одновременно и разговаривают по HTTP. Изоляция БД здесь не помогает: ломает не схема,
а изменённый контракт. Правило:

| Тип изменения | Как деплоить | Почему |
|---|---|---|
| **Добавление** поля/эндпоинта (additive) | можно частично, в любом порядке | N-1 потребитель не знает о новом поле и не ломается |
| **Удаление/переименование/смена типа** (breaking) | **expand → contract, два релиза:** сначала добавить новое и поддержать старое, потребителей перевести, удалить старое отдельным релизом | иначе в окне остаются потребители, читающие удалённое |
| **Смена поведения при тех же полях** (семантика) | только вместе с потребителем, один деплой | контракт не изменился, а наблюдение — да |

**Следствие для `DO-052`:** пункт «порядок: миграции → сервисы → шлюз» корректен, но **недостаточен** — он не описывает,
что делать с breaking-изменением контракта. Критерий: **breaking-изменение не может уехать «само»**, его релиз включает
потребителей (или предваряется expand-релизом). Машинная проверка возможна по `api-index.yaml`: изменение,
удаляющее `operationId` или поле из `request`, — breaking, и требует пометки в задаче, что деплой совместный.

**Почему это не теория:** у нас уже 12 сервисов и `api-index` как единый реестр; первое же удаление эндпоинта
(`/clients/{id}/link-partner` — кандидат по ADR-024) пройдёт через это окно, и если деплой будет «по изменённым образам»
без правила, клиенты получат 404/405 в проде между двумя деплоями.
