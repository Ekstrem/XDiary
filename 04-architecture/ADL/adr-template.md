## Шаблон ADR

```markdown
# ADR-NNN: {Название}

- **Статус:** Предложено | Принято | Отклонено | Заменено
- **Дата:** {дата}
- **Связанные ADR:** {номера}
- **Бэклог:** {US / задача / инициатор}

## 1. Контекст
{Что решаем, почему сейчас, ограничения бизнеса (время/ресурсы — если подтверждаемы),
связанные задачи. Пишет автор; рецензент помогает с полнотой.}

## 2. Варианты решений (минимум 3)
### Вариант A — {имя}
| Аспект | Значение |
|---|---|
| Схема | {диаграмма/кратко} |
| Описание | {особенности, отличие от других} |
| Плюсы | {…} |
| Минусы | {…} |
| Соответствие целям | {какие цели компании закрывает} |

### Вариант B — {имя}
{та же таблица}

### Вариант C — {имя}
{та же таблица}

## 3. Выбранное решение
**Вариант {X}** — {обоснование: сумма «плюсы + цели» > альтернатив; согласовано владельцами}.
{SWOT — при наличии времени}

### 3.1 Протокол согласования
| Роль | Принял | Отклонил | Воздержался |
|---|---|---|---|
| @AR | ✅ {дата} | | |
| Владелец (PO) | | | ⚪ |

### 3.2 Обязательства
| Задача / Поручение | Ответственный |
|---|---|
| {BE-xxx / RnD / …} | {роль} |

### 3.3 Комплаенс
| Что | Значение |
|---|---|
| Условия пересмотра | {когда пересматриваем} |
| Как проверяется | {критерий исполнения} |
| Кто проверяет | {роль / задача} |

## 4. Последствия
- **Плюсы:** …
- **Риски:** …
```

## Процесс согласования

| Шаг | Что происходит | Кто | Артефакт |
|---|---|---|---|
| **1. Идея** | Контекст: что решаем + почему + ограничения (2–3 строки) | автор | ADR (раздел 1) |
| **2. Проработка** | Варианты ≥3 (три столбца: описание/плюсы-минусы/цели) + скоринг | @AR / доменный владелец | ADR (раздел 2) |
| **3. Рецензия вариантов** | Достаточность + согласие по плюсам/минусам/целям (тайминг ~7 мин/вариант) | владельцы архитектуры | комментарии в задаче/PR |
| **4. Принятие** | Презентация + голосование (Принял/Отклонил/Воздержался) | владельцы | протокол (3.1) |
| **5. Статус** | `Предложено → Принято` (или `Отклонено`) | автор | статус в ADR |
| **6. Обязательства** | Задачи/поручения → в бэклог | TL / доменный владелец | задачи BE/DO/FE/TE |
| **7. Комплаенс** | Условия пересмотра + кто проверяет | автор + ревьюер | раздел 3.3 |
| **8. Информирование** | ADL README + сообщение в chat | автор | строка в ADL + chat |

## Ключевые принципы (из статьи)

1. **Минимум 3 варианта** — не бывает решений с одним вариантом; трёхстолбчатая таблица
   (плюсы/минусы/цели) исключает холивары и субъективные веса.
2. **Протокол с персоналиями** — «принял/отклонил/воздержался», а не молчаливое «все согласны».
3. **Бизнес — только требования** («что»), а «как» выбирают инженеры-владельцы архитектуры;
   PO задаёт приоритеты и цели, но технический выбор — за @AR/инженерами.
4. **Жёсткий тайминг** — лимит на обсуждение вариантов и на принятие, чтобы не тонуть в холиварах.
5. **Дробить сложные решения** — если затронуты несколько систем, принимать поэтапно.
