## 1.1. Контракт доставки событий — см. отдельный документ

Транспорт, конверт, гарантии и отказные режимы описаны в ADR-029 (ADL/adr-029.md): **доставка из Event Store через Outbound Handler, at-least-once, идемпотентный приём**; второго журнала событий нет, шина фреймворка (EventBus.InMemory) для межсервисной доставки не используется. **Что это меняет в оценке:** E1 включает Event Consumer, Outbound Handler и эндпоинт приёма (иначе пилот не даёт межсервисной ценности), E5 сокращается до ретраев и dead-letter.

**Факт, важный для E1:** в Journal AddEventStorePostgres **зарегистрирован**, но JournalCommandRepository.SaveAsync пишет через _db.SaveChangesAsync — то есть store **обойдён**. E1 — это переключение пути записи, а не добавление EDM с нуля.

## 2. Признак «долг закрыт» — по каждому пакету, проверяемо

Общий принцип: **долг закрыт, когда это видно кодом/гейтом, а не отчётом.**

| Пакет | Критерий закрытия (что проверяем) |
|---|---|
| E1 | Команда пилота **не** вызывает `SaveChangesAsync` в command-path; событие попадает в **Event Store** (`SaveEventAsync`), из него проектируется **MV** (`UpsertAsync`), query читает MV и **не содержит** `Distinct()`/`SortedSet`/`OrderBy` по всей таблице. Тест: «команда → событие в store → MV обновился» **и** «рестарт сервиса → состояние восстановлено из событий» (это и есть event sourcing) |
| E2 | То же для остальных 9 BC + чек-лист «0 вхождений» запрещённых имён по всему `6-msa` |
| E3 | `Shared/XDiary.Contracts/Infrastructure.cs` удалён (или пуст); `grep` по `IReadRepository|IBusAdapter|ICommandDbContext|INotifier` = 0 |
| E4 | `IBusinessOperationValidator` встречается в агрегатах (>0); anemic-модели без публичных сеттеров; handlers грузят агрегат через `AggregateProvider` |
| E5 | Нет `_ = PublishAsync`; доставка из стора через Outbound Handler + ретраи; тест «приёмник лежит → событие доставлено после восстановления» |
| E6 | MV содержит `clientId`; тест «два клиента → разные агрегаты, перекрёстного нет» |
| E7 | Доки обновлены по ADR-024; миграция эго-партнёров выполнена; тест «эго-партнёр не в `/partners`» + «история читается» |

**Предлагаю сделать это гейтом, а не списком:** `tools/check_edm.py` (зона @DO) с двумя наборами —
**запрещено**: `SaveChangesAsync` в `*.Application/**` (command-path), `IReadRepository`/`IBusAdapter`/`ICommandDbContext` в `6-msa`;
**обязательно**: `AddEventStorePostgres`/`AddEventBus`/`AddReadStore` в `Program.cs` каждого BC, `IHostedService` (consumer), `UpsertAsync` в проекторах.
Тогда «EDM закрыт» = гейт зелёный + негативные контроли (§5.4), а не отчёт @BE. Гейт вводится **поэтапно**: по мере раскатки
список «обязательно» включает BC, на котором пакет закрыт (иначе гейт сразу красный на всём).

### 2.1. Точные правила для `check_edm.py` (на согласование @LM → §5.2/§5.4)

**Как включается поэтапность — маркер, а не ручной список.** В BC, переведённом на EDM, лежит файл-маркер
`6-msa/BC-<Имя>/EDM-CLOSED` (создаётся тем коммитом, что закрывает пакет). Гейт проверяет **только** BC с маркером,
остальные перечисляет в отчёте строкой «не переведены: N из 10». Так:
- прогресс виден цифрой (10 маркеров = закрыто), и это **факт в git**, а не список в конфиге (тот же урок, что с датой создания ADR);
- гейт не красный на промежуточном состоянии;
- добавление маркера — осознанный акт, который видно в истории.

**ЗАПРЕЩЕНО** (внутри BC **с маркером**, grep по `6-msa/BC-<Имя>/**`):
- `SaveChangesAsync` в `*.Application/**` и в `*.Storage/*CommandRepository*` (command-path пишет только через Event Store);
- `IRepository`, `IReadRepository`, `IBusAdapter`, `ICommandDbContext`, `INotifier`, `IReadModel` — свои интерфейсы из `Shared/XDiary.Contracts/Infrastructure.cs`;
- `PostAsJsonAsync` / `HttpClient` в command handlers (ручной паблишер событий);
- `_ = PublishAsync` (fire-and-forget без ожидания/ретрая).

**ОБЯЗАТЕЛЬНО** (внутри BC с маркером):
- в `Program.cs`: `AddEventStorePostgres` **и** `AddEventBus` **и** `AddReadStore`;
- класс с `IHostedService` (Event Consumer) и вызовом `SaveEventAsync`;
- `UpsertAsync` в проекторах (MV);
- `IEventBus` / `Publish(` в пути бизнес-метода агрегата;
- `AggregateProvider.GetAggregateAsync(` в handlers (загрузка из событий, не `_repo.GetByIdAsync`).

**Негативные контроли гейта (§5.4, два направления):**
1. BC с маркером + `SaveChangesAsync` в application-path → **rc=1** с указанием файла:строки;
2. BC с маркером, всё по правилам → **rc=0**;
3. BC **без** маркера с нарушениями → **rc=0** + строка «не переведены: N» (не красный);
4. `--selftest` внутри прогона (синтетическая папка: годный BC / нарушитель / без маркера).

**Кто ставит маркер `EDM-CLOSED` (чтобы не «на глаз»):** маркер добавляет **@BE** — в том же коммите, где BC прошёл
свои тесты (критерий из §2, не «сервис поднялся»); **@AR подтверждает** его на ревью карточки BC
(`На проверке` → вердикт @AR). Если @AR нашёл нарушение — маркер **удаляет @BE** в отдельном коммите (то же правило, что откат кода).
То есть маркер = заявление @BE + подтверждение @AR, а не самоотчёт одной роли. Гейт видит только факт маркера,
поэтому без подтверждения он не «зеленеет» сам.

**Формат маркера (не пустой файл, иначе «переведён» и «поставили на глаз» неразличимы):**

```text
# 6-msa/BC-<Имя>/EDM-CLOSED
migrated-by: BE-055 (или номер карточки)
reviewed-by: @AR
date: 2026-11-XX
checks: event-store, event-bus, read-store, consumer, mv-upsert, replay
```

Гейт проверяет **наличие полей** `migrated-by`, `reviewed-by`, `date`, `checks` — неполный маркер = **error**.
Так «маркер без прошедших тестов/ревью» ловится структурно, а смысл ревью (@AR глазами) остаётся за человеком:
гейт не умеет оценивать качество тестов, но умеет требовать, чтобы заявление было оформлено.

**Канонический набор `checks` (фиксированный, регистрозависимый — иначе «опечатка» не ловится):**
`event-store`, `event-bus`, `read-store`, `consumer`, `mv-upsert`, `replay`.
Появление нового пункта — правка этого раздела и гейта **одним коммитом** (иначе маркер и гейт разъедутся).

**Обратное правило (по просьбе @TL): маркер без прохождения тестов = нарушение.** Гейт этого не видит
(он не запускает тесты), **но приёмка карточки BC — видит**: критерий ревью @AR звучит как
«маркер стоит тогда и только тогда, когда тесты BC зелёные в том же коммите»; если тесты не зелёные или
маркер добавлен «наклейкой» — это дефект, **маркер удаляет @BE**, BC возвращается в «не переведён».
Так @BE и @AR судят по одному правилу, а не по ощущению.

**Распределение ролей по гейту (чтобы не было двух рук в одном файле):**

| Роль | Что делает | Зона |
|---|---|---|
| **@AR** | правила «запрещено/обязательно» (этот раздел), эталон модели, подтверждение маркера на ревью BC | `03-ddd/`, `04-architecture/`, `5-tech-backlog/arch/` |
| **@DO** | инструмент `tools/check_edm.py` + `--selftest` + подключение в CI + перенос в `LoopMaker` (PDR-24) | `tools/`, `.github/` |
| **@BE** | внедрение по BC, правила в коде, файл-маркер `EDM-CLOSED` | `6-msa/` |
| **@TL** | приёмка, зона в карточке | `5-tech-backlog/<роль>/` |

Оценка «гейт» (**1 дн**) относится только к @DO-части; внедрение по BC входит в E1…E6 и **не дублируется**.

## 3. Путь принятия ADR-024 (вопрос @TL №2)

**Кто решает:** ADR-024 меняет **продуктовую модель** (что показываем и что спрашиваем), поэтому решение — **за владельцем**,
я готовлю и фиксирую. **Статус «Принято» ставит @AR** (файл в его зоне) — но **только по прямой отмашке владельца**;
без неё ADR остаётся черновиком, даже если все роли «за». Пока он черновик, **BE-054 (E7) не начинается** — и это в карточке
надо записать как **предусловие** («ADR-024 = Принято по слову владельца») плюс **риск** («опирается на модель, которая может
измениться; при смене постановки объём меняется»).

ADR-024 сейчас **черновик**. Порядок принятия:

1. **Ответ @PO** по обязательным полям (имя + пол — подтверждено владельцем; фото — опционально/убрать).
2. **Протокол**: @AR ✅, @TL ✅ (с уточнениями), владелец ✅ по смыслу; нужны @PO, @BE, @FE.
3. **Статус → Принято**, `Заменяет: —` (уточняет ADR-021 §Последствия про `participant="me"`).
4. **Какие доки меняются (в одном коммите):**
   - `03-ddd/00-context-map.md` — Privacy → часть `Client`; связь `Client → Partners` = **scope владения**, а не «партнёр-«я»»;
   - `03-ddd/BC-Client/02-aggregate-canvas.md` — + `displayName`, `gender`, `photo?`; **− `LinkedPartnerId`** и переходы `Linked`/`Unlinked`;
   - `03-ddd/BC-Privacy/*` — пометка «часть контекста `Client`»: где живёт политика приватности/PIN;
   - `03-ddd/BC-Partners/02-aggregate-canvas.md` — `clientId` = владение, **опционален** (партнёр может стать клиентом);
   - `03-ddd/BC-Journal/02-aggregate-canvas.md` — `orgasms` = **словарь участник→оргазмы**, ключ `"me"` законен;
   - `03-ddd/01-entity-map.md` §4 — дельта помечается «внесено»;
   - `03-ddd/TECHDEBT.md` п.15 — закрыть.
5. **Эго-партнёры на проде** (BE-052): **не удалять до подтверждения владельцем.** Порядок: перенести значения в профиль `Client` → исключить из выдачи `GET /partners` → сохранить id-алиас (история журнала/каталога читается) → удаление отдельным шагом с бэкапом.
6. **Влияние на BC-Journal:** контракт не меняется (`author` = клиент неявно, `partners[]` — только другие, `participant = "me" | partnerId`); если запись ссылалась на эго-партнёра — маппинг на `"me"`.
7. **Влияние на BC-Client:** агрегат получает профиль, теряет `LinkedPartnerId` — это единственная **ломающая** часть, но она внутренняя (в API поле не отдавалось).

## 4. Порядок внутри E (предложение)

`E7 (ADR-024) → E1 (пилот Journal+Partners) → E3 (удаление своего слоя) → E2 (раскатка) → E5 (доставка и ретраи) → E4 (доменная гигиена) → E6 (tenant)`

Почему так: E7 меняет модель (без неё пилот Journal придётся переделывать); E3 после E1, иначе нечем заменить свои интерфейсы;
E2 после E3, чтобы не тащить свой слой в 9 BC и потом выковыривать; E5 — усиливает E1; E6 — последним (P3, MVP = пара).
