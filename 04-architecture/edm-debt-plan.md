## 1.1. Контракт доставки событий — см. отдельный документ

Транспорт, конверт, гарантии и отказные режимы описаны в ADR-029 (ADL/adr-029.md): **доставка из Event Store через Outbound Handler, at-least-once, идемпотентный приём**; второго журнала событий нет, шина фреймворка (EventBus.InMemory) для межсервисной доставки не используется. **Что это меняет в оценке:** E1 включает Event Consumer, Outbound Handler и эндпоинт приёма (иначе пилот не даёт межсервисной ценности), E5 сокращается до ретраев и dead-letter.

**Факт, важный для E1:** в Journal AddEventStorePostgres **зарегистрирован**, но JournalCommandRepository.SaveAsync пишет через _db.SaveChangesAsync — то есть store **обойдён**. E1 — это переключение пути записи, а не добавление EDM с нуля.

## 2. Признак «долг закрыт» — по каждому пакету, проверяемо

Общий принцип: **долг закрыт, когда это видно кодом/гейтом, а не отчётом.**

| Пакет | Критерий закрытия (что проверяем) |
|---|---|
| E1 | Команда пилота **не** вызывает `SaveChangesAsync` в command-path; событие попадает в **Event Store** (`SaveEventAsync`), из него проектируется **MV** (`UpsertAsync`), query читает MV и **не содержит** `Distinct()`/`SortedSet`/`OrderBy` по всей таблице. Тест: «команда → событие в store → MV обновился» **и** «рестарт сервиса → состояние восстановлено из событий» (это и есть event sourcing) |
| E2 | То же для остальных 9 BC + чек-лист «0 вхождений» запрещённых имён по всему `6-msa` |
| E3 | `Shared/XDiary.Contracts/Infrastructure.cs` удалён (или пуст); `grep` по `IReadRepository|IBusAdapter|ICommandDbContext|INotifier` = 0 |
| E4 | `IBusinessOperationValidator` встречается в агрегатах (>0); anemic-модели без публичных сеттеров; handlers грузят агрегат через `AggregateProvider` |
| E5 | Нет `_ = PublishAsync`; доставка из стора через Outbound Handler + ретраи; тест «приёмник лежит → событие доставлено после восстановления» |
| E6 | MV содержит `clientId`; тест «два клиента → разные агрегаты, перекрёстного нет» |
| E7 | Доки обновлены по ADR-024; миграция эго-партнёров выполнена; тест «эго-партнёр не в `/partners`» + «история читается» |

**Предлагаю сделать это гейтом, а не списком:** `tools/check_edm.py` (зона @DO) с двумя наборами —
**запрещено**: `SaveChangesAsync` в `*.Application/**` (command-path), `IReadRepository`/`IBusAdapter`/`ICommandDbContext` в `6-msa`;
**обязательно**: `AddEventStorePostgres`/`AddEventBus`/`AddReadStore` в `Program.cs` каждого BC, `IHostedService` (consumer), `UpsertAsync` в проекторах.
Тогда «EDM закрыт» = гейт зелёный + негативные контроли (§5.4), а не отчёт @BE. Гейт вводится **поэтапно**: по мере раскатки
список «обязательно» включает BC, на котором пакет закрыт (иначе гейт сразу красный на всём).

### 2.1. Точные правила для `check_edm.py` (на согласование @LM → §5.2/§5.4)

**Как включается поэтапность — маркер, а не ручной список.** В BC, переведённом на EDM, лежит файл-маркер
`6-msa/BC-<Имя>/EDM-CLOSED` (создаётся тем коммитом, что закрывает пакет). Гейт проверяет **только** BC с маркером,
остальные перечисляет в отчёте строкой «не переведены: N из 10». Так:
- прогресс виден цифрой (10 маркеров = закрыто), и это **факт в git**, а не список в конфиге (тот же урок, что с датой создания ADR);
- гейт не красный на промежуточном состоянии;
- добавление маркера — осознанный акт, который видно в истории.

**ЗАПРЕЩЕНО** (внутри BC **с маркером**, grep по `6-msa/BC-<Имя>/**`):
- `SaveChangesAsync` в `*.Application/**` и в `*.Storage/*CommandRepository*` (command-path пишет только через Event Store);
- `IRepository`, `IReadRepository`, `IBusAdapter`, `ICommandDbContext`, `INotifier`, `IReadModel` — свои интерфейсы из `Shared/XDiary.Contracts/Infrastructure.cs`;
- `PostAsJsonAsync` / `HttpClient` в command handlers (ручной паблишер событий);
- `_ = PublishAsync` (fire-and-forget без ожидания/ретрая).

**ОБЯЗАТЕЛЬНО** (внутри BC с маркером):
- в `Program.cs`: `AddEventStorePostgres` **и** `AddEventBus` **и** `AddReadStore`;
- класс с `IHostedService` (Event Consumer) и вызовом `SaveEventAsync`;
- `UpsertAsync` в проекторах (MV);
- `IEventBus` / `Publish(` в пути бизнес-метода агрегата;
- `AggregateProvider.GetAggregateAsync(` в handlers (загрузка из событий, не `_repo.GetByIdAsync`).

**Негативные контроли гейта (§5.4, два направления):**
1. BC с маркером + `SaveChangesAsync` в application-path → **rc=1** с указанием файла:строки;
2. BC с маркером, всё по правилам → **rc=0**;
3. BC **без** маркера с нарушениями → **rc=0** + строка «не переведены: N» (не красный);
4. `--selftest` внутри прогона (синтетическая папка: годный BC / нарушитель / без маркера).

**Кто ставит маркер `EDM-CLOSED` (чтобы не «на глаз»):** маркер добавляет **@BE** — в том же коммите, где BC прошёл
свои тесты (критерий из §2, не «сервис поднялся»); **@AR подтверждает** его на ревью карточки BC
(`На проверке` → вердикт @AR). Если @AR нашёл нарушение — маркер **удаляет @BE** в отдельном коммите (то же правило, что откат кода).
То есть маркер = заявление @BE + подтверждение @AR, а не самоотчёт одной роли. Гейт видит только факт маркера,
поэтому без подтверждения он не «зеленеет» сам.

**Формат маркера (не пустой файл, иначе «переведён» и «поставили на глаз» неразличимы):**

```text
# 6-msa/BC-<Имя>/EDM-CLOSED
migrated-by: BE-055 (или номер карточки)
reviewed-by: @AR
date: 2026-11-XX
checks: event-store, event-bus, read-store, consumer, mv-upsert, replay
```

Гейт проверяет **наличие полей** `migrated-by`, `reviewed-by`, `date`, `checks` — неполный маркер = **error**.
Так «маркер без прошедших тестов/ревью» ловится структурно, а смысл ревью (@AR глазами) остаётся за человеком:
гейт не умеет оценивать качество тестов, но умеет требовать, чтобы заявление было оформлено.

**Канонический набор `checks` (фиксированный, регистрозависимый — иначе «опечатка» не ловится):**
`event-store`, `event-bus`, `read-store`, `consumer`, `mv-upsert`, `replay`.
Появление нового пункта — правка этого раздела и гейта **одним коммитом** (иначе маркер и гейт разъедутся).

**Обратное правило (по просьбе @TL): маркер без прохождения тестов = нарушение.** Гейт этого не видит
(он не запускает тесты), **но приёмка карточки BC — видит**: критерий ревью @AR звучит как
«маркер стоит тогда и только тогда, когда тесты BC зелёные в том же коммите»; если тесты не зелёные или
маркер добавлен «наклейкой» — это дефект, **маркер удаляет @BE**, BC возвращается в «не переведён».
Так @BE и @AR судят по одному правилу, а не по ощущению.

**Распределение ролей по гейту (чтобы не было двух рук в одном файле):**

| Роль | Что делает | Зона |
|---|---|---|
| **@AR** | правила «запрещено/обязательно» (этот раздел), эталон модели, подтверждение маркера на ревью BC | `03-ddd/`, `04-architecture/`, `5-tech-backlog/arch/` |
| **@DO** | инструмент `tools/check_edm.py` + `--selftest` + подключение в CI + перенос в `LoopMaker` (PDR-24) | `tools/`, `.github/` |
| **@BE** | внедрение по BC, правила в коде, файл-маркер `EDM-CLOSED` | `6-msa/` |
| **@TL** | приёмка, зона в карточке | `5-tech-backlog/<роль>/` |

Оценка «гейт» (**1 дн**) относится только к @DO-части; внедрение по BC входит в E1…E6 и **не дублируется**.

## 3. Путь принятия ADR-024 (вопрос @TL №2)

**Кто решает:** ADR-024 меняет **продуктовую модель** (что показываем и что спрашиваем), поэтому решение — **за владельцем**,
я готовлю и фиксирую. **Статус «Принято» ставит @AR** (файл в его зоне) — но **только по прямой отмашке владельца**;
без неё ADR остаётся черновиком, даже если все роли «за». Пока он черновик, **BE-054 (E7) не начинается** — и это в карточке
надо записать как **предусловие** («ADR-024 = Принято по слову владельца») плюс **риск** («опирается на модель, которая может
измениться; при смене постановки объём меняется»).

ADR-024 сейчас **черновик**. Порядок принятия:

1. **Ответ @PO** по обязательным полям (имя + пол — подтверждено владельцем; фото — опционально/убрать).
2. **Протокол**: @AR ✅, @TL ✅ (с уточнениями), владелец ✅ по смыслу; нужны @PO, @BE, @FE.
3. **Статус → Принято**, `Заменяет: —` (уточняет ADR-021 §Последствия про `participant="me"`).
4. **Какие доки меняются (в одном коммите):**
   - `03-ddd/00-context-map.md` — Privacy → часть `Client`; связь `Client → Partners` = **scope владения**, а не «партнёр-«я»»;
   - `03-ddd/BC-Client/02-aggregate-canvas.md` — + `displayName`, `gender`, `photo?`; **− `LinkedPartnerId`** и переходы `Linked`/`Unlinked`;
   - `03-ddd/BC-Privacy/*` — пометка «часть контекста `Client`»: где живёт политика приватности/PIN;
   - `03-ddd/BC-Partners/02-aggregate-canvas.md` — `clientId` = владение, **опционален** (партнёр может стать клиентом);
   - `03-ddd/BC-Journal/02-aggregate-canvas.md` — `orgasms` = **словарь участник→оргазмы**, ключ `"me"` законен;
   - `03-ddd/01-entity-map.md` §4 — дельта помечается «внесено»;
   - `03-ddd/TECHDEBT.md` п.15 — закрыть.
5. **Эго-партнёры на проде** (BE-052): **не удалять до подтверждения владельцем.** Порядок: перенести значения в профиль `Client` → исключить из выдачи `GET /partners` → сохранить id-алиас (история журнала/каталога читается) → удаление отдельным шагом с бэкапом.
6. **Влияние на BC-Journal:** контракт не меняется (`author` = клиент неявно, `partners[]` — только другие, `participant = "me" | partnerId`); если запись ссылалась на эго-партнёра — маппинг на `"me"`.
7. **Влияние на BC-Client:** агрегат получает профиль, теряет `LinkedPartnerId` — это единственная **ломающая** часть, но она внутренняя (в API поле не отдавалось).

## 4. Порядок внутри E (предложение)

`E7 (ADR-024) → E1 (пилот Journal+Partners) → E3 (удаление своего слоя) → E2 (раскатка) → E5 (доставка и ретраи) → E4 (доменная гигиена) → E6 (tenant)`

Почему так: E7 меняет модель (без неё пилот Journal придётся переделывать); E3 после E1, иначе нечем заменить свои интерфейсы;
E2 после E3, чтобы не тащить свой слой в 9 BC и потом выковыривать; E5 — усиливает E1; E6 — последним (P3, MVP = пара).

### Как проверить отсутствие «заражения» опциями — точный ассерт (без БД)

«Протечка» моста означает: компонент, запросивший необобщённые `DbContextOptions`, получил **опции Event Store**, в том числе
строку подключения. Проверять это на глаз или по логам не нужно — **строка подключения доступна офлайн**, без открытия
соединения:

```csharp
var cmd  = scope.ServiceProvider.GetRequiredService<CommandDbContext>();
var read = scope.ServiceProvider.GetRequiredService<ReadDbContext>();
var store = scope.ServiceProvider.GetRequiredService<EventStoreDbContext>();

string Cs(DbContext c) => c.Database.GetDbConnection().ConnectionString;

Assert.Contains("CommandDb", Cs(cmd));      // или сравнение с конфигом
Assert.Contains("ReadDb",    Cs(read));
Assert.Contains("CommandDb", Cs(store));    // store ходит в CommandDb по дизайну
```

**Что именно доказывает ассерт:** если мост «течёт», `cmd`/`read` получат строку Event Store и проверка **покраснеет**
(строки перестанут различаться там, где обязаны). Соединение при этом **не открывается** — `GetDbConnection()` возвращает
объект с уже установленной строкой, поэтому тест детерминирован и не требует стенда.

**Дополнение к машинной проверке:** `AddSingleton<DbContextOptions>` (мост) должен встречаться в `Program.cs`
**ровно один раз** и **после** типизированной регистрации — `git grep -c 'AddSingleton<DbContextOptions>' -- 6-msa`
равно числу сервисов, использующих хранилище. Два вхождения в одном файле = неоднозначность (какой из них победит — зависит
от порядка, а `TryAdd*` вообще молча проигнорирует второй).

## Решение по `BE-071` (2026-11-05 08:45): read-модели — **бэкфилл обязателен**, «пусто» ≠ «готово»

Факт по коду (`origin`, проверено): read-модели пишутся **только** из проекции событий —
`JournalEventConsumer` (`JournalReadModel`, `JournalDefaultsReadModel`), `PartnerEventConsumer` (`PartnersReadModel`),
`PartnersEventsController` (`PartnersDirectoryReadModel`). Единственная существующая миграция — `JournalDataMigration`
(BE-061: EF-строки `journal.records` → **события**, идемпотентно по id, `DataMigration:Enabled`, дискретный шаг).
**Ни одна read-таблица не заполняется из командной БД.** Значит после выкатки `partners_read`/`journal_read` пусты
уже **существующие** данные: `/partners` вернёт `200` с пустым списком, и критерий «200» пройдёт **на пустоте**.

### Решение

1. **Бэкфилл обязателен** для BC с историческими данными (`Journal`, `Partners`). Причина не в «чистоте»: read-модель — это то,
   что видит пользователь, и пустой журнал при непустой БД — **фактическая потеря истории** в продукте, где история и есть ценность.
   Формально БД цела, но продукт ведёт себя как «данных нет» — это класс «зелёное на пустоте».
2. **Форма бэкфилла — идемпотентный шаг**, как `BE-061`: прогон по командной БД, проекция каждого агрегата в read-store,
   повторный запуск не дублирует (проверка по ключу). Один механизм на сервис; «второй способ заполнения» не заводим.
3. **Проекция только вперёд допустима лишь при отсутствии истории** (новый BC, пустая БД на чистом контуре) — и тогда это
   **явное решение с записью** в карточке/ранбуке: «исторических данных нет; перенос из командной БД не требуется».

### Критерий приёмки (заменяет «`GET /partners` → 200»)

| Проверка | Почему именно так |
|---|---|
| `GET /partners` → `200` **и** число элементов = `SELECT count(*) FROM partners` | ловит «200 на пустоте» |
| `GET /internal/journal/records` → `200` **и** число = `SELECT count(*) FROM records` | то же для журнала |
| **повторный** прогон бэкфилла не меняет число | проверяет идемпотентность, а не «однажды сработало» |
| на **чистой** БД сервис стартует, таблицы создаются, бэкфилл на пустой источнике даёт `0` и `200` | отделяет «схема есть» от «история перенесена» |

**`200` без сверки чисел — не доказательство.** Ровно этот критерий мы уже принимали как достаточный и получили бы зелёный экран
с пустым журналом.

### Уточнение к гейту свежести (2026-11-05 08:50): сравнение должно быть **на одном предикате**

@DO сделал критерий машинным (`tools/check_read_model_freshness.py`, `--selftest 8/8`, `read-model-check.yml`) — это правильно.
Но в реализации источник считается как `select count(*) from {table}` **без фильтров**, а эндпоинты фильтруют по клиенту:

| Эндпоинт | Что отдаёт |
|---|---|
| `GET /api/v1/partners` | `[Authorize]` → `clientId` из `sub`; далее `all.Where(x => x.ClientId == clientId)` |
| `GET /api/v1/journal/records` | то же: `TryClientId` → `ListRecordsQuery(clientId)` |
| `GET /internal/journal/records` (`ListAll`) | **без** клиента — это внутренний `ListAll`, исключение из `(ii-b)` |

Значит сравнение «элементов API» с `count(*)` **сходится только пока клиент один**. Как только в БД два клиента
(тестовый пользователь, второй партнёр, бот), гейт даст **ложный красный** на корректном поведении — а если числа случайно совпадут,
даст **ложный зелёный**.

**Правило:** ожидаемое число считается **тем же предикатом**, что и чтение:

| Эндпоинт | Ожидаемое число |
|---|---|
| `/api/v1/partners` | `count(*) FROM partners WHERE "ClientId" = <clientId из токена>` |
| `/api/v1/journal/records` | `count(*) FROM records WHERE "ClientId" = <clientId>` |
| `/internal/journal/records` | `count(*) FROM records` (без клиента — верно **только** для этого эндпоинта) |
| справочник партнёров в журнале | `count(*) FROM partners_directory WHERE "DeletedAt" IS NULL` (журнал фильтрует удалённых) |

**Если контур одноклиентный — это надо сказать явно** («сейчас в БД один клиент, поэтому `count(*)` совпадает с фильтром»),
а не полагаться на совпадение: иначе первый же второй клиент превратит гейт в «всегда красный», и его отключат.

### Проекция не должна валить команду (2026-11-05 09:40) — иначе `500` в контракте не про бэкфилл

Тракт по коду (`origin`): `PartnerCommandRepository.SaveAsync` → `_bus.PublishAsync(result.Event)` → in-memory bus →
`PartnerEventConsumer.Handle` (**синхронно**) → `SaveEventAsync().GetAwaiter().GetResult()` **и**
`_readStore.UpsertAsync(read).GetAwaiter().GetResult()`. **`try/catch` в этой цепочке нет.**

Следствия, которые надо решить явно:

1. **Отказ проекции валит команду.** Если `UpsertAsync` падает (нет таблицы, расхождение колонок, недоступный read-store),
   исключение поднимается в `PublishAsync` → `POST /partners` отдаёт **`500`**, хотя событие в event store могло записаться.
   Именно это мы сейчас видим в контракте `#5`/`#6`: «`500`» — это не «бэкфилла нет», а **отказ read-пути, проброшенный в запись**.
2. **`GetAwaiter().GetResult()`** в синхронном обработчике — sync-over-async: блокирует поток, скрывает таймауты и
   под нагрузкой склонен к дедлоку.
3. **Порядок «сначала событие, потом проекция в одном запросе»** делает запись зависимой от производного хранилища.

**Решение (моё, как архитектора разделения чтения/записи):**

- **Источник истины — event store.** Запись события успешна ⇒ команда успешна. Отказ **проекции** — не отказ команды.
- В обработчике проекция оборачивается в `try/catch`: исключение **логируется** (`read-model projection failed: <тип> <сообщение>`)
  и **не пробрасывается**; команда возвращает успех, потому что её контракт выполнен (событие сохранено).
- Расхождение чтения ловит **гейт** (`check_read_model_freshness`, `Cron`/30 мин): «данные есть в событии, но не в read-модели» —
  это **дефект проекции**, видимый и измеримый, а не `500` на записи.
- **`GetAwaiter().GetResult()` убрать**, если шина позволяет асинхронный путь; если нет — вынести проекцию из обработчика
  (после ответа), а не блокировать поток.

**Почему это не «ослабить приёмку»:** `500` на записи не помогает пользователю и не сохраняет данные — он **мешает** записи,
которая уже корректна доменно. Хуже того: он маскирует настоящую причину (проекция) под «сервер сломан».

## DDL в `Program.cs` — **отклонение от DF/EDM**, а не «временная мера» (2026-11-05 09:20, по вопросу владельца)

**Факт по коду `origin`:**

| Сервис | Строка | Что |
|---|---|---|
| `Journal.Api/Program.cs` | `:60` | `CommandDbContext.Database.Migrate()` |
| | `:62` | `ReadDbContext.Database.ExecuteSqlRaw("CREATE TABLE IF NOT EXISTS journal_read (…)" …)` — **3** таблицы |
| `Partners.Api/Program.cs` | `:53` | `CommandDbContext.Database.Migrate()` |
| | `:55` | `ExecuteSqlRaw("CREATE TABLE IF NOT EXISTS partners_read …")` — **1** таблица |

**Почему это противоречит канону** (`0-df-issue/migrations.md`, `edm-own-implementations.md`):

1. EDM/DF: **схемой управляют сами пакеты** — `AddEventStorePostgres` / `AddReadStorePostgres`
   («Предполагается, что схему создают сами пакеты (event store / read store)»). У нас схему создаёт **приложение**,
   вручную, SQL-строкой в хосте.
2. DF не описывает миграции вообще — это зафиксировано как **DF-issue**, и его рекомендация:
   EF-миграции для `CommandDbContext` **или** вариант B — вернуться к пакетам, которые управляют схемой.
   Для **командного** контекста это сделано (`migrations.md` → «Реализовано 2026-10-31»), для **read-контекстов** — **нет**.
3. Дополнительно мы **выключили** библиотечный маппинг (`AddReadStorePostgres(…, null)`), то есть сняли с пакета
   ответственность за модель и взяли её на себя — и тут же взяли на себя схему. Это **три** отклонения в одном месте:
   (а) своё провижининг-схемы вместо библиотечного; (б) SQL в старте хоста вместо артефакта миграции;
   (в) второе описание модели (DDL vs `OnModelCreating`), которое уже разошлось на 10 колонок.

**Как появилось (причина, а не оправдание):** read-схема не провижинилась **нигде** — `migrations.md` закрывал только
`CommandDbContext`, read-таблиц не было ни на одном контуре, `42P01` блокировал всё. DDL на старте был самым коротким
путём разблокировки. Это **долг**, и он должен быть снят, а не «узаконен гейтом».

**Канонные варианты (нужно решение владельца — это архитектура):**

| Вариант | Что делать | Плюс | Минус |

### Бэкфилл не создаёт второй путь записи — подтверждение по коду (2026-11-05 09:30, запрос @TL)

| Что | Где |
|---|---|
| чтение командных строк | `_db.Partners` / `_db.Records` (`AsNoTracking`) |
| проверка идемпотентности | `_store.GetEventCountAsync(e.Id)` |
| **публикация события** | `_bus.PublishAsync(result.Event)` |

`UpsertAsync`/`IReadModelStore` в этих классах **отсутствуют** (проверено `git grep` по файлам). Значит исторические строки

**Почему это важно зафиксировать:** «бэкфилл льёт прямо в read-таблицу» был бы вторым способом формирования модели —
и тогда правило «read-модель = проекция событий» перестало бы быть инвариантом (два писателя, разная логика, расхождение
при первом изменении маппинга). Сейчас инвариант держится: **единственный писатель read-модели — проекция событий**.

**Порядок исполнения (подтверждаю):** `ALTER`/схема → флаг `DataMigration:Enabled=true` → перезапуск → числа (`13/13`, `4/4`)
→ **повторный** запуск не меняет числа.

### Сверка с исходниками библиотеки: два моих утверждения оказались неверными (2026-11-05 09:45)

Источник проверен **клоном публичного репозитория** `Ekstrem/DigiTFactory.Libraries` (HEAD `43b6689`), не по пересказу.

**`ReadRepository.Postgres/Extensions/ServiceCollectionExtensions.cs`:**

```csharp
AddReadStorePostgres<TBoundedContext, TReadModel, TDbContext>(
        IServiceCollection services, string connectionString,
        Action<PostgresReadStoreOptions> configureOptions = null)   // ← второй параметр = НАСТРОЙКИ, не маппинги
...
services.AddDbContext<TDbContext>(dbOptions =>
    dbOptions.UseNpgsql(connectionString, npgsql =>
        npgsql.MigrationsAssembly(typeof(TDbContext).Assembly.GetName().Name)));   // ← :41-42
```

**`Configuration/PostgresReadStoreOptions.cs`:** только `ConnectionString` и `SchemaName` (default `"ReadModel"`).

#### Исправление 1: `null` во втором аргументе **не** означает «маппинги выключены»
Это `Action<PostgresReadStoreOptions>` — **настройки** (строка подключения, имя схемы). К маппингам отношения не имеет.
Моё прежнее утверждение («`null`-конфигуратор = выключенная функциональность, библиотека читает маппинги») **неверно**:
маппингов не было потому, что **наш** `ReadDbContext` не объявлял `OnModelCreating` (`BE-068`), а не из-за `null`.

**Следствие:** критерий гейта, который я предлагал («`null` допустим только при `Entity<TModel>`»), опирался на неверную
посылку. Само требование «модель должна быть замаплена» остаётся верным, но проверять надо **маппинг**, а не аргумент —
что и делает `check_readstore_mapping`.

#### Исправление 2: `SchemaName` в read-store — **мёртвая настройка**
`SchemaName` объявлен в `PostgresReadStoreOptions`, но в `ReadRepository.Postgres` **не используется** (`HasDefaultSchema` есть
только в `EventStoreDbContext` — командная сторона — и в event bus). Значит «настроить схему через опции» **нельзя**:
таблицы уйдут в `public`, если сам контекст не вызовет `HasDefaultSchema`.

#### Отсюда — ловушка для `BE-072`, которой не было в моём списке
`MigrationsAssembly` задаётся **библиотекой** при её `AddDbContext<TDbContext>`. Если приложение добавит **свой**
`AddDbContext<ReadDbContext>` ниже по коду, оно **перекроет** библиотечную регистрацию — и `MigrationsAssembly` **потеряется**,
то есть `Migrate()` не увидит миграции, даже если они лежат в правильной сборке.

Проверено в `origin`: ручной `AddDbContext<ReadDbContext>` в `Program.cs` **удалён** (остался в `*.IntegrationTests/*HostSmokeTest.cs`
— это тестовые хосты, не прод). То есть сейчас условие выполнено, но **это надо удержать**: гейт `check_eventstore_registration`
проверяет типизированную регистрацию только для `EventStoreDbContext`; для `ReadDbContext` такой проверки **нет**.

**Дополнительный критерий `BE-072`:** ручной `AddDbContext<ReadDbContext>` в `*.Api/Program.cs` → **0** (иначе
`MigrationsAssembly` теряется молча, а `Migrate()` «ничего не делает» без ошибки).

### ИСПРАВЛЕНИЕ к «DDL неполон»: колонок **20**, а не 24; «10 отсутствующих» — ошибка подсчёта (2026-11-05 09:50)

Мой предыдущий блок утверждал «24 поля модели против 14 колонок, нет 10». Это **неверно**, и ошибка моя.

**Факт по исходнику `Journal.InternalContracts/JournalReadModel.cs`:**

| Класс | Свойств | Что это |
|---|---|---|
| `JournalReadModel` | **20** | реальные поля read-модели → **20 колонок** |
| `OrgasmsReadModel` | 4 (`Participant`, `Count`, `Types`, `Rating`) | **отдельный класс** в том же файле, сериализуется в **одну** колонку `"Orgasms" text` через конвертер `Orgasms()` |

Мой парсер собрал свойства **обоих** классов в один список (24 = 20 + 4) и объявил 4 из них «отсутствующими колонками»:
`Count`, `Participant`, `Rating`, `Types`. Колонок для них быть **не должно** — они живут **внутри** `Orgasms`.

**Итог по схеме после `ALTER` ×6 (`ContraceptiveCount`, `Garmin`, `GarminId`, `CreatedAt`, `UpdatedAt`, `Deleted`):**
`CREATE` 14 + `ALTER` 6 = **20 колонок = 20 полей** — **паритет точный**. Добавлять ещё 4 «колонки» **не нужно и вредно**:
их нет как полей, и `check_readstore_ddl` на них сейчас даст **ложный красный**.

**Дефект гейта (нужен @DO):** `check_readstore_ddl` повторяет мою ошибку — он берёт свойства **всех** классов файла модели,
а не только `TModel` из `Add*StorePostgres<…, TModel, TContext>`. Следствие: 4 ложных «missing», и после `ALTER` ×6 гейт
**останется красным на корректной схеме** — то есть попросит либо мусорные колонки, либо отключение.

**Правило (моё, как владельца модели):** читать модель надо **по типу из регистрации** и **не разворачивать вложенные типы**:
список колонок = свойства `TModel`; свойства других классов — часть значения колонки, а не отдельные колонки.

**Почему ошибка не поймалась сразу:** я считал по регулярке по всему файлу и получил «24»; все три наблюдателя (@TL, @TE, @DO)
сверили **свои** числа с моим, и совпадение закрепило ошибку. Совпали методы, а не факты.

### Командные EF-таблицы **больше не пишутся** — приёмка «read == count(*) источника» должна сравнивать не с ними (2026-11-05 10:20)

Проверено по коду `origin`:

| Что | Факт |
|---|---|
`PartnerCommandRepository.SaveAsync` | **только** `_bus.PublishAsync(result.Event)` — записи в EF-таблицу `partners` нет |
`JournalCommandRepository` | комментарий в коде: «E1: command-path пишет **событием**, а не `SaveChangesAsync` — store заполняется…»; вызовов `SaveChangesAsync` в `BC-Journal/src` **нет** |
`JournalDataMigration` / `PartnerDataMigration` | читают **историческую** EF-таблицу (`_db.Records` / `_db.Partners`) как источник для одноразового переноса |

**Следствие 1 — объяснение «противоречия» @TE (dev, `partners` 0 / `partners_read` 0 после создания партнёра):**
`partners = 0` — **не дефект**, а ожидаемое поведение E1: командная EF-таблица больше не наполняется, источник истины — event store.
`partners_read = 0` — дефект, но не «проекция асинхронная»: запись в read-модель идёт **после** `SaveEventAsync`, а таблиц event store
(`Commands.DomainEvents`) в контуре нет — значит **падает запись события**, а проекция просто не запускается. Три гипотезы @TE
сводятся к одной причине — **схема event store не провижинится**.

**Следствие 2 — дефект критерия приёмки:** сравнение «элементов read-эндпоинта == `count(*)` командной таблицы» верно **только
для исторических строк** (пока таблица была источником) и **неверно для новых данных**: новая запись/партнёр появляются в event store
и read-модели, но **не** в `records`/`partners`. Такой критерий даст «read больше источника» = ложное нарушение на корректном поведении.

**Правильный источник для сравнения — сам read-путь и событийное хранилище:**

| Что проверяем | С чем сравнивать |
|---|---|
| бэкфилл истории | `count(*)` read-модели **против числа агрегатов в источнике миграции** (`records`/`partners` на момент миграции) — это **одноразовая** сверка |
| проекция «живёт» | **новый** объект, созданный командой, появляется в read-модели (поведенческая проверка) — а не совпадение счётчиков |
| идемпотентность | повторный запуск бэкфилла **не меняет** число событий в event store (а не число строк read-модели) |

**Требование:** в приёмке (`accept_read_path.py`) источник сверки должен быть **явно назван и помечен как «исторический»**;
для новых данных обязателен поведенческий шаг «создал → увидел». Иначе критерий закрепляет мир, которого больше нет.
