# Read paths — откуда берутся данные экрана (спецификация, не решение)

> **Границы:** решений этот файл не вводит. Источники истины: **ADR-004** (Read Store + MV), **ADR-025** (контракты,
> `api-index.yaml`), **ADR-028** (тесты). Здесь только то, чего в них нет: **какой экран какие данные читает, насколько
> они свежие и что видит пользователь, когда чтение не удалось.** Правило: добавил экран или MV — допиши строку сюда
> **в том же коммите**, что и код.

## 1. Правила (обязательные)

1. **Молчаливый `catch` запрещён.** Ошибка чтения обязана быть отличима от «данных нет»: `null`/`[]` на месте ошибки
   показывают пользователю пустоту и убеждают его, что данных не существует. Разрешено: явное состояние «не удалось»
   (неблокирующий бейдж/тост) либо отказ от предзаполнения с сохранением формы (но не тихий пустой список).
2. **Смешанная свежесть называется явно.** Если на одном экране часть данных из локального кэша (`IndexedDB`), а часть —
   из MV по HTTP, у каждого поля должно быть сказано, что оно кэшированное: иначе пользователь считает всё «свежим».
3. **Список MV на экране = контракт.** Появился новый MV, используемый экраном, — строка в §2 обновляется тем же
   коммитом; иначе шаг тихо остаётся без данных (и никто не заметит, потому что §1 п.1 нарушен).
4. **Экран не читает чужие БД.** Только через API своего BC или MV-эндпоинт; локальный кэш — не источник истины,
   а ускоритель (при конфликте побеждает сервер, но факт конфликта должен быть виден).

## 2. Реестр экранов

| Экран / действие | Данные | Источник | Свежесть | Если чтение упало |
|---|---|---|---|---|
| **Визард записи** (открытие «+») | партнёры | `Api.partners.list()` → `Partners.List` (обёртка `DB.getAllPartners()`) | live | **сейчас: хуже тихого** — у `DB.getAllPartners()` нет `.catch`, поэтому `Promise.all` отвергается, а у `reopenWizard`/`openWizard` нет обработчика → **визард не открывается вовсе**, ошибка не показана (`app.js:584,593,599`) |
| | `recent` (lastPartner/lastPlace/lastPositions/lastTags/lastContraceptives/lastFantasies) | `Api.journal.recent()` — MV | live | **сейчас: тихо `null`** → предзаполнение исчезает (`app.js:585`) |
| | `places` | `Api.journal.places()` — MV | live | **сейчас: тихо `[]`** → шаг места пуст (`app.js:586`) |
| | каталог (виды, оргазмы, контрацепция) | `Api.catalog.list()` → `Catalog.List` (обёртка `DB.getAllCatalog()`) | live | **сейчас: тихо `[]`** (`app.js:587`) |
| Журнал (лента) | записи | `Api.journal.list()` | live | показать ошибку, не пустую ленту |
| Партнёры (вкладка) | список | `Api.partners.list()` (MV/таблица) | live | показать ошибку |
| Профиль «я» | свой профиль | `Api.clients.me()` | live | показать ошибку |

**Почему это важно именно сейчас:** решение @PO (`chat/fe.md`, 2026-11-03 19:00) — «предзагружаем **все данные MV одним
пакетом**» — на деле даёт **2 кэш-чтения + 2 HTTP-MV** (`app.js:582-591`), то есть «все данные» не из одного источника.
И все четыре `.catch` глушат ошибку. Итог: при недоступном API визард открывается **с пустыми предзаполнениями**, и это
неотличимо от «у пользователя ещё нет истории» — при том что §1 п.1 запрещает ровно это.


> **Уточнение 2026-11-04 (важное, чтобы §2 не врал):** `DB.getAllPartners()` / `DB.getAllCatalog()` из `app.js` — это
> **обёртки над API**, а не кэш: `repository.js:130,147` переопределяют их на `Api.partners.list()` / `Api.catalog.list()`.
> Кэш-версии живут в `db.js:123,128`, и в визарде они **не используются**. Значит все четыре чтения визарда — **live**,
> и «смешанной свежести» в нём нет; п.2 §1 остаётся правилом для будущих экранов, но не описывает текущий.

## 3. Что требуется от @FE (по §1)

1. Заменить глушение в `loadWizardData` на два состояния на шаг: `data` / `failed`; при `failed` — не подставлять
   пустоту молча (бейдж «не удалось загрузить», предзаполнение считается отсутствующим **и это видно**).
2. Партнёры и каталог — пометить как кэш (например, при `lastSync` старше N часов показывать «данные могли устареть»).
3. Открытие визарда без сети — отдельный сценарий в `front-e2e` (@TE): ожидаемое поведение из §1, а не «пусто и тихо».

## 4. Что требуется от @AR (мной, чтобы правило работало)

- §2 пополняется при каждом новом MV-эндпоинте, который читает экран; ссылка на `operationId` из `api-index.yaml`.
- При добавлении MV — проверить, что контракт (`codes`, `request`) в индексе обновлён: экран, читающий MV, зависит
  от кодов ответа не меньше, чем от полей.

## 5. Какое правило чем проверяется (чтобы §1 не выглядел закрытым целиком)

| Правило §1 | Проверка | Состояние |
|---|---|---|
| **п.1** «молчаливый `catch` запрещён» | `9-tests/RnD/front-e2e/tests/wizard-offline.spec.js` (**TE-054**): (а) форма сохраняется — визард **открывается**; (б) ошибка **видна** в `#view-wizard`/`#toast`; (в) **нет ложной подстановки** (`.partner-card.selected` = 0) | тест написан, включается внешним признаком `XDIARY_READPATH_OFFLINE=1`; до фикса @FE — `skip` с причиной `pending:FE-READPATH`; **негативный контроль обязателен**: на сборке **без** фикса п.1 падает |
| **п.2** «смешанная свежесть названа» | **не покрыто** — метка «данные могли устареть» для кэша (партнёры/каталог) не проверяется ни одним тестом | **открытый пункт** @FE: либо бейдж, либо явная строка в §2 «свежесть не показывается» |
| **п.3** «список MV на экране = контракт» | машинно возможно: все `operationId` из §2 обязаны существовать в `api-index.yaml`, и наоборот — MV, читаемый экраном, обязан быть в §2 | **предложено** @DO как расширение `check_api_index.py` |
| **п.4** «экран не читает чужие БД» | вне E2E (архитектурное ограничение, видно в коде) | проверяется ревью @AR при добавлении экрана |

**Почему это отдельный раздел:** TE-054 закрывает **п.1** и только его. Если не записать это явно, через неделю будет казаться,
что «сценарий без сети» доказывает весь §1, — а п.2 (кэш выглядит как live) и п.3 (забыли MV в списке) останутся незамеченными
ровно так же, как «31/31 в папках сервисов» скрывало несобирающиеся проекты.
