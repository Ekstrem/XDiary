- **Дата:** 2026-11-14
- **Статус:** проект решения (до реализации E1/E5)
- **Связано:** `edm-debt-plan.md` (E1, E5, E6), ADR-026 (внутренний контур), ADR-027 (immutable артефакты), `BC-Journal/02` §2.7, `BC-Partners/02` §11

**Вывод:** проблема не в отсутствии библиотек, а в **обходе** их: store и bus зарегистрированы, но состояние пишется
мимо store, а события не публикуются. Поэтому E1 — это не «добавить EDM», а **переключить путь записи** на него.

### 1.1. Открытые проверки — нужны замером, а не чтением кода (@DO)

| Что проверить | Зачем | Как |
|---|---|---|
| Существует ли схема event store в БД Journal и растёт ли она при команде | подтвердить, что `AddEventStorePostgres` не только зарегистрирован, но и создал таблицы | `dev`: команда → `select count(*) from <events-table>` до/после; контур и дата в отчёте |
| Доставляет ли `AddEventBusInMemory` хоть что-то | понять, есть ли внутрипроцессные подписчики (`INotifier`) | лог регистрации подписчиков на старте |
| Что реально делает `IRepository.SaveAsync` фреймворка при нашем override | не двойная ли запись (EF + store) | прочитать реализацию пакета либо трассировать запросы к БД |

Эти три пункта — **не мнение**: до них любые утверждения «store пишет/не пишет» — гипотеза. Ниже решение от них
не зависит (оно про контракт доставки), но объём работ E1 — зависит.

## 2. Решение

**Транспорт = transactional outbox + HTTP-диспетчер, доставка at-least-once.** Шина фреймворка (`InMemory`)
для межсервисной доставки **не используется** и не должна: у неё нет ни durability, ни адресации между процессами.

| Слой | Что делаем | Почему так |
|---|---|---|
| Запись | **Outbox-таблица в БД того же сервиса**, запись события **в одной транзакции** с изменением состояния | иначе событие врёт: состояние сохранилось, факт потерялся (или наоборот) |
| Доставка | `IHostedService`-диспетчер читает outbox по порядку и **POST-ит** событие в `/internal/events` получателя; ретраи с backoff, `attempts`, `next_attempt_at` | не тянем брокер ради двух пользователей; HTTP уже есть и мониторится |
| Приём | эндпоинт `POST /internal/events`, **идемпотентный**: таблица `processed_events(event_id PK)`; upsert проекции в той же транзакции | at-least-once ≠ exactly-once: дубли будут, обязаны быть безвредными |
| Порядок | гарантируется **внутри агрегата** (outbox пишется в порядке версий, диспетчер — FIFO); **между агрегатами порядок не гарантируется** | глобальный порядок стоит дорого и не нужен для наших проекций |
| Мёртвые | после N попыток событие уходит в `outbox_dead` + `::error::` в лог и карточку | «тихо потерялось» — худший исход |
| Replay | проекции пересобираются из `outbox` (retention ≥ 90 дней) или из event store, когда он появится | retention — часть решения, а не «потом» |

### 2.1. Конверт события (обязательные поля)

```jsonc
{
  "eventId": "uuid",          // PK идемпотентности у получателя
  "type": "Partner.Removed",  // стабильное имя, не имя класса
  "schemaVersion": 1,         // получатель обязан игнорировать НЕИЗВЕСТНЫЕ поля, не падать
  "aggregateId": "uuid",
  "version": 7,               // версия агрегата в момент факта (для порядка и для «устаревшее — пропустить»)
  "clientId": "uuid",         // tenant-скоуп: без него нельзя безопасно проецировать (E6)
  "occurredAt": "2026-11-14T06:00:00Z",
  "correlationToken": "uuid", // сквозная трассировка: команда → событие → проекция
  "payload": { }              // только то, что нужно потребителям; не весь агрегат
}
```

**Правило payload:** «минимум для получателя, максимум для трассировки». Класть весь агрегат нельзя — иначе событие
становится вторым источником правды и расходится с моделью (класс, который мы лечим).

### 2.2. Идемпотентность и порядок у получателя

1. `processed_events(event_id)` — если `eventId` уже есть, вернуть `200` и **ничего** не менять.
2. Проекция обновляется **upsert-ом по `(aggregateId)`**, с условием `version > current_version`; устаревшее событие
   не откатывает состояние назад (иначе гонка двух доставок «оживит» удалённого партнёра).
3. `Partner.Removed` — **выставляет флаг**, строку не удаляет (`BC-Partners/02` §11, `HistoryStaysResolvable`).

## 3. Кто что публикует и кто потребляет (инвентарь)

| Публикует | События | Потребитель | Что делает |
|---|---|---|---|
| **Partners** | `Partner.Registered`, `Partner.Renamed`, `Partner.ProfileUpdated`, `Partner.Removed` | **Journal** (справочник §2.7) | upsert `partners_directory` (включая `Deleted`) |
| **Journal** | `Record.Completed`, `Record.Deleted` | **Analytics** | тренды/сводки (заменяет `HttpJournalEventPublisher`) |
| **DailyMetrics** | `Stress.Recorded`, `Sleep.Recorded` | **Analytics** | те же сводки |
| **SomaticSeries** | `Series.Updated` | **Analytics**, **DailyMetrics** | корреляции/агрегаты |
| Privacy / Catalog / Portability | нет потребителей в MVP | — | публиковать **не нужно** (не создаём события «на будущее») |

**Правило:** событие существует только если у него есть **названный потребитель**. Иначе это не событие, а лог.

## 4. Event Sourcing — что мы делаем и чего не делаем (важно и честно)

| Мы делаем | Мы **не** делаем в этой итерации |
|---|---|
| пишем **все** изменения агрегата как факты в event store/outbox (даже если потребитель один) | не восстанавливаем агрегат из событий (replay командной стороны) |
| проекции — производные, пересобираемые | не убираем command-DB: она остаётся источником истины для агрегата |
| `version` в событии позволяет позже включить replay | не обещаем «полный ES» — это отдельное решение и отдельная цена |

**Почему пишем события сразу, хотя replay не включаем:** включить запись позже = потерять историю за прошедший
период (мы уже проходили это с легаси-строками журнала: истории нет, восстановить нельзя). Цена записи — одна
таблица и один insert в транзакции; цена её отсутствия — необратимая дыра.

## 5. Отказные режимы (что обязано произойти)

| Отказ | Поведение | Проверка |
|---|---|---|
| получатель лежит | outbox растёт, ретраи с backoff, метрика `outbox_lag` + алерт при > 5 мин | тест: остановить приёмник, изменить состояние, поднять приёмник → проекция догнала |
| дубль доставки | `processed_events` отсекает; проекция не меняется | тест: два одинаковых POST → 200 оба раза, состояние одно |
| событие «из прошлого» | `version`-guard: проекция не откатывается | тест: применить `version=5` после `7` → без изменений |
| несовместимая схема | `schemaVersion` + правило «игнорируй неизвестные поля»; ломающее изменение = новое `type` | тест: событие с лишним полем не валит получателя |
| отравленное событие | после N попыток → `outbox_dead` + ошибка в лог, ручной разбор | тест: событие с битым payload → уходит в dead, остальные идут |
| потеря БД сервиса | outbox в той же БД, что состояние → не бывает «состояние без факта» | архитектурно: одна транзакция |

## 6. Что это меняет в плане EDM

| Пакет | Изменение |
|---|---|
| **E1** | добавляется **outbox + диспетчер + эндпоинт приёма**: без них «пилот ES+Bus» даёт нулевую межсервисную ценность |
| **E5** | частично **поглощается E1** (outbox строится сразу) — E5 остаётся про **ретраи и dead-letter** |
| **E6** | `clientId` в конверте — обязательное поле с первого дня, иначе tenant-скоуп Analytics придётся добавлять миграцией событий |
| **E3** | `IBusAdapter`/`INotifier` удаляются, но **после** того, как ни один BC не публикует через них |

**Минимальный вертикальный срез (первым):** `Partner.Removed` → outbox → диспетчер → `POST /internal/partners/events`
→ `partners_directory.deletedAt` → `Journal.Get` отдаёт имя. Один путь, полностью наблюдаемый; после него —
раскатка по остальным событиям.

## 7. Альтернативы и почему не они

| Альтернатива | Почему нет |
|---|---|
| Фреймворковая `EventBus.InMemory` | внутрипроцессная: между контейнерами не доставляет, durability нет |
| Брокер (RabbitMQ/Kafka) | +1 инфраструктурная сущность, +эксплуатация, +бэкапы ради 2 пользователей; наши объёмы — единицы событий в час |
| Прямой HTTP-пуш из команды (как сейчас в Journal→Analytics) | дубль при ретрае, потеря при падении приёмника, нет replay — это и есть E5-долг |
| Отдельная БД событий (event store Postgres из фреймворка) | правильный следующий шаг, но он не отменяет outbox-диспетчер; включаем, когда понадобится replay агрегата, а не проекции |
