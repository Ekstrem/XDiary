# Aggregate Design Canvas: Partner (Партнёр)

> Bounded Context: Партнёры (Partners)
> Агрегат: Partner
> Профиль: Single-writer

## 1. Name (Имя)
- **Имя:** Partner (Партнёр).
- **Создаётся когда:** пользователь регистрирует партнёра.
- **Завершается когда:** удаление партнёра.

## 2. Description (Описание)
Агрегат Partner хранит профиль партнёра. Поставляет выбор партнёра и его пол в Журнал.

**2.1. Идентификатор и корень (DF):**
- Составной ключ `<guid, long>`: `guid` идентифицирует агрегат, `long` — версия. Даёт фреймворк, **доменным полем не является**.
- Корень: `IPartnerRoot : IValueObject` — содержит **`Name`** (единственный «идентифицирующий» признак партнёра).

**2.2. Состояние (`AnemicModel`) — атрибуты корня агрегата** (сверено с кодом `6-msa/BC-Partners`, 2026-11-10):

| Атрибут | Тип | Кард. | Обяз. | Задаётся | Инвариант |
|---|---|---|---|---|---|
| `root.name` | string | 1 | да | `Register(name, clientId)` / `Rename(name)` | `NameRequiredValidator` (`NameRequired`) |
| `gender` | string (`male` \| `female`) | 1 | да (валидируется при `UpdateProfile`) | `UpdateProfile(photo, gender, …)` | `GenderEnumValidator` — **строго словарь** `male`/`female` |
| `photo` | string (dataURL, 512px) | 0..1 (пустая строка = нет) | нет | `UpdateProfile` | — |
| `notes` | string | 0..1 | нет | `UpdateProfile` | — |
| `clientId` | Guid? | 0..1 | нет | `Register` (владелец), `LinkClient` / `UnlinkClient` | связь с аккаунтом клиента, **опционален** (партнёр может стать клиентом, ADR-024) |

**Технические поля** (не доменные, даёт фреймворк): `Id`, `Version`, `CorrelationToken`, `CommandName`, `SubjectName`.

**2.3. Что НЕ хранится (и почему):**
- **Профиль «я»** (`displayName`/`gender` клиента) — в `Client`; в `Partner` не проецируется (ADR-024: одно имя не живёт в двух местах);
- **История актов с партнёром** — в `Record.partners[]` (ссылка по `id`), не в партнёре;
- **Мягкое удаление / `state`:** **нет** — `Remove()` в агрегате не меняет состояние (`Success(Clone())`), удаление физическое на уровне хранения. Поэтому поля `deletedAt`/`state` в модели отсутствуют — и это надо помнить при E1: событие `PartnerRemoved` фиксирует факт, а «удалённость» в модели не выражается.

**2.4. Известное расхождение (найдено при сверке 2026-11-10):** `GenderEnumValidator` в этом BC сравнивает **без нормализации**
(`gender is "male" or "female"`), а канон для профиля клиента (`ADR-024 §3`) требует `Trim().ToLowerInvariant()` → словарь.
**Закрыто:** @BE привёл `Partners` к канону (`a4240279`) — `Normalize` + словарь; «один справочник, два поведения» больше нет.

**2.5. Удаление — было no-op (блокировало E1); решение принято — см. §11.** `Aggregate.Remove() => Success(Clone())`
(`BC-Partners/Aggregate.cs`): состояние не меняется, в модели **нет** `deletedAt`/`state`, а событие `PartnerRemoved`
в канвасе задокументировано. Последствие для E1 (`BE-055`): «удалённость» **не восстановить реплеем** — реплей из событий
даст «партнёр жив», а read-model при этом его не показывает. Состояние и события расходятся, то есть событийная модель
будет **неполной** ровно на удалении.

**Требование:** решить **до** начала E1 и записать в карточку, а не по ходу:

| Вариант | Что делаем | Плюсы / минусы |
|---|---|---|
| **(а) мягкое удаление — предпочтительно** | добавить `deletedAt` (или `state: Active\|Deleted`) и сделать `Remove()` реальным; read-model фильтрует `deletedAt == null` | состояние и событие согласованы, история воспроизводима реплеем; **но** нужно отдельное действие «удалить навсегда» для требования приватности (полная очистка данных) |
| (б) физическое удаление | не эмитить `PartnerRemoved`, а фиксировать `PartnerHardDeleted` + компенсация в read-model | меньше полей; **но** состояние после удаления не восстанавливается, и «компенсация» = скрытая логика вне агрегата |

> Для EDM предпочтителен **(а)**: событийная модель требует, чтобы любое изменение состояния выражалось событием,
> а не отсутствием записи. Окончательный выбор — за @BE при E1, фиксируется в `BE-055`/карточке партнёров.

## 11. Удаление партнёра — модель (решение @AR 2026-11-13, вариант (а) принят)

**Решение: мягкое удаление. «Удалён» — это состояние агрегата, а не отсутствие строки.**

| # | Инвариант | Что значит проверяемо |
|---|---|---|
| **DeletedAtSet** | `Remove()` **ставит** `deletedAt` (`state: Deleted`) и **публикует** `PartnerRemoved` | повторять no-op нельзя: состояние и событие обязаны совпадать |
| **RemoveIdempotent** | повторный `Remove()` на удалённом → **успех**, **без второго** `PartnerRemoved` | идемпотентность команды, событие — только на изменение |
| **DeletedNotVisible** | `GET /partners` не содержит удалённого; `GET /partners/{id}` → **404** (или 403 по принятой конвенции) | «удалён» = «для клиента его нет», а не «помечен, но виден» |
| **HistoryStaysResolvable** | записи журнала, ссылающиеся на удалённого партнёра, **продолжают показывать его имя** | это и есть **настоящая причина** мягкого удаления, см. ниже |
| **PurgeOnlyIfUnreferenced** | физическая чистка (`purge`) допустима, только если на партнёра **не ссылается ни одна запись** журнала (или после обезличивания) | иначе история осиротеет |

**Почему именно мягкое, а не физическое (это не «деталь реализации»):**
журнал ссылается на партнёра **по `id`**, а имя/пол в записи **не хранятся** (`BC-Journal/02` §2.4 — чтобы одно имя
не жило в двух местах). Значит физическое удаление партнёра **осиротило бы историю**: запись есть, участник есть,
а имени нет — и восстановить его неоткуда. Мягкое удаление сохраняет строку (и имя) для чтения истории, при этом
убирает партнёра из выбора и из списка. **Инвариант `HistoryStaysResolvable` важнее самого факта удаления:**
если проекция начнёт фильтровать удалённых **и в резолве имени**, история «потеряет» участников — это регресс,
который пользователь заметит через год, а тесты — никогда (если не написать их явно).

**Следствие для read-model:** в `BC-Journal` проекция участников хранит **всех** партнёров, включая `Deleted`
(флаг нужен для выбора, а не для отображения истории). `GET /partners` фильтрует по флагу; резолв имени
в истории — **нет**.

**Где именно живёт фильтр (типичная ошибка):** фильтр — в **query/read-model** (ListPartnersQuery), а **не** в общем
репозитории. Если отфильтровать в репозитории, который читает проекция журнала, история снова «потеряет» имя —
фильтр в неверном слое молча нарушает HistoryStaysResolvable. Проекция обрабатывает PartnerRemoved
как **установку флага**, а не как удаление строки.

**Факт, который меняет картину (проверено в `origin` 2026-11-13): журнал хранит только `id` партнёров, а не имена.**
`JournalReadModel.Partners` — `IReadOnlyList<string>` (идентификаторы), имена в записи **не хранятся** (§2.4 `BC-Journal/02`).
Имена резолвит **чтение**: фронт грузит `GET /partners` и сопоставляет по `id`. Значит после включения фильтра
(мягкое удаление) **старое имя удалённого партнёра взять неоткуда** — `GET /partners` его не отдаёт,
`GET /partners/{id}` → 404. То есть `HistoryStaysResolvable` **пока не обеспечен механически**: он записан как инвариант,
но в текущей архитектуре его нечем выполнить.

**Как это закрыть (по возрастанию стоимости):**

| Вариант | Что | Оценка |
|---|---|---|
| **(а) сейчас, дешёвый и честный** | фронт при неизвестном `id` показывает **«удалённый партнёр»** вместо пустоты | 0 API-изменений; история не врёт, но имя теряется визуально |
| **(б) цель, EDM-путь** | в `BC-Journal` появляется **проекция-справочник партнёров**, построенная из событий (`PartnerRegistered`/`Renamed`/`Removed` → флаг), и история резолвит имя из неё | не «второй источник правды»: справочник **производный от потока**, а не поле в записи; не зависит от видимости в `Partners` API |
| (в) внутренний lookup | `/internal/partners/{id}` отдаёт имя даже для `Deleted`, журнал/фронт зовут его при рендере | работает, но добавляет сетевой вызов на каждое отображение истории — хуже для P95 |

**Решение:** (а) — **сейчас** (чтобы не врать в UI), (б) — **цель вместе с E1-проекциями** (там же, где MV журнала);
(в) не берём.

**Условие для (а), без которого fallback врёт (@FE, 0.88):** показывать «удалённый партнёр» **только когда список
партнёров успешно загружен**. Если применить fallback к состоянию «ошибка/загрузка», сетевая ошибка превратит
**всех** участников в «удалённых» — пользователь прочитает это как потерю данных, а искать будем в Partners.
Признак «удалён» = id отсутствует в **успешно полученном** списке.

**Что НЕ меняется:** контракты `/api/v1` (пути, коды, тела) — `DELETE` не появляется, удаление остаётся
`POST /partners/{id}/remove`; `PartnerRemoved` уже существует и не переименовывается.

## 10. Контракт создания партнёра — решение 2026-11-11 (@AR)

**Факт:** `POST /api/v1/partners` принимает **только `name`** (`RegisterPartnerCommand(name, clientId)`),
а `gender` задаётся **отдельным шагом** — `POST /api/v1/partners/{id}/profile` (`UpdatePartnerProfileCommand`).
Поле `gender`, переданное в создание, сейчас **молча игнорируется** (@DO на проде: `{"name":"П","gender":"Male"}` → `"gender":""`).

**Решение: вариант (а) — двухшаговый контракт остаётся, но «молча проглотить» запрещено.**
| Что | Как |
|---|---|
| Создание | только `name` (+ `clientId` из токена); `gender` в создании — **ошибка 400**, а не тишина |
| Профиль | `gender` (канон `male`/`female`, нормализация) + `photo`, `notes` — здесь и только здесь |
| Общее правило | **неизвестные поля в командах → 400** (`UnmappedMemberHandling.Disallow`), а не игнор |

**Почему так, а не расширять создание (вариант б):**
1. **Молчаливый игнор — худший из трёх ответов:** клиент получает `200`, считает, что сохранил, и узнаёт правду
   только когда увидит пустой пол. Это тот же класс, что «зелёный тест при неверном поведении».
2. **Двухшаговый контракт уже работает и проверен** (канон на `/profile` — 6/6 у @TE): расширение создания
   создаст **два места**, где задаётся пол, и они разойдутся (ровно то, что мы чинили в `Client`/`Partners`).
3. **Строгость ловит опечатки класса «`gender` vs `Gender`»** — на приватном приложении с одним клиентом
   forward-compatibility не нужна, а цена опечатки сегодня уже видна.

**Область действия правила:** все command-DTO (`POST`) в `6-msa`. Не «только партнёры»: иначе следующий эндпоинт
снова проглотит поле, и мы вернёмся к этому же разговору.

**Что нужно от @BE:** включить `UnmappedMemberHandling.Disallow` для command-моделей + тест «лишнее поле → 400»
на `POST /partners` (и на одном любом другом POST для класса). **@TE:** ассерт `{"name":"П","gender":"Male"}` → **400**.
