### 12. do-deploy без версионирования образов — ✅ **закрыто по тегам 2026-11-07, остался digest** (`DO-113`)
- **Суть (было):** деплой (`deploy.yml`) без версий образов (`latest`/пересборка) — откат к конкретной версии невозможен.
- **Факт 2026-11-07 (проверено @AR по коду):** `git grep ':latest' -- 7-deploy .github` → **0 вхождений**; теги берутся из `7-deploy/images.lock` через `tag_of` (`update.sh` — 3 вхождения, `recreate-service.sh` — 2), формат тега — `single-<sha сборки>` + провенанс `commit=<sha>`. **Откат «на тег» теперь возможен.**
- **Что осталось (и это уже другая карточка):** в lock **нет `digest=`**, выкатки по `@sha256` нет ⇒ неизменяемой идентичности образа нет: пересборка того же коммита даёт другой образ под тем же тегом. Это `ADR-027` (частично) и `DO-113`.
- **Живой пример 2026-11-07 12:28 (первый за неделю):** `lock` пиннит `partners single-ac3962d` (`commit=ac3962d`, коммит `11:19:58`) — **до** фикса `TE-102` (`31fd2af6`, `11:37:11`), а в реестре уже есть `single-6d2d6d0` (`6d2d6d0`, `11:37`) **с фиксом**. То есть «деплой зелёный, а поведение старое» — не гипотеза: **блокер был в lock, а не в сборке**, и снимался **одной строкой**. Проверка: `git merge-base --is-ancestor <fix> <commit-из-lock>`.
  **Ловушка времени, из-за которой это дважды выглядело как «образа нет»:** GHCR отдаёт `created` в **UTC**, и `created 08:38:16Z` — это **11:38:16 локального** (+03:00), то есть **позже** фикса `11:37:11`, а не раньше. ⇒ **норма:** любое время в квитанции/замере — **с зоной** (`Z` или `+03:00`); сравнивать локальную метку с UTC-полем нельзя, вывод переворачивается.
- **Риск:** низкий (остаточный — подмена тега в реестре, ловится только провенансом).
- **Приоритет:** P2 → **P3** (остаток закрывается в `DO-113`).
- **Оценка:** ~~теги образов + версионирование~~ → сделано; остаток — `digest=` и выкатка по нему (`DO-113`).

### 17. Тестовый OTP принимается вне dev **без срока годности** — P1-риск, не дефект кода (2026-11-07)- **Что происходит (проверено @AR по коду):** `TestOtpPolicy.Resolve` (`BC-Client/src/Client.Application/TestOtpPolicy.cs:5-12`) возвращает фиксированный код, если `Clients:AllowTestOtpOutsideDev=true`; в `RegisterClientHandler` (`Commands/ClientHandlers.cs:23`) при этом пишется **один `LogWarning`** на старте («Включён тестовый OTP на проде — временная мера»). То есть принятие кода `000000` вне dev **не отклоняется кодом**, а только логируется.
- **Смягчает:** в git флаг ставят **только** вручную (`7-deploy/test-otp-toggle.sh`, с `--confirm` и `--reason`); в `appsettings*.json`, `deploy.sh` и `.github` его **нет** (проверено: `git grep AllowTestOtpOutsideDev` → 5 файлов, из них сеттер один — скрипт; остальные — код, тесты и ранбук). Прод-`.env` вне git (@DO).
- **Не смягчает:** гарантия держится **на процессе**, а не на коде — одна строка в прод-окружении включает приём фиксированного кода **для любого номера**, и срок действия нигде не задан. «Временная мера» без даты — это постоянная мера.
- **Почему не предлагаю fail-fast сразу:** @BE прав — жёсткий отказ снимет `DO-046` (временный прод-OTP). Значит нужен вариант, который **сохраняет** `DO-046`, но делает его временным по конструкции.
- **Варианты (решение — @EX/@TL, не моё):** (1) **граница деплоя** — шаг в `deploy-prod`, который `grep`-ом по прод-окружению падает, если флаг присутствует (включение становится явным и видимым, код не меняется); (2) **срок в коде** — `Clients:TestOtpUntil=<ISO-дата>`, после неё `Resolve` возвращает `null` (fail-fast только **после** срока: `DO-046` работает до даты, потом сам закрывается); (3) минимальное — поднять лог до `Critical` и добавить счётчик принятых тестовых кодов, чтобы мера была видна в метриках, а не только в логе старта.
- **Вопрос, на который нужен ответ владельца:** **до какой даты** действует `DO-046`? Уточнён 2026-11-10 после чтения скрипта: срок **уже назван в процедуре** — `test-otp-toggle.sh` печатает «снять сразу после входа владельца, **максимум 60 минут**». Значит вопрос не «какая дата», а: **подтверждаете окно 60 минут** (и «снять сразу после входа», а не «через час»), или нужен другой срок/событие?
- **Уточнение 2026-11-10 (@AR, по коду `origin`) — три факта, которые меняют чтение пункта:**
  1. **срок у выпускаемых кодов есть:** `Client.Domain/Implementation/Aggregate.cs:26` `OtpTtlMinutes = 5`; TTL ставится при регистрации (`:33`) и переотправке (`:57`); `VerifyOtp:39` отклоняет просроченный («Код истёк»). То есть «без срока» относится **к флагу тестового OTP**, а не к коду;
  2. **остаточная дыра — `NULL`:** проверка `:39` условная (`OtpExpiresAt is DateTime exp && …`), поэтому строка с **пустым** `otpExpiresAt` принимается **бессрочно** (колонка nullable — `Migrations/20261108120000_AddOtpSecurity.cs`). Это не «нет TTL», а «нет различения NULL и просрочено»;
  3. **есть ещё одна dev-уступка, и она закрыта:** `Otp:Channel=log` вне `Development` → `OtpChannelGuard.cs:7-8` бросает `InvalidOperationException` (тест `OtpChannelGuardTests`). Флаг `Clients:AllowTestOtpOutsideDev` **такой проверки не имеет**.
  4. **срок задан в процедуре, но не в коде, и срок этот — 60 минут:** `7-deploy/test-otp-toggle.sh` (origin, 203 строки) при включении печатает «снять сразу после входа владельца, **максимум 60 минут**», а сам `on` требует `--reason` **и** `--confirm`, делает бэкап `.env`, трогает только `xdiary-client` и **сам откатывает** флаг, если образ его проигнорировал (`:167-175`). То есть риск «включили и забыли» закрыт **не кодом, а процедурой** с явным следом.
  5. **«дрейф таймера» оказался неверным комментарием — моя гипотеза опровергнута проверкой (@DO 2026-11-10):** в `7-deploy` файлов `.timer` — **0**, на dev `systemctl list-timers` по `xdiary|otp` — **пусто**, юнит-файлов нет ⇒ **systemd-таймера не существовало никогда**; источник был **ручной** (внешний скрипт). Класть в репозиторий нечего. Урок: «ссылка на несуществующий механизм» — это **не дрейф инфраструктуры**, а **ложный комментарий**; проверять надо не наличие того, что упомянуто, а **существование самого механизма** (репозиторий + сервер).
