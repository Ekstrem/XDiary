## 1. Что измерено (без эксплуатации чужих данных)

Проба: `POST /api/v1/clients {"phone": <мой тестовый номер>}` — номер **создан мной в этом же прогоне**,
чужие номера не использовались.

| Шаг | Результат |
|---|---|
`POST /api/v1/clients` (новый номер) | `200`, в теле **`otpCode`, `otpAttempts`, `otpExpiresAt`** + внутренний конверт (`commandName`, `correlationToken`, `invariants`, `root`, `subjectName`) |
`POST /api/v1/clients` (тот же номер **повторно**) | `200`, **тот же `id`**, **новый `otpCode`**, `otpAttempts: 0` |
`POST /api/v1/clients/{id}/verify {"code": <код из ответа>}` | **`200` + `accessToken`** (JWT владельца) |

То есть цепочка «запросить код для **известного** номера → получить код в ответе → обменять на JWT» работает
**на проде**. Это не «лишнее поле»: это вход в чужой дневник по одному знанию номера телефона.

Квитанция гейта:

```
::error::check_otp_leak: `POST /api/v1/clients` вернул OTP-поле(я) ['otpAttempts', 'otpCode', 'otpExpiresAt']
квитанция: POST /api/v1/clients → 200 | тело 361 симв. | OTP-полей: 3 | нарушено: 1   (rc=1)
```

На dev (`https://xdiary-vps2.taile0b6ee.ts.net`) — **то же самое**: `rc=1`, 3 поля. Значит исправление `BE-090`
**не в образе**, который выкачен на оба стенда.

## 5. Приёмка `BE-093` на dev: **не измерима — запись создаётся, но не читается**

Прогон `check_be093_stale_fields.py` по живому dev (свой тестовый клиент, свой партнёр, токен получен через

```
GET  /api/v1/journal/records            → 200, 0 записей у этого клиента
```

Гейт отвечает `rc=1`:

```

         запись создаётся, но не читается (read-модель не видит её: BE-088)
```

**Что это значит:** приёмку «`AddPartner` не затирает поля» провести нельзя, пока чтение не работает — не

Отдельно: `POST /journal/records` **не принимает** `place`/`tags` (в ответе `place: ''`, `tags: []`), поэтому

**Чего не подтвердилось:** промежуточное наблюдение «в списке запись с чужим `clientId`» — на чистом клиенте

## 6. Причина `READ_PATH` найдена: **id в read-модели не совпадает с id, который вернул `POST /journal/records`**

Один прогон на dev (свой клиент, один `POST /journal/records` с `when`):

```
мой clientId                    26dca373…
id из POST /journal/records     e5aa6050…
GET /records                   200, записей 1
   id в списке                 a594a1c1…        ← ДРУГОЙ id
   clientId                   26dca373…        ← мой (значит фильтр в порядке)
   startedAt                  ''               ← пусто
   place                      ''               ← пусто
```

То есть запись **есть** (одна, моего клиента), но её `id` **не тот**, который вернул API, а `startedAt`
не заполнен. Поэтому `GET /journal/records/{id}` с «настоящим» id из ответа создания — **всегда 404**,
и это не лаг: 404 держится ≥20 с. Создание «есть», чтение «по id» — нет.

Дополнительно, тем же прогоном (dev):

| Операция | Статус |
|---|---|
`GET /records/{id}` | `404` |
`POST /records/{id}/when` | `400` (валидация, до поиска записи) |
`POST /records/{id}/place` | `404` |
`POST /records/{id}/duration` | `404` |
`POST /records/{id}/partners` | `404` |
`POST /records/{id}/complete` | `404` |
`GET /records` | `200`, запись есть (но с другим `id`) |

Все командные ручки, которым нужна запись, тоже `404` — значит проблема не в одном `GET`, а в идентичности
записи между ответом создания и read-моделью.

**Что смотреть в коде (ссылки по `gh/main`):** `6-msa/BC-Journal/src/Journal.Api/Events/JournalEventConsumer.cs:87`
(`existing = GetByIdAsync(domainEvent.Id) ?? new JournalReadModel { Id = domainEvent.Id }`) и `:134`
(`new JournalReadModel { Id = domainEvent.Id }`), `ApplyVos` `:140-147` (поля `StartedAt`/`ClientId` ставятся
**только** если в diff есть `Root`/`ClientId`). Код в `gh/main` выглядит согласованным, поэтому **наиболее
вероятное объяснение — образ на стенде старше `gh/main`**: там остался `UpsertAsync(Project(evt))` и/или
идентификатор агрегата присваивался иначе.

**Как проверить за минуту после выкатки:** тот же прогон `check_be093_stale_fields.py`; ожидаем
`rc=0` «сохранились N | затерто 0» и совпадение `id`. Если после выкатки `id` снова не совпадает — это дефект
кода, а не образа, и адрес известен (см. ссылки выше).

**Изоляция списка — в порядке:** клиент, который ничего не создавал, получает `GET /records` → `200`, **0**
записей; без токена — `401`. Наблюдение «в списке чужая запись» было ошибкой чтения моего же прогона.

## 7. Доказательство расхождения id (гипотеза @TL `22:21`) и **новый факт: прод `POST /clients` → 500**

### 7.1. Каждый `POST /journal/records` создаёт строку с **другим** id (dev)

```
POST /records → 200, id = 5a565fde…   startedAt = None
POST /records → 200, id = cdea05ce…   startedAt = None
GET  /records → 200, строк 2
   строка id = 3c6e7b26…  clientId = 699d1fd5…  startedAt = ''   совпадает с POST: False
   строка id = e43bf2c5…  clientId = 699d1fd5…  startedAt = ''   совпадает с POST: False
POST /records/{id из ответа}/when → 400
```

Два создания → две строки, и **ни одна** не совпадает с id, который вернул API. Это ровно та гипотеза, что
@TL сформулировал в `22:21`: read-модель получает `Id = domainEvent.Id` (`JournalEventConsumer.cs:66/87/134`),
и если это id **события**, а не агрегата, каждая команда создаёт новую строку. Проверяется без чтения кода —
одним прогоном, числа выше.

### 7.2. Прод: `POST /api/v1/clients` → **500** на новых номерах

```
попытка 1: 500  {"message":"Internal Server Error","http_status_code":500}
попытка 2: 500
попытка 3: 500
/health → 200 ok
/journal/records без токена → 401 (как и должно быть)
```

При этом **20 минут назад** тот же запрос на проде отдавал `200` с `otpCode` (раздел 1). То есть поведение
прода изменилось во время сессии: похоже, идёт/прошла выкатка `client`, и теперь регистрация падает на канале
доставки OTP (Telegram недоступен с прода — вопрос @EX о канале). Практический смысл: **новый пользователь сейчас
не может зарегистрироваться на проде вообще**, а старый путь «код в ответе» сменился на `500`.

### 7.3. Dev: `otpCode` = заглушка

```
POST /clients → 200, "otpCode": "000000", "otpExpiresAt": …
```

На dev канал — заглушка (`000000`), поэтому там вход возможен любым клиентом; это ожидаемо для dev, но
**приёмку «в ответе нет `otpCode`» на dev провести нельзя** — она осмысленна только на проде/с реальным каналом.

**Что нужно от @DO/@BE:** подтвердить, что на проде действительно катится новый `client`; если `500` — следствие
незаполненного канала OTP, то после решения @EX по каналу регистрация должна вернуться к `200` (уже без `otpCode`).
Приёмку повторим сразу: `check_otp_leak.py --base <прод>` → ожидание `rc=0` и «OTP-полей: 0».

## 8. Поправка к объяснению (числа §6–7 верны, трактовка была снята)

В §6–7 я записал причину как «read-модель берёт `id` **события**, а не агрегата». **Это объяснение снято**:

- @BE проверил консолью: `domainEvent.Id` — это и есть id агрегата (`IHasKey`), поэтому строки
  `JournalEventConsumer.cs:66/87/134` **корректны** и менять их не надо;
- реальная причина: `StartManualEntry`/`StartFromGarmin` не проставляли `Id = Model.Id`, то есть у созданной
  агрегатной модели **не было** id — и в read-модель уходила строка с другим идентификатором;
- @TL свою гипотезу про «id события» тоже снял явно (`22:38`: «мой вывод „проекция берёт id события“ был неверным»).

**Что не меняется:** измерения §6–7 — сами числа (два `POST` → id `5a565fde…`/`cdea05ce…`; в `GET /records` строки
`3c6e7b26…`/`e43bf2c5…`; ни одна не совпадает; `startedAt` пустой; `when`/`place`/`duration`/`partners`/`complete` →
`404`). Они воспроизводятся и после смены объяснения; сменился адрес правки: не проекция, а создание агрегата.

**Урок для меня:** «нашёл причину» — это утверждение, которое требует проверки кода/консоли, а не только
совпадения чисел. Числа я померил, а объяснение взял из чужой гипотезы и подал как своё — так делать нельзя.
