# front-e2e: как читать прогон и что делать с падениями

Документ для разбора **следующего** прогона `Front E2E`. Он не заменяет измерения: всё, что здесь
сказано про спеки, — либо проверенный факт (со ссылкой на гейт), либо **гипотеза**, которую прогон
подтвердит или опровергнет. Гипотезы помечены `[гипотеза]`.

## 1. Как получить данные (одна команда)

```bash
python 9-tests/scripts/e2e_triage.py --input front-e2e-results
```

Скрипт сам находит `test-results/receipt.txt` в распакованном артефакте и печатает таблицу
`класс | сколько | примеры спек | самый долгий шаг | лечение`. Классы: `test-timeout`, `wait-timeout`,
`session-lost`, `stand`, `assert`, `other`. Если аннотаций нет — `rc=2` («не измерено»), это не зелёный.

## 2. Класс → кто виноват → что делать

| Класс | Владелец | Действие |
|---|---|---|
| `test-timeout` | @TE | смотреть «самый долгий шаг»: если это `login по PIN`/`Before Hooks` — время входа (оптимизации `TE-057..TE-061`); если конкретный шаг UI — править шаг/ожидание, **не** поднимать общий лимит |
| `wait-timeout` | @TE / @FE | элемент не появился: сначала фазы входа в `::notice::login`, затем существование селектора (гейт `check_e2e_selectors`), затем поведение фронта |
| `session-lost` | @DO / @TE | `401/404` на `/clients/me` или `/journal` = клиента удалили на стенде (очистка или параллельный прогон). Фикстура делает один повтор; массово — значит кэш несовместим с образом |
| `stand` | @DO | `[infra]`, `stale-image`, `502–504`: поднимать стенд, тесты не править |
| `assert` | @TE / владелец дефекта | ожидание не совпало: дефект продукта **или** неверное ожидание. Смотреть данные и карточку |

## 3. Что уже исправлено по итогам первого прогона (`REF 73f59ba7`, `18 failed / 8 passed`)

- **кэш сессии** на процесс: 29 онбордингов → 1 (`TE-059`);
- **кэш партнёра**: −28 партнёров за прогон (`TE-058`);
- **без лишнего `reload`**, когда журнал уже открыт (`TE-060`);
- **отметка PIN как введённого** после быстрого пути (`TE-061`) — иначе `reload` внутри спеки показывает замок;
- **`wizard-record`**: после `reload` снимается замок (был «слепой» reload и падение «не дождались»);
- повтор входа при `401/404`, диагноз с фазами, длительности шагов в аннотации.

## 4. Известные риски по спекам (для сверки с таблицей)

| Спека | Что известно | Статус |
|---|---|---|
| `wizard-record` | «слепой» `reload` после входа → замок → `#view-journal` hidden | **исправлено**, класс закрыт гейтом `check_e2e_reload_lock` |
| `settings`, `edit-delete-record`, `stale-note`, `somatic-detail` | сами снимают замок после `reload` (`unlockIfLocked`) | факт (гейт `check_e2e_reload_lock` = 0 нарушений) |
| `onboarding`, `pin-first-login` | чистое устройство, `loginWithPin` не зовут — кэш сессии их не касается | факт (гейт `check_e2e_clean_device`) |
| `catalog` (4 теста: costume/toy/fantasy/contraception) | все 4 вкладки `data-kind` есть во фронте; добавление идёт через `#btn-catalog-add` → `#btn-catalog-save` → список | факт (селекторы проверены), поведение — по прогону |
| `partner-client-link` | создаёт своего клиента через API (`POST /clients`) и партнёра `TE-LINK-…`; `+7999` телефон | факт (гейт `check_e2e_cleanup_coverage`) |
| `partner-edit` | удаляет партнёра и проверяет `GET /partners/{id}` → `404/403`, плюс контроль `200` **до** удаления | факт (гейт `check_e2e_negative_pairs`) |
| `trends` | `[гипотеза]` единственная спека, которая требует «консольных ошибок нет»; на dev-стенде это может ловить посторонний `console.error` (`read-path:`, `afterAuth/me:`) | проверить по аннотации: если падение в этом утверждении — смотреть текст ошибки в аннотации, а не «UI медленный» |
| `csv` | `[гипотеза]` два входа (`loginWithPin` дважды) и импорт файла; при падении смотреть «самый долгий шаг» | по прогону |
| `catalog-archive` | удаляет позицию и проверяет отсутствие в списке + `getItem(page, id)` | факт (гейт `check_e2e_negative_pairs`) |
| `pin-fallback`, `pin-first-login` | PIN-контур; после `ADR-021` этап 2 в спеках нет вызовов `/privacy/*` | факт (гейт `check_e2e_privacy_calls`) |

## 4.1. Если в прогоне много `404`/`400` на данных — сначала проверь параллельность

Проверено на живых прогонах (#766/#767/#768): их окна тестов пересекались, а шаг «Очистить E2E-данные»
одного прогона попадал **внутрь** тестов другого и удалял клиентов `+7999…` и партнёров `TE-…`. Симптомы:
`POST /journal/records/{id}/when` → 404, `link-client` → 400, пустой `#view-partners`. Это **не дефект BE**.
Проверка: `Actions API` → `jobs[].steps[]` с `started_at/completed_at`; если окна `Front E2E` и `Очистить`
разных прогонов пересекаются — причина найдена.

## 5. Чего НЕ делать при разборе

- **не поднимать `UI_WAIT`/лимит теста** «чтобы прошло»: это прячет причину и увеличивает время прогона;
- **не пропускать спеку** (`test.skip`) без причины в маркере: гейт `check_e2e_skips` требует причину;
- **не повторять до зелёного**: повтор допустим только как диагностика и обязан быть видим в квитанции (`flaky`);
- **не чинить стенд правкой теста** и наоборот — класс из таблицы выше говорит, чей это дефект.

## 6. Что считается «прогон состоялся»

- шаг `check_e2e_all` зелёный (33 гейта);
- браузерный шаг завершился сам (не `cancelled`);
- в артефакте `front-e2e-results` есть `test-results/receipt.txt`;
- квитанция печатает `passed/failed/skipped`, и **исполнено ≥ 1** (иначе `rc=2` — «не измерено»).

**Вторая причина, не путать с первой:** `404` на свежесозданной записи и `400 «Partner not found.»`
бывают **дефектами продукта**, а не гонкой: read-модель с лагом (read-after-write) и полиморфная
сериализация value-объектов (`$type`-дискриминатор). Проверка: если `404`/`400` повторяются на прогоне,
который шёл **один**, — это продукт (`JournalController.EnsureOwns` fallback, `PartnerEventConsumer`
конвертер), и заводится дефект @BE с номером прогона как источником.
