## Как прогнать набор самому (одна команда на шаг)

Порядок без иллюзий: сначала то, что работает **в любой песочнице** (без браузера), потом браузерный
прогон — он требует установленного Playwright и живого стенда.

```bash
cd 9-tests/RnD/front-e2e

# 1) Все проверки набора (32 гейта) — нужен python и node, браузер НЕ нужен
python ../../scripts/check_e2e_all.py            # rc=0 = все зелёные, rc=1 = есть красный,
                                                     # rc=2 = что-то не измерено (НЕ зелёный)

# 2) Исполнение тел спек на заглушках: доказывает, что утверждения доходят до конца
npm run dryrun                                       # напр. «тестов исполнено 21 | упало 0»
npm run dryrun:selftest                              # 3/3: пустая спека действительно краснеет

# 3) Двойник стенда: контракт API проверяется без сети
npm run mock-api                                     # в отдельном терминале, поднимает :4180
node mock-smoke.js                                   # 23/23 проверок контракта

# 4) Браузерный прогон — локально (двойник + msedge), без секретов и без VPS
npm run test:local                                   # playwright.local.config.js
```

**Против живого стенда** (нужен доступ к `xdiary-vps2…` и PIN):

```bash
cd 9-tests/RnD/front-e2e
XDIARY_E2E_BASE_URL=https://…  XDIARY_E2E_PIN=…  npm test
```

**Разбор упавшего прогона:** в артефакте `front-e2e-results` лежит `test-results/receipt.txt`
(его пишет страж-репортёр) — квитанцию можно снять прямо из него:
`python ../../scripts/e2e_receipt.py --input test-results/receipt.txt --ref <sha>`. Либо, если есть
полный лог джобы, положить его в файл и снять квитанцию —
`python 9-tests/scripts/e2e_receipt.py --input <файл> --ref <sha>`; она печатает `passed/failed`,
список упавших спек и `flaky N (пройден ретраем)`.

**Ручки ожиданий** (меняются без правки 22 файлов): `XDIARY_E2E_UI_WAIT` (по умолчанию 30 000 мс) и
`XDIARY_E2E_EXPECT_WAIT` (по умолчанию 10 000 мс). Поднимать на медленном стенде, опускать на быстром.

**Двойник стенда проверяется и на уровне HTTP-контракта.** `node mock-smoke.js` — **26/26**: кроме
маршрутов, добавлены проверки, без которых локальный браузерный прогон падал бы непонятной
CORS-ошибкой: `OPTIONS /partners` → **204** (preflight), `Access-Control-Allow-Origin: *` на
preflight и на обычном ответе, неизвестный путь → **404 JSON** (а не 200). Проверено с двух сторон:
уберёшь CORS из двойника → `rc=1` и два `[FAIL]`; вернёшь → `rc=0`.

**Режим `--table` у квитанции — для шага «Итог по спекам».** `python 9-tests/scripts/e2e_receipt.py
--input <лог> --table --repeat 5 --workers 1 --ref <sha>` печатает markdown-таблицу
`спек | passed | failed | skipped | flaky | итого`, дописывает её в `--summary-file`
(то есть в `$GITHUB_STEP_SUMMARY`) и возвращает `1` при падениях, `2` — если ни один тест не
исполнялся. Нужен потому, что встроенный парсер в `front-e2e-repeat.yml` требовал префикс `tests/`
и не снимал ANSI — на реальном выводе он не разбирал ни одной строки и валил шаг в `::error::`
(измерение флейкости не могло дать чисел). `--selftest` **10/10**.

**Страж «ноль исполненных тестов — не зелёный прогон».** Если на стенде не выполнены условия и
все спеки уходят в `test.skip()`, Playwright завершится кодом 0 («0 passed, N skipped») — для CI
это выглядит успехом, хотя не проверено ничего. Поэтому в `playwright.config.js` подключён
репортёр-страж `reporters/executed-guard.js`: если исполненных тестов ноль, он печатает `::error::`
и выставляет код возврата 1; при частичных пропусках печатает `::notice::` с числом исполненных.
Дополнительно `check_e2e_ci_filter.py` (расширен, `--selftest` **6/6**) требует, чтобы страж был
подключён: уберёшь его из конфига — гейт краснеет («страж исполнения: НЕТ»). И `e2e_receipt.py`
на выводе «всё пропущено» теперь даёт **rc=2** («ни один тест не исполнялся»), а не 0.

**`check_e2e_clean_device.py` — ускорение не ломает сценарии первого входа.** Кэш сессии подкладывает
токен в `localStorage` до старта приложения; спека, которая проверяет **первый вход** (онбординг,
установку PIN на новом устройстве, путь «без PIN»), с засеянной сессией проверяла бы «уже вошли».
Гейт требует, чтобы `onboarding.spec.js` и `pin-first-login.spec.js` **не** вызывали
`loginWithPin`/`seedSession` (только `installBase` + свой сценарий); `no-pin.spec.js` — исключение,
это LEGACY `describe.skip`. Сейчас: **спек 3 | проверено 2 | исключений 1 | нарушено 0**, `rc=0`;
`--selftest` **5/5**.

**Пути входа проверяются поведением без браузера — `login-paths.test.js`.** Ускорения фикстуры
(кэш сессии, «без лишнего `reload`», повтор при `401/404`) статикой не проверить, а браузер в песочнице
не запускается. Скрипт загружает `tests/api.js` как есть, но с подставным `page` и окружением в
`evaluate` (`localStorage`, `fetch`, `window.Pin`), и проверяет **10 путей**: после засева журнал открыт →
вход без `reload` и с PIN; кэш не принят (401) → полный онбординг и `reload`; журнал уже открыт → ни
засева, ни `reload`; `401` посреди входа → **ровно один** повтор, затем падение с диагнозом;
PIN не снимает замок → диагноз с экранами (`PIN введён, но #view-lock не скрылся… views=…`),
а не пустой `timeout`; `expectScreen` несёт **текст тоста** и имя шага; сетевой сбой `POST /verify`
→ повтор вытягивает засев; сетевые сбои исчерпали попытки → падение с **числом попыток**
(`seedSession: засев не удался после 3 попыток (сеть)…`), а не с голым `Failed to fetch`;
кэш принят API, но журнал не открылся → **полный онбординг** (иначе систематический дефект кэша дал бы
массовое «вход не завершился», а повтор входа ждёт `401/404` и не сработал бы); после быстрого пути
PIN **отмечается как введённый** (`xdiary.pin.lastSuccess`) — иначе `reload` внутри спеки показал бы
замок и `settings`/`wizard-record`/`edit-delete-record` падали бы на ожидании журнала.
Сейчас: **10/10**, `rc=0`, запускается агрегатором как JS-проверка. Этот харнесс сразу нашёл реальный
дефект в моей же оптимизации: в кэш-ветке возврат ссылался на `token` вместо `cached.token` →
`ReferenceError` на быстром пути (был бы `Вход не завершился` у всех, кто попадёт в кэш).

**Один `reload` вместо двух на тест.** Если после засева сессии журнал уже открыт (кэш принят,
замка нет), `loginWithPin` ставит локальный PIN и **не перезагружает** страницу: экономится загрузка
и ожидание замка до 15 с. PIN ставится всегда, поэтому спеки PIN-контура (`change-pin`, `remove-pin`,
`pin-first-login`) делают свой `reload` и по-прежнему видят замок. В лог идёт
`::notice::login` с `fastPath: "after-seed"` и временем.

**Сессия кэшируется на процесс — 29 онбордингов заменены одним.** Раньше каждый тест проходил
полный онбординг (`POST /clients` → `verify` → `profile` → `partners` → `goto /`), то есть 2 загрузки
страницы и 5 запросов на **каждый** из 30 тестов; именно время входа расходовало лимит теста на прогоне
`18 failed` (REF `73f59ba7`). Теперь `clientId` + токены кэшируются (`SEED_SESSION`), и второй и далее
тесты входят одной загрузкой: `addInitScript` кладёт токен в `localStorage` до старта приложения, затем
проверка `GET /clients/me` = 200. Если стенд токен не принял (`401/404`) — кэш сбрасывается, печатается
`::warning::seedSession: кэш не принят, полный онбординг`, и сессия засевается заново. То есть «удалили
клиента» по-прежнему лечится, а не маскируется.

**Фикстура больше не плодит партнёров.** `seedSessionOnce` создавал партнёра `TE-SEED-<ts>` на
**каждый** вход (~29 за прогон), а шаг очистки в CI удаляет только клиентов `+7999…`. Список
партнёров рос от прогона к прогону; при 2 600+ карточках `#partners-list` доходил до 588 КБ
(`DO-044`), то есть это прямое топливо для «не дождались» в хуках. Теперь партнёр создаётся
**один раз на процесс** (`workers: 1`) и переиспользуется; проверка «свой партнёр виден клиенту»
по-прежнему выполняется — по id созданного или переиспользованного партнёра. Создание партнёра как
функцию проверяют спеки `add-partner` / `partner-edit` / `wizard-record`, а не фикстура.

**Вход дешевле и устойчив к параллельным прогонам.** `loginWithPin` теперь: (1) пропускает
`reload`+ожидание замка, если журнал уже открыт и токен на месте (3–5 с на каждый тест);
(2) при `401/404` на `/clients/me` или `/journal` считает это **потерей сессии** (другой прогон
мог удалить клиента шагом `Очистить E2E-данные`), засевает сессию заново с **новым телефоном** и
повторяет вход **один** раз, печатая `::warning::login: сессия потеряна, повтор с новым телефоном`;
(3) печатает фазы и число повторов в `::notice::login`. Если и второй вход не удался — падает с
диагнозом (views, последние ошибки, суммы по фазам), а не с пустым `timedOut`.

**Триаж по артефакту — одной командой.** `e2e_triage.py --input <каталог>` сам находит
`test-results/receipt.txt` внутри распакованного артефакта `front-e2e-results` и печатает таблицу
классов. То есть на разбор не нужно ни лога джобы, ни ручной пересылки текста: скачал артефакт —
получил классы. `--selftest` **5/5** (добавлен кейс «каталог вместо файла»).

**`e2e_triage.py` — разбирает лог прогона на КЛАССЫ падений.** Прогон дал `18 failed` (@DO
`2026-11-06 02:34`), и разбирать 18 аннотаций руками — часы, при том что класс определяет лечение.
Инструмент читает лог джобы или `test-results/receipt.txt`, берёт аннотации `::error::` с JSON
(`title/status/steps/error`) и печатает таблицу `класс | сколько | примеры спек | лечение`.
В таблице есть колонка **«самый долгий шаг»** — из аннотации падения берутся длительности шагов
(`login по PIN (61.2s) > открыть (2.0s)`), поэтому видно, где именно ушло время, а не только класс.
Классы: `test-timeout` (исчерпан лимит теста — виновато время в хуках/входе), `wait-timeout`
(не дождались элемента), `session-lost` (`401/404` на `/clients/me` или `/journal` — сессию убили),
`stand` (`[infra]`/`stale-image`/`502–504`), `assert` (ожидание не совпало), `other`.
Проверено на синтетическом логе формы реального прогона: 14 аннотаций → `test-timeout=14`.
`--selftest` **4/4**.

**Аннотация падения печатает длительность шагов.** `reporters/notice.js` выводит
`шаг (12.0s) > шаг (30.5s) [FAIL]`, поэтому в логе CI видно, **где** ушло время — в `Before Hooks`/
входе или в самой проверке. Это ответ на прогон `18 failed, 8 passed` (@DO `2026-11-06 02:34`),
где в аннотации был только `timedOut` без чисел; гейт `check_e2e_local_stack.py` теперь требует
наличия длительностей в аннотации.

**Вход логирует свои фазы (`::notice::login`).** После прогона `18 failed, 3 skipped, 8 passed`
(@DO, `2026-11-06 02:34`) падения были `timedOut` до утверждений, то есть «не дождались». Чтобы
следующий прогон сам ответил, где время, `loginWithPin` печатает `seedMs/pinMs/reloadMs/waitMs`
и при провале входа прикладывает экран (`views`), последние ошибки браузера и сумму времени.
Это заменяет догадку «поднять `UI_WAIT` до 60 с»: `UI_WAIT` ограничивает утверждения, а не вход,
и увеличение втрое внутри одного теста упирается в лимит теста (90 с).

**`check_e2e_reload_lock.py` — после `reload` замок снимают, а не «ждут журнал вслепую».**
Класс из реального прогона: спека входит (`loginWithPin` ставит локальный PIN), затем делает
`page.reload()` и ждёт `#view-journal`. Но после перезагрузки приложение показывает `#view-lock`
(PIN есть), журнал остаётся `hidden`, и тест падает «не дождались» — хотя причина в порядке шагов.
Так падал `wizard-record` (три теста одного спека); теперь там `unlockIfLocked(page)` после `reload`.

## Дисциплина пушей: как не отменить собственный прогон

`front-e2e` запускается на пуш в `main`, кроме `**/*.md`. Значит:

- **Коммит только из `.md`** (README, маркер, чат) **не запускает** браузерный прогон — такие пушы
  безопасны в любой момент.
- **Коммит с `.js`/`.py` в `9-tests/**` запускает прогон.** Если в очереди уже есть `running` или
  `pending`, новый пуш может вытеснить `pending` (GitHub отменяет ожидающий запуск). Поэтому правки
  спек и гейтов **батчу**: несколько изменений одним коммитом, а не по одному на раунд.
- **Перед пушем кода посмотреть очередь** по группе `front-e2e`: пока висит `running`/`pending` —
  не пушить, дождаться завершения (правило 5 минут из `docs/CI-RULES.md`).
- **Пауза кодовых пушей по просьбе @TL (`2026-11-06 00:41`).** Пока не пришли числа прогона,
  в `9-tests/**` идут только `.md`-коммиты. Причина: каждый пуш кода ставит `front-e2e` в очередь
  и занимает единственный dev-стенд; пока прогонов нет, доработки всё равно нечем проверить.
  `concurrency` у джобы **убран** (@DO, `DO-100` п.3 — см. шапку `ci-front.yml`), поэтому отмены
  `pending` больше нет: прогоны просто встают в очередь GitHub и доходят до конца.
- **Нужны числа в тишине** — `front-e2e-repeat.yml` (`workflow_dispatch`, `timeout-minutes: 90`,
  своя группа `front-e2e-manual`): запускается вручную, очередь пушей ему не мешает.

**CI подключён (`2026-11-06`):** джоба `front-e2e` теперь запускает `check_e2e_all` (32 гейта) до
браузера, ставит четыре флага `XDIARY_*` и сохраняет `test-results/` артефактом `if: always()`;
`timeout-minutes: 60` при худшем случае 39 мин. Значит правка спеки, которая валит гейт, теперь
останавливает джобу **до** браузера — это и есть смысл «дисциплины пушей».

История: `2026-11-06 00:41` @TL нашёл, что три прогона подряд не дошли до браузера — их вытесняли
новые пушы. `@DO` убрал job-level `concurrency` из `ci-front.yml` (`DO-100` п.3, строка 4 файла),
поэтому отмена `pending` больше не воспроизводится; дисциплина выше — страховка на будущее.

## Как я коммичу: правка «применилась» ≠ правка «в файле»

Две проверки, обе из реальных сбоев 2026-11-05 (класс «команда сказала ок ≠ сделано»):

1. **`py_compile` / `--selftest` доказывают синтаксис и логику, но не сохранение файла.**
   Скрипт может напечатать успех, а содержимое остаться прежним (here-string с бэктиками;
   правка, откатившаяся при параллельной записи). Проверка **перед коммитом**:
   ```bash
   git status --porcelain -- <путь>     # пусто ⇒ правки НЕТ, что бы ни говорил py_compile
   ```
2. **Проверять результат из `origin`, а не по сообщению скрипта** (@AR `chat/ar.md` `[2026-11-05 19:30]`):
   ```bash
   git show origin/main:<путь> | grep -F "<ожидаемая строка>"
   ```
   Только это отвечает на вопрос «дошло ли», потому что рабочее дерево — не доказательство.

**Почему проверять нужно именно перед коммитом:** в моём случае оба патча применились и `git status`
показывал изменения, но к моменту коммита файл уже совпадал с `origin` — то есть проверка
«сразу после правки» этот сбой не поймала бы. Ловит только проверка **в момент коммита**:
`git diff --cached --stat` обязан содержать каждый путь, который я называю изменённым.

## Методология измерения флейкости (E2E)

Автор формулировки — @LM; зафиксировал @TE (зона `9-tests/`). Обновлено: 2026-11-02.

1. **`5/5` зелёных ≠ «флейкости нет».** Это **верхняя граница**: «пять повторов её не поймали».
   Писать в задаче «флейкости нет» на основании 5/5 нельзя — только «на 5 повторах не
   воспроизвелась». Обратное (`1/5` красный) — доказательство флейкости.

2. **Изолированный и полный прогон — РАЗНЫЕ условия.** Пример: `csv` изолированно дал
   5/5, а в полном прогоне упал (timeout на `#btn-import-open`). Значит часть «флейкости» —
   это **зависимость от состава/порядка прогона и накопленного состояния клиента**
   (IndexedDB одного origin: записи, соматика, настройки, модальные слои). Поэтому
   результат одиночного `--repeat-each` **не переносится** на полный прогон и наоборот.

3. **`--workers=1` обязателен** при измерении флейкости. Иначе несколько воркеров делят
   один dev-стенд и **создают** гонку, которую мы пытаемся измерить. Замер с воркерами > 1
   измеряет не продукт, а конкуренцию за стенд.

4. **Сетевое падение — не доказательство красного продукта.** Пример: единственное
   падение `settings` (4/5) — `page.evaluate: TypeError: Failed to fetch`, то есть сеть/API.
   Возможен общий источник с `somatic-series/slice` (`net::ERR_FAILED`) — **гипотеза**, кодом
   фронта пока не подтверждена (в `8-front/js` нет `setInterval`-поллинга). Для вывода нужен
   стек из аннотации, а не совпадение текста ошибки.

5. **Одинаковая ошибка в двух спеках = искать общий источник.** Если `page.evaluate:
   TypeError: Failed to fetch` встречается и в `settings`, и в `somatic-series/slice`
   (`net::ERR_FAILED`), это скорее один общий helper/сеть, чем два независимых дефекта.
   Правят **источник**, а не каждый спек по отдельности.

**Важно про browser-context:** Playwright даёт **новый context на каждый тест**, поэтому
IndexedDB/localStorage **не переносятся** между спеками. «Утечка состояния браузера» как
объяснение флейкости **не работает**; накопление идёт **на стенде** (одна dev-БД для всех
прогонов), а не в браузере. Проверка гипотезы — прогон с явной последовательностью:
`npx playwright test settings.spec.js csv.spec.js --workers=1`.

6. **«Пустой» прогон — не доказательство (D-12).** Если в прогоне не случилось **измеряемого
   события** (например, ни одного тоста, ни одной ошибки), он не подтверждает ни «до», ни
   «после»: это не «лишний» прогон, а прогон **без сигнала**, и он опаснее избыточного, потому
   что выглядит как доказательство. Пример: прогон `#13` с `repeat=1` не дал ни одного тоста,
   и только `#14` дал пару «до/после». **Порядок:** перед `workflow_dispatch` проверить, нет ли
   уже прогона на нужном `main`-коммите — `ci-front` на том же коммите закрывает
   диагностическую правку без нового запуска (@DO 03:00, @LM 03:21).

**Практическое правило:** перед выводом «стабильно/флейко» фиксировать (а) число повторов,
(б) `--workers`, (в) полный или изолированный прогон, (г) были ли сетевые ошибки,
(д) случилось ли в прогоне вообще **измеряемое событие** (иначе вывод не про что).

## PDR-19: максимальное покрытие шлюза и клиента (A + C, решение владельца)

Обоснование: оба места уже дали инциденты — **502 через шлюз** и **неразвёрнутый `/clients`**.
Тестов на маршрутизацию `ApiGateway` **не было нигде** (`9-tests/Gateways` — это Garmin и
AppleHealth, см. раздел «Имя проекта ≠ имя сервиса»).

### 1. Критерий: что обязано быть покрыто у `ApiGateway`

| Поведение | Ожидание |
|---|---|
| `GET /health` | 200, без авторизации |
| `GET /api/v1/clients/me` без токена | **401** + `WWW-Authenticate: Bearer` |
| `GET /api/v1/clients/me` с токеном | 200, проксирует ответ сервиса; **после E7/ADR-024** `linkedPartnerId` в ответе **отсутствует** (проверено 2026-11-11: поля `id, phone, displayName, gender, photoUrl, verified`) |
| `POST /api/v1/clients` | 200/201, тело доходит до сервиса |
| `POST /api/v1/clients/refresh` | **анонимен** — 401 не возвращает |
| неизвестный путь (`/api/v1/does-not-exist`) | **401** (не 502/504) — фактическое поведение с 2026-11-11; клиент не отличает «маршрута нет» от «не авторизован», находка зафиксирована в `Gateways.Api` (B6) |
| апстрим недоступен | **502** (соединение отклонено) или **504** (таймаут) |
| `Authorization` | прокидывается **как есть** в апстрим (проверять на стороне сервиса) |

### 2. Контракт «шлюз → сервис»: что реально дёргает фронт

Собрано `git grep` по `8-front/js` (не по названиям, а по факту вызовов):

**Клиент (BC-Client):**
```
POST /api/v1/clients                    создание
POST /api/v1/clients/{id}/verify        OTP → client-JWT
POST /api/v1/clients/{id}/link-partner  шим ADR-024: 200 + `Deprecation: true`, удаляется после 0.88
GET  /api/v1/clients/me                 verified (+ профиль `displayName`/`gender`); `linkedPartnerId` **больше нет** (E7)
POST /api/v1/clients/refresh            обмен refresh → новая пара
GET  /api/v1/clients                    **маршрут удалён**: анонимно 401, с токеном 405 (ADR-026 §3)
**Журнал (BC-Journal):**

POST /api/v1/journal/records
GET  /api/v1/journal/recent
GET  /api/v1/journal/places
GET  /api/v1/journal/fantasies
```

**Главный контрактный тест** (актуальная форма, `Point1` + `Point2b` в `Contract.ClientJournal`): `POST /clients` → `/verify` → **`POST /clients/me/profile`** (`displayName` + `gender` по канону `male`/`female`) → **`GET /clients/me`**, где `verified === true`, `gender` — канонический, а `linkedPartnerId` **отсутствует**.
