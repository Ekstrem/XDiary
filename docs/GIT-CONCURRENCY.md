# Конкурентная работа с общим деревом (рекомендация, не запрет)

Норма (что запрещено) — в `AGENTS.md` §5.5 и `RULES.md` §17. Здесь — **почему** и
**что делать вместо**, чтобы не тянуло к `reset`.

## Git неизменяемый: коммит в origin не исчезает

- Пуш **прошёл** → коммит в `origin/main` навсегда, история линейная.
- Пуш **не прошёл** (non-fast-forward: кто-то успел раньше) → твой локальный коммит
  **не потерян**: он живёт в твоём дереве. Следующий `fetch` + `merge` соединит его
  с чужими коммитами и запушит **вместе со своим** — передавать твой коммит руками
  не нужно, его подхватит следующий пуш.

## Пуш не прошёл — рутина, не инцидент

1. `git fetch origin main`
2. `git merge origin/main` — merge сам соединяет твой коммит с чужими.
3. Конфликт в твоём файле → разрешаешь в своей зоне, коммитишь merge.
4. `git push`.

Интеграция — **только merge**. `rebase`/`reset` — переписывание истории; оно и рождает
«фантомы» (коммит есть локально, а в `origin` его нет).

## Что делать, если «merge не подходит»

Обычно это одно из трёх — и у каждого есть ответ без `reset`:

| Кажется, что… | Что на самом деле | Правильное действие |
|---|---|---|
| «надо откатить мой последний коммит» | отмена — это тоже коммит | `git revert <sha>` — создаёт **новый** коммит-отмену, историю не трогает; отменяется новым `revert` |
| «дерево разошлось с origin» | это normal, не беда | `fetch` + `merge` (выше) |
| «хочу отправить только один файл» | пуш идёт коммитами, а не файлами | закоммить только свой путь (`git add <свой файл>`), чужое не индексируй |

## Почему не reset (в одну строку)

`git reset origin/main` двигает HEAD общего дерева назад, и все локальные коммиты,
которых нет в `origin`, становятся `dangling` — их **не видно**, и они «пропадают» без
предупреждения. `merge`, наоборот, **добавляет** коммит-соединение и ничего не прячет.

Три инцидента за сессию (02/06/15.11) — все «хотел синхронизироваться через reset»,
и каждый раз сносился чужой коммит.
