## Проблема

За вечер я **трижды** положил коммит в `main` вместо ветки: сначала потому, что не было правила,
потом потому, что грязный файл блокировал `git switch`, и коммит «падал» в текущую ветку.
Каждый раз исправление стоило `branch -f` + `reset --mixed` — то есть операций с историей
в общем дереве, а это самый рискованный класс действий.

## Предложение

Для `@LM` `main` недоступен для прямых коммитов вообще: все правки — через ветку
(`git switch -c hold/lm-<дата>` **до** начала работы), `main` — только то, что смержил `@TL`.
Технически: `git_sync` для роли `lm` по умолчанию работает как `--hold`.

## Цена

Одна лишняя операция на правку; ветки нужно мержить (уже делает `@TL`). Риск: забытые ветки —
нужен список открытых `hold/*` (можно в дашборде).

## Как проверить

- `git log origin/main --since=<дата> --author=…` не содержит коммитов роли `lm` без мержа;
- число инцидентов «коммит не в ту ветку» = 0 за неделю.

## Что мешает принять сейчас

Правило процесса (нужен владелец) — поэтому пока применяю **как практику**, без нормы.

## Что сказали роли

- @TL — не спрашивали; мержит ветки он, так что его мнение обязательно.

## Текст процедуры (перенесён из `docs/CI-RULES.md`, норматив → черновик)

Если правки готовы, а очередь занята (или @TL держит окно), **не пушим в `main`**:

```
git switch -c hold/<role>-<дата> origin/main   # или: python tools/git_sync.py --role XX --hold
# … коммиты …
git push -u origin hold/<role>-<дата>
```

- тяжёлые workflow (`ci-*`, `deploy`, `docs-budget`) слушают **только `main`** — ветка их не
  запускает, то есть никого не вытесняет;
- в чат — одна строка `→ @TL` «мерж `hold/…` после окна», плюс задача в папке координатора;
- `@TL` мержит, когда очередь пуста; ветка удаляется после мержа;
- **не переносим** в `main` локальные коммиты «потом»: пока работа в ветке, она не вытесняет прогоны.

То же для роли `@LM` действует по умолчанию: `main` — только то, что смержил `@TL`.
