# CI, гейты и git-инциденты: подробные правила

Вынесено из `AGENTS.md` §5.1–5.4, чтобы инструкции не выходили за бюджет DSH
(все `AGENTS.md` грузятся вместе, лимит 64 КиБ; при переполнении файл **молча**
перестаёт подхватываться). Здесь — полные формулировки и истории; краткие нормы —
в `AGENTS.md` §5.

Проверки этих правил: `tools/check_workflow_paths.py` (фильтры путей),
`tools/chat_lint.py --strict-times` (метки), сам CI (окно 5 минут, вытеснение),
`tools/check_docs_size.py` (бюджет).

### 5.1. CI: не отменять прогоны раньше 5 минут

Решение владельца 2026-11-05, задача **DO-023**. Речь **не** о возможностях GitHub, а
о поведении агентов: прогоны отменялись слишком рано — агентом по кнопке/API, конфигом
`cancel-in-progress` и вердиктом «завис, отменяй». Из-за этого приёмка четырёх задач
висела без результата. Факты: `test` зелёный — **69 с** (падение сборки 15–24 с) при
лимите 20 мин; `front-e2e` — лимит 30 мин; отмены приходили на 1–2-й минуте прогона.

**Гарантированное окно: 5 минут.** Никто из ролей (`@TL`, `@DO`, `@BE`, `@FE`, `@TE`,
`@AR`) не отменяет прогон, которому меньше 5 минут от `started_at`.

- Отменять **можно**: прогоны в статусе `queued`, которые ещё не стартовали (дубликаты
  очереди) — это не «ранняя отмена», результата у них нет.
- Отменять прогон **в `in_progress`** — только если он **≥ 5 минут** без прогресса,
  и с записанной причиной в задаче/чате («висит на шаге X, N мин, лог Y»).
- **Нельзя объявлять прогон зависшим по ощущению «давно»** — сначала сверить
  `started_at` / `updated_at` / шаг по API и назвать цифру. Случай 2026-11-05: run'ы
  #749–751 назвали зависшими, а они уже были `completed/failure`.
- Автоматическая отмена новым пушем (`cancel-in-progress`) для `test` и `front-e2e`
  **запрещена** — оба джоба идут в очередь (фактически `false`, группы `ci-tests-test`
  и `front-e2e`). Поэтому требование «test не трогать 5 минут» выполнено с запасом:
  прогон не отменяется вообще.
- Правки задач и чата не запускают тяжёлые джобы (`paths-ignore: 5-tech-backlog/**`
  в `ci-tests.yml`); guard'ы — в отдельном `chat-guards.yml`, который слушает
  `5-tech-backlog/**`, `loop.config.json` и `tools/**`.
- **Расширяя `paths-ignore`, переноси guard-джобы, а не выключай.** Урок DO-031/DO-032:
  сузили `ci-tests` до чата, а `guard-secrets` для файлов задач так и не появился —
  задачи почти сутки не сканировались на секреты, и никто этого не заметил.
- **`cancelled` ≠ «кто-то нажал отмену».** GitHub держит на группу **один** pending-прогон:
  новый пуш **вытесняет** ожидающий, даже если `cancel-in-progress: false`, и тот
  завершается как `cancelled`, не сделав ни шага. Признак вытеснения — нет шагов /
  пустой `started_at`; виноват пушивший. Правило: **не пушить код, пока по группе висит
  pending-прогон** (дождаться или `workflow_dispatch` после). Если шаги были и отмена
  пришла раньше 5 минут — это ручная отмена: автор и причина называются в задаче/чате.
- **Результат отменённого run'а не считается доказательством** — ни зелёным, ни красным.
  Для приёмки нужен прогон, завершившийся сам (success/failure), иначе rerun.
- Порядок разбора: **запуск, перезапуск и диагностика прогонов — @DO** (dispatch, rerun,
  очередь, concurrency, раннеры, минуты). **TL только читает результат** («зелёный/красный»
  по задаче) и не запускает прогоны сам — это зона DevOps. Пустые аннотации
  («Process completed with exit code 1» без имени теста) — повод открыть лог, а не
  объявлять причину по памяти.

### 5.2. Воспроизводимость инфраструктуры

**Состояние сервера, которого нет в репозитории, не существует.** Скрипты деплоя жили
только на VPS — и любой heal/апдейт воспроизводил не репозиторий, а дрейф: шлюз полдня
ходил без `--add-host clients`, а 502 искали в коде сервиса (DO-034).

- серверные скрипты (`deploy.sh`, `update.sh`, `heal-network.sh`) — в репозитории;
- списки сервисов/хостов генерируются из compose, а не переписываются руками в двух местах;
- «починил на сервере» без коммита — это не починка, а ещё один дрейф.

### 5.3. Git-инцидент: STOP и один восстановитель

Решение владельца 2026-11-06 (после дня взаимных потерь: чужие правки затирались
`autostash`/`rebase`, каждый «чинил по-своему»).

**Признаки инцидента:** конфликт при `rebase`/`merge`, «cannot autostash», пропали
коммиты или правки, локальная и удалённая ветвь разошлись, чужой force-push, дерево не
собирается из-за чужой полуправки.

**STOP — только при потере или повреждении.** Обычный non-fast-forward (на remote
появился `chore(chat)` от бота, кто-то успел запушить раньше) — **штатная рутина**:
`fetch` + `rebase` (или `pull --rebase`) без force-push и без STOP. Останавливать всех
ради расхождения ветвей нельзя — иначе правило начнут применять к каждому пушу.

| Ситуация | STOP? | Что делать |
|---|---|---|
| non-fast-forward, «Everything up-to-date», обновление чата/документа на remote | **нет** | `git fetch` + `git rebase origin/main` (или `pull --rebase`), запушить |
| конфликт в `rebase`/`merge`, «cannot autostash» | **да** | STOP, восстанавливает @TL |
| пропали коммиты или правки, чужой force-push, дерево не собирается из-за чужой полуправки | **да** | STOP, @TL восстанавливает и объявляет «работа возвращена» |

**Протокол (обязателен):**

1. **@TL пишет STOP всем ролям** — одна строка в `chat/tl.md` со перечислением ролей,
   временем и признаком инцидента.
2. **Все роли останавливаются:** не пушат, не правят рабочее дерево, не запускают
   `git reset / checkout -- . / stash / rebase / pull`. Можно только читать.
3. **Восстанавливает один — @TL**: `git fetch`, сверка `origin/main`, `rebase`, разбор
   стеша, повторная проверка артефактов в `origin`.
4. **@TL объявляет «работа возвращена»** и перечисляет: что восстановлено, что потеряно,
   на каком коммите `origin/main`.
5. **Историю не переписываем** (force-push запрещён): при реальной потере — повторная
   правка поверх, а не «откатить всё».
6. **Урок — в правило**: если инцидент выявил дыру, она фиксируется в `AGENTS.md`/`STATUSES.md`
   тем же днём (так появились §3 «незакоммиченное не существует» и §5.1 про вытеснение).

### 5.4. Гейт должен соответствовать тому, что деплоится

Наблюдение 07.11 (DO-035): гейт `smoke` был один на всё — `deploy-dev → smoke → deploy-prod`,
внутри и API-тесты, и `front-e2e`. Из-за этого **фронтовый** баг (FE-027) останавливал
доставку **бэкенда**: образ `clients` с `TelegramOtpSender` не мог доехать, хотя `test`
был зелёный дважды. Единственным «быстрым» выходом остался ручной `podman pull` — то есть
обход гейта.

Правила:

1. **Гейт выбирается по природе изменения, а не «один на всё»**: `6-msa/**`, `7-deploy/**`
   → API-гейт; `8-front/**` → front-гейт; смешанный diff → оба. Имя гейта = имя артефакта.
2. **Ручной обход гейта запрещён** (ручной `podman pull`, «по-быстрому задеплою», временный
   скрипт на VPS). Это делает доставку невоспроизводимой (§5.2) и **прячет дефект гейта**:
   следующий раз то же самое повторится с другим багом.
3. **Гейт, который блокирует не то, что деплоится, — дефект гейта.** Если для доставки
   бэкенда нужно починить фронт — чинится гейт (задача), а не обходится доставка.
4. **Гейт, который постоянно ждут или отменяют, — тоже дефект.** Если дважды подряд
   пришлось ждать/обходить/отменять — переделываем гейт (как DO-023 про отмены).
5. **Дисциплина сохраняется:** окно 5 минут и `cancel-in-progress: false` для тяжёлых
   джобов не отменяются оптимизацией (§5.1).

## Пуш и транспорт: подробности

**Симптом.** `git push origin` → `ssh.exe: couldn't create signal pipe, Win32 error 5`.
Это не права и не ключи: git по умолчанию берёт ssh из `C:\Program Files\Git\usr\bin`,
который в песочнице DSH не может создать pipe.

**Причина точно.** `git config --get core.sshCommand` пусто → используется bundled ssh.
С системным OpenSSH та же команда проходит.

**Лечение (один раз на машину, действует на все роли):**

```
git config --global core.sshCommand "C:/Windows/System32/OpenSSH/ssh.exe"
git ls-remote --heads origin main      # должно ответить
```

**Если ssh недоступен в принципе** — HTTPS-фолбэк: токен берётся из личного хранилища
роли **вне репозитория** и передаётся только через переменную окружения
(`AUTHORIZATION: basic base64(x-access-token:<токен>)`), никогда — в argv, в `git config`
или в файл в репозитории. Путь к хранилищу в документах не пишем: репозиторий публичный,
а `check_rule_docs.py` такие строки ловит.

**Проверка результата — только после `fetch`:**

```
git fetch origin main
git rev-list --count origin/main..HEAD     # 0 = всё ушло
git merge-base --is-ancestor <sha> origin/main && echo "коммит в истории"
```

**Почему `wip` — по зоне.** `git add -A` в общем дереве захватывает чужие правки; в истории
уже был `wip(be)` с `AGENTS.md`. Поэтому `wip.py` фильтрует пути по `zones` из
`loop.config.json`, а `--all` остаётся осознанным исключением.

### Дополнение к §5.3: повреждённые метаданные git

Инцидент 2026-11-02 18:39–18:45 показал класс состояний, которого не было в протоколе:
`.git/rebase-merge` остался после неудачного `rebase --autostash` — **только файл
`autostash`**, без `head-name`/`onto`. Признаки: `git rebase --abort` отвечает
`could not read .git/rebase-merge/head-name`, любой следующий `rebase`/`pull --rebase`
падает, а в `autostash` могут лежать чужие незакоммиченные правки.

Порядок (обязательный):

1. **Объявить в чат** — `→ всем: нашёл повреждённые метаданные git (<что вижу>), STOP
   для `rebase` до сигнала`. Без объявления действие считается инцидентом само по себе.
2. **Один восстановитель** — координатор. Роли не трогают `.git/`, не запускают
   `rebase`/`pull`, не удаляют стеши до «работа возвращена».
3. **Автостэш сначала восстановить, потом удалять метаданные:** `git stash apply <sha>`
   (не `pop` — чтобы объект остался), проверить содержимое, и только потом убрать
   повреждённый каталог.
4. **Сохранить SHA перед удалением** и записать в чат: удалённый стеш должен быть
   восстановим из reflog, а не «был мусором» на словах.
5. **Проверка после:** `git log --oneline -1 origin/main`, `git status --short`,
   `git rev-list --count origin/main..HEAD` — цифры в чат.

Урок: два восстановителя одновременно (координатор и процессная роль) — опаснее
самого повреждения; правило «один восстанавливает» нужно именно в момент, когда
дерево выглядит сломанным и руки чешутся.
