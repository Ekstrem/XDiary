## Варианты, которые рассматривались

вердикт по строке (сейчас) | пакетный вердикт по плану класса

## Решение и детали

- **Статус:** обсуждается. **Владелец:** `@TL`.
- **Зачем:** 5 раундов «правка → push → прогон → вердикт» на один класс; вердикт по строке
  дороже вердикта по плану.
- **Предложение:** `@TL` проверяет план класса («три инфра-правки одним пакетом — вердикт
  один»), артефакты — по списку, а не по одному.
- **Плюсы:** минус 3 из 5 раундов; меньше переключений контекста у обеих сторон.
- **Минусы:** если в пакете одна плохая правка, откатывается пакет; нужен критерий «что
  считается пакетом» и кто отвечает за дефект внутри.
- **Критерий:** `cycle` по роли до/после; число раундов на класс.

## Критерий и метрика

- **Как проверяется:** фиксировалось в тексте правила/гейта (до 07.11 отдельного
  поля «критерий» не было — это и стало причиной перехода на папку файлов).

## Позиция @TL (владелец, 21:05)

Принимает пакетный вердикт **с четырьмя ограничениями**:

1. **Пакет = один класс** (инфра / фикстура / доки). Продуктовые правки с инфраструктурными
   не смешивать — у них разные гейты (§5.4). «Пакет» из нескольких классов — не пакет, а свалка,
   отклоняется.
2. **Вердикт один, но перечисление по пунктам:** «принято» перечисляет каждый артефакт и его
   статус, иначе «пакет принят» скрывает недоделанный пункт.
3. **Возврат всего пакета одной причиной**, без поштучных переговоров; ответственный за дефект —
   роль, запушившая пакет.
4. **Критерий приёмки:** один прогон, завершившийся **сам** (не `cancelled`, не 0 шагов),
   плюс негативный тест на каждый исправленный гейт.

**Метрика:** раундов на класс — было ~5, цель **≤ 2**.
