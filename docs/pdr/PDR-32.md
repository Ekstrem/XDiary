| Поле | Значение |
|---|---|

| **Согласования** | владелец 2026-11-11 (автор мысли); @LM 2026-11-11 (драфт) |
| **Дата** | 2026-11-11 |

## Мысль владельца (дословно по смыслу)

> При наличии APIM артефакты из `03-ddd`, описывающие API (напр. `03-ddd/BC-Journal/04-query-api.md`),
> следует заполнять сразу там.

## Как я это понял

`03-ddd/BC-*/` содержит документы, описывающие API каждого bounded context — например
`04-query-api.md` (эндпоинты `GET /api/v1/journal/...`, Response DTO, потребители). Сейчас это **markdown
в репозитории**. Раз у нас появился APIM (ранбук `apim.md`, `check_openapi.py` на дрейф/breaking), такие
API-артефакты надо **вести сразу в APIM**, а не поддерживать две расходящиеся копии (markdown в `03-ddd`
и реестр в APIM). APIM становится **каноном API**, а markdown — производным (генерируется/сверяется),
либо отмирает.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. `03-ddd` markdown остаётся каноном, APIM — поздняя копия | привычно | дрейф `03-ddd` ↔ APIM, «две правды» |
| **B. APIM заполняется сразу: API-артефакт появился/изменился → регистрируется в APIM в том же шаге** | один канон, контракт актуален, `check_openapi --registry apim` работает по назначению | ритуал «описал API → зарегистрировал в APIM» |
| C. ничего не менять | 0 | — |

## Решение (предварительное)

**Вариант B.** API-артефакт из `03-ddd` (эндпоинты/DTO `04-query-api.md` и аналоги) регистрируется в APIM
**в том же рабочем шаге**, а не отдельной задачей позже. Проверка — `check_openapi.py`
(`--registry apim --base <rev>` на breaking, `--generated <dir>` на дрейф).
