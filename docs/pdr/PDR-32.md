## Мысль владельца (дословно по смыслу)

> При наличии APIM артефакты API следует заполнять сразу там.

## Как я это понял (⚠️ уточни, если не так)

APIM у нас уже есть (ранбук `apim.md`, `check_openapi.py` для дрейфа/breaking). Значит, когда у сервиса
появляется API (OpenAPI-спека/контракт) — его надо **сразу регистрировать в APIM**, а не держать контракт
только в репозитории и «подтягивать в APIM потом». APIM становится **первичным реестром артефактов API**,
репозиторий — источник для сверки (drift-check), а не наоборот.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Репозиторий первичен, APIM — поздняя синхронизация | просто | дрейф repo↔APIM, контракт «для галочки» |
| **B. APIM заполняется сразу при появлении/изменении API** | единый реестр, контракт актуален, `check_openapi --registry apim` работает по назначению | нужен ритуал «создал API → зарегистрировал в APIM в том же коммите/шаге» |
| C. ничего не менять | 0 | — |

## Решение (предварительное)

**Вариант B.** При появлении или изменении API-контракта (`6-msa/BC-*/openapi/*.json`) он регистрируется
в APIM **в том же рабочем шаге**, а не отдельной задачей позже. Проверка — `check_openapi.py`
(`--registry apim --base <rev>` на breaking, `--generated <dir>` на дрейф).

### Комплаенс

| Что | Значение |
|---|---|
| Где первичный реестр | APIM (артефакты API) |
| Где сверка | `check_openapi.py` (repo ↔ APIM) |
| Когда пересматриваем | при первом дрейфе repo↔APIM |
| Кто проверяет | @DO (инфра), @AR (контракты) |

## Критерий приёмки и метрика

- гейт: `check_openapi --registry apim` → rc=0 (дрейф 0) на трёх API (journal/client/partners);
- метрика: API-контракт, существующий только в repo и отсутствующий в APIM, = 0.
