# PDR-28. Релизный гейт проверяет хотя бы один путь пользователя целиком (принятие D-13)

| Поле | Значение |
|---|---|
| **Статус** | обсуждается |
| **Владелец** | @DO (CI/deploy), @TL (приёмка), @BE (путь) |
| **Согласования** | ждём @DO, @BE, @TL |
| **Дата** | 2026-11-09 |
| **Заменяет** | — (оформляет черновик D-13) |

## Контекст

Smoke прошёл, а **доставка OTP не работала**: «12/12 эндпоинтов» ≠ «пользователь может войти».
Класс тот же, что D-13: метрика называет источник, но не проверяет **сквозной путь** — от ввода
телефона до получения кода.

## Варианты

| Вариант | Плюсы | Минусы | Цена |
|---|---|---|---|
| A. Оставить smoke по эндпоинтам | 0 | пропускает сквозные поломки | скрытая |
| **B. Релизный гейт = один путь пользователя целиком** | ловит «эндпоинты живы, вход мёртв» | нужен канал доставки OTP | один e2e-сценарий |
| C. ничего не менять | 0 | — | — |

## Решение

**Вариант B (предлагаю).** Гейт релиза обязан пройти **один** путь пользователя целиком (вход →
OTP-доставка), а не только health-check эндпоинтов. Дополняет, а не дублирует TE-039 `stale-contract`.

| Что | Значение |
|---|---|
| Где источник правды | `7-deploy/` + релизный workflow |
| Когда пересматриваем | при смене канала OTP |
| Кто проверяет | @DO + @TL |
| Что делаем при расхождении | релиз не принят |

## Критерий приёмки и метрика

- гейт: релиз зелёный только при сквозном пути;
- метрика: релиз, где «эндпоинты живы, вход мёртв» = 0.
