# Process Decision Record (PDR)

Лог процессных решений петли: что решили, **почему**, чем это стоило и кто был против.
Один документ вместо памяти чата — чтобы через месяц не спорить заново и не искать,
«откуда взялось правило».

Ведёт `@LM`. Решения принимает владелец или координатор; здесь фиксируется факт,
обоснование и цена. Новое предложение живёт в разделе «Обсуждается», пока не собраны
мнения тех, кого оно затронет (`§18`: правило без владельца и проверки не принимается).

## Шаблон записи

| Поле | Что писать |
|---|---|
| ID | `PDR-NN`, сквозная нумерация, не переиспользуется |
| Статус | `принято` / `обсуждается` / `отклонено` / `заменено PDR-MM` |
| Решение | одна-две строки, что именно действует |
| Почему | инцидент или цифра, из которых решение выросло |
| Плюсы / минусы | честно, включая стоимость поддержки |
| Мнения | чьи возражения собраны (`@DO`, `@AR`, `@TE`, `@TL`) и чем закрыты |
| Доказательство | коммит, workflow, метрика, прогон |
| Влияние | какая метрика дашборда должна сдвинуться |

## Принятые решения

### PDR-01. Восемь статусов задачи

- **Статус:** принято (07.11).
- **Решение:** `Идея → На проработке → ToDo → В работе → В паузе → На проверке → Закрыта`
  + `Отклонена`; синонимы запрещены и ловятся линтером.
- **Почему:** «Открыта» смешивала три состояния (сырая идея / на проработке / готова к работе),
  а «В работе» — работу и осознанную паузу. Обход не мог отличить застой от блокировки.
- **Минусы:** больше полей в карточке; миграция 139 задач через `migrate_statuses.py`.
- **Доказательство:** `tools/status_lint.py --strict` в CI, 0 ошибок на 148 файлах.

### PDR-02. Ревью по домену и запрет саморевью

- **Статус:** принято (07.11), уточнено (07.11: саморевью = автор задачи).
- **Решение:** ревьюер определяется доменом; если автор задачи совпадает с ревьюером —
  проверяет `@TL` (для архитектурных `@AR`).
- **Почему:** один TL как единственный ревьюер 148 задач — горлышко, которое не улучшалось
  ни на одной итерации. Первая версия правила («ревьюер = папка») дала **12 ложных
  срабатываний**: для `devops/`-задач корректный ревьюер как раз `@TL`, а не `@DO`.
- **Минусы:** нужно дисциплинировать поле `Проверяет:`; метрика «ревью не автором» стала
  проверяемой только после переделки формулировки.
- **Доказательство:** `status_lint` предупреждает о саморевью; метрика `31/31`.

### PDR-03. Артефакт вместо обещания

- **Статус:** принято (01–07.11).
- **Решение:** первый шаг по задаче — `Статус: В работе` + строка в outbox; ход нельзя
  заканчивать обещанием; «незакоммиченное не существует»; проверять артефакт в `origin`,
  а не в рабочем дереве.
- **Почему:** агент заканчивал ход планом («беру TE-015, потом TE-016»), файл не менялся —
  для петли ничего не происходило. Дважды отчитались «проверено», глядя в незакоммиченное
  дерево (DO-031/DO-032 «были сделаны» — в `origin` их не было).
- **Минусы:** больше коммитов (в т.ч. `wip`); нужно помнить про `git_sync`.
- **Доказательство:** §3 `AGENTS.md`; `sweep` ловит «обещано, но не начато».

### PDR-04. Гейт должен соответствовать тому, что деплоится

- **Статус:** принято (07.11, после DO-035).
- **Решение:** гейт выбирается по природе изменения (`6-msa/**`,`7-deploy/**` → API;
  `8-front/**` → front); ручной обход запрещён; гейт, который блокирует не то, что
  деплоится, — дефект гейта.
- **Почему:** единый `smoke` связывал фронт и бэк: фронтовый баг FE-027 остановил доставку
  образа `clients` с `TelegramOtpSender`, и единственным выходом остался ручной `podman pull`.
- **Минусы:** два гейта дороже по минутам; нужно поддерживать `diff`-логику.
- **Доказательство:** `14306ca` (`smoke-api`/`smoke-front`), §5.4 `AGENTS.md`.

### PDR-05. Дисциплина прогонов: 5 минут, вытеснение, dispatch

- **Статус:** принято (05.11), дополнено (07.11: dispatch).
- **Решение:** прогон младше 5 минут не отменяет никто; `cancel-in-progress: false` для
  тяжёлых; `cancelled` без шагов = вытеснение, а не ручная отмена; отменённый прогон —
  не доказательство; перед `workflow_dispatch` дождаться пустой очереди по группе.
- **Почему:** четыре задачи висели без приёмки из-за отмен на 1–2-й минуте; dispatch
  вытеснялся собственным пушем; `--reporter=list,json` + `>` писал два формата в один файл.
- **Минусы:** нельзя «быстро перезапустить» — надо ждать; запуск прогонов только у `@DO`.
- **Доказательство:** §5.1 и `docs/CI-RULES.md`; `check_workflow_paths.py` в CI.

### PDR-06. Git-инцидент: STOP и один восстановитель

- **Статус:** принято (06.11), дополнено (07.11: повреждённые метаданные).
- **Решение:** STOP только при потере/повреждении; объявление **до** действий; восстанавливает
  один (координатор); SHA удаляемого в `.git/` фиксируется в чате; автостэш восстанавливается
  через `git stash apply`, а не удаляется.
- **Почему:** два восстановителя работали параллельно (LM и TL) — оказалось опаснее самого
  повреждения `.git/rebase-merge`; до этого день взаимных потерь из-за `autostash`.
- **Минусы:** координатор становится единственной точкой на время инцидента.
- **Доказательство:** §5.3 `AGENTS.md`, `docs/CI-RULES.md`, `RULES.md` §17.

### PDR-07. Единый источник инструментов

- **Статус:** принято (07.11).
- **Решение:** инструменты живут в LoopMaker, в проект копируются; манифест
  `tools/.sources.json` (sha256) + `guard-tools` в CI.
- **Почему:** репозиторий-шаблон приватный, CI проекта его не читает → копии расходились
  молча (5 расхождений). Направление синка — только LoopMaker → проект.
- **Минусы:** правка в двух местах до `sync_tools --pull`; риск «поправил копию, а не источник».
- **Доказательство:** `sync_tools --check`: 17/17 совпадают, drift 5 → 0.

### PDR-08. Процессная роль `@LM`

- **Статус:** принято (06.11).
- **Решение:** `@LM` — правила, линтеры, миграции статусов, шаблоны, дашборд. Статусы задач
  и результаты прогонов ему не адресуют.
- **Почему:** проектная сводка в процессном треде раздувала контекст и создавала дубли работы.
- **Минусы:** появился хоп «вопрос → LM»; мерим SLA (`< 30` мин, сейчас 45–48 — 🟡).
- **Доказательство:** `RULES.md` §18, метрика `lm_sla`.

### PDR-09. Бюджет инструкций

- **Статус:** принято (07.11).
- **Решение:** все `AGENTS.md` ≤ 64 КиБ суммарно; `AGENTS.md` ≤ 32 КБ на файл;
  норма — в `AGENTS.md`, истории — в `RULES.md`/`docs/`; гейт `check_docs_size.py`.
- **Почему:** 67.7 КБ суммарно → `XDiary\AGENTS.md` **молча** перестал загружаться, роли
  работали без правил.
- **Минусы:** правила размазаны по двум-трём файлам; нужно помнить, где искать.
- **Доказательство:** 47 КБ сейчас, `docs-budget.yml` зелёный.

### PDR-10. Метки времени в чате = часы машины

- **Статус:** принято (07.11), разворот по предложению `@TL`.
- **Решение:** `--next-stamp` (часы машины, `shift_hours = 0`); на границе — строка-маркер;
  линтер проверяет только «новую шкалу»; `--strict-times` в CI.
- **Почему:** метки писали «по памяти» и уехали на 106 часов; в чате `03:25`, на машине
  `17:25`, в GitHub `13:52Z` — всё про один прогон. Сдвиг узаконил бы дрейф.
- **Минусы:** старые 840 меток остались «будущими»; их отсекает маркер, а не перепись.
- **Доказательство:** `chat_lint --report`: впереди шкалы 0, порядок 0.

### PDR-11. Единое правило пуша

- **Статус:** принято (07.11).
- **Решение:** транспорт — ssh с `core.sshCommand` на системный OpenSSH (одна настройка
  машины); синхронизация — `git_sync.py`; `wip` строго по зоне роли; «дошло» проверяется
  после `fetch`; пути к хранилищам токенов в доках запрещены (`check_rule_docs`).
- **Почему:** ssh через bundled ssh падал у всех (`signal pipe`), три роли спотыкались;
  `wip(be)` захватил `AGENTS.md`.
- **Минусы:** одна настройка вне репозитория (машина), при переезде её надо повторить.
- **Доказательство:** §5.5, `RULES.md` §19, `check_rule_docs` 0/0.

### PDR-12. Ротация чата с архивом

- **Статус:** принято (07.11).
- **Решение:** активный файл роли ≤ 150 сообщений; старое — в `chat/archive/<роль>/`;
  каталог не сканируется мостом; миграция ключей — best effort.
- **Почему:** `tl.md` 399 КБ / 693 сообщения (60% переписки) — дорого читать, любой агент
  «читает все outbox'ы».
- **Минусы:** история в двух местах; `chat_inbox` не видит архив (осознанно).
- **Доказательство:** `c8909c3`: 693 → 150 сообщений, 399 → 137 КБ, повторов доставки 0.

### PDR-13. Канон адресатов — `+`

- **Статус:** принято (07.11), после возражения `@DO`.
- **Решение:** `→ @DO + @TE: …` — канон; мост понимает и `/ , ;`, но это не канон.
- **Почему:** `@TL/@TE` не делился → адресат `TL/TE` не находился → сообщение пропускалось
  **без ошибки** (28 строк в `do.md`, 90 по чату). При этом утверждение «`@A + @B` не
  доставлялись» оказалось **неверным**: `+` работал всегда (`split('+')` + `trim`), терялась
  **сводка** (`merge_chat` до `6644daf` не делил адресатов).
- **Минусы:** нужно переписать привычку; старые 28 строк остались как история.
- **Доказательство:** node-тест (`@DO + @TE` → `["DO","TE"]`), `docs/CI-RULES.md`, README п.6.
- **Проверено `@DO` независимо (21:50):** `git show origin/main:...README.md` п.6 — канон `+`;
  `git grep` по «молча теряют»/«не доходят» в `docs/` — пусто; противоречия документов больше нет.
  Практика «двоим — две строки» **отменена** как страховка от несуществующей проблемы.
- **Диагностический порядок (из этого случая):** «роль не видела сообщение» → сначала проверить
  **сводку/фильтр по роли** (`_dialogue.md`, `chat_inbox`), и только потом транспорт: это разные
  места, а симптом один.

### PDR-14. Дашборд и flow-метрики

- **Статус:** принято (07.11).
- **Решение:** `health.py` → `HEALTH.md` + история; состояния (статусы, гейты, drift) плюс

- **Минусы:** медиана цикла считается по git-истории файла, а не по полю `В работе с`

- **Доказательство:** 12 строк дашборда; `cycle 0.4 дн (n=116)`, `lm_sla 48 мин (n=24)`,
  `wip 2%`, `формат 93 из 786`.

### PDR-16. Декомпозиция `ci-tests.yml` и дубль guard'ов

- **Статус:** обсуждается (порядок согласован с `@DO`, ждёт выполнения). **Владельцы:** `@DO`
  (workflow), `@TE` (карта тестов, получена).
- **Факт, который меняет план (проверено):** `ci-guards.yml` **уже существует** как
  `chat-guards.yml` (`check-chat` + `guard-secrets`), и `ci-tests.yml` держит **те же два джоба
  ещё раз** (`check-chat`, `guard-secrets`) плюс `test` и `front-e2e`. То есть guard'ы уже
  дублируются — остаток DO-032, и он опаснее, чем «бэкенд и фронт в одном файле».
- **Порядок (по `@DO`):** (a) свести guard'ы в один файл (`chat-guards.yml` → `ci-guards.yml`,
  джобы как есть); (b) `ci-tests.yml` → `ci-backend.yml` (`test`) + `ci-front.yml` (`front-e2e`);
  (c) переносить джоб за джобом **с негативным тестом** (фейковый секрет в файле задачи →
  `guard-secrets` краснеет → убрать).
- **Почему именно так:** без шага (a) получим **три** места с секрет-сканером вместо одного.
- **Карта тестов (`@TE`):** `ci-tests.yml` = `check-chat`, `guard-secrets`, `test`, `front-e2e`;
  7 проектов в `9-tests` (Garmin+AppleHealth в `Gateways`, не `ApiGateway`); деление по слоям
  нельзя, по артефактам можно; `E2E.Tests` остаётся в backend как «сквозной».
- **Критерий:** guard'ы ровно в одном файле с негативным тестом; `test` и `front-e2e` в разных
  workflow; ни один джоб не потерян (сверка списка до/после).

### PDR-17. Пакетный вердикт координатора

- **Статус:** обсуждается. **Владелец:** `@TL`.
- **Зачем:** 5 раундов «правка → push → прогон → вердикт» на один класс; вердикт по строке
  дороже вердикта по плану.
- **Предложение:** `@TL` проверяет план класса («три инфра-правки одним пакетом — вердикт
  один»), артефакты — по списку, а не по одному.
- **Плюсы:** минус 3 из 5 раундов; меньше переключений контекста у обеих сторон.
- **Минусы:** если в пакете одна плохая правка, откатывается пакет; нужен критерий «что
  считается пакетом» и кто отвечает за дефект внутри.
- **Критерий:** `cycle` по роли до/после; число раундов на класс.

### PDR-18. Пилот: субагент на board-cleanup (DO-022)

- **Статус:** согласовано с `@DO` (22:25), запуск — из его треда. **Владелец:** `@DO`.
- **Зачем:** проверить на безопасном классе (сеть + отчёт, ноль пересечений с workflow),
  где субагенты реально ускоряют, а где нет.
- **Ограничения (по `@DO`, из личного опыта):**
  1. **Бюджет запросов в брифе:** «не больше N страниц/запросов», и что делать при

  2. **Отчёт обязан быть закоммичен** — по §3 незакоммиченное не существует; отчёт-файл и есть

- **Метрики пилота:** `cycle` задачи до/после, число карточек-сирот, число конфликтов/`wip`-коммитов.
- **Стоп-условие:** канонических ≠ 139 или у активной задачи пропал статус → остановиться и сказать `@TL`.

### PDR-19. Покрытие тестами: где реальная дыра

- **Статус:** обсуждается. **Владельцы:** `@TE` (политика), `@BE` (тесты сервисов), `@DO` (CI).
- **Факты (проверено по репозиторию, 02.11):** 12 сервисов + `Shared`. Тестовые проекты есть
  у **11** сервисов; в CI (`dotnet test` в `ci-*.yml`) подключены **10** — у `BC-Client` тесты
  (`Client.IntegrationTests/ClientTokenServiceTests`, 68 строк) **не запускаются** в CI.
  У `ApiGateway` тестов **нет вообще** (ни в сервисе, ни в `9-tests`).
- **Важное уточнение (моя ошибка и ошибка `@TE`):** проект `9-tests/Gateways/Gateways.IntegrationTests`
  содержит тесты **Garmin и AppleHealth** (домены приёма данных), а не маршрутизацию `ApiGateway`;
  в нём нет ни одного упоминания `clients`/`api/v1`/`health`. То есть «тесты шлюза уже есть» —
  **неверно**; название проекта вводит в заблуждение.
- **Решение (рекомендация `@TE`, поддержана):** **A для шлюза** — добавить маршрутный тест
  `/clients` (новый проект или расширение `9-tests`, не «с нуля всё»); **C для клиента** —
  сначала включить существующий `ClientTokenServiceTests` в `ci-client`, затем контрактные тесты
