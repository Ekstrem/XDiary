# Памятка: способы достижения идемпотентности (справочник @BE)

> Для BE-051 и любых «повтор команды создал дубль». Формализация: **операция идемпотентна, если повторное
> применение к тому же состоянию даёт то же состояние и тот же результат, без дополнительного побочного эффекта**
> (`f(f(x)) == f(x)`).
>
> По HTTP (RFC 9110 §9.2.2): **идемпотентны** `GET`/`HEAD`/`PUT`/`DELETE`/`OPTIONS`/`TRACE`; **не идемпотентны**
> `POST` и `PATCH`. Поэтому «дубль на create» — это всегда неидемпотентный `POST`: сам по себе метод идемпотентным
> не сделать, идемпотентность достигается детерминированным id + уникальным индексом (п.2–3), а не «сделать POST идемпотентным».

## Сначала — отличить идемпотентность от соседнего

| Понятие | Что делает | Это идемпотентность? |
|---|---|---|
| **Идемпотентность** | свойство операции: повтор → то же состояние | — |
| **Оптимистичная версия** (`<id, version>`, `If-Match`) | контроль конкурентности: команда с ожидаемой версией, не совпала → `409` | **Нет** — защищает от потерянного обновления, а не от дубля create |
| **Ключ корреляции** (`Idempotency-Key`) | кэш «запрос → сохранённый ответ» на границе | **Нет** — это дедуп повторов на границе, а не свойство операции |

`<id, version>` — это про конкурентность (не перезаписать чужое), и прикладывать его к «дублю на create» — техническое ухищрение, а не решение.

## Способы (от естественного к «костылю»)

1. **Естественная идемпотентность (абсолютное присваивание).** `PUT /x` (полное тело), `DELETE /x`, `SET k=v`, `upsert`.
   Повтор пишет **абсолютное состояние**, поэтому не меняет результат. Никакой механики не нужно — лучший вариант, когда применим.

2. **Детерминированная идентичность (для create).** Ключевой способ сделать create идемпотентным:
   **id ресурса определяется запросом, а не генерится сервером.** Либо клиент шлёт UUID (и переиспользует при retry),
   либо id выводится детерминированно из содержания (`hash(clientId, kind, normalizedName)`).
   Повтор той же команды → тот же id → «ensure-exists» → дубля нет.

3. **Уникальный индекс на бизнес-ключе (страховка в БД).** Даже при детерминированном id БД должна **гарантировать**:
   `UNIQUE (clientId, kind, normalizedName)`. Тогда «две одинаковые» физически невозможны, а не «надеемся, что не случится».
   Insert либо проходит один раз, либо `ON CONFLICT DO NOTHING`/`DO UPDATE`.

4. **Дедупликация событий (event-sourcing).** Событие несёт стабильный id (`aggregateId` + `eventId`/уникальный `eventId`);
   append в event store идемпотентен (unique index / upsert). Повторная публикация того же события — no-op.
   Это «родная» идемпотентность в event-sourced системах.

5. **Оптимистичная версия** (`<id, version>`, `If-Match`) — конкурентность, **не** идемпотентность. Полезна для UPDATE,
   чтобы не перезаписать чужое изменение.

6. **Ключ корреляции** (`Idempotency-Key`) — кэш «ключ → ответ» на границе. Честно: это **повтор/дедуп запросов**,
   а не идемпотентность операции. Плюс — работает с любым бэкендом. Минус — ключ надо хранить (TTL, чистка),
   согласовывать между сервисами, «вернуть тот же ответ» ≠ «перевыполнить». Костыль в смысле «маскирует
   неидемпотентную операцию, а не чинит её».

## Для BE-051 (дубль «костюмчика» на `POST /api/v1/catalog`)

Правильная пара — **2 + 3**:
- команда несёт стабильный `id` (клиентский UUID, переиспользуется при retry) либо `id = hash(clientId, kind, name)`;
- `UNIQUE (clientId, kind, normalizedName)` — физическая гарантия «дубля нет».

`<id, version>` и `Idempotency-Key` здесь не решение (первое — про конкурентность, второе — про повторы на границе).

## Рекомендация по умолчанию

- **create** → детерминированный id + уникальный индекс (п.2 + п.3);
- **update/delete** → естественная идемпотентность (`PUT`/`DELETE` абсолютные), при необходимости + версия для конкурентности (п.5);
- сквозной повтор на границе → ключ корреляции (п.6) как **дополнение**, а не замена.
