## 1. Шесть механизмов (каждый — проверяемый)

### 1.1. Утверждение = артефакт в том же сообщении
О состоянии кода/контракта/прода пишу **только с командой и её выводом** (`git show <sha>:<файл>`, `curl -s -o /dev/null -w '%{http_code}'`, `grep -cF`), и с **временем проверки**.
Нет артефакта — нет утверждения. *Метрика: число утверждений, опровергнутых ролью (цель 0).*

### 1.2. Приёмка только по квитанции с числами
Карточка закрывается, когда есть `rc` **и** строка с числами («проверено полей 2, затерто 0», «74/74 + 4/4 = 78 из 82»). Слова «всё зелёное» приёмкой не считаются. *Метрика: отозванных приёмок (цель 0).*

### 1.3. Прод — только чтение
Разрешено: `GET /health`, `OPTIONS`-preflight, версия фронта, `GET` без записи. **Запрещено:** любой `POST/PUT/DELETE`.
Если дефект виден **только** на проде — это дефект паритета контуров, задача @DO, а не моя проба. *Метрика: write-операций TL на проде (цель 0).*

### 1.4. Решённое не переоткрывается
Перед вопросом владельцу — читаю `OWNER-DECISIONS.md`. Вопрос допустим, только если (а) решения нет, (б) оно противоречит факту, (в) есть срок/цена выбора.
**Не больше одного вопроса владельцу за сообщение.** *Метрика: вопросов владельцу в сутки (цель ≤ 1, только блокирующие).*

### 1.5. Однa карточка — один источник правды
Контракт/поведение меняются **только** через карточку с тремя полями: что меняется, кто владелец, какой гейт это поймает. Второй источник (чат, память, «TL сказал») не действует. *Метрика: разворотов одного контракта (цель ≤ 1).*

### 1.6. Диспетчеризация вместо простоя
Каждый час — таблица «дорожка → кто → что ждёт → блокер». Роль без задачи получает задачу в тот же час; я не жду пассивно. *Метрика: роле-часов простоя > 15 мин (цель 0).*

## 2. Журнал ошибок (errata) — веду открыто

Каждая опровергнутая гипотеза — запись: **что утверждал / что оказалось / чем проверено / что изменил в методе.**
Журнал: `5-tech-backlog/tl/ERRATA.md`. Цель — не «не ошибаться», а **не повторять один и тот же класс ошибки дважды**.

## 3. Что делаю прямо сейчас (не обещания, а шаги)

1. `OWNER-DECISIONS.md` — создан, читается перед вопросами;
2. `QUALITY.md` (этот файл) — создан, механизмы 1.1–1.6 действуют с этого коммита;
3. `ERRATA.md` — заведу и внесу семь случаев из §0, чтобы класс ошибок был виден.

## 4. Как это ускоряет выпуск (рамка владельца: изоляция + скорость)

| Механизм | Что ускоряет |
|---|---|
| 1.1 и 1.2 | меньше раундов «сказал → проверили → оказалось иначе» (сегодня 4 таких раунда = часы) |
| 1.3 | прод не ломается пробами (сегодня: `500` на 20 мин + потеря env) |
| 1.4 | не переоткрываются решённые вопросы (сегодня: час на «какой канал OTP») |

| 1.6 | роли не простаивают, деплой не ждёт «пока TL заметит» |
