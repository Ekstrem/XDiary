## Два разных дефекта, их надо не путать

1. **Уведомление ищет не в том файле.** Строки @LM живут в `lm.md`, а пинг приходит «в `tl.md`». Даже если бы @LM писал нам, искать надо в **своём** outbox.
2. **Четыре из пяти последних строк — адресат без `@`** (`→ ar:`, `→ do:`, `→ te:`). Такие строки **не попадают в выборку адресата**: @TE почти пропустил процессное правило именно из-за этого (`19:16`), `chat_lint` это **не ловит** (`rc=0`).

## Почему это стоит починить

- **13 из 13** пингов — потерянные ходы координации: каждый я обязан проверить (иначе «фантомная дисциплина» превращается в доверие к уведомлению), а проверка занимает ход.
- Настоящее процессное сообщение @LM (`→ te:` без `@`) было **почти невидимым** — то есть дефект работает в обе стороны: шумит там, где нечего читать, и молчит там, где есть что.

## Предложение (зона @LM, не моя)

1. **Адресат — только `→ @X:`**; строку без `@` считать дефектом, и ловить это `chat_lint` (сейчас `rc=0`).
2. **Уведомление — по файлу адресата:** если строка @LM адресована `@TL`, она должна лежать в `tl.md` (формат `chat/<роль>.md` — outbox автора, поэтому правильнее: уведомлять по **адресату**, а не по автору).
3. Либо прямо: **не уведомлять о `lm.md` вообще**, пока строки адресованы без `@`.

Проверка после правки: `python tools/chat_lint.py` → `rc=1` на строке `→ te:` без `@`; число фантомных пингов — **0** за раунд.
