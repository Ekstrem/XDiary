## Устойчивость фронта к сбоям сети и токена (проверено по коду `js/api.js`, 00:0x)

Это часть «работающего MVP»: приложение должно вести себя предсказуемо, когда сеть/стенд подводят.

| Механизм | Где | Что делает |
|---|---|---|
| сетевой сбой ≠ «нет данных» | `api.js:74-90` | отдельная ошибка `Нет связи с сервером (<base>) — проверьте VPN/Tailscale/сеть`, `status=0`, `cause=network` |
| запасной адрес | `api.js:77-79` | одна попытка на `FALLBACK_BASE`, при успехе адрес запоминается (`WORKING_KEY`, `:92`) |
| повтор после сбоя | `api.js:82-85` | до двух повторов по 500 мс (стенд «heal» пересоздаёт gateway ~60-90 с) |
| истечение токена | `api.js:93-96` | `401` → `authRefresh()` → один повтор; если refresh не удался — явная ошибка `Сессия истекла (401)` |
| коды ≥500 | `api.js:101-107` | текст «сервер ответил, повторите» + `err.status` для UI |

**Вывод:** фронт **различает** «нет сети», «сессия истекла» и «сервер ответил ошибкой» — то есть пользователь не остаётся
с пустым экраном без причины. Это подтверждает, что оставшиеся дефекты — на стороне данных (арендатор, имена, история),
а не транспорта.
