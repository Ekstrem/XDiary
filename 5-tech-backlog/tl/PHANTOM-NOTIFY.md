# PHANTOM-NOTIFY — фантомные уведомления о сообщениях в чате (как проверять за 5 секунд)

## Что наблюдается

Внешние уведомления вида «в чате X.md есть сообщение от РОЛИ — N шт. (последнее <дата время>)» **не соответствуют** файлам:
числа и метки не совпадают ни с одной строкой. Класс: уведомление собирается из **упоминаний** роли в чужих outbox-ах
и подставляет случайную метку времени.

## Проверка за 5 секунд (копировать)

```bash
git fetch origin main -q && git log --oneline -1 origin/main && git show origin/main:5-tech-backlog/chat/<файл>.md | grep -cF "<дата время>"
```

Если `0` — уведомление фантомное, файлы не трогать. Если `>0` — читать по позиции в файле, а не по метке (метки бывают
из будущего: в `ar.md` встречались `2026-11-08`, `2026-11-16`, при этом порядок строк достоверен).

## Вывод (для процесса)

1. **Источник правды — файлы в `git`**, а не уведомления и не авто-сводка.
2. Метка времени в строке **не гарантирует** монотонность; позиция строки — гарантирует порядок.
3. Если уведомление расходится с файлом — это **не повод что-то править**; это повод записать расхождение сюда.
4. @DO ранее проследил класс до **драйвера сессии** (лаг ~4 часа, немонотонные метки); отдельной карточки на это нет,
   потому что драйвер — вне репозитория. Здесь фиксируется **приёмочный способ проверки**, а не дефект продукта.

## Шаблон №3: «метка есть, но не там и не тогда» (2026-11-06, 15-й случай)

Уведомление: «`tl.md`, от LoopMaker, `2026-11-06 21:13`».
Проверка: в `tl.md` метки `21:13` — **0**; в `lm.md` — метка `21:13` **есть**, но это `2026-11-14 21:13`, адресовано `@AR`
и про формулировку канона ADR (уже обработано @AR).

**Вывод:** метка существует, но **в другом файле и с другой датой** ⇒ для `tl.md` это фантом, а не «снимок устарел».
Отличие от случая `23:05` (@TE/@AR): там метка была в том же файле и той же датой, просто позже пуша.

**Как проверять (две команды, обе обязательны):**

```bash
git show refs/remotes/origin/main:5-tech-backlog/chat/tl.md | grep -cF '2026-11-06 21:13'   # 0
git grep -c '21:13' refs/remotes/origin/main -- 5-tech-backlog/chat/*.md                    # где-то есть, но иная дата/адресат
```

**Правило:** фантом подтверждён только если совпали **файл + дата + время**; совпадение одного времени — не доказательство.

## Шаблон №4: файл и время верны, **автор другой** (2026-11-06, 16-й случай)

Уведомление: «`tl.md`, от LoopMaker, `2026-11-06 21:46`».
Проверка: в `tl.md` на этой метке **6 сообщений — все от @TL** (`→ @AR`, `→ @BE`, `→ @FE`, `→ @EX`), ни одного от @LM.

**Вывод:** совпали файл, дата и минута, но **автор указан неверно** ⇒ фантом, который проверка «метка есть» не ловит.

**Итоговое правило (четыре признака):** фантом подтверждён только при совпадении **файл + дата + время + автор**.

### Фантом 2026-11-14 01:00: «в `tl.md` сообщение от LoopMaker `2026-11-12 12:55`»

| Проверка | Результат |
|---|---|
| `git show origin/main:5-tech-backlog/chat/tl.md` \| `grep -c '2026-11-12 12:55'` | **0** |
| то же по `chat/lm.md` | **0** |

Реальные сообщения `@LM` рядом: `06:42` и `14:53` — «команда стоит: 7/7 ролей простаивают > 15 мин» (шаблонная нагайка), и `15:35` — «[пинг — проверка работы чата]». На `14:53` нагайка была **по факту**: последние строки ролей — `te 14:05`, `do 14:06`, `be 22:25` (предыдущие сутки), `fe 22:50`, `ar 03:00` — то есть тишина 47 минут. Но уже через час роли работали: `be 15:54` (`BE-099`), `do 15:59`, `te 14:05` (`TE-107`).

**Вывод:** сигнал «роль простаивает» измеряет **время**, а не **причину**: в 14:53 роли стояли потому, что все их карточки ждали решений, а не потому, что они не работали. Для процесса это значит: нагайка должна нести **чье именно действие разблокирует простой**, иначе она превращается в шум (что и произошло — две почти идентичные строки `06:42` и `14:53`).
