# P0-PRIVACY: один класс, три карточки — данные пользователей не разделены (@TL, 2026-11-06 00:05)

## Суть

Во всех трёх случаях **одна причина**: сервис не знает, чьи данные отдаёт. Аутентификация при этом **работает**
(снаружи 401 через APIM, в сервисах fallback-политика). Дыра не в «пускает без токена», а в том, что **токен не
используется для разделения**.

| Карточка | Механизм | Что видит пользователь |
|---|---|---|
| **`BE-083`** | `AnalyticsPrecomputeService.cs:29` тянет `internal/journal/records` → `ListAllAsync` (**все** записи), в `JournalRecord` **нет** `ClientId`, `AnalyticsSnapshot` — глобальный singleton, `AnalyticsController` **без `[Authorize]`** | агрегаты (топы, распределение, корреляции) по **чужим** записям — и те же числа, что у всех |
| **`BE-084` (a)** | `BC-Catalog`: `ClientId` — **0 файлов** в сервисе | чужие позиции каталога (`photo`/`notes`/`fantasyPartner`) видны и **редактируемы** |
| **`BE-084` (b)** | `BC-SomaticSeries`, `BC-DailyMetrics`: `ClientId` — **0 файлов** | общая лента пульса/HR/body-battery и сна/стресса |
| **`BE-084` (c)** | `PortabilityController.cs:25-27` → `GetDocumentQuery()` **без параметров** | `GET /api/v1/portability/document` отдаёт **CSV другого клиента** |

Доказательства лежат в самих карточках: пути файлов, номера строк, grep-выводы. Это не «кажется», это код.

## Порядок, который предлагаю (по цене и по риску)

1. **`BE-084(c)` Portability — самый дешёвый и самый явный:** `GetDocumentQuery(Guid clientId)` + `sub` из токена в контроллере; отдавать только свой документ (иначе 404). Одна карточка, одна миграция.
2. **`BE-084(a)` Catalog:** добавить `ClientId` в модель + миграция; писать из `sub`; фильтровать чтения; чужой `id` → 404.
3. **`BE-084(b)` Somatic/DailyMetrics:** то же, но данных больше — нужна миграция с планом для старых строк (у них владельца нет).
4. **`BE-083` Analytics:** после того как журнал станет per-client, снимок строить по `clientId`; плюс `[Authorize]` на контроллере и закрыть `POST events`.

## Один вопрос, который надо решить до миграций (владельцу)

У **существующих** строк в этих сервисах владельца нет. Варианты:
- **(а)** `ClientId = NULL` и такие строки **не отдаются никому** (безопасно, но данные пропадают из UI);
- **(б)** backfill по известному источнику (если он есть — например, из журнала/логов);
- **(в)** обнулить тестовые данные и начать с чистого состояния (dev — тестовый контур).

Это решение **про данные**, поэтому его принимает владелец, а не роль.

## Почему это блокирует «MVP для реального пользователя»

Пока данных не разделены, любой второй пользователь видит чужое. Для дневника это не «недоделка», а недопустимое
состояние — и оно не лечится фронтом.
