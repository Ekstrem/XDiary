# Чат ролей (outbox-модель)

Каждая роль пишет **только в свой файл** (свой outbox) — поэтому одновременная запись в один файл невозможна и merge-конфликтов нет. Читать нужно **все** файлы и брать адресованные тебе.

| Файл | Роль |
|---|---|
| `be.md` | back-end |
| `do.md` | devops |
| `fe.md` | front-end |
| `te.md` | tester |
| `ar.md` | architect |
| `tl.md` | TechLead |
| `ex.md` | владелец (Ekstrem, `@EX`) |
| `lm.md` | LoopMaster — процессная роль (`@LM`): статусы, правила, проверки, миграции |
| `po.md` | Product Owner (пользователь) |

## Авто-сводка
`_dialogue.md` — **генерируется автоматически** (GitHub Action `Merge role chat`) из всех outbox-файлов, отсортированный по времени, и **коммитится** в репозиторий. Руками не редактировать (правки перезапишутся при следующем merge).

## Формат сообщения
```
- [YYYY-MM-DD HH:mm] → @КОМУ: текст
```

Пример:
```
- [2026-10-30 15:20] → @FE: VPS-1 поднят, шлюз на :8080, жди TLS
- [2026-10-30 15:25] → @PO: нужен домен для TLS или Tailscale?
```

## Правила
1. Пишешь — **только в свой outbox** (никогда в чужой).
2. Читаешь — сканируешь все файлы, фильтруешь `→ @<твоя роль>`.
3. Вопрос адресуется тегом: `@BE`/`@DO`/`@FE`/`@TE`/`@AR`/`@TL`/`@PO`/`@LM`/`@EX`. **Владельца тегаем `@EX`** (его outbox — `ex.md`, читаем как все остальные).
   - **`@EX` — только вопросы и решения.** Статусы, подтверждения и «принято» владельцу **не пишем** (решение 07.11: «этот чат со мной только для вопросов, не спамь»). Нужен ответ — пишем один конкретный вопрос; не нужен — молчим, сводка идёт в отчёте TL.
4. Блокер → `@TL`; вопрос вне компетенции → `@PO`.
   - **`@PO` — только про продукт:** что делать/не делать, приоритет, состав релиза, противоречие в требованиях, приёмка фазы. Всё остальное — инфраструктура (PAT, Secrets, зависшие CI-раны, деплой), перф-баги, синхронизация тестов, борда, роли — **зона @TL и ролей**, PO в это не зовём.
   - **Статус PO получает редко и пачкой:** при закрытии фазы или по запросу. Не пересылать PO каждый промежуточный прогон CI и не эскалировать «у меня красный job» — это шум. (Замечание владельца 2026-11-05: за день ушло 8 сообщений, из них продуктовых — 2.)
   - **`@LM` — только процесс:** правила, линтеры, миграции статусов, `AGENTS.md`/`STATUSES.md`, проверки CI. **Статусы задач и прогонов ему не адресуем** — это шум: у LoopMaster нет продуктовых решений, а очередь чата растёт.
5. TechLead раз в час читает все outbox'ы и эскалирует неотвеченные.
- **«Не дошло сообщение» — сначала сводка, потом транспорт.** Проверь `_dialogue.md` и
  фильтр по роли (`chat_inbox`), потому что «роль не видела» чаще означает потерю **сводки**,
  а не доставки; транспорт проверяется логом моста (`→ role: ...`).
6. **Адресаты — через `+`.** Канон: `→ @DO + @TE: …` (один адресат — тоже канон). Мост (`lib/parse.js`) делит и по `+`, и по `/ , ;` — но `/` до 02.11 **не** делился и сообщения с `@TL/@TE` уходили в никуда; поэтому канон `+`. Отдельно: до 03.11 `merge_chat.py` не делил адресатов в **сводке**, из-за чего роль-фильтры в мониторинге их не видели (доставка при этом работала).
   - **Описывая инцидент, тоже не цитируй** — пиши «фрагменты скрыты». Второй заход был именно такой: сообщение о первом инциденте само процитировало хвосты (04.11, `tl.md`).
   - Сравнивать значения — `python LoopMaker/tools/keycmp.py --a-env A --b-env B`: «совпадают/нет» + `len` + `sha256[:8]`, без значений.
   - Автопроверка: `python LoopMaker/tools/check_secrets.py --config loop.config.json` — ловит и `assign`-паттерны «ключ = значение», и обрезанные хвосты ключей.

## Зачем so
- Нет конкуренции за файл (1 писатель на файл).
- Асинхронно, в git — агенты читают при следующем запуске.
- История сообщений версионируется.
8. **Границы по CI:** TL смотрит только **результат** — «зелёный/красный» по задаче и что это значит для приёмки. **Диагностика CI — @DO:** почему run в `queued`, `concurrency`, минуты/раннеры, PAT/Secrets, перезапуск workflow. TL не разбирает инфраструктуру и не эскалирует её владельцу — это делает @DO, если реально нужен доступ владельца. (Замечание владельца 2026-11-05: я лез в `check-runs`/`concurrency`/billing, хотя это зона @DO.)
   - **Отменённый run ≠ доказательство:** результат `cancelled` не считается ни зелёным, ни красным для приёмки — валиден только прогон, завершившийся сам (`success`/`failure`). (DO-023)
9. **Меньше чата.** Одна строка на роль за цикл работы; статус «взял/делаю» — только в задаче (Статус:), не в чате. Не дублировать одно и то же разным адресатам и не писать «подтверждаю принятое». Если сообщений накопилось много — это сигнал, что координация идёт через чат вместо задач. (Замечание владельца 2026-11-05: очереди ответов у ролей, слишком много переписки.)

## Шкала времени

Метка `[YYYY-MM-DD HH:mm]` — **часы машины** (MSK), без сдвига. Печатать её:
`python tools/chat_lint.py --next-stamp`. Не писать по памяти.

**История:** до 07.11 метки писали «по памяти» и уехали вперёд на ~106 часов (в чате `03:25`,
на машине `17:25`, в GitHub `13:52Z` — всё про один прогон). Это ломало порядок и любой
разбор «сколько шли тесты / сколько задача в паузе». Исправлено: `chat_time.shift_hours = 0`,
старые метки не переписаны (на них завязано состояние моста), поэтому в отчёте линтера
старые нарушения порядка — ожидаемый исторический шум.

## Правило пуша (единое для всех ролей)

Полное правило — `AGENTS.md` §5.5, подробности и фолбэк — `docs/CI-RULES.md`
(раздел «Пуш и транспорт»). Кратко:

1. транспорт чинится **одной настройкой машины** (`core.sshCommand` → системный OpenSSH),
   проверка — `git ls-remote --heads origin main`;
2. синхронизация — `python tools/git_sync.py --role XX`; `wip` берёт **только зону** роли;
3. «дошло» проверяется **после `fetch`**: `git rev-list --count origin/main..HEAD` = 0;
4. запрещено: `--force`, ссылка на SHA без `merge-base --is-ancestor`, токены и пути
   к хранилищу в документах.

Пути к личным хранилищам секретов в этом репозитории **не публикуем** (он публичный);
для этого есть `python tools/check_rule_docs.py`.
