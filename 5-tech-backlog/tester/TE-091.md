# TE-091. Приёмка `BE-090`: OTP не должен утекать в ответе `POST /api/v1/clients`

- **Статус:** На проверке
- **Проверяет:** @TL
- **Роль:** @TE
- **Источник:** `chat/tl.md` `2026-11-06 21:18` (`→ @TE`): «приёмка после выкатки — за тобой: (1) `POST /api/v1/clients`
  на проде — в теле **нет** `otpCode` (после выкатки `BE-090`)…»; сам дефект — `BE-090` (P0)

## Проблема

`POST /api/v1/clients` с **уже существующим** номером возвращал `200`, тот же `id` и **снова `otpCode`**
(`otpAttempts: 0`). То есть сервер выдаёт свежий код для любого известного номера, а
`POST /clients/{id}/verify` с этим кодом даёт **JWT владельца** — доступ к чужому дневнику. Это не «лишнее поле»,
это контроль доступа.

Приёмка по этому пункту упиралась в ручную проверку «посмотреть ответ глазами» — а такой проверки у нас нет в
машиночитаемом виде.

## Что сделано

`9-tests/scripts/check_otp_leak.py` — проверяет **тело** ответа, а не только код:

1. ищет `otpCode` / `otp_code` / `otpAttempts` / `otpExpiresAt` / `otpExpires` — рекурсивно по JSON
   (в т.ч. вложенные: `{"client":{"otpExpiresAt":…}}`);
2. если тело не JSON — ищет по тексту (`otpCode=`, `otpCode :`), чтобы «не разобрали» не выглядело как «чисто»;
3. `rc=1` при утечке с объяснением последствия («по этому коду можно получить JWT владельца»);
4. `rc=2`, если нет `--base` или стенд недоступен — «не измерено» ≠ зелено.

`--selftest` **7/7**: дефект `BE-090` (`200` + `otpCode` + `otpAttempts`) → `rc=1`; чистое тело → `rc=0`;
вложенная утечка → `rc=1` с путём `client.otpExpiresAt`; `400` с OTP в теле → `rc=1`; не-JSON с `otpCode` → `rc=1`;
пустое тело `401` → `rc=0`.

## Офлайн-проверка на факте дефекта

```
--status 200 --body '{"id":"c1","otpCode":"123456","otpAttempts":0}'
  → rc=1  «OTP-полей: 2 ['otpAttempts', 'otpCode'] | нарушено: 1»
--status 200 --body '{"id":"c1","version":1,"verified":false}'
  → rc=0  «OTP-полей: 0 | нарушено: 0»
без --base → rc=2 «не измерено»
```

## Приёмка на проде после выкатки (`single-766e59e`, REF `7c00e211`): **ПРОЙДЕНА**

```
POST /api/v1/clients → 200 | тело 155 симв.
поля: id, version, phone, otpExpiresAt, verified
otpCode: НЕТ | otpAttempts: НЕТ
гейт: rc=0  «OTP-полей: 0 | разрешено контрактом: 1 ['otpExpiresAt'] | нарушено: 0»
```

**И здесь была моя ошибка критерия, а не дефект продукта:** `otpExpiresAt` я держал в `LEAK_FIELDS`, хотя
`04-architecture/api-index.yaml:177` прямо разрешает это поле в теле `200` («новый номер: тело id, version, phone,
otpExpiresAt, verified, delivery»). По метке времени JWT не получить. Исправлено:

- `LEAK_FIELDS` — только `otpCode` / `otp_code` / `otpAttempts` (по ним получают доступ);
- `CONTRACT_ALLOWED` — `otpExpiresAt` / `otpExpires`: печатается `notice`, в нарушения **не** идёт;
- `--selftest` **10/10** (добавлены кейсы: «`otpExpiresAt` разрешён контрактом — не красный», «факт прода после
  выкатки: тело без кода», «код вернулся вместе с `otpExpiresAt` — снова красный»).

**Dev при этом по-прежнему `rc=1`** — там старый образ (`otpCode` + `otpAttempts` в ответе, код `000000`).
То есть гейт теперь различает «фикс выкачен» (прод, `rc=0`) и «фикс не выкачен» (dev, `rc=1`) — а не краснит
исправленный код из-за разрешённого контрактом поля.

## Чему это меня учит (запись для себя)

Критерий приёмки — это тоже артефакт, и он бывает **неверным**. Когда гейт краснит код, который прошёл
ревью контракта, первым делом надо читать контракт (`api-index.yaml`), а не требовать правку в сервисе.
Иначе «зелёный гейт» начинает диктовать продукту неверное поведение.
