# TE-037: `change-pin` и `remove-pin` переписать под локальный PIN (MVP-канон ADR-021 п.3)

- **Статус:** ToDo
- **Приоритет:** P1 (единственный способ убрать третье падение гейта: `remove-pin` красный на серверном assert)
- **Источник:** @TE 2026-11-02 19:17 — `change-pin.spec.js` построен на серверном PIN (`POST /privacy/pin/set`, `POST /privacy/token {pin}`); канон MVP — **локальный** `window.Pin`, серверный `/privacy/pin/*` = legacy. Подтверждено вердиктом **AR-009 = B (legacy)** и ADR-021, раздел «PIN: серверный vs локальный»
- **Зависимости:** AR-009 (решён), ADR-021, FE-025/FE-029 (локальный замок), FE-031 (0.66)
- **Проверяет:** @TL (TechLead)

## Задача — два спека, оба переводятся на локальный PIN
### 1. `change-pin.spec.js`
Смена **локального** PIN через UI Настроек (`window.Pin.setPin` / экран смены), проверить:
1. новый локальный PIN пускает в журнал (`unlockIfLocked` с новым значением);
2. старый локальный PIN больше не пускает;
3. после смены `Pin.hasPin()` = true; в `finally` возвращается исходный PIN (чистота стенда).

### 2. `remove-pin.spec.js`
1. **Серверный assert `pin/has` убрать из гейта:** серверный блок — `describe.skip` с причиной «серверный PIN — legacy (ADR-021 / AR-009), вне MVP».
2. Проверять **локальное** состояние: `window.Pin.hasPin()` = true до снятия и **false после** снятия через UI; журнал после снятия открывается без PIN-экрана.
3. Серверные вызовы `/privacy/pin/*` не должны быть условием прохождения спека.

## Критерии приёмки
- [ ] Ни `change-pin`, ни `remove-pin` не проверяют серверный `/privacy/pin/*` как продуктовый контракт.
- [ ] `remove-pin` проверяет локальный `window.Pin.hasPin()` до/после снятия.
- [ ] Пометки `legacy` в шапках сняты там, где спека снова проверяет MVP-путь; где остаются — указана причина и ADR.
