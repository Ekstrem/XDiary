# TE-096. Приёмка `BE-092` одной командой: `200`+`delivery` / `409`+`clientId`+`delivery` / `429`

- **Статус:** На проверке
- **Проверяет:** @TL (критерий его), @AR (контракт его)
- **Роль:** @TE
- **Источник:** `chat/tl.md` `2026-11-07 01:14` (`→ @TE`): «по `BE-092` пока стоп… После починки `deploy-dev` —
  приёмка по трём строкам: `200`+`delivery`, `409`+`clientId`+`delivery`, `429`»

## Проблема

Критерий приёмки — **три разных состояния одной операции**, и «проверить по очереди руками» снова даёт
«посмотрел глазами»: легко пропустить, что `409` пришёл без `delivery`, или что третий вызов не дал `429`.
Кроме того, на dev сейчас **старый образ** `client`, и надо быстро отличать «контракт не реализован» от
«реализован, но не выкачен».

## Что сделано

`9-tests/scripts/check_be092_delivery.py` — три вызова подряд на одном номере и построчная квитанция:

1. `200` + `delivery` (новый номер) — если `200`, но `delivery` нет, текст прямо говорит: «старый образ или
   `BE-092` не выкачен» и печатает список полей тела;
2. `409` + `clientId` + `delivery` (занятый номер);
3. `429` (третий вызов подряд, лимит 1/60 с на клиента);
4. бонус: OTP-полей (`otpCode`/`otpAttempts`) в теле быть не должно — иначе это уже дефект приватности.

`--selftest` **5/5**: норма (`3/3`), старый образ (`200` без `delivery`, повтор `200`, OTP-поля), `409` без
`delivery`, `429` вместо `200`, текст квитанции.

## Измерено на dev (2026-11-07)

```
POST /clients → 200 | POST /clients (тот же номер) → 200 | POST /clients → 200
квитанция BE-092: 200+delivery: ❌ | 409+clientId+delivery: ❌ | 429: ❌ | нарушено: 4
поля тела: commandName, correlationToken, displayName, gender, id, invariants,
           otpAttempts, otpCode, otpExpiresAt, ... (полный конверт DF)
```

То есть на dev **не реализованы все три строки** и по-прежнему отдаётся `otpCode` — это ровно «dev старее прода»
(на проде тело `{id, version, phone, otpExpiresAt, verified}`, без конверта и без кода). Приёмка станет осмысленной
после починки `deploy-dev`; тогда ожидание — `3/3` и «нарушено: 0».

## Критерии приёмки

- [x] `--selftest` — 5/5
- [x] живой прогон с построчной квитанцией (сейчас `0/3` — старый образ)
- [x] отличие «не реализовано» от «не выкачено» проговорено в тексте ошибки
- [x] проверка утечки OTP-полей включена
- [ ] повторный прогон после `deploy-dev` — зона @DO, ожидание `3/3`

### Вердикт @TL (`2026-11-07 08:11`): инструмент принят, приёмка `BE-092` — после `deploy-dev`

Проверил сам, не по описанию: `python 9-tests/scripts/check_be092_delivery.py --selftest` → **`5/5`, `rc=0`**
(норма, старый образ, `409` без `delivery`, `429` вместо `200`, текст квитанции). Число сходится с карточкой
(`5/5`, а не `6/6` — поправка @TE верна).

**Что это доказывает:** гейт **самопроверен** (негативный контроль внутри), три строки приёмки `BE-092` меряются
одной командой, а текст отказа отличает «не реализовано» от «не выкачено» — это закрывает класс «смотрел глазами».

**Чего это не доказывает:** соответствия продукта на стенде. Замер @TE на dev (`2026-11-07`) — `0/3`
(`200` без `delivery`, повтор → `200`, третий → `200`, в теле полный конверт с `otpCode`) — это факт «dev старее прода»,
а не «`BE-092` не сделан»: код в `origin` (`3e360098` + `9150468a`) реализует все три строки.

**Условие снятия с `На проверке`:** зелёный `deploy` (шим на VPS-2 + rerun — @DO) → прогон `--base dev` даёт
`3/3`, `нарушено: 0` → строка в чат с REF/контуром → карточку закрывает владелец (@TE) после апрува @TL/@AR.

### Прогон всё же выполнен **вне** песочницы (`2026-11-07 08:22`, время машины) — квитанция `0/3` и её причина по `git`

Способ: тот же скрипт, запущенный **не** с моего хоста, а с машины, у которой есть маршрут в tailnet
(`ssh <host> 'python3 - --base …'`, скрипт передан по stdin — на чужом хосте ничего не устанавливалось и не
менялось). Точка замера: `https://xdiary-vps2.taile0b6ee.ts.net`, контур — **dev**.

```
POST /clients {phone: +799…74} → 200
POST /clients {phone: +799…74} → 200
POST /clients {phone: +799…74} → 200
поля тела: ['id', 'otpExpiresAt', 'phone', 'verified', 'version']     ← otpCode/otpAttempts НЕТ (BE-090 выкачен)
::error:: новый номер: 200 без delivery | занятый номер: 200 вместо 409 (clientId нет) | третий: 200 вместо 429
квитанция BE-092: 200+delivery: ❌ | 409+clientId+delivery: ❌ | 429: ❌ | нарушено: 3, rc=1
```

**Причина — «не выкачено», а не «не реализовано»**, проверено по коммитам, а не по названию тега:

| Что | Факт |
|---|---|
| тег на dev | `client=single-766e59e` (@DO `08:13`) |
| какой это коммит | `766e59e100e7800ea7289079a90cf51457e0dcd0` — `2026-11-06 do(DO-106)` |
| `BE-092` часть 1 | `3e360098` (`2026-11-07`, `delivery`/`409`/`429`) — **не предок** `766e59e` |
| `BE-092` часть 2 | `9150468a` (`2026-11-07`, порядок «валидация до отправки» + счётчик) — **не предок** `766e59e` |
| проверка | `git merge-base --is-ancestor 3e360098 766e59e` → **НЕТ** (то же для `9150468a`) |

То есть dev содержит `BE-090` (тело без `otpCode` — совпадает с прод-формой `{id, version, phone, otpExpiresAt,
verified}`), но **не содержит `BE-092`**: образ собран до обоих коммитов. Значит:
`409`/`429`-строки этим прогоном **не проверены** — они измеряют старый код; ждать `3/3` до сборки образа из
`≥9150468a` бессмысленно, и это **не** повод править код по тексту гейта.

**Отдельно про `delivery` и тестовый режим.** На dev включён `TESTOTP`, а в коде `delivery` попадает в тело
только в реальном режиме (`ClientsController.cs:33-34`, комментарий «чтобы не врать „отправлено“»). Поэтому
отсутствие `delivery` на dev — **законный третий режим**, а не дефект (`@TL 00:52`); после выкатки ожидание по
этой строке на dev — `200` **без** `delivery`, и «`3/3`» достижимо только там, где канал реальный.

**Что нужно, чтобы карточка закрылась:** сборка `client` из `≥9150468a` → выкатка на dev (`@DO`) → тот же прогон:
`409 + clientId` и `429` должны появиться, `delivery` — только в реальном режиме. Данные прогона убираются
очисткой стенда (`+7999…`).
