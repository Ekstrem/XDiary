# TE-024: Есть ли онбординг/идентификация клиента?

- **Статус:** Закрыта
- **Приоритет:** P1 (PO: «ощущение, что онбординга/идентификации нет»)
- **Источник:** PO 2026-11-03; ADR-018 (нет изоляции по пользователям — by design)
- **Зависимости:** —
- **Вердикт:** **онбординга НЕТ; идентификация неявная (устройство = «я»). ADR-018 (нет изоляции данных) — by design, но онбординг им не описан → это продуктовая дыра, а не баг реализации.**

## Задача
Проверить по коду и на живом dev-стенде, есть ли **онбординг клиента (идентификация)** — и что видит новый пользователь:

1. **Первый запуск на новом устройстве:** что показывается (экран PIN? device-токен?) и кто «я» в записях?
2. **Идентификация:** как приложение понимает, кто пользователь/партнёр — есть ли профиль «я» (имя, пол), приглашение партнёра, выбор «кто из пары сейчас пишет»?
3. **Сверка с ADR-018:** там зафиксировано «JWT/device-токен идентифицирует инстанс, а не юзера», `Partner` — доменные данные. Это осознанный дизайн или дыра в продукте?
4. **Что именно ломается:** сценарий «поставил приложение, одна пара, два устройства» — можно ли пройти без ручных костылей?

## Критерии приёмки
- [x] Вердикт: онбординга нет / есть частично / есть — с указанием файлов/экранов.
- [x] Если нет — шаги (что видит пользователь на новом устройстве) + лог/скрин.
- [x] Передать @TL → @AR: это баг, продуктовая дыра или by design (ссылка на ADR-018).

## Ход работы — вердикт по пунктам

1. **Первый запуск — онбординга нет.** Новое устройство: `lock()` (`8-front/js/app.js:194`) → `Api.auth.login("")` → 401 (на стенде PIN) → `showLockScreen()` (FE-007) → ввод PIN → журнал. **Ни** «кто вы», **ни** «создайте пространство/пару», **ни** «пригласите партнёра». Живое подтверждение — сценарий `9-tests/RnD/front-e2e/tests/pin-first-login.spec.js` (TE-023): чистый контекст → `#view-lock` → PIN → журнал.

2. **Идентификация — неявная, на уровне устройства.**
   - «Я» = **устройство**; единственный явный атрибут — `myGender` в настройках (`app.js:33`, `setMyGender` → `renderMyGender`), хранится **локально**; на втором устройстве его задают **вручную**.
   - Партнёр — сущность `Partner` (имя/пол/фото) = **доменные данные**, не аккаунт (ADR-018).
   - JWT/device-токен — на **инстанс** (ADR-008/018), не на человека.
   - Профиля «я» (имя/аватар), приглашения партнёра, выбора «кто из пары пишет» — **нет**.

3. **Автор записи не различается.** В записи есть `partners[]` (участники) и оргазмы «я/партнёр» (`orgasmTallyChips("me", myGender)`), но поля «автор/кто внёс» **нет** — данные общие (ADR-018).

4. **ADR-018** прямо фиксирует отсутствие изоляции данных как **by design** (пара = единое пространство). **Но онбординг (первый запуск, роли, приглашение) в нём не описан** — это не «изоляция», а UX первого запуска, и его нет. То есть подозрение PO — **не про изоляцию, а про отсутствие онбординга**: продуктовая дыра, не баг кода.

5. **Сценарий «пара, два устройства»**: работает (оба входят одним PIN → общие данные), но с оговорками: (а) «я» на каждом устройстве — вручную (пол в настройках); (б) приглашения нет — второе устройство использует **тот же PIN** (на проде он дефолтный `1234` — отдельная проблема безопасности); (в) автор записи не различается.

## Что предлагаю (для @AR/@PO)
- Либо зафиксировать в ADR-018 явно: «онбординг не требуется, пара настраивается вручную», —
- либо завести FE-задачу на минимальный онбординг: «кто я» (имя + пол) при первом запуске, «пригласить партнёра» (хотя бы объяснение, что второй входит тем же PIN), различение автора записи.

## Результат
- Вердикт принят @TL и @PO: **(а) by design** до стабильного прода. Онбординг вынесен в следующий продуктовый эпик — **AR-004 (P3)**; @AR допишет в ADR-018, что онбординга нет by design. Реальная продуктовая дыра, но **не в этом релизе**.
- Аудит опирался на код (`lock()`/`login("")`, `myGender`, `Partner`, JWT на инстанс) и на живой сценарий `tests/pin-first-login.spec.js` (TE-023).
