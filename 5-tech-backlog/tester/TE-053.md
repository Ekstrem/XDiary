## Ответ @FE по факту (проверено на `REF=bdf1cbdf`)

**Гап подтверждён, и он хуже «просто не покрыто».** Что есть сейчас:

| Спека | Что делает | Покрывает путь (1)? |
|---|---|---|
`tests/no-pin.spec.js` | **`test.describe.skip`** — legacy FE-025/026 + ADR-021: «PIN не выдаёт токен», `#tabbar` убран. В шапке: «переписать — отдельная задача» | ❌ не запускается вообще |
`tests/pin-first-login.spec.js` | (а) чистое устройство → онбординг **без** PIN-экрана; (б) после `reload` **допускаются три исхода**: `lock.or(onb).or(jr)` | ❌ только «терпит», не утверждает |

Ключевое: шаг 3 разрешает **любой** из трёх экранов и делает `unlockIfLocked` лишь в ветке «если замок виден».
Если PIN-экран перестанет появляться или не примет PIN, тест **останется зелёным** — то есть путь (1)
(«стенд с PIN, устройство без локального PIN → `login("")` → 401 → экран PIN → `login(pin)` → журнал»)
не просто непокрыт: он **разрешён быть любым**. Это тот же класс, что «зелёный на пустоте».

## Задача

Новая спека `tests/pin-fallback.spec.js`, которая **утверждает** путь (1) детерминированно:

1. **Проба стенда (внешний факт, не поведение UI):** `POST {API_BASE}/api/v1/privacy/token {pin: ""}`.
   - `401` → на стенде PIN задан, сценарий применим, идём дальше;
   - `200` → `test.skip('стенд без PIN — сценарий требует стенда с PIN')` с явной причиной;
   - иное → падать с сообщением (неизвестное состояние стенда не «пропускаем»).
2. **Состояние устройства «как после переустановки»:** `installBase(page)` + очистить **локальный PIN**
   (ключи PIN/`xdiary.legacy`), но **сохранить** `xdiary.clientId` и `xdiary.accessToken` — иначе это
   не «то же устройство без PIN», а первый вход.
3. **Утверждения:**
   - открывается **`#view-lock`** (а не онбординг, не журнал) — это и есть проверяемый факт;
   - ввод **неверного** PIN → остаёмся на `#view-lock`, виден текст ошибки, `#view-journal` скрыт;
   - ввод **верного** PIN (`PIN` из `tests/api.js`) → `expectScreen('#view-journal')`.
4. **Никаких `or(...)` в этом сценарии:** допустимый исход один.

## Критерии приёмки

1. Спека входит в `9-tests/RnD/front-e2e/tests/` и в таблицу «экран → спека» маркера `front-e2e.md`.
2. `npx playwright test tests/pin-fallback.spec.js` на стенде с PIN — **зелёный**.
3. **Негативный контроль (обязательно):** если PIN-экран спрятать (временно убрать `#view-lock` из
   разметки локально) — спека **падает**, а не пропускается. Иначе повторится история «`or(...)` терпит всё».
4. На стенде **без** PIN спека честно `skip` с причиной «стенд без PIN», а не зелёная.
5. В шапке спеки — ссылка на этот файл и на `TE-007`-линию (`FE-007`), чтобы маркер не терял трассировку.

**Исправление моей же ошибки:** в ответе @FE я сослался на `TODO-owner-decisions.md` §6 («credential без `client_id`»), но это состояние **более позднее**, а к инциденту `08:00` относится строка `10:50` — там PIN был **сброшен**, то есть «PIN не подходит» → «PIN нет вовсе». Проверка — чтением (`SELECT count(*), count(client_id), bool_or(locked) FROM pin_credential`) или поведением в CI, но не подбором.

## Перепроверка на фронте `0.90` — сценарий изменился по дизайну (`REF=f9e86dab`)

`FE-042` этап 1 убрал в `0.90` вызовы `Api.privacy.*` из `app.js`:
`git grep -n "Api\.privacy\." -- 8-front/js/app.js` → **пусто**; два оставшихся упоминания
`privacy` — **комментарии** (`app.js:240`, `app.js:2268`); версии синхронны (`0.90` / `xdiary-v90`).

**Следствие:** исходный сценарий (FE-007: «на стенде PIN есть, локально нет → `login("")` → 401 →
экран PIN») на `0.90` **исчез по дизайну** — PIN по ADR-021 / AR-009 `B` локальный, и
`ensureView()` показывает `#view-lock` только при `Pin.hasPin() = true`, а при `false` уходит
в онбординг/`afterAuth()` (`app.js:182-188`). То есть «без локального PIN показали замок»
теперь было бы **дефектом**, а не нормой.

**Что сделано:** спека переписана под текущий инвариант (не пропущена и не удалена):

1. нет локального PIN (при любом состоянии стенда) → `#view-lock` **обязан быть скрыт**
   (`toBeHidden`), приложение показывает онбординг **или** журнал — но не «через замок»;
2. после `window.Pin.setPin(PIN)` + reload → замок **есть**, неверный PIN даёт `#pin-error`,
   верный открывает журнал. Это и есть fallback-путь в текущей модели и одновременно
   **негативный контроль**: если замок перестанет появляться при локальном PIN, тест упадёт.

`node --check` по спеке → rc=0; применимость по-прежнему определяется **внешним фактом**
(ответ стенда на пустой PIN), а не наблюдением за UI; неизвестный ответ = падение, не «пропуск».

**Остаток:** прогон на стенде — из песочницы @TE недоступен (см. «Пределы песочницы агента»
в `9-tests/README.md`). На этапе 3 `FE-042` пробу `/privacy/token` придётся заменить внешним
признаком — это зафиксировано в `TE-055`.
