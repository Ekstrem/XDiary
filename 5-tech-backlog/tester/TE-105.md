## Уточнение `2026-11-12` (круг 21): что **отозвано**, а что **осталось**

@TL в `2026-11-13 01:30` отозвал свою премису `00:00`: «Аннотации показывают `5 failed из 5` и `exit code 1`
на шаге тестов — тесты **падали**, шаг итога был прав».

Согласен и уточняю механизм: у шага «Repeat run (list)» стоит **`continue-on-error: true`**
(`front-e2e-repeat.yml:146`) — поэтому его зелёный статус **не значит**, что тесты прошли: падения
незаметны в статусе шага и ловятся только шагом «Итог по спекам». Это нормальная конструкция, а не дефект.

**Отзываю** свой пункт «красный из-за разбора list-вывода»: аннотации @TL показывают реальные `5 failed из 5`,
значит разбор сработал. Остаётся один дефект — артефакты.

## Дефект (доказан): шаг артефактов не срабатывает **никогда**, когда падают тесты

```
:144  - name: Repeat run (list)
:146    continue-on-error: true        ← падение тестов НЕ делает шаг failed
:159  - name: Артефакты падения (…)    ← if: failure()  (:160)
:161    uses: actions/upload-artifact@v4
:176  - name: Итог по спекам           ← if: always(); именно он краснеет
```

К моменту `:159` ни один шаг не имеет статуса `failure` (повторный прогон — `continue-on-error`), поэтому
`if: failure()` = **false** ⇒ `skipped` ⇒ артефактов нет. Замер: **0 артефактов у пяти прогонов подряд**
(`#25`, `#24`, `#23`, `#22`, `#21`).

Отдельно важно: комментарий в workflow `:157-158` утверждает, что это уже починено 2026-11-07
(«`artifacts: 0` в #1785 … Теперь трассы поднимаются всегда»). Факт говорит обратное — класс вернулся,
потому что условие не учитывает `continue-on-error`.

**Правка:** шаг артефактов — после «Итог по спекам», с `if: failure()`; либо `if: always()` с
`if-no-files-found: warn` (тогда на зелёном прогоне предупреждение, а на красном — файлы).

## Машинная проверка (добавлена `2026-11-12`, круг 26) — `9-tests/scripts/check_ci_artifacts.py`

Чтобы класс не вернулся молча, сделал гейт в своей зоне (`--selftest` **3/3**): он ищет `upload-artifact`
под `if: failure()`, если **раньше** в workflow стоит шаг с `continue-on-error: true`.

Сейчас гейт красный **на этом самом дефекте** — квитанция:

```
::error::check_ci_artifacts: front-e2e-repeat.yml:221 — `upload-artifact` под `if: failure()`,
но раньше стоит `continue-on-error: true` (строка 146): падение тестов не пометит шаг failed,
артефакт не сохранится (класс TE-105)
квитанция: workflow 41 | нарушений 1 — блокирует (--strict)
```

То есть после правки workflow достаточно прогнать `python 9-tests/scripts/check_ci_artifacts.py --strict`
→ ожидается `rc=0` («нарушений 0»), и это **не** «зелёный на пустоте»: на текущем `origin` тот же вызов
даёт `rc=1` и указывает строку.

## Две разные проверки — не путать (уточнение `2026-11-12`, круг 29)

@TL `2026-11-13 14:00` прав: «артефакт при падении» **не доказан** — после `da4138c4` красных прогонов
`front-e2e-repeat` не было (последний — #26 зелёный). Поэтому карточка разделяет два факта:

| Факт | Как проверяется | Когда доступен |
|---|---|---|
| **A. Фикс сделан** (порядок шагов и условие) | `python 9-tests/scripts/check_ci_artifacts.py --strict` → **`rc=0`**; на текущем `origin` тот же вызов даёт `rc=1` и указывает `front-e2e-repeat.yml:221` | **сразу**, статически |
| **B. Фикс работает** (артефакт появляется при падении) | первый **красный** прогон `front-e2e-repeat` после фикса: у прогона в списке артефактов **не 0** (например `front-e2e-results` или `test-results`) | на первом красном прогоне |

Пока B не наступил, карточка **не закрывается** — даже если A зелёный. И наоборот: зелёный прогон
артефактов не создаёт **по замыслу** (`if: failure()`), поэтому «на зелёном артефактов 0» дефектом не является.

## Почему это мешает закрывать задачи

`TE-053`, `TE-054`, `TE-104` (и `BE-044`) ждут `REF` браузерного прогона. Пока красный прогон не оставляет
ни лога, ни артефакта, квитанцию собрать нечем: `check_run_receipt.py` требует **лог**, а лог недоступен
анонимно. Починка шага артефактов — предусловие для закрытия этих карточек.

### Причина названа @TL 2026-11-13 04:00 (ревизия `29ecfe535`) — **шаг артефактов стоит ДО шага, который фиксирует падение**

Из `.github/workflows/front-e2e-repeat.yml`:

```yaml
:159  - name: Артефакты падения (trace, скриншоты, error-context)
:160    if: failure()
:161    uses: actions/upload-artifact@v4
:169  # 2026-11-10 (@TE 11:45): классы падений — в лог, а не только в артефакт
:171    if: always()
:177    if: always()
```

Порядок шагов в прогоне **#25**: `Repeat run (list)` = **success** → `Артефакты падения` = **skipped** → `Классы падений` = success → **`Итог по спекам` = failure**.

- **`if: failure()` смотрит на статус ЗАВЕРШЁННЫХ шагов, а не на будущие.** К моменту `:159` ни один шаг не упал (тесты в оболочке завершились с нулём, а вердикт считает шаг «Итог по спекам» позже) ⇒ артефакты **не собираются именно в том прогоне, где они нужны**. В зелёном #24 они тоже `0` — по определению.
- **Почему это важно:** имя упавшей спеки и текст ошибки есть только в аннотациях; trace/скриншоты/`error-context` — нет. Диагностика красного прогона держится на одном источнике.

**Что нужно (зона `@DO`), варианты:**

1. **перенести** `Артефакты падения` **после** «Итог по спекам» и поставить `if: always()` + условие на результат итога (`steps.summary.outcome == 'failure'`), либо
2. оставить артефакт там, где он есть, но сделать шаг `if: always()`, а «Итог по спекам» не ронять, а писать в `$GITHUB_STEP_SUMMARY` и завершать `exit 1` **после** артефакта, либо
3. самый дешёвый: `if: always()` на `:160` — соберёт артефакты и у зелёных (шум), но красные перестанут быть «немыми».

**Критерий приёмки:** красный прогон любого класса оставляет **≥1** артефакт (`artifacts` > 0), и в нём есть trace упавшей спеки; у зелёного — артефакта нет (или есть, но это записано как принятая цена).
