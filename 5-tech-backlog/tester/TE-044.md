# TE-044: `pin-first-login` падает на шаге «телефон → OTP» (строка 35) — назвать причину

- **Статус:** На проверке
- **В работе с:** 2026-11-07
- **Причина (найдена @DO 17:45, не гипотеза):** телефон в спеке = `'+7999777' + String(Date.now()).slice(-4)` → **10 000** вариантов; при 1751 накопленных клиентах вероятность коллизии за прогон ≈ `1 - exp(-1751/10000)` ≈ **16%**. Дубликат телефона → `POST /api/v1/clients` отвечает **500** с `Npgsql.PostgresException 23505` (BE-046), UI не переходит на OTP → падение на строке 35 выглядит как «флейк». Те же 10 000 вариантов были ещё в двух спеках.
- **Приоритет:** P1 (единственное оставшееся падение: **1 из 20 = 5%** на чистом стенде, `#6`)
- **Источник:** @DO 2026-11-03 16:55 — в `#6` на очищенном стенде падение **другое**, чем в `#5`: `#5` — «Список партнёров пуст на шаге привязки…» (строка ~84, закрыто очисткой), `#6` — **шаг «телефон → OTP», строка 35**, `Received: hidden`, 44 полла, артефакт `trace.zip` приложен прогоном
- **Зависимости:** DO-044 (очистка стенда — сделана), TE-032 (счётчики/fail-fast — сделано), TE-041 (не блокирует, но @TE сначала её)

- Падает **не** привязка, а **переход к OTP-экрану**: локатор ждёт видимости `#onb-otp` (строка 35), получает **`hidden`**, 44 попытки.
- Стенд чистый (партнёров/клиентов после очистки — единицы), значит дело не в объёме данных.
- В `#5` этот шаг проходил у 8 из 10 прогонов.
- **Уточнение по коду спеки:** клик идёт по `#btn-onb-phone` (**строка 34**), и именно после него не появляется `#onb-otp`. То есть падает **первый** шаг (`телефон`), до `link-partner` дело не доходит.
- **В артефактах прогона `#6` есть всё для разбора:** `test-failed-1.png`, `error-context.md`, **`trace.zip`** (`npx playwright show-trace <файл>`) — там видно, был ли тост/ошибка от `POST /clients` или UI просто не переключил экран.

## Сделано
- **Единая генерация телефона в `api.js`:** добавлена функция `uniquePhone(prefix)` → `'+7999' + String(Date.now()).slice(-7)`. Это **10 млн** вариантов (11 цифр, валидный РФ-номер) вместо 10 тыс.: при том же объёме данных вероятность коллизии ≈ **0,02%** вместо ≈16%. Функция экспортирована рядом с остальными хелперами `api.js`.
- **Заменено во всех трёх спеках**, где был шаблон с 4 цифрами: `pin-first-login.spec.js` (`+7999777`), `onboarding.spec.js` (`+7999000`), `partner-client-link.spec.js` (`+7999555`) — все три теперь берут `uniquePhone('+7999')`, комментарий с причиной оставлен рядом с константой.
- **Диагностика в трёх шагах (по просьбе @DO 17:15):** `reportStep` теперь в начале каждого шага `pin-first-login` — `шаг 1: чистое устройство → онбординг`, `шаг 2: телефон → OTP` (до заполнения телефона), `шаг 3: после reload устройство помнит вход`; прежняя обёртка «OTP → привязка» осталась внутри шага 2. `test.step` = 3, `reportStep` = 4.
- **Коллизия в C#-контуре не роняет тест (`dc484468`):** `E2EInfra.LoginAsync` делает до 3 попыток, при 409/400/500 с маркером дубликата (`duplicate`/`23505`/`already`) берёт новый телефон; если не вышло — бросает с кодом и **усечённым телом**, а не «http 500».
- **Проверки:** `node --check` всех четырёх файлов (`api.js` + три спека) = 0; `dotnet build` = 0 ошибок / 0 предупреждений.
- **Что не мой дефект:** сам `500` на дубликат телефона — зона @BE (**BE-046**: 409/400 вместо 500 с EF-стеком).
