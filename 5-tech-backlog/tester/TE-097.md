## Дефект, который остался

`"abc"`, `"123"`, `"не телефон"` — **проходят** `PhoneRequiredValidator` (он про пустоту, а не про формат),
поэтому на dev OTP уходит на мусорный номер: `200`, `delivery.ok` зависит от канала, а в логе — «OTP
отправлен на abc». Порядок шагов тут уже не помогает: до `SendAsync` доходит валидное (по мнению валидатора)
значение.

**Почему на dev это не видно и почему лог не доказательство:** при включённом `TESTOTP` ветка отправки не
исполняется, поэтому «отправки не было» пройдёт при **любом** порядке и при **любом** валидаторе — то есть
проверка по логу ничего не доказывает. Доказательство — только тест с подставным `IOtpSender`, считающим вызовы.

## Что нужно (зона @BE, спецификация — моя)

1. `PhoneRequiredValidator` (или отдельная спецификация формата) отвергает номер, не похожий на телефон
   (минимум — цифры и `+`, длина); решение «какой формат считать валидным» — @BE, лишь бы `"abc"` → отказ.
2. Тест в `Client.IntegrationTests`: `Register("abc")` → `res.Result.IsSuccess() == false` **и**
   `Assert.Equal(0, sender.SentCount)` — та же форма, что уже есть для пустого номера.
3. Негативный контроль (правило §5.4): убери валидацию формата — тест обязан краснеть; верни — зелёный.

## Критерии приёмки

- [ ] `Register("abc")` → отказ, `sender.SentCount == 0` (тест в `Client.IntegrationTests`, зона @BE)
- [ ] `Register("+79990000000")` → `SentCount == 1` (положительная пара, иначе «0 вызовов» зеленеет на сломанном сендере)
- [ ] негативный контроль: без проверки формата тест красный
- [ ] прогон, который **реально собрал** `Client.IntegrationTests` и прогнал тесты (REF прогона), а не «локально прошло»
