## Дефект, который остался

`"abc"`, `"123"`, `"не телефон"` — **проходят** `PhoneRequiredValidator` (он про пустоту, а не про формат),
поэтому на dev OTP уходит на мусорный номер: `200`, `delivery.ok` зависит от канала, а в логе — «OTP
отправлен на abc». Порядок шагов тут уже не помогает: до `SendAsync` доходит валидное (по мнению валидатора)
значение.

**Почему на dev это не видно и почему лог не доказательство:** при включённом `TESTOTP` ветка отправки не
исполняется, поэтому «отправки не было» пройдёт при **любом** порядке и при **любом** валидаторе — то есть
проверка по логу ничего не доказывает. Доказательство — только тест с подставным `IOtpSender`, считающим вызовы.

## Что нужно (зона @BE, спецификация — моя)

1. `PhoneRequiredValidator` (или отдельная спецификация формата) отвергает номер, не похожий на телефон
   (минимум — цифры и `+`, длина); решение «какой формат считать валидным» — @BE, лишь бы `"abc"` → отказ.
2. Тест в `Client.IntegrationTests`: `Register("abc")` → `res.Result.IsSuccess() == false` **и**
   `Assert.Equal(0, sender.SentCount)` — та же форма, что уже есть для пустого номера.
3. Негативный контроль (правило §5.4): убери валидацию формата — тест обязан краснеть; верни — зелёный.

## Рецепт проверки (замер @TE `2026-11-12 00:45`, премиса карточки **актуальна**)

Проверено чтением `origin` — не по названию файлов:

- формат телефона **не проверяется**: единственный валидатор — `PhoneRequiredValidator`
  (`6-msa/BC-Client/src/Client.Domain/Specifications/PhoneRequiredValidator.cs:7`), и он смотрит только
  `!string.IsNullOrWhiteSpace(model.Root.Phone)`, то есть **наличие**, а не формат;
- в обработчике он вызывается первым (`Client.Application/Commands/ClientHandlers.cs:31-32`), после чего
  сразу идут `_rateLimiter.TryAcquire(r.Phone, …)` (`:36`), поиск существующего (`:40`) и
  `_sender.SendAsync(r.Phone, otp, ct)` (`:47`) — то есть строка `"abc"` доезжает до отправки;
- в `Client.IntegrationTests/RegisterClientHandlerTests.cs` тесты есть только на **занятый** телефон
  (`Register_ExistingPhone_ReissuesOtp_And_MarksExisting`, `Register_Race_DuplicatePhone_*`), теста
  на **формат** нет;
- фейковый отправитель уже считает вызовы: `SendAsync(...) { SentCount++; … }` — то есть утверждение
  «`SentCount == 0`» писать не с нуля.

**Что должно появиться (зона @BE, тест — в папке сервиса по ADR-028):**

1. `Register_InvalidPhone_DoesNotSendOtp`: `Register("abc")` → отказ, `sender.SentCount == 0`;
2. `Register_ValidPhone_SendsOtpOnce`: `Register("+79990000000")` → `sender.SentCount == 1`
   (положительная пара — иначе «0 вызовов» зеленеет на сломанном сендере);
3. негативный контроль: **до** правки тест (1) обязан быть красным — это и докажет, что проверка формата
   действительно нужна, а не «уже есть».

Правка кода (тоже @BE, порядок важен): валидатор формата — **до** `TryAcquire`/`SendAsync`, иначе OTP
уходит на мусор и лимитер расходуется на невалидные номера.

_(после внедрения @BE — REF прогона + вывод по двум строкам: `abc` → 0 вызовов, валидный → 1 вызов)_
