# TE-047: P0 — смоук падает после BE-048: `seedSession` кладёт `clientId` без JWT

- **Статус:** На проверке
- **В работе с:** 2026-11-08
- **Приоритет:** **P0** (держится красный `smoke-front` → `deploy-prod` не выполняется)
- **Источник:** @DO 2026-11-08 18:00 — `deploy` #816 (`6b907c5f`) = failure на `smoke-front`: `tests/add-partner.spec.js:7` → `expect(#view-partners).toBeVisible()` падает (14× `view hidden`), `tests/wizard-record.spec.js:41` → `expect(#view-wizard).toBeVisible()`. В логе: «API жив: `/partners` без токена = 401 (client-JWT обязателен)». То есть смоук знает про авторизацию, но **фикстура `seedSession` кладёт только `clientId`, без `accessToken`** — приложение не может получить партнёров, экран остаётся `hidden`
- **Зависимости:** BE-048 (`[Authorize]` на `/partners`), TE-041 (client-JWT в `api.js`), dev-стенд с `CLIENTS__TESTOTP=000000`
- **Проверяет:** @TL (TechLead)

## Задача (зона @TE, `9-tests/RnD/front-e2e`)
1. **`seedSession` должен получать реальный токен**, а не только `clientId`: `POST /api/v1/clients {phone}` → `POST /api/v1/clients/{id}/verify {code}` → сохранить `accessToken` (+`refreshToken`) в `localStorage` (`xdiary.accessToken`, `xdiary.refreshToken`) рядом с `xdiary.clientId`. На dev `Clients__TestOtp=000000` позволяет пройти верификацию без Telegram.
2. Убрать зависимость от старого контракта (`token` вместо `accessToken` уже обработан — не сломать).
3. **Добавить одну проверку в смоук:** «с валидным токеном `/partners` отвечает 200, без токена — 401» — чтобы падение фикстуры было видно по делу, а не по `hidden`.
4. Проверить те спеки, которые падают именно из-за auth: `add-partner`, `wizard-record` — они должны проходить с новым `seedSession`.

## Критерии приёмки
- [ ] `smoke-front` зелёный (самостоятельно завершившийся прогон), в нём нет `hidden`-таймаутов из-за отсутствия токена.
- [x] `seedSession` кладёт `clientId` + `accessToken` + `refreshToken`.
- [x] Есть явная проверка «`/partners`: 200 с токеном / 401 без».

## Результат
**Пункты 1–2 в фикстуре уже были — проверено по коду `origin`** (`9-tests/RnD/front-e2e/tests/api.js`, `seedSessionOnce`):
```
POST /api/v1/clients {phone}                      → id
POST /api/v1/clients/{id}/verify {code: TEST_OTP} → accessToken (+ refreshToken; поддержан и старый `token`)
localStorage: xdiary.clientId, xdiary.accessToken, xdiary.refreshToken, xdiary.apiBase
партнёры: Authorization: Bearer <token>
```
То есть «кладёт только `clientId`» кодом не подтверждается. Фронт читает токен оттуда же: `8-front/js/api.js:17` — `storeGet = localStorage.getItem`.

**Пункт 3 добавлен** (не хватало второй половины — проверялось только «с токеном»):
```
lp   = GET /api/v1/partners с  Authorization: Bearer
anon = GET /api/v1/partners без Authorization            ← новое
::warning::{"title":"seedSession: auth-контур /partners","anonStatus":…,"withTokenStatus":…,
            "authEnforced":…,"tokenAccepted":…,"partnersCount":…,"partnerCreated":…,"partnersOwnVisible":…}
throw, если withTokenStatus !== 200 → «client-JWT не принят … это auth-контур, а не hidden-экран»
```

**Живой замер на dev (тот же флоу, без браузера):**
```
GET /api/v1/partners  без токена → 401      ← auth enforced (BE-048 на стенде)
GET /api/v1/partners  с токеном  → 200 []   ← токен принимается, список пуст
```

**Про пустой список:** `200 []` после успешного `POST /partners` — это не auth, а отсутствие привязки партнёра к клиенту (`POST /partners` не проставляет `ClientId`); @FE закрывает это вызовом `link-client` после создания (`4df37204`, пока локально). Когда доедет, `partnersCount` станет `1`, `partnersOwnVisible: true` — и `add-partner`/`wizard-record` пройдут без правок спеков (под `hidden` их не подгонял).

**Проверки:** `node --check` = 0 для `api.js` и пяти спеков (`add-partner`, `wizard-record`, `onboarding`, `pin-first-login`, `change-pin`).

**Осталось (за прогоном):** зелёный `smoke-front` — @DO; поведение спек не менял.
