# TE-032: E2E-фикстуры под новую модель входа (PIN = замок, client-JWT обязателен)

- **Статус:** На проверке
- **Приоритет:** P1 (без этого почти все спеки красные — по причине, не связанной с продуктом)

- **Источник:** @FE 2026-11-05 20:00/22:20 (фронт `0.58`/`0.59`), AR-008, BE-036/BE-038
- **Зависимости:** FE-025 (готов), BE-036, BE-038

## Проблема
После AR-008 + BE-036/BE-038 + FE-025:
- `/privacy/token`, `pin/set`, `pin/has` **требуют client-JWT** (в шлюзе не анонимны);
- фронт без client-JWT уходит **в онбординг**, PIN-экрана на чистом устройстве нет.

А большинство спеков сейчас логинятся `loginWithPin` **на чистом устройстве**: `add-partner`, `catalog`, `catalog-archive`, `wizard-record`, `edit-delete`, `trends`, `csv`, `settings`, `remove-pin`, `change-pin`, `somatic-detail`. Все они уйдут в онбординг → **красные не из-за регрессии**, а из-за устаревшей фикстуры.

## Задача
1. **Общий хелпер** (в `tests/api.js`): `seedSession(page)` — до загрузки приложения выставить в `localStorage` `xdiary.clientId` + валидный client-JWT (полученный через `/clients` → `/verify` с `Clients:TestOtp`), либо `xdiary.legacy = "1"` там, где идентификация не нужна спекую.
2. Перевести спеки на `seedSession` вместо `loginWithPin` (кроме спеков, которые **проверяют** вход/онбординг).
3. **`pin-first-login`** — переписать под новую модель: чистое устройство → онбординг; PIN — только после client-JWT (локальный замок).
4. `remove-pin`/`change-pin` — убедиться, что работают с client-JWT (не 401).
5. Отметить в спеке, если проверяется именно legacy-режим (`xdiary.legacy`).

## Критерии приёмки
- [ ] Все спеки, ранее использовавшие `loginWithPin` на чистом устройстве, проходят с `seedSession`.
- [ ] `pin-first-login` зелёный под новой моделью (онбординг first).
- [ ] Нет ни одного спека, который падает из-за 401 на `/privacy/token` без JWT.
- [ ] В README `9-tests/RnD/front-e2e` описано: как засеять сессию и когда нужен `legacy`.

## Ход работы
- **Причина** (по коду `0.59`): `unlock()` больше не зовёт `ensureToken`/`Api.auth.login`; при `!Api.config.token()` сразу `openOnboarding()` — до `afterAuth()` (где legacy-ветка `hasPin → markLegacy → openJournal`) дело не доходит. Поэтому `loginWithPin` (локальный PIN + `waitToken`) даёт «JWT не получен».
- **План:** helper `seedSession(page)` в `tests/api.js` — **сначала `installBase(page)`** (он ставит `window.__XDIARY_E2E__ = true`, иначе после FE-024 фронт уедет на прод), затем телефон → OTP `000000` → `POST /clients` → `/verify` → `link-partner` → в `localStorage` кладём `xdiary.clientId` + `xdiary.accessToken`. `loginWithPin` переводится на него; `Pin.setPin` остаётся вторым слоем для `remove-pin`/`change-pin`/`pin-first-login`.
- **Объём:** одна правка helper'а (все 10 спек зовут `loginWithPin`), а не 10 правок спеков.

**Вывод (уточнённый):** в **0.68** `POST /link-partner` из UI **не отправлялся вообще** — обработчик клика не вызывался (карточки пересоздавались, обработчик висел на элементе). Дефект до вызова, а не в ответе сервера. В **0.69** (делегирование на `#onboarding-list`, `85b27f7`) запрос уходит и `linked:true` — то есть FE-031 закрыт по факту, и искать там больше нечего.

**Что осталось и чья зона:** `pin-first-login` — падение на ожидании `#view-journal` после PIN-less онбординга. На момент #32/#33 в этом спеке **не было** создания партнёра при пустом `#onboarding-list` (в `onboarding` — было), поэтому список был пуст, клик не выполнялся и журнал не открывался. Фикс перенесён 1:1 (`6cc0f05`) + добавлен `dumpViews` перед ожиданием журнала, чтобы при повторе было видно активный экран, а не только «journal hidden».

**Следствие для `front-e2e`:** `wizard-record` и `remove-pin` сняты ранее (TE-036/TE-037), `onboarding` позеленел на `#32`/`#33`, `no-pin`/`change-pin` в skipped. Ожидание после `6cc0f05` — **0 failed**.
