# TE-077. Уборка партнёра «падала» на уже удалённом объекте (`status 400`)

- **Статус:** На проверке
- **Проверяет:** @TL
- **Роль:** @TE
- **Источник:** прогоны Front E2E #773, #775 — строки `cleanup partner: {"ok":false,"removed":false,"status":400}`

## Проблема

`removeByName(page, 'partner', name)` (`tests/api.js`) перечисляет партнёров, находит по имени и зовёт
`POST /api/v1/partners/{id}/remove`, затем возвращает `ok: d.ok`. В логах прогонов это давало
`{"ok":false,"removed":false,"status":400}` — то есть **уборка считалась неуспешной**, хотя объект уже
удалён.

`400` здесь означает `Partner not found.` (`Partners.Application/PartnerHandlers.cs`:
`Fail("Partner not found.")` → маппинг в 400). Ситуации, когда это происходит, безобидны:
- объект удалил предыдущий шаг той же спеки;
- объект удалил параллельный прогон (до сериализации CI);
- soft-delete (`@BE`: `Remove()` ставит `DeletedAt`, повтор идемпотентен) — повторный вызов может идти по
  уже удалённой записи.

То есть **цель уборки уже достигнута**, а тест писал ошибку — это шум, из-за которого `cleanup`-строки
приходилось разбирать вручную в каждом прогоне.

## Что изменено

`removeByName` читает тело ответа и трактует `400`/`404` с текстом `not found` как успех:

```js
if (!d.ok) {
  const body = await d.text().catch(() => '');
  if ((d.status === 400 || d.status === 404) && /not found/i.test(body)) {
    return { ok: true, removed: false, alreadyGone: true, status: d.status };
  }
  return { ok: false, removed: false, status: d.status, body: String(body).slice(0, 120) };
}
return { ok: true, removed: true, status: d.status };
```

Что **не** изменилось: реальные ошибки (5xx, 401, 403, прочие 400 без `not found`) по-прежнему дают
`ok:false` и печатаются в лог с телом ответа. Проверять «объект удалён» спеки продолжают через API
(`GET /partners/{id}` → `404`), уборка ничего не доказывает и не маскирует.
