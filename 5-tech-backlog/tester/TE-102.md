## Причина по @BE `11:37` — и что именно исправлено (проверено в `origin`)

Формулировка @BE: `Photo`/`Gender`/`Notes` **не были в VOs** ⇒ `UpdateProfile` давал пустой DIFF ⇒ проекция
возвращала `Name=''` ⇒ затирала. Подтверждается кодом коммита `31fd2af6`:

| Часть фикса | Где |
|---|---|
| поля профиля стали value-объектами (участвуют в change-track) | `Partners.Domain/Implementation/AnemicModel.cs:25-27` — `["Photo"]/["Gender"]/["Notes"] = new StringValueObject(…)` |
| проекция отдаёт **nullable** Diff | `PartnerEventConsumer.cs:111` — `record Diff(string? Name, string? Photo, string? Gender, string? Notes, Guid? ClientId, DateTime? DeletedAt)` |
| upsert только по изменённым полям | `PartnerEventConsumer.cs:74-82` — `if (read.Name is not null) existing.Name = read.Name;` и так же для остальных |

**Документарная деталь (не моя зона, но важна для `@AR`):** `0-df-issue/edm-own-implementations.md:26` говорит
«скаляры (`Photo`/`Gender`/`Notes`) не участвуют в change-треке `Commit()`». Фикс делает их VO — то есть строка

прочитает её как «profile вообще не проецируется».

## Риск, который надо проверить сразу после выкатки (мой, по коду)

`GET /journal/recent.lastPartner.name` берёт имя из **справочника Journal** (`partners_directory`), а он
наполняется отдельным DTO: `Journal.Api/Controllers/PartnersEventsController.cs` — `record PartnersEventDto(Guid
PartnerId, string Name, Guid? ClientId, DateTime? DeletedAt)`, `Name` — **простая строка**. Значит после фикса имя
попадёт в справочник, только если Partners **публикует** его после `profile` (а не только на `Register`/`Rename`).
Если публикация идёт лишь по этим двум событиям, `recent.lastPartner.name` останется **id** даже с исправленной
проекцией. Проверю это тем же замером, что просил @TL, сразу после выкатки — и это будет отдельная строка
приёмки, а не «показалось».

## Прогон на выкаченных образах (`@DO 2026-11-10 14:08`): оба кейса красные, причина измерена

`partners` выкачен из lock (`single-a2bade2`), `journal` — `single-60f3fc6`. Квитанции:

```
profile-stage1 → rc=1   (в ответе приходит id вместо имени)
ordering       → rc=1   (name=None, 3 итерации из 3)
```

**Причина по @DO:** `partners` публикует `POST http://journal:8080/internal/partners/events`, Journal отвечает
**HTTP 500**, потому что `partners_directory.Name` объявлен `text NOT NULL`.

**Механизм, проверенный мной по коду (чтобы @BE не искал):**

1. `Journal.Storage/.../20261105170525_AddReadStores.cs:67` — `Name = table.Column<string>(type: "text", nullable: false)`;
2. `Journal.InternalContracts/PartnersDirectoryReadModel.cs:16` — `public string Name { get; set; } = string.Empty;`
   (значение по умолчанию спасает только при **отсутствии** поля в JSON, но не при явном `null`);
3. `Journal.Api/Controllers/PartnersEventsController.cs` — `record PartnersEventDto(Guid PartnerId, string Name, …)`
   без проверки: `<Nullable>enable</Nullable>` в проекте есть, **но** `System.Text.Json` по умолчанию **не**
   применяет NRT-аннотации (`RespectNullableAnnotations` не выставлен), поэтому `{"Name": null}` связывается с
   `string Name` без ошибки;
4. дальше `UpsertAsync` пишет `null` в `NOT NULL` ⇒ PostgreSQL `23502` ⇒ **500**.

Отсюда адрес правки (зона @BE): проверять `Name` на входе контроллера (или включить `RespectNullableAnnotations`,
или согласовать `Name` с nullable-колонкой). Пока это не исправлено, `TE-102` **не может** быть зелёным ни на одном
образе — и это не дефект приёмки.
