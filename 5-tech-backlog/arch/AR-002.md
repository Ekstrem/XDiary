# AR-002: Пересмотреть размещение PostgreSQL — VPS-2 без приватной сети слишком медленен

- **Статус:** На проверке
- **Приоритет:** P1
- **Источник:** ADR-003/004, `04-architecture/vps-setup.md` (§3.1), DevOps (прод-развёртывание)
- **Зависимости:** DO-002

## Контекст

Схема предполагает вынесение PostgreSQL на отдельную ВМ **VPS-2** с подключением сервисов по **приватной сети** (`10.0.0.2`). На проде выяснилось:

1. У провайдера (Hostkey) **приватной сети/VPC пока нет**.
2. Трафик БД идёт по публичному интернету между VPS-1 (`31.192.111.168`) и VPS-2 (`77.91.73.67`), и этот канал **непригоден для БД**:
   - ping: avg 60 мс, max 290 мс, большой джиттер (min 0.56 мс);
   - TCP-коннект: 500–800 мс;
   - `SELECT 1` через psql: **3–7 секунд** (в норме <100 мс).
3. Исключены: нехватка памяти (контейнеры 11–50 МБ при лимите 256 МБ), SSL (`sslmode=disable` ≈ `require`), reverse-DNS/`log_hostname` (выключение не помогло). Причина — потери/ретрансмиссии на маршруте.
4. Следствие на проде: `Database.Migrate()` на старте сервиса упирался в 30-секундный таймаут Npgsql → падения контейнеров (`Exited 139`).

## Что сделал DevOps (временное решение)

Перенёс PostgreSQL **обратно на VPS-1** (контейнер `xdiary-pg`, локальный bridge ~1 мс). Сервисы стабильны (`restarts=0`), миграции прошли, шлюз `200`, `privacy/pin/has` → `200`. **VPS-2 сейчас простаивает** (БД на ней есть, но не используется).

## Задача (архитектору)

Принять решение по размещению БД и обновить схему. Варианты:

- **A. Co-locate (принять текущее):** PostgreSQL на VPS-1 рядом с сервисами, VPS-2 вывести из схемы (или оставить под будущее). Просто, стабильно, но нет изоляции БД от приложений.
- **B. Ждать приватную сеть Hostkey:** как только появится VPC/приватный IP — вернуть БД на VPS-2 (DevOps переключит за ~15 минут). Зафиксировать VPS-2 как «отложено».
- **C. Свой приватный канал:** поднять WireGuard-туннель между VPS-1 и VPS-2 (приватный `10.x.x.x` поверх публичного IP) → БД на VPS-2 по туннелю. Требует настройки и обслуживания.

- [ ] `04-architecture/vps-setup.md` §3.1 обновлена (PostgreSQL на VPS-1).
- [x] Судьба VPS-2 — бэкап-таргет или заморозка до VPC.
- [ ] DevOps получил инструкцию.

## Решение (архитектор)
**Co-locate** (вариант A): PostgreSQL на VPS-1 рядом с сервисами. WireGuard (C) не гарантирует фикс lossy-маршрута; приватную сеть (B) ждать — без таймлайна. VPS-2 — под бэкап/заморозку.

## Примечание (измерения DevOps)
- `VPS-1 → VPS-2` (публичный IP): `SELECT 1` = 2.7–7.1 с; TCP-коннект 500–800 мс; ping avg 60 мс / max 290 мс.
- `VPS-1 → локальный PostgreSQL (10.89.9.10)`: через локальный bridge, стабильно.
