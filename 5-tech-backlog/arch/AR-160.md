```
$ git ls-tree --name-only origin/main openapi/
$ for f in openapi/*.json; do jq -c '.servers' $f; done     # (или python)
```

| спек | `servers` |
|---|---|
**journal.json** | **`[{"url": "/"}]`** |
**partners.json** | **`[{"url": "/"}]`** |
api-gateway.json | `[{"url": "/"}]` |
catalog / client / privacy / analytics / daily-metrics / garmin / apple-health / portability / somatic-series | **отсутствует** |

Падают ровно `journal` и `partners` — то есть **те и только те** измеряемые API, у которых в спеке прописан `servers: "/"`. Остальные девять (без `servers`) отвечают корректно (401).

## Механизм

`7-deploy/apim/import.sh` отправляет спеку целиком в Gravitee (`POST …/apis/import`, `{"type":"BOTH","definition": <spec as string>}`). Gravitee берёт `servers[0].url` как базу/endpoint API. При `"/"` получается API без валидного backend-таргета: шлюз принимает запрос и не может проксировать в сервис, поэтому отдаёт `500` **своим** телом (`{"message":"Internal Server Error","http_status_code":500}`) и заголовками `X-Gravitee-*` — ровно то, что мы видим на живом проде.

Косвенно это уже было видно в `7-deploy/apim/import.sh` (комментарий про «definition» и про то, что v2-пути обязаны содержать контекст организации/среды, иначе 500) — то есть мы имеем дело с тем же классом: неверная метаинформация в спеке ломает весь API.

## Задача

1. Убрать `servers` из `journal.json`, `partners.json` и `api-gateway.json` (как в девяти остальных спеках), либо проставить корректный `servers[0].url`, если он нужен по канону;
2. Синхронизировать `_meta.json`/генератор, если `servers` появляется из генерации, а не вписан руками — иначе вернётся при следующей перегенерации;
3. После правки — **ре-импорт** в APIM (`bash 7-deploy/apim/import.sh`, зона @DO) и повторный замер канона.

## Критерии приёмки

- [ ] ре-импорт выполнен, `GET /api/v1/journal/records` без токена → **401** (не 500);

**`HTTP 401` на всех 12 импортах = неверные админ-креды Gravitee.** `API в APIM: ~0` — это тот же 401 при чтении списка API. То есть механика довезена целиком, осталось дать рабочую пару логин/пароль.

Этот дефект уже зафиксирован в истории: `DO-098` (реестр неработающего), пункт 8 — «`apim.env` с **нерабочими** админ-кредами: `GRAVITEE_ADMIN_USER`/`PASSWORD` есть (2026-11-04)». С тех пор креды, судя по 401, так и не обновлялись.

**Что нужно (зона @DO / владельца):**
1. привести `GRAVITEE_ADMIN_USER`/`GRAVITEE_ADMIN_PASSWORD` в `/opt/xdiary/secrets/apim.env` к актуальным (или пересоздать админа в Gravitee и записать), значение в git/чат не писать;
2. либо, если Gravitee работает на memory-провайдере с `admin/admin`, убрать/переименовать устаревший `apim.env`, чтобы `import.sh` пошёл под дефолтом (он это умеет: файла нет → `admin/admin`);
3. затем прогнать `deploy` с `reimport_apim=true` (или руками `bash /opt/xdiary/7-deploy/apim/import.sh`) и повторить замер канона.

**Критерий готовности этот же, что выше:** `/journal/records` → 401, `/partners` → 401, канон `rc=0`, `smoke-api` зелёный.

## Окончательный диагноз блокера (прогон 43508343867)

Проверены **обе** известные пары — обе дают 401:

```
APIM-REIMPORT: спек в /opt/xdiary/openapi — 13
APIM-REIMPORT: креды из /opt/xdiary/secrets/apim.env
креды НЕ подошли: и apim.env, и заводские admin/admin дают 401
  → нужен актуальный админ Gravitee (DO-098 п.8)
import.sh: импортировано 0, ошибок 12; API в APIM: ~0
```

**Почему заводская пара не подошла:** `up.sh:83-84` монтирует `/opt/xdiary/secrets/apim-gravitee.yml` в management-контейнер; значит админ **кастомный**, и файл на месте (иначе сработал бы `admin/admin`). Пароль хранится в этом файле (в Gravitee — в виде хеша), поэтому «вычитать» его и подставить в Basic-аутентификацию нельзя.
