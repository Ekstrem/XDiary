# AR-162 — Проработка профиля `Cqrs`: две БД на BC (Command DB / Read DB)

- **Статус:** На проработке
- **Приоритет:** P2 (техдолг; не блокирует функционал, но ограничивает CQRS)
- **Прорабатывает:** @AR
- **Источник:** `BE-139` (P2, техдолг) + слова владельца 2026-11-19: «базы должно было быть две — это и есть CQRS»; `ADR-002` (путь `Single → BudgetCqrs → Cqrs → Ceqrs`), `ADR-034` (три схемы в одной БД — принятый минимум).
- **Зависимости:** решение @AR (поправка `ADR-002`/`ADR-034`) → провижининг @DO → конфигурация @BE.
- **Проверяет:** @TL (домен — архитектура, автор @AR, саморевью запрещено).

## Задача

Дать решение по `BE-139`: переходить ли с профиля **`Single`** (одна БД на BC, три схемы) на **`Cqrs`** (Command DB и Read DB — разные базы), и если да — в каком объёме и с какими критериями.

Что установлено при проработке:

1. **Канон уже выполнен по минимуму.** `ADR-034` (принят 2026-11-05): «Command DB и Read DB — **разные базы** (или как минимум разные схемы)». Сейчас реализован **минимум** — три схемы в одной БД (`deploy.sh:67-77`: `CommandDb = ReadDb = <bc>`). То есть это **не дефект**, а незакрытая ступень эволюции профиля.
2. **Риск, который создаёт минимум:** `EventStoreDbContext` и `ReadDbContext` вызывают `Database.Migrate()` в одной БД ⇒ **общая `__EFMigrationsHistory`**; пока ID миграций уникальны — работает, при пересечении/откате конфликт неочевиден.
3. **Смена профиля — архитектурное решение, а не настройка:** переход `Single → Cqrs` меняет `ADR-002` (профиль) и уточняет `ADR-034` (история миграций разделяется по БД). По правилу владельца 2026-11-16 архитектуру решает @AR **после обсуждения с владельцем** ⇒ нужен явный выбор владельца (приоритет: сейчас / после спринта / не делаем).

## Что даёт проработка (артефакт, а не мнение)

1. **Поправка ADR** (новый ADR, старый только меняет статус — правило владельца): профиль `Cqrs` для 11 BC, раздельные `__EFMigrationsHistory`, правило «read-БД пересобираема из событий».
2. **Раскладка по ролям** (после решения): @DO — провижининг `<bc>_read` + права + строки подключения в `deploy.sh`/`recreate-service.sh`/`rotate-db-password.sh`; @BE — `appsettings.json` каждого BC, проверка раздельных историй, `DatabaseCreationTests` на двух БД.
3. **Критерии приёмки** — переносятся из `BE-139` без изменения (две БД на BC, раздельные истории, независимая пересборка read-модели, зелёные `deploy-dev`/`deploy-prod`).
4. **Оценка объёма и порядок** (что можно сделать одним этапом, а что требует простоя).
