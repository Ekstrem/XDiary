# AR-003: Техдолг — явные POST-эндпоинты Command API + уточнить MV (БД-операции)

- **Статус:** Открыта
- **Приоритет:** P1
- **Источник:** edm-net (Command API: `POST /api/v1/{context}`, `POST /api/v1/{context}/{id}/{action}`); ADR-006, ADR-013
- **Зависимости:** —

## Контекст
Аудит `03-ddd` выявил два расхождения с конвенцией EDM/DF:

1. **Command API (`03-command-api.md`)** — в 9 из 10 контекстов HTTP-эндпоинты не расписаны (есть только таблица «команда → метод → событие → VO»; единственный явный эндпоинт — `POST /api/v1/privacy/token`, добавленный TL). По edm-net команды должны быть сопоставлены с POST-эндпоинтами.
2. **Materialized Views (`05-materialized-views.md`)** — в проекционных правилах используются `PUT`/`DELETE` (напр. `ItemRenamed | PUT (name)`, `ItemRemoved | DELETE`). Это **операции БД** (upsert/delete строки read-model), а не HTTP-глаголы, но визуально путаются с REST.

## Задача
1. В каждом `03-command-api.md` расписать явные POST-эндпоинты:
   - `POST /api/v1/{context}` — создание/старт;
   - `POST /api/v1/{context}/{id}/{action}` — действие (`complete`, `delete`, `archive`…).
   **Без PUT/DELETE** — команды только POST (идемпотентные операции).
2. В `05-materialized-views.md` заменить `PUT` → `UPDATE`, а `DELETE` оставить как явную БД-операцию (подписать «INSERT/UPDATE/DELETE строки read-model»), чтобы не путать с HTTP.

## Критерии приёмки
- [ ] Во всех 10 контекстах Command API есть явные POST-эндпоинты; PUT/DELETE отсутствуют.
- [ ] MV-правила однозначно читаются как БД-операции (INSERT/UPDATE/DELETE), а не как HTTP-глаголы.
- [ ] Согласовано с фактическим кодом `6-msa` (контроллеры) и шлюзом (YARP-роуты).
