# AR-001: TLS и публичный доступ без доменного имени

- **Статус:** На проверке
- **Приоритет:** P0
- **Источник:** ADR-009, `04-architecture/vps-setup.md` (§2.3, §6)
- **Зависимости:** —

## Контекст
У заказчика **нет доменных имён**. Памятка архитектора (§2.3) предполагает домен для Let's Encrypt (caddy/nginx+certbot). Без домена выпустить TLS-сертификат от Let's Encrypt нельзя → HTTPS не поднимется. DevOps упрётся в это при настройке (DO-004).

## Задача (архитектору)
Принять решение, как обеспечить защищённый доступ к PWA без доменного имени. Варианты:
- **A.** Self-signed сертификат (HTTPS с предупреждением в браузере, привязка по отпечатку).
- **B.** Доступ только по VPN / приватной сети (без публичного HTTPS).
- **C.** Бесплатный DDNS-домен (duckdns, sslip.io, nip.io) → Let's Encrypt.
- **D.** Доступ по IP + self-signed, сертификат закрепить (pin) на устройстве пары.

Ограничение PWA: Service Worker и secure-context API требуют **HTTPS или localhost**.

## Критерии приёмки
- [x] Выбран и обоснован способ — **ADR-015** (Tailscale).
- [x] DevOps получил инструкцию — `vps-setup.md` §2.3 обновлена.
- [x] Учтено требование PWA (валидный TLS → secure context → Service Worker).

## Решение (архитектор)
**Tailscale + MagicDNS + `tailscale cert`** (ADR-015): частная VPN-сеть + валидный Let's Encrypt-сертификат без домена и без публичного доступа.

## Разблокировано
DevOps (DO-004): доступ и TLS — через Tailscale (см. `vps-setup.md` §2.3).
