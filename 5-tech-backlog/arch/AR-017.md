## Проблема

Правило DF («сущность = идентифицирующие признаки, `id`/`version` даёт фреймворк») привело к тому, что в канвасах
**не было таблицы атрибутов состояния**: §2 перечислял 2–3 «идентифицирующих» поля и отдельный список VO, а
`state`, `durationMin`, `orgasms`, `deletedAt`, `createdAt` — растворялись. При этом в `03-ddd/README.md` элемент
«Состояние (AnemicModel)» **был объявлен**, но ни один канвас не содержал его таблицей. Это дефект шаблона, а не
отдельного файла: `state` вообще отсутствовал как атрибут, хотя §3 описывает переходы `Draft → Recorded → Deleted`.

## Задача

1. Пилот **сделан:** `BC-Journal/02-aggregate-canvas.md` §2.2 — полная таблица атрибутов (тип, кардинальность,
   обязательность, чем задаётся, инвариант, источник US) + §2.3 VO + §2.4 «что не хранится и почему».
2. Правило зафиксировано в `03-ddd/README.md` (секция «Атрибуты корня агрегата»).
3. **Осталось:** привести остальные BC к тому же виду — по одному коммиту на BC, чтобы откат был по компоненту:
   `BC-Partners`, `BC-Client`, `BC-Catalog`, `BC-SomaticSeries`, `BC-DailyMetrics`, `BC-GarminGateway`,
   `BC-AppleHealthGateway`, `BC-Portability`, `BC-Privacy` (`PinCredential`), `BC-Analytics` (read-only — таблица
   «атрибуты проекции» вместо корня).
4. Особое внимание: `state` как **атрибут** (у `Partner`/`CatalogItem` — есть ли мягкое удаление?), и поля,
   которые в коде есть, а в канвасе нет (сверять `git grep` по `AnemicModel`, а не по памяти).

**Правило, которое делает работу дешёвой:** §2.2 отвечает на «какие поля у агрегата и кто их задаёт», §2.2.1 — на «через
какой `operationId`»; API-контракт (пути, коды, тела) в канвасе **не переписывается**. Иначе получаем ровно то,
из-за чего AR-016 и появился.

## Результат (2026-11-04)

**Покрытие 11/11 BC.** §2.2 «Состояние (`AnemicModel`) — атрибуты корня агрегата» есть в каждом канвасе, кроме Analytics,
где §2.2 объясняет, **почему** агрегата нет (проекционный контекст, `AnemicModel` в коде отсутствует — проверено
`git grep -l AnemicModel -- 6-msa/BC-Analytics` → 0 файлов).

**Все таблицы сверены с кодом** (`I<X>AnemicModel` + `<X>Root`), а не переписаны из прежнего текста канваса.

**Найденные расхождения «канвас vs код» записаны в §2.2.2 каждого канваса, а не сглажены:**

| BC | Расхождение |
|---|---|
| Client | нет `status`/`deletedAt` в модели при 4 состояниях в §3; PIN живёт в отдельном `BC-Privacy` |
| Partners | `ClientId` nullable + владелец не проверяется (`PartnerOwnedByClient` не enforced); `Photo`/`Notes` не nullable → «не задано» и «не менялось» неразличимы |
| Catalog | `Brand`/`FantasyPartner` не ограничены по `Kind`; словарь видов не зафиксирован машинно |
| SomaticSeries | не видно, где проверяется идемпотентность по `t` → повторный импорт за день удвоит ряд |
| Privacy | `ClientId` хранится дважды (Client и Privacy) при раздельных сервисах |
| DailyMetrics | `Stress` — `int`, «нет данных» и `0` неразличимы → ложный ноль на графике |
| Portability | типы колонок не описаны: ошибка «дата вместо числа» вылезет при разборе, а не при загрузке |
| GarminGateway | `Credentials` в состоянии агрегата — секрет попадает в модель/снапшоты (требование §6 держится дисциплиной) |
| AppleHealthGateway | `ProcessedFiles` растёт без ограничения — неограниченный рост состояния |
| Analytics | агрегата нет по замыслу; проверять нужно вход (события) и выход (MV), а не атрибуты |
