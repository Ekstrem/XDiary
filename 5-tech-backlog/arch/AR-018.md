## Проблема (проверено в `origin`, 2026-11-04)

1. **PII в долгоживущем токене.** `ClientTokenService.cs:23` выдаёт `refresh` на **30 дней**, а `CreateToken(...)` (`:55`)
   добавляет claim **`phone`** — и в `access`, и в `refresh`. Фронт хранит refresh в `localStorage`
   (`xdiary.refreshToken`, `api.js:9`), серверного состояния у токена нет → **отозвать нельзя**.
   Итог: номер телефона живёт в браузере месяц и переживает выход из приложения; доступен любому скрипту на странице.
2. **Политика продублирована.** `AccessMinutes = 15`, `RefreshDays = 30` объявлены **дважды** — в `ClientTokenService`
   и в `Privacy` `TokenService` (там же `DeviceAccessMinutes = 5`). Документы говорят «как Privacy, ADR-008», но связь
   между двумя наборами констант **ничем не проверяется**: изменят в одном сервисе — второй останется.

- [x] **В `refreshToken` нет PII:** claims = `sub` + `kind`; `phone`/`displayName` отсутствуют. `TryValidateRefresh`

- [x] **Тест на состав артефакта** (`Client.ApiTests`, без сети): декодировать refresh → проверить `sub` есть,
      `kind == "refresh"`, `phone` **отсутствует**. Негативный контроль: если `phone` вернуть — тест красный.
- [x] **Политика одна и проверяема:** тест фиксирует канонические значения по ADR — access `15` мин, refresh `30` дней —
      **в обоих сервисах** (`Client` и `Privacy`). Расхождение констант → красный тест, а не молчаливый дрейф.
- [x] `ADR-021` и `BC-Client/03-command-api.md` соответствуют коду после правки — **проверено 2026-11-10 (@AR):** `03-command-api.md:59-60` содержит правило «refresh несёт только `sub` + `kind`» и подтверждение состояния с адресами (`ClientTokenService.cs:64`, `:52-53`, `:57-61`, тест `:40/:47`); `ADR-021:99-104` требует то же и то же проверяет приёмкой. **Одно расхождение осталось в ADR:** `adr-021.md:106` утверждает, что политика объявлена **дважды** (`Client` и `Privacy`) — на 2026-11-10 это неверно (всё через `XDiary.Contracts.TokenPolicy`, дублей 0); ADR-текст не правлю, предложил @TL датированную пометку.
      то есть код отстаёт от контракта).

## Почему это P1, а не «когда-нибудь»

Дневник пары подразумевает **общее устройство** и высокую чувствительность данных. Телефон в 30-дневном артефакте
браузера — единственный класс данных, который переживает выход из приложения, доступен при XSS и попадает в любую
выгрузку `localStorage`. Правка при этом — **не передавать `phone` для `kind == "refresh"`**: одна строка + один тест.


- [x] **PII в refresh невозможен НИ ПО ТИПУ, НИ ПО ВЫЗОВУ** (критерий @AR, принят @TL 2026-11-11 02:30; исполняет @BE). Проверяется **тремя машинными фактами**, а не чтением:
  1. **Сигнатура:** в `ClientTokenService.cs` нет метода, принимающего PII (`phone`/`displayName`) на пути **refresh**. Проверка: `git grep -n "CreateRefresh\|WriteToken" -- 6-msa/BC-Client/src` → ни у одного метода, вызываемого из `Issue` для refresh, нет параметра `phone`; если `WriteToken` общий, у него **нет** параметра PII, а claim добавляется только в access-ветке;
  2. **Состав claims:** `try { new JwtSecurityTokenHandler().ReadJwtToken(refresh).Claims }` даёт **ровно** `{sub, kind}` (ни `phone`, ни `displayName`, ни иных PII). Тест: `ClientTokenServiceTests` — `Assert.Equal(2, claims.Count)` + отсутствие PII-типов;
  3. **Негативный тест:** попытка собрать refresh с PII **не компилируется** (нет параметра) — то есть защита на уровне типа, а не соглашения. Если параметр оставлен ради access — он должен быть **недоступен** для refresh-пути (отдельный метод/перегрузка).
  **Почему так:** сейчас защита держится на том, что `CreateRefresh` передаёт `null` (`:53-54`), а `WriteToken` принимает `phone` (`:56`) и добавляет claim при непустом значении (`:61`) — это защита **по вызову**, её ломает любая новая ветка.
  `phone` и добавит claim, если он непустой ⇒ сейчас инвариант держится **вызовом** (`phone = null` в `ClientTokenService.cs:24`),
  а не сигнатурой. Разделить пути: `CreateAccess(sub, phone)` / **`CreateRefresh(sub)`** — тогда `phone` в refresh
  **не передать**, и тест `RefreshToken_HasNoPhone` остаётся страховкой, а не единственной защитой.
  Проверка: `CreateToken` с параметром `phone` для refresh **не существует** (`git grep`/сигнатуры), `Client.sln` зелёная.

### Вердикт @TL 2026-11-11 02:20 — **РЕШЕНИЕ @TL: переоткрыть в `ToDo` (правка @BE), не закрывать по 4 из 5**

- Критерий 5 — про **PII по типу**, а не по вызову: `ClientTokenService.WriteToken(string sub, string kind, DateTime expires, string? phone)` по-прежнему принимает `phone` и добавляет claim. Это ровно тот класс, который мы ловим весь день: «проверка выполняется, но не там, где свойство гарантируется».
- **Вариант (1) — переоткрыть:** `Статус: ToDo`, `Проверяет: @TL`, правка в зоне **@BE** (убрать параметр `phone`, `access` собирать отдельно), критерий 5 остаётся как есть. Остальные четыре критерия **засчитаны** — их не переделывать.

### Вердикт @TL 2026-11-11 04:00 — **принято по критерию 5, можно закрывать**

- **Сигнатура чистая:** `WriteToken(IEnumerable<Claim> claims, DateTime expires)` (`:64`) больше не принимает PII; `phone` добавляется **только** в `CreateAccess` (`:50`, `:53`); `CreateRefresh` собирает ровно `{sub, kind}`.
- **Тип, а не вызов:** раньше защита держалась тем, что `CreateRefresh` передаёт `null`, — её ломала любая новая ветка. Теперь PII **нельзя передать**, не изменив сигнатуру, и это ровно то, что требовал критерий «по типу».
- **Тест держит инвариант числом:** `RefreshToken_HasNoPhone` с `Assert.Equal(2, Claims.Count())` — «ровно два claim'а», а не «нет `phone`»: второе прошло бы и при трёх claim'ах без телефона.
- **Комментарий `:22` теперь правда** — он утверждает «phone невозможен по сигнатуре», и это проверяемо командой из критерия.
