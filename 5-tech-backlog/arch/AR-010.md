# AR-010: Деплой по компонентам вместо одного `deploy.sh` — архитектурный вопрос

- **Статус:** Закрыта
- **Приоритет:** P2
- **Источник:** владелец, 2026-11-08: «возможно `deploy.sh` потенциально можно поделить на деплой отдельных микросервисов, шлюза, фронта? Если это уходит большим куском, может это не совсем правильная архитектура деплоя?» + факты D-15/DO-050 (инцидент «33 часа на старом образе»)
- **Зависимости:** DO-050 (пост-проверка digest — сделана), D-15 (аудит `|| true`)
- **Прорабатывает:** @AR
- **Проверяет:** @TL (TechLead)

## Задача

Оценить архитектуру деплоя: один монолитный `deploy.sh` на весь стек против **деплоя по компонентам**
(каждый микросервис / `ApiGateway` / фронт — отдельно), и дать рекомендацию в формате ADR
(«почему так»), если решение меняется.

Контекст, который нужно учесть:

1. **`deploy.sh` отсутствует в репозитории** — живёт только на сервере `/opt/xdiary/7-deploy/deploy.sh`,
   хотя его вызывают `update.sh:52` и оба ранбука (`deploy-heal`, `secrets-rotation`). `podman`-логика
   исполняется там, значит аудит §5.2 и D-15 его **не покрывает**.
2. **Инцидент:** `update.sh` 33 часа пуллил неверное имя образа, ошибка глоталась `|| true`,
   контейнер клиента жил на старом образе; «деплой success» при этом был зелёным (DO-050).
3. **Сейчас обновление — «всё или ничего»:** хеш считается по всем образам сразу
   (`update.sh:48`), изменение любого образа ведёт к `deploy.sh` целиком. Это удобно, но:
   - нет изоляции: сломанный компонент требует передеплоя всего стека;
   - нельзя обновить только фронт или только шлюз;
   - откат — тоже «весь стек».
4. **Есть ли реальная потребность в по-компонентном деплое?** Возможно, текущая монолитность —
   осознанное решение (простота, одна машина, podman-compose). Нужно оценить цену разделения:
   compose-зависимости, порядок запуска, health-цепочки, миграции БД (их точно нельзя «по одному
   сервису» без порядка).

## Вопросы к @AR

1. Компонентный деплой (front / gateway / сервис) — это архитектурно оправдано для текущего размера
   продукта или преждевременное усложнение?
2. Если оправдано: где границы компонентов (по образам? по compose-профилям? по зависимостям
   миграций?), и что становится источником правды для «порядка и состава»?
3. Нужен ли ADR «архитектура деплоя» — сейчас решение живёт в скрипте, а не в документе.
4. Что из этого — предусловие: вынести `deploy.sh` в репозиторий (это не архитектура, а §5.2,
   но без него оценка невозможна — скрипт не читается).

## Вердикт @AR (2026-11-08)

- **Фактическая схема:** `update.sh` тянет все образы → один агрегатный хеш → любое изменение → `deploy.sh` пересоздаёт все 12 контейнеров (`rm -f` + `podman run` по hardcoded IP). Compose есть, но `deploy.sh` его обходит.
- **Ответ:** **компонентный деплой — каждый BC = независимая единица деплоя** (EDM: 1 BC = 1 контейнер = 1 деплой-единица). Не path-based-компромисс (первая версия была слабой — снял).
- **Обоснование:** микросервис по определению деплоится отдельно (цель EDM); БД изолированы по сервису → порядок миграций per-service безопасен; шлюз статичен и фронтует всех → пересоздаётся последним.
- **ADR-022** (пересмотрено) — варианты A/B/C с ценой/риском + решение C.
