# AR-012: «Я» виден в списке партнёров — интерфейс должен показывать партнёров, не меня (с @PO)

- **Статус:** В паузе
- **Приоритет:** **P1** (владелец назвал нелогичным; смешение «я» и «партнёр» в интерфейсе)
- **Пауза:** ретро владельца (объявлена 2026-11-09) — работы не ведутся
- **Разблокирует:** решение владельца после ретро
- **Источник:** владелец 2026-11-09 03:5x: «Я вижу себя в партнёрах — это же не логично! тут должны быть (в интерфейсе) мои партнёры, но не я. Обсуди это с Arch и PO»
- **Прорабатывает:** @AR (совместно с @PO)
- **Зависимости:** AR-011 (модель «я vs партнёр»), BE-048 (скоуп по `sub`), FE-033
- **Проверяет:** @PO (продукт) + @TL (техника)

## Проблема
`GET /api/v1/partners` возвращает всех партнёров, связанных с клиентом, **включая запись «я»** (та же сущность `Partner` с `ClientId` = текущий клиент). Вкладка «Партнёры» поэтому показывает самого пользователя («Евгений» на скриншоте владельца) — для продукта это ошибка: там должны быть **другие** люди.

## Задача
1. **Решение с @PO:** как интерфейс разделяет «я» и «партнёры» — отдельный раздел «Профиль» для себя, а вкладка «Партнёры» только для других; либо скрывать `isSelf` из списка.
2. **Технически:** контракт списка должен позволять фронту отличить «я» (`isSelf`/`selfId`) — сейчас признак есть только в модели (`self`), проверить, отдаётся ли он в API; если нет — добавить (аддитивно, в `/v1`).
3. **Проверить влияние на онбординг:** экран «Кто ты?» использует тот же список для выбора себя — после AR-011 он не должен зависеть от «списка партнёров».

## Критерии приёмки
- [ ] Продуктовое решение @PO: где «я», где «партнёры».
- [ ] Вкладка «Партнёры» **не содержит** запись «я» (подтверждено владельцем).
- [ ] Контракт API: список не содержит «я» — 🟡 **черновик ADR-024, не принято**.

## Статус проработки (2026-11-09, после правки владельца)
Симптом верный («я» не должен быть в списке партнёров), но **причина глубже**: в доке
`BC-Client` есть `Client.LinkedPartnerId` — «партнёр-«я»», и именно это смешение вылезло в UI.
Владелец: клиент (аккаунт) и партнёр (участник акта) — **разные контексты**, «я» в акте не
выбирается.

Работа: `03-ddd/01-entity-map.md` (инвариант «я» никогда не Partner; дельта доков §4; открытые
вопросы §5). ADR-024 — черновик, реализация ждёт ответов владельца.

## Технический вердикт (2026-11-04, @AR) — вопрос решается данными и потоком, а не фильтром

**Факты (проверено в коде `origin`):**
1. Фронт `0.88` (`app.js:65`) список партнёров берёт из `Api.partners.list()` (`repository.js:130`), рендерит **все** строки
   (`renderPartners`, `app.js:1117-1130`) — фильтра «я» нет.
2. В контракте `GET /api/v1/partners` признака «я» **нет**: `git grep -i isSelf|selfId -- 6-msa` → **пусто**.
3. **`ClientId` не может отличить «я»**: это *владение* (мой партнёр принадлежит мне), а не *идентичность*. В моём списке
   у **всех** партнёров `ClientId == my sub`, включая «я»-строку старой модели — то есть по `ClientId` они неразличимы.
4. В проде «партнёров-я» — **0** (@DO, проверка по совпадению имени с профилем клиента: 13 партнёров, 10 с `ClientId`, 21 клиент).
5. Онбординг `0.88` больше **не создаёт** партнёра для себя: `POST /api/v1/clients/me/profile` (E7/ADR-024).

**Вывод:** фильтровать в контракте нечего и незачем. «Я» больше не является записью партнёра — это профиль `Client`.
Значит `AR-012` закрывается **не** добавлением `isSelf`/`selfId` (это был бы признак, вычислимый только сравнением с профилем,
то есть склейка двух BC в одном ответе), а тремя условиями:
- онбординг создаёт профиль, не партнёра (сделано в `0.88`);
- легаси-строки «я» в проде отсутствуют (проверено: 0);
- на всякий случай — **однократная** проверка на dev/проде по тому же признаку перед релизом (если появится: чистится данными, не кодом).

**Что остаётся продуктовым (ждёт владельца):** какое имя показывать в интерфейсе для «я» (профиль `Client.displayName`)
и как назвать вкладку — это `AR-011`/`AR-012` в части UX, и оно не требует изменения контракта партнёров.
