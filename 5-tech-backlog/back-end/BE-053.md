# BE-053: Журнал не скоуплен по клиенту — `journal.records` без `ClientId`, `GET /journal` отдаёт всё

- **Статус:** В работе
- **Приоритет:** **P0 (приватность)** — любой клиент видит записи других; именно поэтому владелец увидел 6 чужих актов
- **В работе с:** 2026-11-09
- **Источник:** @DO 2026-11-09 05:45 («это код, а не данные: нужен `ClientId` в `journal.records` + миграция + фильтрация `GET/POST /journal` по `sub`, ровно как в `partners`») + владелец: «в списке актов уже что-то было» (скриншот, 6 записей от 01.11.2026)
- **Зависимости:** BE-048/BE-049 (тот же приём в `partners`), DO-057 (временная мера: мягкое удаление), ADR-021 (client-JWT)
- **Проверяет:** @TL (TechLead; доменный — @AR по границам BC)

## Проблема
`journal.records` **не содержит `ClientId`** и `GET /api/v1/journal` не фильтрует по `sub`. Поэтому клиент видит **все записи журнала** в системе. Чистка данных (DO-057) лечит симптом: следующий клиент снова увидит чужие записи. Это тот же дефект класса, что был в `partners` до BE-048.

## Задача (зона @BE, `6-msa/BC-Journal`)
1. **Модель:** добавить `ClientId` (владелец записи) в `journal.records`; EF-миграция с nullable-семантикой для существующих строк (старые записи без владельца не должны «прилипать» к первому клиенту).
2. **Запись:** `POST /journal` ставит `ClientId` из `sub` (JWT), не из тела.
3. **Чтение:** `GET /journal` фильтрует `WHERE ClientId == sub`; записи с `ClientId IS NULL` **не отдаются** никому.
4. **Тесты:** «A видит только свои», «B не видит записи A», «строка с `NULL` не видна» (тот же набор, что в `PartnerReadRepositoryTests`).
5. **Согласовать с @AR:** как это соотносится с «участники = «я» + `partners[]`» (карта `03-ddd/01-entity-map.md`): запись принадлежит клиенту-автору, партнёры — участники, не владельцы.

## Критерии приёмки
- [ ] `GET /journal` для клиента A возвращает только записи A (проверено на проде фактом).
- [ ] Тесты из п.4 зелёные в `ci-backend`.
- [ ] Владелец не видит ни одной чужой записи, и после нового клиента — тоже.
- [ ] Инвариант **PartnersAreParticipants** (@AR 15:52, BC-Journal/02-aggregate-canvas.md): партнёр — участник, но **не** владелец и не получает доступ.
- [ ] Инвариант **AuthorFromToken**: clientId берётся из JWT sub; попытка задать владельца телом запроса игнорируется/отклоняется (есть тест).
- [ ] clientId **обязателен для новых записей**; NULL — только состояние миграции для легаси-строк, они не отдаются и не «прилипают» к первому клиенту.

## Риск интеграции (обязательно к решению)

BC-Analytics/.../AnalyticsPrecomputeService.cs ходит в GET {journal}/api/v1/journal/records **без токена**. Включение [Authorize] на этом маршруте сломает precompute молча (пустые «Тренды»). Решение — одно из трёх, записать в карточке: (а) внутренний маршрут /internal/journal/records без [Authorize], не публикуется шлюзом; (б) service-to-service токен; (в) оставить /journal/records анонимным, скоуп — только на GET/POST /journal. Нужен тест «precompute проходит» (или «401 не ломает Analytics»).
