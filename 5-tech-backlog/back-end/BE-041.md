# BE-041: `POST /api/v1/clients/refresh` + выпуск refresh-токена при `/verify`

- **Статус:** На проверке
- **В работе с:** 2026-11-02 17:30
- **Приоритет:** P1 (без этого пользователь вылетает в онбординг каждые 15 минут)
- **Источник:** @AR 2026-11-02 17:26 — модель токена зафиксирована: access **15 мин**, refresh **30 дней**, эндпоинт `POST /api/v1/clients/refresh`; PIN — локальный замок, не условие выдачи (ADR-021, `BC-Client/03-command-api.md`)
- **Зависимости:** BE-040 (401 на `/clients/me` — сначала он), BE-038 (JWT-middleware), AR-008
- **Проверяет:** @TL (TechLead)

## Проблема
`ClientTokenService.Issue()` выпускает **только access** (`AddMinutes(15)`) и **не выпускает refresh**. Контракта на обновление нет. Следствие: через 15 минут любой запрос получает 401, и фронт (FE-025/FE-027) уводит пользователя в онбординг — то есть из дневника выбрасывает.

## Задача
1. **Выпуск пары токенов на `/clients/{id}/verify`**: `{ accessToken, refreshToken, expiresAt }` — как в Privacy `TokenService` (`BC-Privacy/.../TokenService.cs`): access 15 мин, refresh 30 дней, HS256, issuer `xdiary`.
2. **`POST /api/v1/clients/refresh`**: принимает refresh-токен, проверяет подпись/срок/`sub`, выпускает новую пару. Невалидный/просроченный refresh → `401`.
3. **Маршрут в шлюзе**: `/api/v1/clients/refresh` — анонимный (refresh-токен сам является credential), `refresh` не должен требовать access-токен.
4. **Не ломать BE-040-фикс**: claim `sub` в access обязателен, `Me()` читает `User.FindFirst("sub")`.
5. Обновить `BC-Client/03-command-api.md` при расхождении с реализацией.

## Критерии приёмки
- [x] `/clients/{id}/verify` возвращает `accessToken` + `refreshToken`.
- [x] `POST /api/v1/clients/refresh` с валидным refresh → новая пара (200); с битым/просроченным → 401.
- [x] `GET /clients/me` работает с новым access.
- [x] В задаче — пример запроса/ответа (для @FE и @TE).
## Результат
Реализовано по эталону Privacy `TokenService` (коммит локальный). `ClientTokenService` выпускает пару: access 15 мин + refresh 30 дней, HS256, issuer `xdiary`, claims `sub=clientId` + `kind=access|refresh` + `phone`.

- `POST /api/v1/clients/{id}/verify {code}` → `{ aggregateId, version, result:"Verified", accessToken, refreshToken, expiresAt }`.
- `POST /api/v1/clients/refresh {refreshToken}` → 200 `{ accessToken, refreshToken, expiresAt }`; битый/просроченный refresh (или `kind != refresh`) → 401.
- Маршрут `/api/v1/clients/refresh` в шлюзе — анонимный (refresh-токен сам credential).
- `GET /clients/me` с новым access → 200 (claim `sub` читается, BE-038).

Пример для @FE/@TE:
```
POST /api/v1/clients/refresh
{ "refreshToken": "<jwt>" }
→ 200 { "accessToken": "<jwt>", "refreshToken": "<jwt>", "expiresAt": "2026-..." }
```
