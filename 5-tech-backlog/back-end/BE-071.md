# BE-071 — бэкфилл read-моделей: `partners_read`/`journal_read` пусты для существующих данных

- **Статус:** ToDo
- **Приоритет:** P1 (проверка «`200`» пройдёт на **пустом** списке — зелёный тест при пустом экране)
- **Источник:** @TE `2026-11-05 08:21` (риск приёмки) + @TL `08:22`: `partners_read` заполняется **только** проекцией событий, бэкфилла в репозитории нет
- **Зависимости:** `BE-069`, `BE-068` (маппинг + DDL + `partners_read`)
- **Проверяет:** @AR

## Задача

`Partners.Api/Events/PartnerEventConsumer.cs` пишет `PartnersReadModel` **только когда приходит событие**
(`IReadModelStore<IPartners, PartnersReadModel>`, `Project(IDomainEvent<…>)`). Значит после выкатки
`partners_read` пуст: партнёры, созданные **до** появления read-таблицы, в проекцию не попадут.

Следствие: `GET /api/v1/partners` вернёт **200 с пустым списком**, и формальная приёмка «200» пройдёт,
хотя данные существуют. Это тот же класс, что «зелёный `grep → 0`» и «`restarts = 0`»: **зелёное
утверждение при пустом результате**.

## Критерии приёмки

- есть **бэкфилл** read-моделей из источника истины (`partners` → `partners_read`,
  `records` → `journal_read`/`journal_defaults`): одноразовая команда или шаг старта, **идемпотентный**;
- критерий приёмки уточнён: `GET /api/v1/partners` изнутри → **200 И непустой список**, если в
  `partners` есть строки (число совпадает с `SELECT count(*)`);
- то же для `journal`: `GET /internal/journal/records` → **200 И** количество записей равно `records`;
- бэкфилл покрыт проверкой: «до бэкфилла — 0, после — N», и это записано в `## Результат`;
- если решено не делать бэкфилл (проекция только вперёд) — это **явное решение** с записью в ADR/ранбуке
  и с критерием «пустой список допустим для исторических данных», а не молчаливая дыра.

## Решение @AR `2026-11-05 12:55` — бэкфилл **обязателен**

**Проверено по коду `origin`:** read-модели пишутся **только** из проекции событий —
`JournalEventConsumer` (`JournalReadModel`, `JournalDefaultsReadModel`), `PartnerEventConsumer`
(`PartnersReadModel`), `PartnersEventsController` (`PartnersDirectoryReadModel`); ни одна read-таблица
**не заполняется из командной БД**. `JournalDataMigration` (`BE-061`) переносит `records` → **события**,
а не в read-store. Значит «проекция только вперёд» допустима **лишь при отсутствии истории**.

**Форма — тот же механизм, что `BE-061`:** идемпотентный шаг (прогон по командной БД → проекция агрегата
в read-store; повтор не дублирует по ключу). Один механизм на сервис: «ещё один бэкфилл рядом» — второй
источник истины в заполнении, он разойдётся с первым при первом изменении модели.

### Критерий приёмки (заменяет «`200`»)

1. `GET /partners` изнутри → **`200` И** число = `SELECT count(*) FROM partners`;
2. `GET /internal/journal/records` → **`200` И** число = `SELECT count(*) FROM records`;
3. **повторный прогон бэкфилла не меняет число** (идемпотентность);
4. на **чистой** БД: старт + создание таблиц + бэкфилл `0` ⇒ `200` с пустым списком (норма).

Причина: read-модель — это то, что видит пользователь; пустой журнал при неполной БД — **потеря истории**
в продукте, где история и есть ценность. Формально БД цела, а продукт говорит «данных нет».

## Уточнение критерия по клиенту (@TE `2026-11-05 08:40`, учитывать при приёмке)

`GET /partners` возвращает **список клиента**, а `SELECT count(*)` по `partners_read` считает **все**
строки. Если у тестового клиента партнёров меньше, чем строк в таблице, числа не совпадут **на законных
данных** — это ложное красное.

**Правильный критерий:** `count(GET /partners) == SELECT count(*) FROM partners_read WHERE "ClientId" = <clientId>`,
либо сравнение с `count(*)` по клиенту, чей токен используется. Для `journal` — то же с учётом области
клиента.

## Диагноз и точная правка (@TL `2026-11-05 09:59`, по факту выкатки @DO)

**Факт с контура:** `journal_read` = 20 колонок, `/internal/journal/records` → **200**, `42P01` = 0 —
схема и ручка в порядке. Но `records` = 4 при `journal_read` = **0**; `check_read_model_freshness`
даёт `НАРУШЕНИЕ — эндпоинт пуст, а в БД 4 строк`, `rc=1`. `DataMigration__Enabled=true` был включён —
и **не сработал**: в логе нет ни одной публикации события.

**Причина — первая же строка цикла** (`JournalDataMigration.cs`, метод `MigrateAsync`):

```csharp
var existing = await _store.GetEventCountAsync(e.Id, ct);
if (existing > 0) continue;
```

`_store` — это `IEventStoreRepository<IJournal, IJournalAnemicModel>`, то есть запрос идёт в
**событийное хранилище** (`Commands.DomainEvents`). В проде этой таблицы нет (журнал исторически
писал в EF-таблицу `records`, а не в event store), поэтому проверка падает/не находит данные —
и до `PublishAsync` дело не доходит. Это не «флаг не тот», а «проверка требует того, чего нет».

**Правка (минимальная, без второго пути записи):**

1. убрать `GetEventCountAsync` из цикла — идемпотентность обеспечивает **проекция**: `UpsertAsync`
   пишет `ON CONFLICT (Id)`, повтор перезаписывает те же поля;
2. повторный запуск должен давать **то же** число (`journal_read` 4 → 4), а не 8;
3. события идут тем же путём `IEventBusProducer → JournalEventConsumer → UpsertAsync` — второго
   пути записи в read-модель не появляется.

**Альтернатива, если хочется сохранить предварительную проверку:** создать схему событийного
хранилища на проде (это вопрос к библиотеке `AddEventStorePostgres` — почему таблицы нет).
Это дороже и это отдельная задача (@AR), а не блокер бэкфилла.

**Проверка приёмки:** `accept_read_path.py --partners-read 13 --partners-src 13 --journal-read 4
--journal-src 4 --journal-http 200 --partners-http 200 --contract-passed 4 --contract-failed 0
--rerun-journal-read 4 --rerun-partners-read 13` → `rc=0` (`@TE`, `--selftest 8/8`).
