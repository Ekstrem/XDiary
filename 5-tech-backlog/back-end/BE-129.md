## 🔄 Переформулировка (2026-11-18 16:13): **не дефект кода, а рассинхрон схемы БД стенда**

**Факты:**
- @DO (16:12): dev крутит ровно `single-378a56c`, `RepoDigests` совпадают с lock (`partners sha256:8fe6a72…`, `journal sha256:512f923d…`), оба контейнера `Up 7 hours` ⇒ **стенд не старее lock**;

**Единственное, что различает «работает у @BE» и «500 на стенде»** — состояние схемы: на dev колонки добавлялись **руками** (`ALTER`), а в `main` это делают миграции (`AddStateToJournalRead`, `AddVersionToJournalRead`). Если в dev `journal_read` не хватает колонки (или тип/`NULL`-ность иная), то `RecordEventReplay`/запрос падает на старой схеме, хотя код тот же.

**Проверка (одна, зона @DO):**
```bash

```
Сверить с миграциями `20261116130100_AddStateToJournalRead` и `20261117210000_AddVersionToJournalRead` из `main`.

- **колонки не хватает / другой тип** ⇒ корень = рассинхрон схемы; лечится прогоном миграций (`Database.Migrate()` в образе из `main`), а не кодом Journal;
- **схема совпадает** ⇒ тогда 500 связан с данными (конкретная запись), и нужен лог исключения — но это уже не тот дефект, который мы искали.

## 🔎 Схема read-модели проверена @DO (16:14) и **исключена** → остаётся **легаси-данные в EventStore**

```
\d journal_read  → State integer NOT NULL DEFAULT 0 · Version bigint NOT NULL DEFAULT 0
__EFMigrationsHistory → 20261116130100_AddStateToJournalRead ✔ · 20261117210000_AddVersionToJournalRead ✔
```

⇒ read-схема полная. Но `/when` и `/partners` — это **command-путь**: `GetAggregateAsync` → чтение `Commands.DomainEvents` и **десериализация** `ChangedValueObjectsJson`.

**Почему у @BE не воспроизводится, а на стенде 500:** @BE проверял на **свежей** БД (его локальный Postgres), где все события записаны **текущим** сериализатором. На dev в `DomainEvents` лежат события, записанные **до** фикса `$type`-дискриминатора (`@TE 04:32`), — тогда `IValueObjectJsonConverter` не может их прочитать ⇒ исключение ⇒ 500 именно на командах (чтение списка идёт из read-модели и работает).

**Решающая проверка (одна строка, зона @DO):**

```sql
SELECT "Version", left("ChangedValueObjectsJson", 200)
FROM "Commands"."DomainEvents"
WHERE "Id" = 'cc752cae-f516-454d-a54a-461afbef857d'
ORDER BY "Version";
```

- в JSON **есть** `"$type"` ⇒ версия неверна, идём в логи исключения;
- в JSON **нет** `$type` ⇒ **корень найден:** легаси-события без дискриминатора; лечится либо обратной совместимостью в конвертере (@BE), либо очисткой dev-данных (@DO) — но **не** «схемой read-модели».

**Критерий:** `POST /journal/records/{id}/when` и `/partners` → `200` на dev без правок данных вручную.

## 🔁 Гипотеза «легаси без `$type`» опровергнута (@DO 16:16) → **`StartedAt = 0001-01-01`**

@DO по id `cc752cae-…`:

```
has_type = t
"Root": {"$type": "Journal.Domain.Implementation.RecordRoot, Journal.Domain, Version=1.0.0.0…",
         "value": {"Partners": [], "StartedAt": "0001-01-01T00:00:00+00:00"}}
```

⇒ `$type` **есть**, легаси-версия не при чём.

**Что видно в данных:** `StartedAt = 0001-01-01` (`DateTimeOffset.MinValue`) — это **черновик**, созданный `POST /journal/records` **без тела** (`StartManualEntry` ставит `MinValue`).

**Почему это может валить команды, хотя «свежая БД работает»:** у @BE в тестах записи создаются с реальной датой, а на dev —
- либо сериализация/десериализация `DateTimeOffset.MinValue` с ненулевым смещением (`0001-01-01T00:00:00+03:00` → `-0001-12-31T21:00` → **underflow**),
- либо арифметика/валидация в `SpecifyWhen`/`AddPartner` на `MinValue`.

`RecordRoot` объявлен как `internal sealed record RecordRoot(IReadOnlyList<string> Partners, DateTimeOffset StartedAt)` — то есть тип правильный; вопрос в значении, а не в типе.

**Дешёвый эксперимент для @BE (5 минут, на его локальной БД):**
1. `POST /journal/records` **без тела** (создать черновик с `MinValue`);
2. сразу `POST /journal/records/{id}/when {startedAt}` и `POST …/partners {partnerId}`;
3. если 500 воспроизводится — корень в `MinValue`-черновике (а не в `$type`, не в схеме, не в конвертере как таковом).

**Критерий:** `/when` и `/partners` → 200 на записи, созданной без тела.
