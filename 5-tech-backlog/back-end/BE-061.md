## Задача (зона @BE, `6-msa/`)

1. Одноразовая миграция: существующие строки EF-таблиц (`journal.records`, `partners`) превращаются в **события** (по одному событию создания на агрегат/запись, с исходными датами и автором).
2. Проекция прогоняется по этим событиям — read-model должна дать **те же** данные, что были в таблицах (количество, порядок, ключевые поля).
3. Идемпотентность: повторный прогон миграции не создаёт дублей (по `id` записи).
4. Прогон на dev на реальном объёме, затем на проде в окне с бэкапом.

### Сценарий теста, которого не хватает (@TL 2026-11-11 22:50) — **чтобы это была спецификация, а не пожелание**

Тест уровня `Journal.ApiTests` (зона `@BE`), три части:

1. **Дано:** подготовить «старое» состояние — записи журнала без `ClientId` (или с `null`), известное число агрегатов `N_before` и событий `E_before`.
2. **Когда:** прогнать `JournalDataMigrationRunner` (полный прогон миграции).
3. **Тогда (инвариант G1):**
   - `N_after == N_before` и `E_after >= E_before` — ни один агрегат не потерян;
   - у каждой записи `ClientId != null` (или документированное исключение с причиной);
   - **повторный прогон миграции не создаёт дублей** (`N_after2 == N_after`) — идемпотентность;
   - число событий не уменьшилось ни в одном потоке.

- **Почему идемпотентность обязательна:** миграция запускается раннером на старте; если она не идемпотентна, второй рестарт удвоит данные — и это будет тише, чем любая ошибка компиляции.
- **Почему без теста нельзя:** карточка именно про «перенести существующие данные»; без инварианта «до/после» единственное доказательство — «на стенде вроде заработало», а это ровно тот класс, где `ERRATA` №26 (пустое состояние как результат).
