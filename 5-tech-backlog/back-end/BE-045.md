# BE-045: `pin/has` после снятия PIN возвращает `true` — серверный assert не проходит

- **Статус:** В паузе
- **Приоритет:** P2 (E2E `remove-pin`; продуктовый эффект ниже, чем у FE-031)
- **Источник:** `ci-front` #5 (`77b145b`), лог шага (нашёл @DO): `views (ПОСЛЕ ПАДЕНИЯ) = view-settings=visible`, остальные hidden — UI дошёл до настроек, падение на assert «после снятия `pin/has` = false»
- **Зависимости:** BE-034 (скоупинг `pin/has` по устройству), BE-036, ADR-008 (серверный PIN — legacy, вне MVP), ADR-021 (локальный PIN — канон)
- **Проверяет:** @TL (TechLead)
- **Пауза:** ждём архитектурного вердикта — исполнитель не должен решать, legacy контракт или живой (это зона @AR).
- **Разблокирует:** AR-009 (вердикт по серверному PIN, ADR-021 п.3)

## Контекст
Серверный `/api/v1/privacy/pin/*` — **legacy** (ADR-008). В MVP локальный PIN живёт в IndexedDB (`window.Pin`), а серверный PIN не используется продуктом. Но спек `remove-pin` продолжает проверять серверный `pin/has` — и падает.

## Задача — выбрать один из двух путей (и записать выбор в задаче)
**A. Починить серверный контракт:** `DELETE /privacy/pin` (или соответствующий) должен реально сбрасывать состояние устройства, чтобы `GET /privacy/pin/has` возвращал `false`; проверить, не остаётся ли запись из-за скоупинга по `deviceId` (другой deviceId в следующем запросе).
**B. Признать спеку legacy:** если продукт серверный PIN не использует (ADR-021 п.3), спек `remove-pin` перевести в `describe.skip` с причиной (как `change-pin`/`no-pin`), а проверку перенести на **локальный** `window.Pin` (`hasPin()` через IndexedDB).

Рекомендация: **B** (соответствует ADR-021: серверный PIN — legacy; проверять надо локальный), но решение фиксируется по факту кода.

## Критерии приёмки
- [ ] Выбранный путь записан в `## Результат` со ссылкой на ADR.
- [ ] `remove-pin` либо зелёный, либо `skipped` с причиной «серверный PIN — legacy (ADR-021 п.3), проверка локального PIN в TE-037».
- [ ] Нет «тихого» расхождения: если серверный путь остаётся, он покрыт тестом.
