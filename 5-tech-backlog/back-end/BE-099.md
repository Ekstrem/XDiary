## Задача

`6-msa/BC-Journal/src/Journal.ApiTests/PartnerSoftDeleteTests.cs:174-175`:

```csharp
// История остаётся разрешимой: имя видно ПОСЛЕ мягкого удаления партнёра.
Assert.Contains(partnerName, afterBody, StringComparison.Ordinal);
```

**Что происходит:** до `remove` имя в ответе журнала есть (`:163-165`), после `POST /partners/{id}/remove` — **имя исчезает**. То есть запись журнала остаётся, а её человекочитаемое имя — нет: история технически есть, но пользователь видит идентификатор вместо «с кем».

**Где смотреть:**
- `JournalReadRepository.cs:90` — «TE-102: имя `lastPartner` резолвим из `partners_directory`» — значит резолв идёт через проекцию;
- `PartnersEventsController.cs:10` — «E1 (срез `Partner.Removed` → `partners_directory`)» — событие удаления приходит в журнал;
- вопрос, который надо решить кодом: **удаление должно оставлять имя в `partners_directory`** (строка с `DeletedAt`), а не удалять/обнулять его; резолв в журнале — не фильтровать по `DeletedAt` для исторических записей.

### Причина названа построчно @TL 2026-11-13 10:30 (ревизия `dbbff5247`) — **фильтр `DeletedAt is null` при резолве имён**

`6-msa/BC-Journal/src/Journal.Storage/JournalReadRepository.cs`:

```csharp
:29  private async Task ResolveNamesAsync(IEnumerable<JournalReadModel> models, CancellationToken ct)
:33      var dir = await _dir.GetAllAsync(new Paging(1, int.MaxValue), ct);
:34      var byId = dir.Where(x => x.DeletedAt is null)      // ← вот здесь удалённые выпадают
:35          .ToDictionary(x => x.PartnerId, x => x.Name);
:38      m.PartnersNames = m.Partners
:39          .Select(id => Guid.TryParse(id, out var g) && byId.TryGetValue(g, out var n) ? n : id)
:40          .ToList();                                   // не нашли имя → отдаём id
```

- **Механика дефекта:** после `POST /partners/{id}/remove` строка в `partners_directory` остаётся (с `DeletedAt`), но `ResolveNamesAsync` её **исключает** из словаря (`:34`) — и `:39` честно отдаёт `id` вместо имени. Отсюда `Assert.Contains(partnerName, afterBody)` на `:175` контрактного теста падает.
- **Тот же фильтр есть во втором месте — и там он, скорее всего, уместен:** `GetRecentAsync` (`:95`) — «последние партнёры» для визарда не должны предлагать удалённого.
- **Правка, которую предлагаю (зона `@BE`):**
  1. `ResolveNamesAsync` (`:34`) — строить словарь **без** фильтра `DeletedAt is null`, чтобы **история** читалась (имя у записи — факт прошлого, оно не должно зависеть от текущего статуса партнёра);
  2. `GetRecentAsync` (`:95`) — фильтр **оставить** (это выбор из доступных сейчас);
  3. в комментариях к обоим местам — одна строка «почему по-разному», иначе следующий правщик снова унифицирует их и вернёт дефект.
- **Критерий не меняется:** `passed: 4, failed: 0` прогоном `test-partner-softdelete`.
- **Граница:** проверено чтением кода; прогон — за `@DO` (локально `testhost` не стартует, `spawn EPERM`/`EnsureWatchingForExit`).
