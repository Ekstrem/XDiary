# BE-036: PIN per-client — миграция `pin_credential.client_id` + команды по JWT

- **Статус:** Открыта
- **Приоритет:** P1 (снимает инцидент «E2E затёр PIN владельца»; закрывает AR-008 и DO-024)
- **Источник:** AR-008 (`03-ddd/BC-Privacy/02-aggregate-canvas.md` L19, `03-command-api.md` L4, `adr-008.md` L31), инцидент 2026-11-05
- **Зависимости:** AR-008 (контракт), DO-024 (E2E не должен затирать PIN), ADR-021 (`sub = clientId`)

## Задача
Реализовать per-client PIN по контракту @AR:
1. **Модель:** `PinCredential.clientId` (uuid) — чей PIN. Миграция БД: колонка `client_id` в `privacy.pin_credential` (+ индекс/уникальность).
2. **Инвариант `SinglePinPerClient`** — один PIN на клиента (валидатор в агрегате, как `SingleSourcePerClientValidator` в BE-032).
3. **Команды/запросы:** `pin/set|change|remove|verify|has` — работают в скоупе `clientId` из JWT (`sub`). Без JWT — 401 (кроме `pin/set` при первичной установке, если так решено контрактом — уточнить у @AR).
4. **`/privacy/token`** — выдаёт JWT клиента, PIN проверяется в скоупе `clientId`.
5. **Миграция данных:** существующие PIN-записи (без `clientId`) — либо привязать к первому клиенту при старте, либо очистить (dev/prod согласовать с @DO; на проде — сохранить владельца).

## Критерии приёмки
- [ ] Два клиента на одном стенде имеют **независимые** PIN: смена/удаление одного не влияет на другого.
- [ ] `pin/has` и `pin/verify` скоупятся по `clientId` из JWT.
- [ ] Миграция применяется без потери доступа владельца на проде (согласовать с @DO).
- [ ] Тесты в `9-tests` (негатив: чужой `clientId`; позитив: два клиента) зелёные, CI `test` не красный.
- [ ] После этого `7-deploy/reset-dev-pin.sh` может сбрасывать PIN **только тестового клиента** (снимает DO-024).
