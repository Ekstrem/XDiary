- **Зависимости:** нет (класс `BE-134`, но другая форма: не «проекция не применяет», а «проекции нет вовсе»)

## Замер (dev, 2026-11-19)
```
POST /api/v1/catalog {"kind":"toy","name":"TL-CAT-…"}          → 200, id 2ab596bd-…, version 1795076429013 (ms!)
POST /api/v1/catalog {"id":"2ab596bd-…","kind":"toy","name":…}  → 200, тот же id            ← идемпотентность по id РАБОТАЕТ
GET  /api/v1/catalog                                            → 200 []  (элементов 0; и через 1 с, и через 3 с)
```
То есть команда принимается, идемпотентность по клиентскому `id` подтверждена, а **чтение пусто** — позиция в список не попадает.

## ИСПРАВЛЕНО 2026-11-19 11:24 — мой первый корень был НЕВЕРЕН

**Дамп @DO по БД `catalog` (три таблицы: `__EFMigrationsHistory`, `catalog_items`, `catalog_read`):**
```
catalog_items — 10+ записей, у ВСЕХ ClientId = NULL
колонка ClientId: uuid, nullable, есть индекс IX_catalog_items_ClientId
```
⇒ `GET /catalog` с фильтром по `ClientId` **законно** возвращает пусто. Дефект **не** в отсутствии проекции: записи создаются и лежат, но **не привязаны к клиенту**.
Плюс это согласуется с каноном EDM `05baa758a` («BusAdapter: store в command-path, не fire-and-forget») — запись попадает в `catalog_items` синхронно, поэтому «нет консьюмера» не объясняет 10 записей.

**Следствие для задачи:** фикс — в `CreateCatalogItem` (проставлять `ClientId` из актора) и/или в `LinkCatalogItem`, **а не** в добавлении проекции. Моя исходная формулировка («нет обработчика событий ⇒ read-модель никем не наполняется») отозвана — она противоречит дампу.

## Первый (ошибочный) разбор — оставлен для истории
В `6-msa/BC-Catalog/src/Catalog.Api/` **нет ни одного обработчика событий** (в каталоге файлов: `Program.cs`, `CatalogController.cs`, `HealthChecks/`, `HttpActorProvider.cs` — и всё). При этом read store зарегистрирован: `Program.cs:35` — `AddReadStorePostgres<ICatalog, CatalogReadModel, ReadDbContext>(…)`.
⇒ read-модель создаётся пустой и **никем не наполняется**: `GET /catalog` читает таблицу, в которую никто не пишет.

Для сравнения, как это сделано правильно: в `BC-Client` есть `Events/ClientEventConsumer.cs` + `AddHostedService<ClientEventConsumer>()` и `AddSingleton<ClientEventHandler>()` (см. `BE-134`).

## Задача
Добавить в `BC-Catalog` проекцию: консьюмер (как `ClientEventConsumer`: `IEventBusConsumer`, подписка, `IServiceScopeFactory` для scope-зависимостей) + проекция `ChangedValueObjects → CatalogReadModel` (`Id`, `Kind`, `Name`, `Deleted`) + регистрация `AddHostedService` и хендлера; плюс миграция read-таблицы, если полей не хватает.
Заодно проверить `Version`: ответ команды отдаёт **ms-таймстамп** (`1795076429013`) ⇒ при stale-skip понадобится `LegacyTimestampFloor` (как в `BE-137`).

## Критерии приёмки
- `POST /catalog {kind,name}` → `GET /catalog` содержит созданную позицию (по `name` и `id`);
- `POST` с тем же клиентским `id` не создаёт дубль (идемпотентность сохраняется);
- удаление (`/remove`) убирает позицию из списка;
- проба @TE `probe_catalog` печатает `чтение: непусто` вместо `::warning::`.

## Воспроизведение (@TE, три прогона на dev — просил внести в карточку)

```
POST /catalog {kind, name} с одним и тем же id  → 200 дважды, в ответе ТОТ ЖЕ id   (идемпотентность записи есть)
GET  /catalog/<id>                              → 404
GET  /catalog                                   → 200 []   и через 1 с, и через 3 с
```

**Что это доказывает:** запись проходит и идемпотентна, а чтение не отдаёт ни элемент, ни список. Вместе с дампом @DO (`catalog_items` 10+ записей, у всех `ClientId = NULL`) это даёт полную картину: **данные есть, но не привязаны к клиенту**, поэтому фильтр `GET /catalog` по `ClientId` законно пуст, а `GET /catalog/<id>` для чужого/несвязанного элемента отдаёт 404.

**Критерий приёмки после фикса:** `POST /catalog` → `GET /catalog` содержит позицию; `GET /catalog/<id>` → **200**; идемпотентность по `id` сохраняется (два POST → один элемент).

**Регресс-защита:** проба @TE `9-tests/scripts/probe_catalog_idempotency.js` (`#2994`) — теперь разделяет запись и чтение: `rc=0` при идемпотентности, а пустое чтение печатает `::warning::` с классом `BE-138`, а не ложное «идемпотентность не подтверждена».
