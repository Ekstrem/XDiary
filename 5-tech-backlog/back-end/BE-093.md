## Факт (код, не догадка)

`6-msa/BC-Journal/src/Journal.Api/Events/JournalEventConsumer.cs`:


А `JournalProjection.Project` заполняет **только четыре** поля:

```csharp
:125  return new JournalReadModel
:126  {
:127      Id = domainEvent.Id,
```

`JournalReadModel` же содержит **~20 полей**: `DurationMin`, `Place`, `Positions`, `Tags`, `Costumes`, `Toys`,
`Fantasies`, `Contraceptives`, `ContraceptiveCount`, `Orgasms`, `Garmin`, `GarminId`, `CreatedAt`, `UpdatedAt`, `Deleted` и др.

## Следствие (если `UpsertAsync` = «вставить или заменить строку целиком»)

Любое событие, меняющее `Root` (например `AddPartner`), **перезаписывает строку read-модели моделью из 4 полей** ⇒
все остальные значения (`Place`, `Tags`, `Orgasms`, `Garmin*`, `CreatedAt/UpdatedAt`, `Deleted`…) становятся
**значениями по умолчанию**. События, не меняющие `Root` (например `Complete`), наоборот **не проектируются вовсе** —
но это безобидно, пока в модели нет поля статуса (его действительно нет).

Проверить одной операцией: создать запись с `Place`/`Tags`, затем выполнить действие, меняющее `Root` (добавить партнёра),
и прочитать запись. Если `Place`/`Tags` пусты — дефект подтверждён.

## Почему это важно

`BE-077` («52 из 2481») до сих пор не имел объяснения: по логам всё зелёное, события пишутся, а данные расходятся.
Частичный upsert объясняет расхождение **без** падений и ошибок — данные просто затираются «зелёным» путём.

## Что сделать

1. **Не upsert-ить частичную модель.** Варианты:
   - **read-modify-write:** прочитать существующую строку, обновить только поля, которые пришли в diff (`Root`, `ClientId`), остальное сохранить;
   - **или** патч на уровне SQL (`UPDATE … SET partners=…, started_at=… WHERE id=…`), без полной замены.
2. `Project` должен возвращать **не** `JournalReadModel`, а **diff-набор** (пары «поле → значение»), чтобы невозможно было
   «случайно затереть» то, чего в событии нет. Это же устранит класс «новое поле забыли в проекции».
3. Тест: запись с `Place`/`Tags`/`Orgasms` → действие, меняющее `Root` → поля **на месте**; и тест «новое поле модели не
   обнуляется событием, которое его не меняет».

## Критерии приёмки

- после события, меняющего `Root`, остальные поля строки **сохраняются**;
- тест «частичный upsert не затирает поля» падает на текущем коде и проходит после правки;
- `## Результат`: прогон с числами (до/после: сколько полей непустых у записи после N событий).

## Канон @AR §15 «Проекция обязана применять дельту» — инварианты для правки

`04-architecture/edm-canon.md` §15 фиксирует: `ChangedValueObjects` — **диф**, поэтому отсутствие ключа `Root` у события,
меняющего не корень (`Complete()` → только `Status`), это **норма**, а `return null` на этом основании — **дефект проекции**.

Инварианты (положить в основу правки):

1. **Идентификатор агрегата есть у любого события** — он в **конверте**, а не в диффе; проекция берёт его оттуда, а не из `Root`.
2. **Отсутствие ключа ≠ основание пропустить событие:** применяем **имеющиеся** поля (`UPDATE … SET status=…`).
3. `null`/«пропустить» допустимо **только** если событие не несёт **ни одного** применимого поля — и это **явное** решение с логом.
4. Перед `null` проекция обязана различать «**нечего применять**» и «**не понял событие**»; второе должно быть **видно**
   (счётчик/`/health`), а не тонуть в тишине.

## Связь с текущим дефектом

- `Complete()` (только `Status`): в `JournalReadModel` **нет** поля статуса ⇒ по инварианту 3 применять нечего — это законный
  пропуск, но он должен быть **явным** (лог/счётчик), а не молчаливым `null`.
- `AddPartner` (`Root` меняется): сейчас вызывается `UpsertAsync(частичная модель)` ⇒ **затираются** `Place`, `Tags`, `Orgasms`,
  `Garmin*`, `CreatedAt/UpdatedAt` и др. Это **инвариант 2 в самом грубом виде** — «применили» не то, что пришло.

Обе части лечатся одной правкой: `Project` возвращает **дельту** («поле → значение»), а применение — **патч** к существующей строке.
