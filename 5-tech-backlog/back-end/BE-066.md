# BE-066: `Jwt:SigningKey` — один фолбэк на все сервисы или fail-fast (сейчас разные фолбэки = тихий 401)

- **Статус:** ToDo
- **Приоритет:** P1 (класс «тихий 401, который выглядит как правильная защита»)
- **Источник:** @DO 2026-11-11 06:00: у шлюза фолбэк-ключ `xdiary-dev-signing-key-32bytes-min!`, у клиента `…minimum-32-bytes-2026` — **разные**; при отсутствии `Jwt__SigningKey` приложение **не падает**, а отдаёт **401 на всех защищённых путях** при `/health` 200 и `GET /clients` 401, то есть неотличимо от корректной работы
- **Зависимости:** ADR-008 (JWT), инцидент 2026-11-11 (потеря env у шлюза при пересоздании)
- **Проверяет:** @TL (код) + @DO (деплой-проверка)

## Проблема

Отсутствие `Jwt:SigningKey` в окружении **не диагностируется**: каждый сервис подставляет свой dev-фолбэк, ключи не совпадают, и результат — молчаливое 401 на защищённых маршрутах. Именно это стоило нам утреннего расследования (искали причину в сервисах, а резал шлюз).

## Задача (зона @BE, `6-msa/`)

1. **Один источник значения**: `Jwt:SigningKey` читается одинаково во всех сервисах (общий extension/хелпер), фолбэк — **один на весь репозиторий** либо **отсутствует**.
2. **Fail-fast:** если `Jwt:SigningKey` не задан в **не-Development** окружении — приложение **падает на старте** с внятным сообщением («Jwt:SigningKey не задан»), а не работает с фолбэком.
3. Убрать из кода литералы dev-ключей, если они не нужны для локального запуска (это ещё и минус секретоподобные строки в публичном репозитории, §6).

## Критерии приёмки

- [ ] Запуск без `Jwt__SigningKey` в проде/`Single` → **падение на старте** с явным сообщением (проверено фактом).
- [ ] Запуск с ключом → `GET /clients/me` 200, `GET /journal/records` 200, `GET /partners` 200 (тот же токен).
- [ ] В `6-msa/` не осталось **разных** фолбэк-ключей (`git grep` по литералам — 0 или один общий).
- [ ] Ранбук @DO дополнен: «после пересоздания шлюза `grep -c '^Jwt__'` ≥ 1», плюс «если сервис упал на старте с сообщением про ключ — это правильное поведение, а не авария».
