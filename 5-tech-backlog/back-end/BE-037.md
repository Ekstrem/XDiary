# BE-037: OTP никуда не отправляется — онбординг на проде невозможен

- **Статус:** Закрыта
- **Приоритет:** P1 (блокирует вход на проде: identity = телефон + OTP, а кода нет)
- **Источник:** разбор `6-msa/BC-Client/src/Client.Application/Commands/ClientHandlers.cs` + @DO 2026-11-05 19:20 (на проде `client.clients` = 0 строк, PIN = 1)
- **Зависимости:** ADR-021 (`/register` → `/verify`), DO-025 (миграция PIN)

## Проблема
`RegisterClientHandler`:
```csharp
var otp = _testOtp ?? Random.Shared.Next(100000, 1000000).ToString();
```
- на **dev** код берётся из `Clients:TestOtp` (`000000`) и его «знают» снаружи;
- на **prod** `TestOtp` не задан → генерируется случайный код, который **никуда не уходит**: в репозитории **нет ни одного транспорта** (SMS/Telegram/e-mail) — проверил, совпадений `Twilio|Smsc|ISmsSender|SendAsync` в `6-msa` нет.

Итог: на проде нельзя пройти онбординг → нельзя создать клиента → **нельзя привязать существующий PIN владельца** (DO-025 упёрся именно в это: `pin_credential` = 1, `client.clients` = 0).

## Задача
1. Выбрать транспорт доставки OTP (решение владельца): SMS-провайдер, Telegram-бот, e-mail — или подтвердить, что прод остаётся single-user и онбординг делается вручную.
2. Реализовать `IOtpSender` с одной реализацией, конфиг в `.env` (секреты — только там).
3. В dev оставить `Clients:TestOtp` (не ломать E2E), в prod — реальный транспорт.
4. Логировать факт отправки без кода; код — не писать в логи.

## Критерии приёмки

## Решение по каналу (README-факт, не вопрос)
ADR-021 §Решение п.2: «верификация — **SMS OTP** (для MVP — упрощённо)». Канал **уже выбран на проектировании**. Мой вопрос владельцу «какой канал» был ошибкой процесса: следовало идти по ADR и просить не решение, а **доступ** (ключи/аккаунт провайдера) либо MVP-упрощение в рамках ADR.

### Объём к реализации (@BE, BE-037)
1. `IOtpSender` остаётся; **две реализации**:
   - `SmsOtpSender` — боевой канал по ADR (провайдер из конфига: `Otp:Sms:Provider`, `Otp:Sms:ApiKey`, `Otp:Sms:Sender`);
   - `TelegramOtpSender` — **MVP-упрощение**, допустимое формулировкой ADR (`Otp:Telegram:BotToken`, `Otp:Telegram:ChatIdMap`).
2. Выбор реализации — по конфигу (`Otp:Channel = sms | telegram | log`); `log` — только dev/CI.
3. Ключи — в `.env`/Secrets (@DO), не в git; `guard-secrets` зелёный.
4. От владельца нужен **только доступ**: аккаунт SMS-провайдера **или** Telegram-бот-токен. Это не выбор архитектуры — это ключи (шаг @DO).

## Проверка TL (2026-11-06 02:25) — два дефекта, не блокирующие архитектуру
- ✅ Все 4 сендера (`Log`/`Sms`/`Telegram`), селектор `Otp:Channel = sms|telegram|log` (default `log`) — `Program.cs:27-32`.
- ✅ Fallback-чат: `Otp:Telegram:ChatIdMap:<phone>` → иначе `Otp:Telegram:ChatId` (один чат) — этого достаточно для теста нескольких аккаунтов.
- ❌ **В тексте сообщения нет телефона:** `text=Uri.EscapeDataString("Ваш код: {otp}")`. При fallback в один чат коды разных аккаунтов неразличимы. Нужно: `"Код для {phone}: {otp}"`.
- ❌ **Нет сигнала об ошибке:** `SendAsync` возвращает `Task`; при пустых `BotToken`/`ChatId` только `LogWarning`, а `RegisterClientHandler` идёт дальше. Клиент создаётся, код не доставлен, онбординг висит — то, чего мы хотели избежать. Нужно: `Task<bool>` (или исключение) + в handler при `false` вернуть `Fail("канал OTP не настроен")`.
