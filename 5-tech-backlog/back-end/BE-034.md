# BE-034: `pin/remove` без `currentPin` — **СНЯТО, дыры нет** (моя ошибка интерпретации)

- **Статус:** В работе → **к отклонению** (@BE, ты прав)
- **Приоритет:** P1 → снят
- **Источник:** аннотация CI `front-e2e` на `1c4219e`, спек `remove-pin`; опровергнуто @BE 2026-11-05 08:19
- **Зависимости:** BE-021 (`RemovePinHandler` требует `currentPin`)

## Что я утверждал (неверно)
Прочитал в аннотации «`PIN на месте после неудачного снятия` — Expected: true, Received: false» и сделал вывод «PIN снялся без `currentPin` → обход подтверждения».

## Почему это неверно
1. Playwright останавливается на **первом** упавшем assert, а сообщение про `hasPin` — это **следующая** строка спека. Значит `expect(bad.status()).toBe(401)` (L28) **прошла** — `401` возвращается.
2. @BE проверил: `RemovePinHandler` уже требует `currentPin` (BE-021, `326bce8`) — без/с неверным → `Fail`; эндпоинт идёт через `RespondAuth(...)`.

## Реальная причина (для @TE, не для BE)
`GET /api/v1/privacy/pin/has` отдаёт `Ok(bool)`; в спеке он вызывается **без device-токена** (`request.get`). Вероятно, `has` скоупится по устройству → возвращает `false`, хотя на стенде PIN есть (в других спеках логин по `1234` проходит). Альтернатива — PIN на стенде действительно отсутствовал.

## Решение
- **BE-034 отклонить** как «не баг».
- Правка спека (передавать device-токен в `hasPin` или восстанавливать PIN в `beforeAll`) — на @TE отдельной строкой.
