## 🎯 КОРЕНЬ НАЙДЕН (статический разбор @TL): миграция `AddVersionToPartnersRead` не имеет `.Designer.cs` и атрибутов → EF её **не применяет**

**Файл:** `6-msa/BC-Partners/src/Partners.Storage/Migrations/ReadStore/20261117210000_AddVersionToPartnersRead.cs`

```csharp
public partial class AddVersionToPartnersRead : Migration   // ← нет [DbContext(...)] и [Migration("...")]
{
    protected override void Up(MigrationBuilder migrationBuilder) =>
        migrationBuilder.AddColumn<long>(name: "Version", table: "partners_read", type: "bigint", nullable: false, defaultValue: 0L);
}
```

**Чем это отличается от рабочих миграций того же проекта:**

| миграция | `.cs` | `.Designer.cs` |
|---|---|---|
`20261105170447_AddReadStores` | есть | **есть** ← атрибуты `[DbContext]`/`[Migration]` лежат в нём |
`20261117210000_AddVersionToPartnersRead` | есть | **НЕТ** |

EF Core находит миграции **по атрибутам** `[DbContext(typeof(ReadDbContext))]` + `[Migration("<id>")]`, которые генерируются в `.Designer.cs`. Здесь их нет → `Database.Migrate()` эту миграцию **не видит** → колонка `Version` в `partners_read` не создаётся → `PartnersReadModel.Version` (поле есть в модели, `public long Version { get; set; }`) попадает в SELECT → PostgreSQL `42703` → **500**.

**Это же объясняет `journal`:** там ровно та же картина — `20261117210000_AddVersionToJournalRead.cs` **без** `.Designer.cs` (у `AddStateToJournalRead` Designer есть). Поэтому `journal` тоже пришлось лечить руками (`ALTER` + `INSERT` в историю), и та же причина ударит на любой **свежей** БД — в том числе на проде.

## Что нужно (зона @BE)

1. Сгенерировать Designer для обеих миграций (правильный путь): `dotnet ef migrations add AddVersionToPartnersRead ...` → EF создаст `.Designer.cs` и запишет `[DbContext]`/`[Migration]`; либо добавить атрибуты руками.
2. Проверить, что `ReadDbContextModelSnapshot.cs` содержит `Version` (содержит — значит снапшот уже обновлён, не хватает только атрибутов/Designer).
3. **Проверка на свежей БД** (без неё фикс не считается): поднять пустой Postgres, `Database.Migrate()`, затем `GET /partners` → 200. Именно это ловит класс «миграция есть в файлах, но не применяется» — в CI это `DatabaseCreationTests` (см. `BE-118`, критерий 2).

## Что делать прямо сейчас, чтобы не ждать (для @DO)

Ручной `ALTER` + `INSERT` в `__EFMigrationsHistory` (как для `journal`) **разблокирует dev** и даст зелёные smoke → `deploy-prod`. Но это **временная мера**: без пункта 1 на проде повторится та же 500 при первом же чистом развёртывании. Поэтому карточка не закрывается по факту «dev зелёный» — только вместе с миграцией в коде.
