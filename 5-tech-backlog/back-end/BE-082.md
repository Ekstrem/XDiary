- **Статус:** На проверке

- **На проверке с:** 2026-11-10

- **Источник:** проверка @TL по коду `2026-11-05 23:5x`
- **Проверяет:** @TL

## Факт 2 — отправителя НЕТ

То есть **Partners не публикует события в Journal** — ни через HTTP, ни через шину. Значит `partners_directory` пуст.

## Факт 3 — что видит пользователь

`JournalReadRepository.ResolveNamesAsync()` (`JournalReadRepository.cs:29-42`):

```csharp
m.PartnersNames = m.Partners
    .Select(id => Guid.TryParse(id, out var g) && byId.TryGetValue(g, out var n) ? n : id)   // ← fallback = id
```

Если справочник пуст, `byId` пуст ⇒ `PartnersNames` = **сырые идентификаторы**. На экране журнала это выглядит как набор GUID вместо имён.

## Задача

1. **Связать Partners → Journal:** при создании/переименовании/удалении партнёра публиковать событие в `internal/partners/events`
   (через `HttpClient` с внутренним адресом `journal:8080`, либо через шину, если она уже прокинута между сервисами).
2. **Закрыть `[AllowAnonymous]`** на этом эндпоинте: это **внутренняя запись** в read-модель; анонимный доступ к ней —
   возможность испортить справочник. Нужен сервисный секрет/подпись (ADR-008), а не «доверенная сеть» по умолчанию.
3. Прогнать проверку на **новых** данных: создать партнёра → запись с ним → убедиться, что `PartnersNames` содержит **имя**.

## Критерии приёмки

- `partners_directory` содержит строку для созданного партнёра (`SELECT count(*) … WHERE "PartnerId" = …` = 1);
- `GET /api/v1/journal/records` для записи с партнёром отдаёт **имя**, а не UUID (`PartnersNames` не содержит `-`-формат GUID);
- тест, который это фиксирует (unit или ApiTests), а не ручная проверка;
- `(ii-c)` по `/internal/**` снаружи остаётся 401/403/404 (2xx = нарушение) — проверить после закрытия авторизации.

### Вердикт @TL 2026-11-11 03:10 — **принято, можно закрывать**

- **Код и замер сходятся:** `profile-stage1` → `rc=0` (`recent.lastPartner.name` = имя), `partners_directory` — **4 строки, 0 с NULL-именем** (было 0 строк). Это то, что требовалось: не «поправил», а «запись проходит».
- **Цепочка проверена по коду:** `Id`-ключ у read-модели + `HasColumnName("PartnerId")` (миграция не нужна), guard на пустое имя в публикаторе, `400` на входе, лог публикации. Каждое звено названо адресом, а не «сделано».
- **`ordering` не входит в эту карточку:** он краснел из-за **дефекта кейса** (мерил пустое состояние), правка — зона @TE. Поэтому карточку закрываю по своим критериям, а не «вместе с чужим дефектом».
- **Граница, которую фиксирую:** строка `ordered` на пустой базе всё ещё может дать `null`, и это **не** дефект `BE-082` — это ответственность приёмки (предусловие должно создаваться кейсом).

## Результат

Связь Partners→Journal реализована и подтверждена измерением (@DO 14:55, REF 66d55131d):

- `PartnerEventPublisher` → `POST /internal/partners/events` сервис-токеном `sub=partners`; `PartnersEventsController` — `[Authorize]` + проверка `sub=partners` (иначе `Forbid`), `[AllowAnonymous]` закрыт;
- ключ read-модели `PartnersDirectoryReadModel.Id` → колонка `PartnerId` (`HasColumnName`) — корень `500` от DF `UpsertAsync` (искал `Id`);
- guard пустого имени (publisher + `400` на приёме) + `LogError` вокруг `UpsertAsync`;
- детерминированные тесты: `Handle_ProfileFirst_DoesNotWipeName` (имя из event store), `Handle_ProfileFirst_NoPreviousState_DoesNotPublishEmptyName`, + `FakePublisher` проверяет второй канал.

Измерение: `profile-stage1` → **`rc=0`** (`recent.lastPartner.name` = имя), `partners_directory` — 4 строки / 0 NULL. Второй кейс (`ordering`) — не дефект кода: @TL 22:25 снял «гонку» (кейс мерил пустое состояние без записи), исправлен на стороне @TE.

## Дополнение: шина НЕ может это закрыть — она внутрипроцессная (@TL 23:5x)

Проверил, почему «просто опубликовать событие» не поможет:

| Сервис | Регистрация шины |
|---|---|
| `Partners.Api/Program.cs:41` | `AddEventBusInMemory()` |
| `Journal.Api/Program.cs:43` | `AddEventBusInMemory()` |

`AddEventBusInMemory` — **внутрипроцессная** шина. Два разных контейнера её не разделяют, поэтому событие
`Partner.Removed`, опубликованное в Partners, **физически не может** дойти до Journal.

`OutboxDispatcher` (`Partners.Api/Events/OutboxDispatcher.cs:16-51`) реконструирует событие из `outbox` и
повторно публикует его **в тот же in-memory bus** — то есть outbox даёт «хотя бы один раз» **внутри сервиса**,
а не между сервисами.

**Следствие для задачи:** связать Partners → Journal можно только
**(а)** HTTP-вызовом `POST http://journal:8080/internal/partners/events` из Partners (по образцу других межсервисных
вызовов, с сервисным секретом), либо **(б)** введением реального брокера (это уже архитектурное решение, не «правка кода»).

Пункт (а) — минимальный и не меняет правил: внутренний endpoint уже существует, контракт DTO уже есть
(`PartnersEventDto`).

## Второй экземпляр того же дефекта, уже без справочника (@TL 23:5x)

`JournalReadRepository.GetRecentAsync()` (`:76-92`) заполняет «последнего партнёра» так:

```csharp
LastPartner = last.Partners.Count > 0
    ? new PartnerRef { Id = last.Partners[0], Name = last.Partners[0] }   // ← Name = ID
    : null,
```

То есть **имя принудительно равно идентификатору**, даже если справочник `partners_directory` был бы заполнен.
Фронт использует именно `name`:

- `8-front/js/app.js:679` — `draft.partner = data.recent.lastPartner.name || ""` ⇒ в мастере записи предзаполняется **GUID**;
- `8-front/js/app.js:792` — этот же GUID попадает в подсказки имён (`names.add(...)`).

**Значит даже после настройки `partners_directory` предзаполнение мастера останется сломанным**, пока здесь не будет
резолва имени из справочника (или из `JournalReadModel.PartnersNames`, который резолвится в `ResolveNamesAsync`).
