# BE-075: провижининг схемы Event Store — корень потери событий

- **Статус:** Закрыта
- **В работе с:** 2026-11-05
- **Приоритет:** P0 (риск целостности: event store — источник истины по `ADR-003 FullEventSourcing`)
- **Источник:** @AR `2026-11-05 23:00` + факт выкатки @DO `09:54`: `42P01: relation "Commands.DomainEvents" does not exist` (116× у `journal`, 164× у `partners`)
- **Зависимости:** `BE-072` (миграция **read**-контекста — другой контекст), `BE-073` (проекция + счётчик потерь)
- **Проверяет:** @AR

## Задача

На проде и dev **нет схемы event store**: таблица `Commands.DomainEvents` не существует, потому что
никогда не создавалась (журнал и партнёры писали в EF-таблицы `records`/`partners`).
Следствия: `DataMigration:Enabled` уводит сервис в краш-луп `42P01`; `SaveEventAsync` в проекции
падает; `try/catch` (`f56e9e81`) снимает `500` и **делает потерю событий невидимой**.

**Почему отдельная карточка, а не часть `BE-072`:** там миграция `ReadDbContext`, здесь —
`EventStoreDbContext`: другой контекст, другая схема.

## Критерии приёмки

- EF-миграция для `EventStoreDbContext` **в сборке контекста** (`MigrationsAssembly` = сборка `TDbContext`)
  + `Database.Migrate()` в старте, без ручного SQL;
- на **чистой** БД после старта `to_regclass` по таблице `Commands.DomainEvents` → **не NULL**;
- на существующей БД миграция идемпотентна, данные не теряются;
- `DataMigration:Enabled=true` на контуре **не даёт** `42P01` и доводит миграцию до конца;
- после этого `events_skipped_total` (из `BE-073`) **не растёт** при обычной записи;
- `journal_read`/`partners_read` пересобираются из событий, а не из объявленного SQL-ремонта.
