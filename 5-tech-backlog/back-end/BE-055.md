## Риск для миграции (найден @AR 2026-11-10 15:44, подтверждён @TL в коде)

`BC-Partners/Aggregate.cs:50` — `Remove() => Success(Clone())` (**no-op**), в модели нет `deletedAt`/`state`, при этом событие `PartnerRemoved` в канвасе описано. Для E1 это значит: «удалённость» **не восстановить реплеем**, и миграция партнёров в события даст «партнёр жив» после удаления.

- (б) оставить физическое удаление и эмитить `PartnerHardDeleted` с компенсацией в read-model (тогда отказ от `PartnerRemoved`).

## Решение по риску миграции (до старта E1)
Выбрано **(а)**: добавить в `Partner` `DeletedAt`/`IsDeleted` и сделать `Remove()` реальным — состояние и событие `PartnerRemoved` согласованы (предпочтительно для EDM). Физическое удаление не применяем; удалённость выражается флагом.

## Условия решения (а) — приняты @TL 12:10
1. `DeletedAt` ставится в `Remove()`, событие `PartnerRemoved` публикуется, повторный `Remove()` идемпотентен.
2. Чтения фильтруют: `GET /partners` и `GET /partners/{id}` не отдают удалённого.
3. Контракты `/api/v1` не меняются (аддитивно).
4. Тесты: `Remove()` → партнёр исчез из списка; повторный `Remove()` → успех без второго события; `GET /partners/{id}` после удаления → 404/403; до миграции — старые записи без `DeletedAt` читаются.

## Инварианты §11 (подтверждены @AR 12:20)
`DeletedAtSet` (Remove() → deletedAt + PartnerRemoved), `RemoveIdempotent` (повтор → успех без второго события), `DeletedNotVisible` (список без удалённого, /{id} → 404/403), `HistoryStaysResolvable` (проекция участников журнала держит всех с флагом, резолв имени в истории НЕ фильтрует), `Purge` (физическая чистка только если ни одна запись журнала не ссылается). Старые строки без deletedAt → Active.
