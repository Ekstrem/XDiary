## Что это значит

- `/fantasies` и `/places` (простые проекции) работают, а `/records` и `/recent` — **500**. Это согласуется с `BE-124`: read-модель `JournalReadModel` содержит поля `state`/`version`, а в **таблице** `journal_read` этих колонок нет ⇒ EF формирует запрос по ним ⇒ PostgreSQL `42703 (column does not exist)` ⇒ 500.
- Миграции `20261116130100_AddStateToJournalRead` и `20261117210000_AddVersionToJournalRead` **есть в коде**, но, судя по 500, **на dev-БД не применены** (или применены не полностью).

## Что нужно

1. **@DO:** проверить на dev, применены ли миграции read-стора: `podman exec xdiary-journal …` либо прямой `psql` — `SELECT "MigrationId" FROM "__EFMigrationsHistory" WHERE "MigrationId" LIKE '%AddState%' OR "MigrationId" LIKE '%AddVersion%';` и `\d journal_read` (есть ли `state`, `version`).
2. **@BE:** если миграция не применяется автоматически на старте — добиться, чтобы `readDb.Database.Migrate()` её применял; если применяется, но колонки нет — разобрать, почему (конфликт `MigrationsAssembly`/история).
3. **Логи `journal` (`podman logs --tail 120 xdiary-journal`)** — там будет точный `42703` с именем колонки; это и есть квитанция дефекта.

## Критерии приёмки

- [ ] `GET /api/v1/journal/records` с валидным JWT → **200** (не 500);
- [ ] `GET /api/v1/journal/recent` → **200**;
- [ ] в `__EFMigrationsHistory` на dev есть `AddStateToJournalRead` и `AddVersionToJournalRead`;
- [ ] `smoke-api` (`Journal.ApiTests`) → зелёный.

## Почему карточка, а не «продолжим в чате»

`BE-124` был закрыт как «дефект гейта, колонки есть в миграциях» — и это было верно **про файлы**. Но живой замер показывает, что **в БД** их нет. Это разные уровни, и теперь у нас есть факт: 500 на двух ручках при валидном токене.

## 🔍 Гипотеза (d), которую я нашёл в репозитории: это может быть APIM target, а не контейнер (@TL, статический разбор)

В `7-deploy/apim/import.sh` (строки 257-260) **уже описан наш симптом дословно**:

```
# Факт 2026-11-16 05:5x: маршруты journal/partners/каталог уже есть (404 ушёл), но journal и
# partners отдают 500 от Gravitee — определение API смотрит в невалидный target (следствие
# `servers: "/"`, AR-160). Ставим target явно: http://<host>:8080 и перезапускаем API.
```

И для этого случая есть **готовый скрипт** `7-deploy/apim/fix-target.sh` (78 строк):

```
# Запуск на VPS-1:  bash /opt/xdiary/7-deploy/apim/fix-target.sh [journal partners]
# находит API по listener-пути /api/v1/<svc>, показывает текущий target,
# ставит http://<svc>:8080, перезапускает API
```

**Что это объясняет лучше, чем «контейнер упал»:**
- `partners` → **502 на всех** роутах (`/partners`, `/partners/directory`) — как будто шлюз не может достучаться до backend;
- `journal` → `/records` и `/recent` **500**, а `/fantasies` и `/places` **200**: если у Gravitee отдельные определения API на разные пути, «сломанный target» может задевать только `journal`-API, а не вспомогательные;
- `catalog` и `somatic-series` — 200, то есть шлюз в целом жив.

**Порядок проверки (дешевле, чем логи):**
1. `bash /opt/xdiary/7-deploy/apim/fix-target.sh partners journal` — скрипт **сам печатает текущий target** до правки; если там мусор/невалидный хост, гипотеза подтверждена;
2. сразу после — повторный замер `GET /api/v1/partners` с валидным JWT (ожидание 200) и `GET /api/v1/journal/records` (ожидание 200);
3. если после правки target всё равно 502/500 — тогда уже `podman logs` (контейнер), и это будет уже вторая итерация, а не первая.

**Важно для `deploy-prod`:** `apim-parity` в прогонах **зелёный**, но он сверяет пути/контракт OpenAPI, а **не** backend-target — поэтому наш 502 он не ловит. Это стоит записать как дефект гейта (кандидат в `DO-138`-класс: «гейт зелёный, а маршрут в никуда»).
