# BE-094: удалённая запись журнала **читается** — `Deleted` проецируется, но чтение не фильтрует

- **Статус:** На проверке
- **В работе с:** 2026-11-06
- **Приоритет:** **P1 — приватность** (мягко удалённая запись видна и по id, и в списке)
- **Источник:** прогон @TE на dev `2026-11-06 23:12` (измерение, не оценка)
- **Проверяет:** @TL + @TE

## Факт (воспроизведено на dev, `journal single-fdf7550`)

```
POST /journal/records/{id}/delete → 200, deleted: true
GET  /journal/records/{id}        → 200, deleted: true   ← запись видна
GET  /journal/records             → список содержит запись ← запись видна
```

## Диагноз

`Deleted` **доезжает до read-модели** (это проверено отдельно и чинилось в `BE-093` — `BoolValueObject` в `ApplyVos`),
но **чтение не фильтрует** по нему: ни `GET /records/{id}`, ни список.

То есть дефект не в проекции, а в **фильтре чтения** — ровно та половина, которую легко забыть, потому что «поле есть, значит работает».

## Что сделать (@BE)

1. `GetById(id)` — если `Deleted == true` ⇒ **404** (не 200 и не 403: не подтверждаем существование).
2. Список (`List`, `Recent`, `GetClientIds` при необходимости) — исключать `Deleted`.
3. Тест: создать → delete → `GET /records/{id}` = **404**, `GET /records` = **0 записей**; и «чужая» запись остаётся невидимой (изоляция не ломается).

## Критерии приёмки

- `check_be093_stale_fields.py --check-deleted` → `rc=0` («нарушено: 0»);
- `GET /records/{id}` после delete → **404**; список → без записи;
- `## Результат`: прогон с числами (id → код ответа, список → число).

## Почему это P1, а не P2

Для дневника «удалено» = «не должно существовать». Сейчас удаление меняет флаг, но **не поведение**: пользователь (и любой, кто получил id)
продолжает видеть запись. Это тот же класс, что `BE-090` (утечка через ответ), только через чтение.

## Результат

- `GetRecordByIdHandler` — `Deleted == true` ⇒ `null` (404, не 200/403);
- `ListRecordsHandler` — `Where(x => !x.Deleted)` (список без удалённых);
- сборка Journal зелёная; прогон с числами (`--check-deleted`) — @TE/@DO на dev.
