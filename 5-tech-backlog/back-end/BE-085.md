- **Приоритет:** **P0 — авторизация** (IDOR: доступ к чужому объекту по одному `id`)
- **Источник:** проверка @TL по коду `2026-11-06 00:0x`
- **Проверяет:** @TL

## Факт (по коду, `PartnersController.cs`)

| Строки | Эндпоинт | Проверка владельца | `[Authorize]` |
|---|---|---|---|
| `:33-44` | `POST {id}/remove` | **ДА** — `existing.ClientId != clientId → Forbid()` | **ДА** |
| `:29-30` | `POST {id}/name` (Rename) | **НЕТ** | нет (только fallback) |

| `:47-48` | `POST {id}/unlink-client` | **НЕТ** | нет |

## Что это позволяет

Любой аутентифицированный клиент, зная `id` партнёра другого клиента:

1. **переименовать** его (`POST /api/v1/partners/{id}/name`);
2. **изменить профиль** — фото/пол/заметки (`{id}/profile`);
3. **перепривязать к себе** — `{id}/link-client` с `clientId` из тела; после этого чужой партнёр появляется в **своём** списке
   (список фильтруется по `sub`), а у прежнего владельца — исчезает;
4. **отвязать** чужого партнёра (`{id}/unlink-client`).

Для дневника «партнёр» — это имя человека из интимных записей; правка чужого профиля и перепривязка — прямое вмешательство.

## Задача

1. Ввести **единый** путь проверки владельца (как в `remove`): `sub` → `clientId`; `GetPartnerByIdQuery(id)`;
   `null → NotFound()`, `existing.ClientId != clientId → Forbid()`.
2. `link-client`: **не доверять** `ClientId` из тела — брать из `sub` (`c with { AggregateId = id, ClientId = clientId }`).
3. `unlink-client` — тоже проверять владельца.
4. Добавить `[Authorize]` **явно** на все пять мутаций (сейчас у четырёх его нет; работает только fallback-политика —
   `check_api_index` печатает «auth-стек 6/6 с fallback»).
5. Тест на изоляцию: клиент B не может ни переименовать, ни перепрофилировать, ни привязать/отвязать партнёра клиента A
   (ожидаем **403/404**, не 200).

## Критерии приёмки

- все пять мутаций имеют `[Authorize]` + проверку владельца;
- `link-client` игнорирует `ClientId` из тела (проверено тестом: попытка привязать к чужому `clientId` не меняет владельца);
- чужой `id` → **403/404**, и объект **не меняется** (проверить повторным чтением);
- тест на изоляцию в `Partners.ApiTests` (не ручная проверка).

## Результат

- `PartnersController` — `[Authorize]` + `ClientId()` из `sub` + `OwnerGuardAsync(id, clientId)` (GetPartnerByIdQuery → NotFound/Forbid) на rename/profile/remove/link/unlink/Get;
- `link-client` — `c with { ClientId = clientId.Value }` (владелец из токена, не из тела);
- сборка Partners зелёная.

## Уточнение критерия: где именно писать тест (@TL 00:48)

Мой прежний текст говорил «`Partners.ApiTests`» — **такого проекта в репозитории нет**, и это моя неточность.


Достаточно двух вещей в `Partners.IntegrationTests`:

1. **Тест guard'а на контроллере:** создать `PartnersController` со **стабом `IMediator`** (возвращает партнёра с чужим
   `ClientId`), подложить `ControllerContext.HttpContext` с claim `sub` = `clientId`; вызвать `Rename`/`UpdateProfile`/
   `Remove`/`LinkClient`/`UnlinkClient` по чужому `id` → ожидать **`ForbidResult`**; и отдельно — `NotFound` при `null`.
2. **Тест на `link-client`:** вызвать с телом, где `ClientId` = **чужой**; проверить, что в стаб `IMediator` ушла команда
   с `ClientId == sub` (а не со значением из тела). Это ровно тот баг, который был.

Такой тест ловит именно `BE-085` (и не требует ни БД, ни сети) — то есть может жить в обычном `dotnet test`.
