- **Приоритет:** P0 (без проекции read-модель живёт только ремонтом; `TE-050`, `FE-041` недостижимы)

## Задача

На **dev** создание партнёра через API не приводит к появлению строки в `partners_read`.
Это **не** «не измерено», а подтверждённый дефект: замер сделан, число названо.

**Важно уточнить до правки (одно измерение):** после `POST /partners` снять **оба** числа —
`SELECT count(*) FROM partners` и `SELECT count(*) FROM partners_read`, плюс строку из лога
`PartnerEventConsumer`/`PartnerEventHandler`.

- если `partners = 1`, а `partners_read = 0` → дефект **проекции** (потребитель не подписан / не пишет / событие без `ClientId`);
- если `partners = 0` → дефект **командной стороны** (событие не публикуется или транзакция не сохраняется) — тогда это другой класс, и карточка переформулируется.

## Критерии приёмки

- `POST /partners` (валидный, с client-JWT) → `200`; в течение **5 с** `partners` = 1 **и** `partners_read` = 1;
- повторный `GET /partners` с тем же токеном возвращает ровно того партнёра, которого создали (проверка `ClientId`);
- событие несёт `ClientId` (проверить в `ChangedValueObjects`/модели события): без него проекция не сможет положить строку «этому клиенту»;
- `PartnerEventConsumer` зарегистрирован как hosted service/subscriber на dev (тот же код, что на проде);
- контракт `test-partner-softdelete` → **`4 passed`** (это же и есть критерий `TE-050`);
- отчёт содержит **оба** числа до/после и строку лога — иначе «проекция работает» не доказана.

**Граница:** проверка проводилась по коду, а не на dev (стенд недоступен). Если после выкатки строка в `partners_read` по-прежнему не появляется — это **новый** дефект: мерить `SELECT count(*)` до/после и лог `PartnerEventConsumer`, карточку переоткрою.

## Критерий уточнён: два поведения, две проверки (@TE `14:30`, @TL `14:48`)

Замер `POST /partners` → 200 при `count=0` сделан **11:14**, то есть **между** `f56e9e81` (10:21, обёртка
добавлена) и `47dfd808` (11:33, обёртка снята) — то есть **на варианте B**. После откатa на **A**
поведение **не измерялось ни разу**. Поэтому приёмка требует **обоих** исходов:

- [ ] **схема Event Store есть** ⇒ `POST /partners` → **200** **и** `GET /partners` содержит созданного;
- [ ] **схемы нет** ⇒ `POST /partners` → **`5xx`** (проверка варианта A: «падает громко», а не теряет молча);
- [ ] в `## Результат` указано, **на каком образе** (SHA/время) сделан замер — иначе вердикт применяется не к той версии.

**Признак подмены версии:** если при отсутствии схемы `POST` возвращает `200` — развёрнут **старый образ**
(B), а не A. Это не дефект проекции, а дефект выкатки.

**Как читать обе строки выше (историю не переписываем):** на **B** (`f56e9e81` 10:21 → `47dfd808` 11:33)
замер дал `POST 200` + пустую read-модель — это **поведение B**, и потеря при нём **невидима**.
На **A** (после 11:33) при отсутствии схемы `POST` обязан давать **`5xx`**; на контуре это
**не измерялось ни разу**. Поэтому «проекция не пополняется» — формулировка про мир, снятый откатом.
