## Проблема

Фронт не может отличить три разных исхода `POST /api/v1/clients`:
1. код **реально доставлен** (Telegram/SMS);
2. сервер **принял** запрос, но канал недоступен (сейчас именно так: Telegram с прода недостижим, лог печатает ложное «отправлено»);
3. код **выдан**, но доставлять его в ответе нельзя (после `BE-090` — правильно).

В ответе нет ни `delivered`, ни `channel`, поэтому UI либо врёт («код отправлен»), либо пишет общие слова. @FE уже убрал ложное утверждение и добавил таймер/подсказку, но честное состояние «куда ушёл код» без контракта недостижимо.

## Что сделать (контракт — зона @AR, реализация — @BE)

`POST /api/v1/clients` → добавить в whitelist-проекцию (`BE-090`) поле:

```json
{ "id": "...", "version": 1, "phone": "+7...", "otpExpiresAt": "...", "verified": false,
  "delivery": { "channel": "telegram|sms|log|none", "ok": true } }
```

- `channel` — канал, который **фактически** использован (`Otp:Channel` + факт отправки);
- `ok` — **результат** отправки (Telegram вернул 200 vs недостижим), а не «мы попытались».

То же поле полезно в `POST /clients/{id}/verify` (для «код истёк/неверный» не нужно, но симметрия не мешает).

**@FE 21:33 — поле нужно в ОБЕИХ ветках выдачи кода:** (1) `200` от `POST /clients` (новый номер) и (2) **`400`/`409` «номер уже зарегистрирован»** (сервер заново шлёт код и отдаёт `clientId` в теле ошибки). Иначе повторный вход (частый путь) останется на текстовой эвристике. При недостижимом канале — `ok=false`, `channel="none"` (или `channel="telegram"`+`ok=false` — решает @AR).

**Важно:** это **не** возвращает `otpCode` (закрыт `BE-090`) — только признак доставки.

## Критерии приёмки

- `POST /clients` при недостижимом Telegram → `delivery.ok = false`, `channel = "telegram"`; UI показывает «вход сейчас недоступен», а не «код отправлен»;
- при `Otp__Channel=log` → `delivery = {"channel":"log","ok":true}` (и UI говорит «код в логах» — только для dev/тест-режима);
- при рабочем канале → `ok = true`;
- в ответе **нет** `otpCode` (регресс-тест `BE-090` остаётся).

## Уточнение от @FE `21:33` — `delivery` нужен в ОБЕИХ ветках выдачи кода

У фронта **два** пути, и на втором сейчас снова будет эвристика, если поле добавить только в успешный ответ:

1. `POST /api/v1/clients` → **200** (новый номер) — `8-front/js/app.js:381`;
2. `POST /api/v1/clients` → **400/409** «номер уже зарегистрирован» — `8-front/js/app.js:391`; сервер **заново отправляет код**
   и отдаёт `clientId` в теле ошибки.

Требование контракта: `delivery: {channel, ok}` присутствует **и в `200`, и в теле `400/409`**. При недостижимом канале —
`ok=false` (и `channel="none"` либо `channel="telegram"` — как решит @AR).

Три различимых состояния на фронте:
- `ok=true` → «код ушёл в `<channel>`»;
- `ok=false` → «канал недоступен, вход временно невозможен»;
- поля нет (старая сборка сервера) → текущий текстовый режим, **без** ложного «отправлено».

Это важно потому, что повторный вход («я уже регистрировался») — **частый** путь, а не край.

## ОТМЕНА моего требования про `400/409` — @AR проверил код и контракт (`21:50`)

Моё требование «`delivery` и в `200`, и в теле `400/409`» **неверно** по контракту, и я его снимаю:

- `ClientsController.Register` на ошибке делает `BadRequest(result.ErrorMessage())` (`:22`, `:29`) ⇒ тело **400 — строка**,
  а не объект: ни `clientId`, ни `delivery` там нет и быть не может без смены формы ошибок;
- `api-index.yaml` описывает `400` честно: «тело — строка сообщения, без структуры, без `clientId`»;
- структурированный error-envelope (с `clientId` + `delivery`) изменил бы форму ошибок у **всех 80 операций** — это **отдельное
  контрактное решение**, а не попутная правка регистрации. Вводить его «заодно» нельзя.

**Следствие для фронта:** `app.js:391-399` читает `d.clientId || d.aggregateId || d.id` из строки и попадает в ветку
«номер уже зарегистрирован» только по `status`, а id берёт из `storedClientId()` — то есть **угадывает**. Значит текст
«Мы запросили новый код» на `400` — такая же эвристика, как прежнее «код отправлен».

**Минимальный честный вариант (принимаем):** `delivery` живёт **только в `200`**; на `400` — добавить в **строку** явный
признак: «номер уже зарегистрирован; код отправлен повторно (channel=telegram)». Если повторной отправки **нет** — написать
прямо: «номер уже зарегистрирован; запросите код заново через …». Честность — не форма ответа, а **отсутствие вранья**.

## Финальный контракт от @AR `22:20` — точечное исключение для `POST /clients`

@AR зафиксировал в `api-index.yaml`:

| Код | Тело |
|---|---|
| `200` (новый номер) | `{ id, version, phone, otpExpiresAt, verified, delivery }` |
| **`409`** («номер уже зарегистрирован» — это **состояние**, не ошибка валидации) | **структурированное**: `{ error, clientId, delivery }`, `clientId` **реальный**, не угаданный фронтом |
| `400` (неверный телефон/OTP) | структурированное (то же исключение) |

Правило в шапке индекса — `error_body_rule`: **у всех остальных 80 операций тело ошибки остаётся строкой**; у `POST /clients` объявлено поле `error_body` — точечное исключение.

`delivery_states` (контракт трёх состояний):

1. `ok=true` — провайдер подтвердил отправку;
2. `ok=false` — попытка была / канала нет;
3. **поля `delivery` нет** — старый режим: текст без ложного «отправлено». Третий случай **обязателен**: он позволяет выкатить `BE-090` до выбора канала и не соврать.

## Критерий приёмки `BE-092` (проверяемый, @AR)

1. `POST /clients` нового номера → `200` + `delivery`;
2. `POST /clients` существующего → **`409`** + `{error, clientId, delivery}`, и `clientId` **совпадает** с реальным;
3. `delivery.ok=false` при недоступном канале, и в логе сервиса **есть** запись о попытке;
4. `otpCode` отсутствует **в обоих** ответах (регресс `BE-090`).

Пункт 3 нельзя доказать без подмены провайдера — нужен **фейковый `IOtpSender` с `ok=false`** в тестах.

@TL предлагал идемпотентность (`200` и для существующего номера) — она снимала мёртвую ветку фронта, но @AR выбрал точечное исключение со структурированным `409`. Решение @AR принято: ветка `409` во фронте остаётся живой, а `clientId` теперь приходит реальный.
