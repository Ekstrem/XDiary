# BE-092: `delivery` в ответе регистрации + идемпотентный `POST /clients` + лимит `429`

- **Статус:** ToDo
- **Приоритет:** **P1** (без `delivery` фронт не может честно показать «код ушёл / канал недоступен»; без лимита идемпотентность = OTP-бомбинг)
- **Источник:** @FE `21:27` + @AR `22:20` → отозвано в `21:45` → **идемпотентность принята @AR `21:50`, подтверждена @TL `23:1x`**
- **Проверяет:** @TL

> **Единственный источник правды — `04-architecture/api-index.yaml`, операция `Client.Register`.** Этот файл — пояснение к индексу;
> если они разойдутся, прав индекс.

## ФИНАЛЬНЫЙ КОНТРАКТ (реализовать ровно это)

| Код | Когда | Тело |
|---|---|---|
| **`200`** | **и новый, и существующий номер** — ответ и статус **одинаковы** | `{ id, version, phone, otpExpiresAt, verified, delivery }` — **`id` присутствует всегда** |
| **`400`** | неверный формат телефона / неверный или истёкший OTP | **строка** (как у всех остальных операций) |
| **`429`** | превышен лимит запросов кода | строка |

- **`409` не вводится.** Структурированных тел ошибок нет **ни у одной** операции (`error_body_rule` в шапке индекса).
- **Отдельной операции переотправки нет:** `POST /clients` = «**запросить код для номера**»; повторный вызов — это и есть переотправка.
- **Лимит обязателен:** не чаще **1 раза в 60 с** на клиента и **5 раз в час** на номер, наружу — **`429`**.
  Без лимита `200` для любого номера = OTP-бомбинг и счёт за SMS (@AR `21:50`).
- **`delivery` — три состояния:**
  1. `ok=true` — провайдер подтвердил приём;
  2. `ok=false` — попытка была / канала нет;
  3. **поля `delivery` нет** — старый режим: фронт показывает текст без ложного «отправлено». Третий случай **обязателен**: он позволяет выкатить `BE-090` до выбора канала и не соврать.

## Почему идемпотентность, а не `409` (аргументы @AR `21:52`, совпадают с @TL `21:44`)

1. `409` «даёт реальный `clientId`» — но идемпотентный `200` даёт **то же самое**: `id` в теле всегда; выигрыш `409` был только в «различии состояния», и за него платили бы исключением из правила для 79 операций.
2. `409` **сохраняет** две ветки на фронте и мёртвый код; идемпотентность **удаляет** ветку целиком (`storedClientId()` и догадка `d.clientId` уходят).

## Критерии приёмки (проверяемые, без «на глазок»)

1. `POST /clients` нового номера → **`200`** + `delivery`, `id` в теле;
2. `POST /clients` существующего → **`200`** + **тот же** `id`, форма тела идентична (различаются только значения `verified`/`delivery`);
3. **два запроса подряд на один номер → второй `429`**, а не второй код (негативный тест обязателен);
4. `delivery.ok=false` при недоступном канале **и запись о попытке в логе** (для доказательства нужен фейковый `IOtpSender` с `ok=false`);
5. `otpCode` отсутствует **в обоих** ответах (регресс `BE-090`).

## Что было отменено (история, чтобы не реализовать повторно)

- **`409` + структурированное тело `{error, clientId, delivery}`** — предлагалось @AR `22:20`, **отозвано** им же в `21:45`; `409` в индексе нет.
- **`POST /clients/{id}/otp/resend`** — предлагалось как отдельная операция, **снято**: роль выполняет повторный `POST /clients`.
- **`POST /clients/verify {phone, code}`** — предлагалось @TL, **не нужно**: при идемпотентном `200` `id` приходит всегда, зависимость от `clientId` исчезает.
- **Идемпотентность** — предлагалась @TL `21:44`, **принята** @AR `21:50`, **подтверждена** @TL.

## Ограничение гейта (найдено @AR)

`target_codes` в `check_api_index` работает для **кодов**, но не для **маршрутов**: добавив операцию с `codes_status: target` заранее, получили `rc=1`
(«индекс 83, код 82, anonymous 5»). Поэтому маршрут вносится **одновременно с кодом**. Сейчас индекс `82 = 82`, `rc=0`.
