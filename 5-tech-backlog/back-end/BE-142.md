## Контракт (сначала спека, потом UI)
В `openapi/garmin-gateway.json` **висячий `$ref`**: `#/components/schemas/ConnectCommand` — секция `components.schemas` ПУСТА (проверено @TL 2026-11-20), ответы — только «ok/validation» без тела. То есть Gravitee публикует контракт, из которого FE не может узнать поля.

## Задача
1. **Спека:** добавить `components.schemas` (`ConnectCommand`, `CredentialsDto`, `SyncCommand`, `SyncConfigDto`, ответ `state`) по коду DTO и по полям из `api-index.yaml` (@AR, AR-163) — без висячих `$ref`; ответы с телами. Спека следует из кода — код и спека в одном PR.
2. Проверить `POST /connect` end-to-end: валидация Credentials (`CredentialsValidator`), сохранение в агрегат `GarminSync`, ответ для UI (`state`).
2. `SyncCommand`/`FetchActivitiesCommand` — реально ходят в Garmin Personal API с сохранённым токеном (или явно задокументировать, если пока прокси-заглушка), ошибки истечения токена — по спецификации `ReauthOnExpiry`.
3. Тесты: `GarminGateway.Domain.Tests` (Credentials/истечение) + `*.ApiTests` на `/connect` 401 без токена и 200/4xx с валидными/невалидными данными.

## Критерии приёмки
- `/connect` с валидными Credentials → агрегат сохранён, `GET /state` его показывает; с невалидными → 4xx с причиной.
- `/sync` с подключённым токеном отрабатывает (или документированный статус «прокси ещё не подключён» с картой следующих шагов).
- Истёкший `TokenExpiry` → предсказуемая ошибка/`ReauthOnExpiry`-путь, а не 500.
- Тесты зелёные; контракт описан для @FE (поля, коды).
