# BE-123 — P1: ответы аутентификации не различают состояния (401 без тела, один код на «нет токена» / «истёк» / «невалиден»)

- **Статус:** ToDo
- **Приоритет:** P1 (по решению владельца 2026-11-17: «401 без пояснения — бага»; фронт не может отличить «нужно войти» от «токен истёк» и от «сервер недоступен»)
- **Источник:** замер @TL 2026-11-17 22:0x по живому проду `xdiary-vps1` (владелец попросил написать @BE)
- **Зависимости:** согласование с @AR — меняется контракт ошибок, а это `ADR-026` (архитектура; решает @AR после обсуждения с владельцем)
- **Проверяет:** @TL
- **Исполняет:** @BE (`6-msa/`)

## Факты (замер, не мнение)

| запрос | ответ прода |
|---|---|
`GET /api/v1/partners` без токена | **401**, `WWW-Authenticate: Bearer`, **тело 0 байт**, `Content-Length: 0` |
`GET /api/v1/partners` с `Authorization: Bearer <мусор>` | **401**, **точно такой же ответ**, тело 0 байт |
`GET /api/v1/nope-does-not-exist` | **404** (APIM: «No context-path matches the request URI») |
`OPTIONS /api/v1/partners` (preflight, Origin=Pages) | **204**, CORS-заголовки на месте |
`GET /health` | **200** |

CORS на проде корректен: `Access-Control-Allow-Origin: https://ekstrem.github.io`, `Access-Control-Expose-Headers: content-type, www-authenticate`.

**Вывод:** 401 сам по себе корректен (deny-by-default, ADR-026). Дефект в том, что ответ **неинформативен**: нет машиночитаемого кода, нет различия «токен отсутствует» / «токен истёк» / «токен невалиден», тело пустое. Фронт на этом месте вынужден гадать и показывает «нет связи» вместо «войдите заново».

## Что нужно

1. **Различать состояния** в теле ответа (машиночитаемо), например:
   - нет заголовка `Authorization` → `401` + `{"code":"token_missing"}`;
   - токен истёк → `401` + `{"code":"token_expired"}` + `WWW-Authenticate: Bearer error="invalid_token", error_description="expired"` (RFC 6750 §3.1);
   - токен невалиден (подпись/аудитория) → `401` + `{"code":"token_invalid"}`;
   - нет прав при валидном токене → `403` + `{"code":"forbidden"}` (сейчас, вероятно, тоже 401 — проверить).
2. **Сохранить** `WWW-Authenticate: Bearer` на всех 401 (сейчас есть — не потерять при изменении).
3. **Не раскрывать** деталей, по которым можно перебирать валидность подписи: текст причины — только «expired» / «invalid», без внутренних исключений.
4. **Согласовать с @AR** форму кода (это контракт зоны `04-architecture`, ADR-026) — карточка не стартует без его решения.
5. **Контрактный тест** (зона @BE, `Client.ApiTests`): три кейса — без токена, истёкший, мусорный — и `403` для «валидный, но нет прав» (если такой сценарий есть).

## Критерии приёмки

- [ ] `curl` без токена → `401` + тело с `code` (не пустое);
- [ ] истёкший токен → `401` + `code=token_expired` и `error="invalid_token"` в `WWW-Authenticate`;
- [ ] мусорный токен → `401` + `code=token_invalid` (отличается от `token_expired`);
- [ ] несуществующий путь → по-прежнему `404` (не 401);
- [ ] preflight `OPTIONS` → `204` без авторизации (не сломать);
- [ ] контрактный тест покрывает все кейсы и живёт в `6-msa/BC-Client/src/Client.ApiTests` (ADR-028 ред. 3);
- [ ] ADR-026 (или приложение к нему) описывает коды — правка через @AR.

## Чего НЕ делаем

- Не отвечаем `404` вместо `401` на закрытых ручках (это маскировка и ломает диагностику).
- Не убираем авторизацию с `/api/v1/partners` и других приватных ручек.
- Не меняем коды, на которые уже опирается фронт (`FE-051`/`FE-056` различают `4xx`/`5xx`), без согласования с @FE.
