## Задача

Сейчас схема read-store создаётся **строкой SQL в хосте**: `Journal.Api/Program.cs:62` и
`Partners.Api/Program.cs:55` — `ExecuteSqlRaw("CREATE TABLE IF NOT EXISTS …")`. Это три отклонения
в одном месте (@AR): (а) свой провижининг вместо библиотечного; (б) SQL в старте хоста вместо артефакта
миграции; (в) **второе описание модели** (`DDL` vs `OnModelCreating`), которое уже разошлось.

**Решение владельца: путь A** — EF-миграция `ReadDbContext` + `Database.Migrate()`; SQL удалить.

## Критерии приёмки

- `dotnet ef migrations add AddReadStores --context ReadDbContext` в проекте **`Journal.Storage`**
  (и `Partners.Storage` для `partners_read`): так надо, потому что `AddReadStorePostgres` регистрирует
  `UseNpgsql(..., npgsql.MigrationsAssembly(typeof(TDbContext).Assembly.GetName().Name))` — миграции обязаны
  жить в **той же сборке**, что и контекст;
- `ExecuteSqlRaw(...)` из обоих `Program.cs` **удалён**, вместо него `readDb.Database.Migrate()`;
- `git grep -c 'CREATE TABLE IF NOT EXISTS' -- 6-msa` → **0**; `git grep -c EnsureCreated -- 6-msa` → **0**;
- **чистая БД:** старт сервиса создаёт все read-таблицы; `\d journal_read` → 20 колонок с типами
  (`ContraceptiveCount integer`, `Garmin`/`Deleted` boolean), `partners_read` → 7; запросы к ним → 200;
- на **существующей** БД (dev/прод) миграция применяется идемпотентно, данные не теряются;
- `check_readstore_mapping` и `check_readstore_live` остаются зелёными.

### Подтверждение про `MigrationsAssembly` (@TL `2026-11-05 17:20`) — это факт из исходников, а не предположение

Публичная библиотека `Ekstrem/DigiTFactory.Libraries`, файл
`ReadRepository.Postgres/Extensions/ServiceCollectionExtensions.cs`, строки **41–42**:

```csharp
dbOptions.UseNpgsql(connectionString, npgsql =>
    npgsql.MigrationsAssembly(typeof(TDbContext).Assembly.GetName().Name)));
```

То есть сборка миграций = **сборка типа `TDbContext`**. Для `Journal` это `Journal.Storage`
(там же лежат миграции `CommandDbContext`, включая `CommandDbContextModelSnapshot.cs`), для `Partners` —
`Partners.Storage`. Следствие: `dotnet ef migrations add … --context ReadDbContext` надо запускать
**в проекте Storage**, иначе `Database.Migrate()` их не увидит.

**Проверяемый признак в приёмке:** список миграций контекста (`dotnet ef migrations list --context ReadDbContext`)
содержит новые, и на **чистой** БД после старта есть `journal_read`/`partners_directory`/`journal_defaults`/`partners_read`.

### Воспроизводимая проверка `MigrationsAssembly` в **опубликованном** пакете (@TL `2026-11-05 17:40`)

`git grep` по **нашему** репозиторию даёт 0 — это ожидаемо: строка живёт в чужой сборке. Проверяется по DLL из NuGet-кэша:

```python
import glob, os
p = glob.glob(os.path.expanduser('~/.nuget/packages/digitfactory.libraries.readrepository.postgres/*/lib/net8.0/*.dll'))[0]
b = open(p, 'rb').read()
print(b.count(b'MigrationsAssembly'), b.count(b'UseNpgsql'), b.count(b'EnsureCreated'))
# → 1 1 0
```

То есть в **шипнутом** `0.1.0` вызов `MigrationsAssembly` есть (1), `EnsureCreated` — нет (0), и это совпадает
с исходником (`ReadRepository.Postgres/Extensions/ServiceCollectionExtensions.cs:41-42`).
