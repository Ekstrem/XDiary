## Задача

Сейчас схема read-store создаётся **строкой SQL в хосте**: `Journal.Api/Program.cs:62` и
`Partners.Api/Program.cs:55` — `ExecuteSqlRaw("CREATE TABLE IF NOT EXISTS …")`. Это три отклонения
в одном месте (@AR): (а) свой провижининг вместо библиотечного; (б) SQL в старте хоста вместо артефакта
миграции; (в) **второе описание модели** (`DDL` vs `OnModelCreating`), которое уже разошлось.

**Решение владельца: путь A** — EF-миграция `ReadDbContext` + `Database.Migrate()`; SQL удалить.

## Критерии приёмки

- `dotnet ef migrations add AddReadStores --context ReadDbContext` в проекте **`Journal.Storage`**
  (и `Partners.Storage` для `partners_read`): так надо, потому что `AddReadStorePostgres` регистрирует
  `UseNpgsql(..., npgsql.MigrationsAssembly(typeof(TDbContext).Assembly.GetName().Name))` — миграции обязаны
  жить в **той же сборке**, что и контекст;
- `ExecuteSqlRaw(...)` из обоих `Program.cs` **удалён**, вместо него `readDb.Database.Migrate()`;
- `git grep -c 'CREATE TABLE IF NOT EXISTS' -- 6-msa` → **0**; `git grep -c EnsureCreated -- 6-msa` → **0**;
- **чистая БД:** старт сервиса создаёт все read-таблицы; `\d journal_read` → 20 колонок с типами
  (`ContraceptiveCount integer`, `Garmin`/`Deleted` boolean), `partners_read` → 7; запросы к ним → 200;
- на **существующей** БД (dev/прод) миграция применяется идемпотентно, данные не теряются;
- `check_readstore_mapping` и `check_readstore_live` остаются зелёными.
