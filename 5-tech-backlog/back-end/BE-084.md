# BE-084: в четырёх сервисах нет измерения «клиент» — данные пользователей не разделены

- **Статус:** На проверке
- **В работе с:** 2026-11-06
- **Приоритет:** **P0 — приватность** (catalog/somatic/daily-metrics/portability хранят пользовательские данные без владельца)
- **Источник:** систематическая проверка @TL по коду `2026-11-06 00:0x`
- **Проверяет:** @TL + @AR

## Факт: `ClientId` отсутствует в коде целиком


Для сравнения, там где измерение есть: `BC-Journal` (`JournalReadModel.ClientId`), `BC-Partners`

## Что это значит практически

Все четыре сервиса хранят данные **без владельца**:

| Сервис | Что лежит | Следствие |
|---|---|---|
| `BC-Catalog` | позиции каталога с `photo`/`notes`/`fantasyPartner` (интимные предпочтения) | любой аутентифицированный клиент видит **чужие** позиции и может их править/архивировать |
| `BC-SomaticSeries` | пульс/HR/body-battery по минутам (здоровье) | общая лента для всех |
| `BC-DailyMetrics` | сон/стресс/шаги по дням | общая лента |
| `BC-Portability` | экспорт/импорт данных | без владельца — экспорт чужого |

**Важно:** аутентификация при этом работает (снаружи 401 через APIM, и есть fallback-политика в сервисах —
`check_api_index` печатает «auth-стек 6/6 с fallback»). Дыра не в «пускает без токена», а в том, что **токен не
используется для разделения данных**: сервис не знает, чьи строки он отдаёт.

## Задача (по каждому из четырёх)

1. Добавить измерение владельца: `ClientId` в модель + в миграцию (новая миграция, не правка применённых).
2. Писать `ClientId` из `sub` на командах; фильтровать **все** чтения по `sub`.
3. Запретить доступ к чужим объектам по `id` (404/403, не 200).
4. Проверить, что миграции не конфликтуют с уже существующими данными (у старых строк владельца нет — нужен явный
   план: либо `ClientId = NULL` и такие строки не отдаются никому, либо backfill по известному источнику).

## Критерии приёмки

- два клиента с разными данными получают **разные** списки в `catalog`, `somatic`, `daily-metrics`;
- доступ к чужому объекту по `id` → **404/403**;
- есть тест на изоляцию (unit или ApiTests) — «клиент A не видит ни одной строки клиента B»;
- для уже существующих строк — зафиксированный план (в `### Вердикт @TL 2026-11-11 12:00 — **принято — измерения «клиент» добавлены в 4 сервиса**

- Проверил в `origin` по адресам: миграции `AddClientIdToDocument` (Portability), `AddClientIdToSomaticPoint` (SomaticSeries), `AddClientIdToDailyMetrics` (DailyMetrics), `AddClientIdToCatalogItem` (Catalog) — по **1 файлу** каждая; владение проверяется (`EnsureOwns`/`OwnerGuardAsync` — **4** вхождения в `6-msa`).
- `ClientId` пишется из `sub` и фильтрует чтения — это то, что требовалось: «клиент» стал измерением, а не соглашением.
- **Граница, которую фиксирую:** старые строки получают `ClientId = NULL` и **не отдаются никому** — это осознанный выбор (вариант (а)), но он того же класса, что легаси-`Self`: данные целы, видимость потеряна. Backfill — отдельное решение владельца (`DECISIONS.md` п.2).

## Результат

- `ClientId` добавлен в 4 сервиса (модель + команда + read-model + миграция): Portability (`AddClientIdToDocument`), SomaticSeries (`AddClientIdToSomaticPoint`), DailyMetrics (`AddClientIdToDailyMetrics`), Catalog (`AddClientIdToCatalogItem`);

- `catalog`/`somatic`/`daily-metrics` зелёные; изоляция проверяется доменными тестами + фильтром `ListAsync(clientId)`;
- «сколько строк без владельца» — сверка @DO на dev (подсчёт `ClientId IS NULL`).

## Уточнение по `Portability`: механизм конкретнее, чем «нет ClientId» (@TL 00:0x)

Сервис **не** stateless — он хранит CSV-документ, и выдача не привязана к владельцу:

```csharp
// PortabilityController.cs:25-27
[HttpGet("document")]
public async Task<IActionResult> Document(CancellationToken ct)
{ var r = await _mediator.Send(new GetDocumentQuery(), ct); return r is null ? NotFound() : Ok(r); }
```

```csharp
// PortabilityQueries.cs:4
public sealed record GetDocumentQuery : IRequest<CsvDocumentReadModel?>;   // ← БЕЗ параметров
```

**Следствие:** клиент A делает `export` (создаёт/перезаписывает документ), клиент B вызывает `GET /api/v1/portability/document`
и получает **CSV клиента A**. Никакого `id`/`sub` в запросе нет — значит проверять владельца негде.

**Минимальная правка:** `GetDocumentQuery(Guid clientId)` + `sub` из токена в контроллере; документ хранить с `ClientId`
и отдавать только свой (иначе 404). Это же требование закрывает сценарий «чужой экспорт».

**И проверка на будущее:** `ExportRecordsCommand(IReadOnlyList<string> Rows)` — данные приходят **от клиента**, то есть
сервис ничего не читает сам; это хорошо (нет утечки через export), но означает, что изоляция нужна именно на **хранении и выдаче** документа.

## Подтверждение по `Catalog`: данные персональные, а не справочные (@TL 00:17)

Модель каталога содержит пользовательские поля — то есть это **не** общий справочник, а личные записи:

```
6-msa/BC-Catalog/src/Catalog.Domain/Abstraction/ICatalogAnemicModel.cs
  :6   string Photo { get; }
  :7   string Notes { get; }
  :10  string FantasyPartner { get; }
```

Эндпоинты `CatalogController`: `POST /` (создать), `/{id}/name`, `/{id}/details`, `/{id}/archive`, `/{id}/restore`,
`/{id}/remove`, `GET /`, `GET /{id}` — то есть пользователь **создаёт и правит свои** позиции, а измерение владельца
отсутствует в сервисе целиком (`ClientId` — 0 файлов).

**Вывод по карточке:** в `Catalog` утечка не «теоретическая»: при двух клиентах второй увидит и сможет изменить
личные позиции первого (фото/заметки/партнёр-фантазия).
