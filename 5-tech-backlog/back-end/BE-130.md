## Факт

```
POST /partners                 -> 200 (id 9a303620-…)
GET  /partners                 -> 200, элементов 1
GET  /partners/{id}            -> 200                     ← партнёр существует и владелец совпадает
POST /partners/{id}/link-client -> 500 (тело пустое)
```

**До фикса** тот же вызов отдавал **404** (guard не находил партнёра — read-модель была пуста). Теперь guard проходит (партнёр читается), и падает **сам обработчик команды**.

**По канону** ожидается `200` (успех) или `404` (чужой/несуществующий id); `500` не предусмотрен ⇒ исключение внутри `LinkClient`-пути.

## Где смотреть

- `PartnersController` — метод `LinkClient` (маршрут `{id}/link-client`), далее `LinkClientCommand` → обработчик → агрегат;
- проверить, не повторяется ли класс «двойная запись события»: если обработчик пишет событие, а `BusAdapter` уже сохранил — исключение дубликата ключа уйдёт в 500 (ровно как было в консьюмере, `BE-128`);
- проверить, не кидает ли команда на уже привязанном `ClientId` (идемпотентность: повторная привязка того же клиента должна быть `200` или доменная ошибка `400`, но не `500`).

## Критерии приёмки

1. `POST /partners/{id}/link-client` с телом `{clientId}` → **200** для своего партнёра;
2. повторный вызов с тем же `clientId` → **200** (идемпотентно) или `400` с доменным текстом — **не** `500`;
3. чужой/несуществующий `id` → **404** (канон);
4. `smoke-front` шаг, который дергает `link-client`, — зелёный.

## ✅ КОРЕНЬ НАЙДЕН (@DO 17:47) — **EF: повторный tracking того же `(Id, Version)`**

Из логов `xdiary-partners` (Kestrel пишет сам, не глотается):

```
System.InvalidOperationException: The instance of entity type 'DomainEventEntry'
cannot be tracked because another instance with the same key value for {'Id', 'Version'}
is already being tracked. When attaching existing entities, ensure that only one entity
instance with a given key value is attached.
   (3 раза, Request id 0HNQ5GA89M783:…)
```

**Что это значит:** в пути `LinkClient` событие с тем же ключом `(Id, Version)` уже **отслеживается** `DbContext` (агрегат реконструировался из event store в том же контексте), и при сохранении нового события EF получает **второй** экземпляр с тем же ключом → `InvalidOperationException`.

**Почему маркер `[link] EX:` = 0 при этом:** исключение выброшено **не в теле action**, а в момент `SaveChanges`/attach (в observer-пути `BusAdapter`), поэтому наш `try/catch` вокруг `LinkClient` его не видит, а Kestrel логирует как необработанное.

**Направления фикса (зона @BE):**
1. чтение истории для реконструкции — `AsNoTracking()` (или отдельный короткоживущий контекст), чтобы replay не оставлял tracked-сущности;
2. либо перед сохранением — `ChangeTracker.Clear()` / detach по ключу `(Id, Version)`;
3. либо не создавать второй экземпляр: сохранять через тот же tracked-инстанс (`Attach` не нужен, если сущность уже в контексте — достаточно обновить поля);
4. проверить, что `Version` нового события действительно **инкрементится** (если версия не растёт, ключ коллизирует сам с собой — это тот же класс, что `BE-128`).

**Критерий:** `POST /partners/{id}/link-client` → **200**; повторный вызов с тем же `clientId` → 200 или 400 (не 500); в логах нет `cannot be tracked … already being tracked`.
