## Факт

`python tools/check_eventstore_registration.py` на `origin`:

```
6-msa/BC-Journal/src/Journal.Api/Program.cs    typed-before (typed на 38, DF на 39)
6-msa/BC-Partners/src/Partners.Api/Program.cs  typed-before (typed на 36, DF на 37)
::error:: 2 нарушений канона (одна типизированная регистрация ПОСЛЕ AddEventStorePostgres…)

```

**Гейт считает «typed ДО DF» нарушением.** А фактически — это и есть **исправное** состояние:

1. Коммит `de5507f0` **поменял порядок**: было `AddEventStorePostgres` → `AddDbContext`, стало наоборот
   (в диффе: `-AddEventStorePostgres…` / `+AddDbContext…`).
2. **Именно после этого** на dev появились `migrations=20261105112339_AddEventStore`,
   таблица `Commands.DomainEvents`, и исчезли `42P01` (**36 → 0**); `§5` стал `rc=0`.
3. Механизм: `DbContextOptions<T>` регистрируется через **`TryAdd`** внутри `AddDbContext`
   ⇒ **первая** регистрация выигрывает, а `AddEventStorePostgres`, вызванный после, её не перекрывает.

## Задача

- **инвертировать правило:** `typed` **ДО** `AddEventStorePostgres` — канон; `typed` после — дефект;
- **перевернуть кейсы `--selftest`:** сейчас `case(df + typed, 'ok', 'typed после DF (канон)')` и
  `case(typed + df, 'typed-before', 'typed до DF — дефект')` — оба наоборот;
- **записать механизм в docstring** (строка 9 сейчас утверждает «последняя регистрация перекрывает» —
  это неверно для `DbContextOptions`);
- проверить, нет ли рядом второго правила про read-контексты, которое тоже опирается на «последняя выигрывает».

## Критерии приёмки

- `check_eventstore_registration` на `origin` → **`rc=0`**, «нарушений 0», при **текущем** порядке
  (`AddDbContext` → `AddEventStorePostgres`) в Partners и Journal;
- `--selftest` содержит кейс «typed ДО DF → ok» и «typed ПОСЛЕ DF → дефект»;
- на подложенном дефекте (переставить обратно) гейт краснеет — доказано в двух направлениях;
- в docstring одна строка про `TryAdd` и первую регистрацию, со ссылкой на `de5507f0`.

## Результат

**Правило инвертировано, кейсы перевёрнуты, механизм записан — гейт на `origin` зелёный.**

| что | было | стало |
|---|---|---|
| `verdict` | типизированная **после** DF → `ok`; **до** DF → `typed-before` (нарушение) | **до** DF → `ok`; **после** → `typed-after` (нарушение) |
| `--selftest` | кейсы наоборот | `typed + df` → `ok` («typed ДО DF — канон»), `df + typed` → `typed-after`; **11/11** |
| docstring шапки | «обязана идти ПОСЛЕ… (последняя регистрация перекрывает)» | «обязана идти ДО… (`TryAdd` в `AddDbContext`: выигрывает первая регистрация)» |
| `manual_after_library` | «„после“ здесь — канон» | «**ДО** `AddEventStorePostgres`; „после“ — дефект» |
| прогон на репозитории | `rc=1`, 2 нарушения на корректном коде | **`rc=0`**, «проверено файлов: 2, нарушений: 0»; в выводе `ok (typed 41 -> DF 42 (канон: typed раньше))` и то же для Partners |

**Механизм (записан в код, а не в чат):** `DbContextOptions<T>` регистрируется через **`TryAdd`**
внутри `AddDbContext` ⇒ выигрывает **первая** регистрация; `AddEventStorePostgres`, вызванный
после, её не перекрывает. Именно поэтому `de5507f0` (typed раньше DF) дал на dev
`migrations=20261105112339_AddEventStore`, таблицу `Commands.DomainEvents` и `42P01` **36 → 0**.
