# DO-139 — P0: на dev `GET /api/v1/partners` → **502** (сервис `xdiary-partners` не отвечает)

- **Статус:** ToDo
- **Приоритет:** **P0** — из-за этого падает `smoke-front` (add-partner) и `deploy-prod` остаётся `skipped`
- **Источник:** замер @TL 2026-11-18 00:3x с валидным JWT на dev; `deploy-dev` в `run 44177958253` — **success**, DI-ошибки в логе больше нет
- **Зависимости:** `DO-128` (пересоздание/имя контейнера), `BE-125` (старт `BC-Partners` — уже влит)
- **Проверяет:** @TL
- **Исполняет:** @DO (инфраструктура) + @BE (если сервис падает на миграциях)

## Факт (замер с валидным JWT, не по внешнему 401)

```
GET /api/v1/partners            -> 502 (пустое тело)
GET /api/v1/partners/directory  -> 502 (пустое тело)
```

При этом `catalog`, `journal/fantasies`, `journal/places`, `somatic-series` отвечают (200), а `journal/records` и `journal/recent` — 500 (это `BE-126`). Значит именно `partners` недоступен за шлюзом.

## Что нужно (три read-only команды)

```bash
podman ps -a --filter name=xdiary-partners --format "{{.Names}} {{.Status}}"
podman logs --tail 120 xdiary-partners
podman inspect xdiary-partners --format "{{.ImageDigest}}"
```

и сверить digest с `7-deploy/images.lock` (`partners single-b536455 …`).

**Гипотезы, которые разведёт этот вывод:**
1. контейнер **crashloop** — в логах будет EF `42703` (колонка `version`) или иная ошибка старта;
2. контейнер **не создан** — `podman ps` покажет отсутствие, причина в `recreate-service` (`DO-128`);
3. контейнер жив, но **не в сети `xdiary`** — тогда 502 от шлюза, а сервис внутри отвечает.

## Критерий

`GET /api/v1/partners` с валидным JWT → **200**, `smoke-front` (add-partner) → зелёный, `deploy-prod` перестаёт быть `skipped`.

## Стенд ФЛАПАЕТ: `clients` тоже отдаёт 502 (замеры 00:29-00:32)

| время | кто | `POST /api/v1/clients` | вывод |
|---|---|---|---|
00:29 | @TL | **200** (логин прошёл, `/verify` 200) | работало |
00:31 | @TE | **502**, три попытки подряд | не работало |
00:32 | @TL | **200** (логин снова прошёл) | работало |

То есть дело не в одном «упавшем» сервисе: `clients` **то отвечает, то нет** в пределах трёх минут. Это признак **перезапусков/нестабильности контейнеров** (crashloop с окнами доступности или нехватка ресурсов), а не «фича сломана».

**Следствие для методики:** одиночный замер на dev ничего не доказывает — ни «зелено», ни «сломано». Нужен протокол: **3 попытки с интервалом**, фиксировать все статусы; «зелено» = 3/3, «сломано» = 0/3, иначе «флап, причина — контейнеры».

`partners` при этом стабильно 502 (все три замера), а `journal/records` и `recent` стабильно 500 — их это не оправдывает, это отдельные дефекты (`BE-126`).

## Важное уточнение: `partners` 502 — **НЕ следствие** упавшего `clients`

Гипотеза «partners 502 потому, что логин не поднялся» проверена и **отброшена** замером в одном прогоне:

| время | `POST /clients` | `GET /partners` (с валидным JWT) |
|---|---|---|
00:29 | **200** (логин прошёл) | **502** |
00:32 | **200** | **502** |
00:34 | **200** | **502** |

То есть когда `clients` **работает**, `partners` всё равно отдаёт 502 ⇒ это **два независимых дефекта** (в `DO-139` — `partners`; флап `clients` — отдельная строка там же).

Симметрично: `journal/records` и `/recent` → **500 во всех замерах**, включая те, где логин работал (`BE-126`).

## Окно 502 у `clients` закончилось — и это НЕ «исключение в обработчике» (проверено @TL 00:35)

Гипотеза @TE («400 на невалидное тело отдаёт валидация, 502 появляется на работе с БД/событиями ⇒ это исключение внутри обработчика, класс `BE-126`») **проверена и отброшена**:

| проверка | результат |
|---|---|
`POST /clients` с телом `{}` (невалидное) | **400** «One or more validation errors» (подтверждает наблюдение @TE) |
`POST /clients` с валидным телом, **5 раз подряд** с интервалом 3 с | **200 × 5** (487/170/179/331/1030 мс), клиенты созданы, `otpExpiresAt` выставлен |
`GET /partners` (валидный JWT, тот же момент) | **502** — не изменилось |
`GET /journal/records` / `/recent` | **500** — не изменилось |

Вывод: **запись в БД у `clients` работает** (5/5), значит 502 из окна `00:31–00:36` — это **не** schema-исключение и **не** crashloop: окно закрылось само (перезапуск после `deploy-dev` 00:15 / короткая деградация APIM). А вот `partners` (502) и `journal` (500) — **стабильны** во всех замерах, включая текущие.

**Что это меняет для `DO-139`:** пункт «clients» понижается до «флап, окно 00:31–00:36 прошло, сейчас 200»; главным остаётся `partners` — там 502 в каждом замере, при рабочем логине.

## 🔍 Гипотеза (d), которую я нашёл в репозитории: это может быть APIM target, а не контейнер (@TL, статический разбор)

В `7-deploy/apim/import.sh` (строки 257-260) **уже описан наш симптом дословно**:

```
# Факт 2026-11-16 05:5x: маршруты journal/partners/каталог уже есть (404 ушёл), но journal и
# partners отдают 500 от Gravitee — определение API смотрит в невалидный target (следствие
# `servers: "/"`, AR-160). Ставим target явно: http://<host>:8080 и перезапускаем API.
```

И для этого случая есть **готовый скрипт** `7-deploy/apim/fix-target.sh` (78 строк):

```
# Запуск на VPS-1:  bash /opt/xdiary/7-deploy/apim/fix-target.sh [journal partners]
# находит API по listener-пути /api/v1/<svc>, показывает текущий target,
# ставит http://<svc>:8080, перезапускает API
```

**Что это объясняет лучше, чем «контейнер упал»:**
- `partners` → **502 на всех** роутах (`/partners`, `/partners/directory`) — как будто шлюз не может достучаться до backend;
- `journal` → `/records` и `/recent` **500**, а `/fantasies` и `/places` **200**: если у Gravitee отдельные определения API на разные пути, «сломанный target» может задевать только `journal`-API, а не вспомогательные;
- `catalog` и `somatic-series` — 200, то есть шлюз в целом жив.

**Порядок проверки (дешевле, чем логи):**
1. `bash /opt/xdiary/7-deploy/apim/fix-target.sh partners journal` — скрипт **сам печатает текущий target** до правки; если там мусор/невалидный хост, гипотеза подтверждена;
2. сразу после — повторный замер `GET /api/v1/partners` с валидным JWT (ожидание 200) и `GET /api/v1/journal/records` (ожидание 200);
3. если после правки target всё равно 502/500 — тогда уже `podman logs` (контейнер), и это будет уже вторая итерация, а не первая.

**Важно для `deploy-prod`:** `apim-parity` в прогонах **зелёный**, но он сверяет пути/контракт OpenAPI, а **не** backend-target — поэтому наш 502 он не ловит. Это стоит записать как дефект гейта (кандидат в `DO-138`-класс: «гейт зелёный, а маршрут в никуда»).
