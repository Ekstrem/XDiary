## Настоящая причина: путь `--from-registry --write` не проставляет digest-и

`.github/workflows/lock-sync.yml`:

```
74-88|  Перегенерировать lock:
          python tools/gen_images_lock.py --from-registry --write     # при rc!=0 → git checkout --
95-109| Guard — digest не уменьшился:
          python tools/gen_images_lock.py --check-digests             # rc=1 → откат и exit 1
```

При смене релизного тега **все** сервисы получают новый `single-<sha>`, поэтому `merge_digests` (он сохраняет digest **только для того же тега**) не переносит ни одного — а шага `--fill-digests` в workflow **нет**. Итог: перегенерация даёт 12 строк **без** `digest=sha256:`, гейт `DO-113` видит «было 12, стало 0» и откатывает lock.

**А `tools/gen_images_lock.py` умеет это делать** — есть готовый флаг:

```
657|  ap.add_argument("--fill-digests", …)   # DO-113: дописать digest=sha256:… из реестра
616|  def fill_digests(path, registry="ghcr.io", owner="ekstrem", digest=manifest_digest, …)
```

То есть фикс — **добавить шаг в workflow**, а не менять инструмент.

## Патч

`5-tech-backlog/tl/patches/lock-sync-fill-digests.patch` — вставляет перед шагом Guard:

```yaml
      - name: Заполнить digest из реестра (DO-113)
        run: python tools/gen_images_lock.py --fill-digests || true
```

`|| true` — потому что `fill_digests` для `front` заведомо не найдёт образ (он не публикуется); остальным проставит. Guard после этого увидит заполненные digest-и и не откатит lock.

**Критерий:** `lock-sync` на новом head пишет lock с новым тегом **и** ≥12 `digest=sha256:`; `deploy` на этом lock доходит до `deploy-prod`.
