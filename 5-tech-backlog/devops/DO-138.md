## Дефект 1 — `check_env_hosts` падает в CI, потому что по умолчанию читает VPS-файл

Проверено по коду `tools/check_env_hosts.py`:

```
111|     ap.add_argument('--env', default='/opt/xdiary/7-deploy/secrets/.env')
118|     if not os.path.exists(a.env):
119|         print('::error::check_env_hosts: нет файла %s' % a.env)
```

То есть при запуске **без `--env`** гейт требует файл, который существует только на VPS (`/opt/xdiary/7-deploy/secrets/.env` — секрет). В CI этого файла нет по определению ⇒ гейт всегда красный, независимо от содержимого репозитория.

**Почему это дефект, а не «так и надо»:** гейт, который в CI не может быть зелёным, не проверяет ничего — он просто блокирует очередь. Плюс он подталкивает «обходить» его (что и произошло: `merge queue` стоит).

**Что нужно:** в CI (когда файла нет) — **явный skip с notice** («файл не передан — проверка не выполнена»), а `rc=1` оставить только для случая «файл есть, но Contour/Host не совпал». На VPS-шаге, где файл реально передаётся, поведение не меняется.

## Дефект 2 — `check_readstore_ddl` читает только `CREATE TABLE`, но не `AddColumn`

Проверено по коду `tools/check_readstore_ddl.py`:

```
33| DDL = re.compile(r'CREATE\s+TABLE\s+IF\s+NOT\s+EXISTS\s+...')
58| (докстринг) {таблица: {колонки}} из EF-миграции `CreateTable(name: "...", columns: table => new { ... })`.
65| for m in re.finditer(r'name:\s*"([a-z0-9_]+)"', text):
70| for cm in re.finditer(r'([A-Za-z0-9_]+)\s*=\s*table\.Column<...>\(\s*type:\s*"([^"]+)"', region):
```

Колонки берутся только из `CreateTable(...)`; **`AddColumn(...)` не парсится вообще**. Поэтому колонка, добавленная отдельной миграцией (`AddStateToJournalRead` и подобные), считается отсутствующей — ложное срабатывание.

**Что нужно:** учитывать `AddColumn` (и, желательно, `AddColumn` с `schema`/`nullable`) при сборке списка колонок; сохранить текущее поведение для `CREATE TABLE`/`CreateTable`.

## Что НЕ входит в эту карточку

Отсутствующая колонка `version` в `journal_read` — **реальный хвост @BE** (он это сам признал). После исправления гейта она должна честно покраснеть и закрыться миграцией, а не быть замазанной.

## УТОЧНЕНИЕ по дефекту 3 (2026-11-17 21:0x) — pyyaml НЕ «не ставится», а **пропускается**

Проверил шаги job `check-chat` в прогоне `44139899378` (`gh api …/actions/jobs/134239507804`):

```
failure  Check chat format (нет молча потерянных сообщений)
skipped  Зависимости гейтов (PyYAML) — до первого чтения YAML      ← ПРОПУЩЕН
failure  Реестр API ↔ код — DO-064 (…)                             ← запущен БЕЗ pyyaml
```

Механика:
- шаг установки (`ci-guards.yml:154-155`, `python -m pip install … pyyaml`) **не имеет `if: always()`** ⇒ при падении предыдущего шага GitHub его **пропускает**;
- шаг «Реестр API ↔ код» **имеет `if: always()`** ⇒ он всё равно запускается, но уже **без** зависимости;
- `04-architecture/gen_openapi.py:39` печатает `нужен pyyaml` и отдаёт `exit 2`.

**Важно:** `pip install` в файле **есть** (добавлен @DO `995b4b169`, 11-13 08:45), и он стоит **до** первого чтения YAML. То есть дефект не «забыли поставить», а **порядок отказоустойчивости**: `if: always()` есть у потребителя, но не у поставщика зависимости.

**Правильное лечение:** либо `if: always()` у шага установки PyYAML (чтобы зависимость ставилась всегда, когда будет запущен потребитель), либо перенести `pip install pyyaml` **внутрь** шага «Реестр API ↔ код» (первой строкой), либо убрать `if: always()` у потребителя. Первый вариант минимален и не меняет семантику остальных шагов.

**Следствие для очереди:** пока `Check chat format` красный (сейчас — порядок строк в `ar/fe/te/dr`), шаг API **всегда** будет давать ложный `exit 2`. То есть `#2439`/`#2429` блокирует **не** pyyaml, а порядок строк в чатах; pyyaml — вторичный эффект.
