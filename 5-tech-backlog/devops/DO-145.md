# DO-145 — P1: `deploy-dev` **повторно** падает на `recreate xdiary-client` → фиксы до кода не доезжают

- **Статус:** Закрыта
- **Приоритет:** **P1** — блокирует весь конвейер: `deploy-dev` падает → `smoke-*`/`apim-parity` = skipped → `deploy-prod` не запускается
- **Источник:** два прогона @TL-замера: `44382324004` (head `dea07646`, 22:38) и `44384265810` (head `dd461808`, 22:48)
- **Зависимости:** `DO-143` (readiness-гейт — частично поможет, но это отдельная причина)
- **Проверяет:** @TL
- **Исполняет:** @DO (`7-deploy/`)
- **В работе с:** 2026-11-18
- **Результат:** —

## Факт: два прогона подряд, одна и та же строка
```
recreate-service: ОШИБКА: xdiary-client не поднялся. Восстановить: bash /tmp/recreate-client.sh.<random>
откат api-gateway → bb0493f0… (OK)
вход отвечает: GET /clients=401, POST /clients=400
##[error]Process completed with exit code 1.
```
При этом сам сервис после падения **отвечает**: `POST /clients` → 200 (проверено @TL 22:46 и 22:50), `GET /partners` → 200. То есть контейнер жив, а `recreate-service.sh` считает, что «не поднялся».

## Направления (по коду `7-deploy/recreate-service.sh`)
1. **healthcheck-таймаут** — окно ожидания меньше реального старта `client` (в логе строка появляется через ~6-7 секунд после старта контейнера);
2. **rollback-путь не чистит за собой** — `откат client не удался (нужно вручную)` (было в первом прогоне) означает, что вторая попытка тоже падает по той же причине;
3. **`recreate` проверяет `podman ps` сразу после `run -d`**, а не `RestartCount`/`ExitCode` + `/health`;
4. в логе `POST /clients=400` при проверке входа — разобраться, ожидался ли 200/201 (если да, то это ложный провал проверки, а не реальный отказ).

## Критерий
`deploy-dev` зелёный → `smoke-api`/`smoke-front`/`apim-parity` реально исполняются (не `skipped`); `podman ps` ↔ `images.lock` совпадают.

## Настоящая причина (найдена @TL 23:22, прогон `44387527593`, head `4cd9ada2` — уже с фиксом `#2801`)

```text
ОШИБКА: POST /api/v1/clients = 502 (ждали 200/201/400; 502 = нет псевдонима clients)
api-gateway не поднялся — прекращаю и откатываю остальные
провал на api-gateway: откат на предыдущие образы
<далее откат ВСЕХ сервисов по кругу>
```

**Механизм:** проверка входа в `deploy.sh` обращается к `POST /api/v1/clients`, шлюз отвечает `502` с пояснением «нет псевдонима `clients`» (в `deploy.sh` псевдоним объявлен как `client` — единственное число). Скрипт трактует это как «api-gateway не поднялся» и **откатывает все 12 сервисов**.

**Почему это важно:** причина **детерминированная**, не таймаут — поэтому каждый `deploy` будет падать одинаково, `smoke-*` не запустятся, `deploy-prod` не стартует, и ни один фикс (включая `BE-131`) не доедет до стенда.

**Правки:**
1. согласовать псевдоним: либо `client` → `clients` в конфиге шлюза (если контракт `/api/v1/clients`), либо проверять путь, который реально маршрутизируется;
2. **не откатывать все сервисы** при провале проверки входа — достаточно `exit 1`, состояние должно остаться диагностируемым;
3. (из `DO-143`) readiness-ретраи вместо разового `curl`.

## Склеенная цепочка причин (@FE 23:34 + @TL 23:22)

1. **`recreate-service.sh:332-356`** — критерий готовности: `podman ps --format '{{.Names}}' | grep -qx "$CONTAINER"` (без `-a`, без HTTP; окно 3 × (`bash runner` + `sleep 3` + `sleep 5`)). В логе прогона приложение печатает `Application started` / `Now listening on: http://[::]:8080`, а `ps` его **не показывает** ⇒ либо другой podman-store (rootless vs root), либо контейнер в момент проверки перезапускается.
2. ⇒ `api-gateway` признаётся неподнявшимся.
3. ⇒ проверка входа получает `POST /api/v1/clients = 502` и печатает «нет псевдонима `clients`» — **это следствие отсутствия шлюза, а не причина**.
4. ⇒ скрипт выполняет **откат всех 12 сервисов**, `deploy-dev` = failure, `smoke-*` = skipped.

**Порядок правок:**
- **(A) первым, 3 строки:** не откатывать все сервисы при провале одной проверки — `continue` + итоговый список проблемных; это сразу даёт `smoke-api` в прогоне и ответ по `BE-131`;
- **(B) вторым:** критерий готовности → `podman inspect --format "{{.State.Status}} {{.State.RestartCount}} {{.State.ExitCode}}"` **в том же `sudo`/store, что и `run`** (иначе повторим ошибку «смотрим не в тот store» из `DO-143`), плюс HTTP-проверка с **белым списком кодов** (`401`/`400` валидны для закрытых сервисов, `-f` не годится).


## Класс, зафиксированный по итогам (формулировка @TE, 22:59)

**«Проверка отработала раньше, чем появился объект проверки».**

Три наблюдения одного класса за 2026-11-19:

| случай | проверка | объект | итог |
|---|---|---|---|
| `lock-sync` | сверка digest с реестром | образы, которые `Release` ещё собирал | «lock актуален» → lock отстал, `deploy-prod` упал на страже |
| `chat_lint` | порядок/дубли строк | файл до `rstrip`-фикса | ложные срабатывания на «пустых» строках |
| `guard-secrets` | сканер секретов | дерево до фикса сканера | `rc=1` на усечённом digest |

**Критерий:** триггер обязан **следовать за событием**, которое он проверяет.
Реализация: `lock-sync` получил `workflow_run: types [completed]` (`#3105`), плюс защита от
маскировки ошибки (`|| echo 0` → явный отказ) и минимум 2 итерации ожидания.

**Признак в логе (для будущих ревью):** если проверка завершилась быстрее, чем её объект мог появиться,
результат «всё хорошо» — не доказательство, а совпадение.
