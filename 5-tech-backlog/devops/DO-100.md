## Найденная причина №2: `Backend tests` падает на **любом** пуше, где не менялся BC (@TL 00:4x, без логов — по коду и diff)

`ci-backend.yml:79-81`:

```bash
bcs=$(printf '%s\n' "$changed" | grep -oE '^6-msa/(BC-[A-Za-z0-9]+|ApiGateway(\.Tests)?)' \
      | cut -d/ -f2 | sed 's/\.Tests$//' | sort -u | tr '\n' ' ')
```

GitHub запускает `shell: bash` как **`bash -eo pipefail`**. Если в пуше **нет** файлов, подходящих под
`6-msa/BC-…`, то `grep -oE` завершается с кодом **1** → `pipefail` делает весь конвейер неуспешным →
присваивание `bcs=$(…)` проваливается → `-e` **прерывает шаг** → «Определить зону» краснеет.

**Проверка на фактах:** оба упавших прогона `Backend tests` — это пуши, где менялись только `9-tests/**` и чат:

```
06d78e0a (base a19583fe): 5-tech-backlog/chat/te.md, 9-tests/README.md,
                          9-tests/RnD/front-e2e/tests/edit-delete-record.spec.js,
                          9-tests/scripts/check_e2e_positional.py      → совпадений с BC: 0
a8ef6234 (base 94f1d73e): 5-tech-backlog/chat/te.md, 9-tests/README.md,
                          9-tests/scripts/check_e2e_all.py,
                          9-tests/scripts/e2e_receipt.py              → совпадений с BC: 0
```

⇒ **Это не «флейк» и не «стенд»: гейт зелёный только тогда, когда менялся BC.** Любой пуш в `9-tests/**`,
`.github/**` или docs ломает job.

**Минимальная правка (одна):**

```bash
bcs=$(printf '%s\n' "$changed" | grep -oE '^6-msa/(BC-[A-Za-z0-9]+|ApiGateway(\.Tests)?)' \
      | cut -d/ -f2 | sed 's/\.Tests$//' | sort -u | tr '\n' ' ' || true)
# и ниже, при пустом списке — NONE (уже есть: ${bcs:-NONE})
```

То есть достаточно `|| true` у конвейера (или `|| echo`), чтобы пустой список стал `NONE`, а не падением.

## Найденная причина №3: `Front E2E` не падает, а **отменяется** — очередь concurrency «съедает» прогоны (@TL 00:4x)

Факты из API (последовательность прогонов `Front E2E`):

```
21:36:23  sha a8ef6234  → cancelled
21:39:11  sha 8442dbcc  → cancelled
21:40:32  sha f075bcaa  → pending
```

Каждый новый пуш в `9-tests/**` (а его триггерит `ci-front.yml`) приходит, когда в группе `front-e2e`
уже есть **running** + **pending**. GitHub в такой ситуации **отменяет pending** прогон и ставит новый pending.
`cancel-in-progress: false` защищает **running**, но не спасает **pending** от вытеснения.

Итог: пока в `9-tests/**` идут активные пушы (сегодня их было много — @TE правил тесты), прогон
**никогда не доходит до браузера**, и «чисел `passed/failed/skipped`» нет не потому, что тесты падают,
а потому что прогон не начинается. Это тот же класс, что «зелёный гейт, который не запускается», только наоборот:
**красный отчёт, которого нет**.

### Варианты (выбрать один, решает @DO как владелец workflow)

1. **Убрать `concurrency` у `ci-front.yml`** — прогоны будут вставать в очередь GitHub и доходить до конца
   (дороже по минутам, зато есть числа).
2. **`cancel-in-progress: true`** — «побеждает последний», но прогон **всё равно** завершается (отменяется старый
   running, а не pending) — числа будут у последнего пуша.
3. **Оставить как есть, но запускать `front-e2e-repeat.yml` (workflow_dispatch) в тишине** — когда пуши в
   `9-tests/**` прекратились. Это то, что просил @TE: числа + `REF`.

```
квитанция: тестов 26 | timeout 90 с | workers 1 | худший случай 39.0 мин | таймаут джобы 30 мин | нарушено: 1
```

Таймауты: `ci-front.yml:40` — **30 мин**, `deploy.yml:152` (`smoke-front`) — **30 мин**.

**Следствие:** если один тест зависнет (а именно это и бывает на живом стенде), job будет **убит по таймауту**,
и прогона с числами `passed/failed/skipped` **не будет вообще** — вместо красного отчёта получим обрыв.
Это тот же класс, что «не измерено», только выглядит как «прогон пропал».

**Правка (любая из двух):**
1. поднять `timeout-minutes` до **45** в `ci-front.yml` и `deploy.yml` (запас 39 + установка браузеров ≈ 5 мин);
2. либо снизить `timeout` теста с 90 до **60 с** — тогда 26 × 60 = 26 мин < 30.

Рекомендую (1): тесты на живом стенде иногда честно идут долго, а 15 минут запаса стоят дешевле повторного разбора.
