# DO-130 — прод-деплой не пересоздаёт контейнеры: recreate шёл под `sudo` в rootless-среду

- **Статус:** На проверке
- **Приоритет:** P0 (прод не обновлялся; все прошлые «красные прода» — следствие)
- **Источник:** прогон `deploy` #2050: `deploy-prod` → `recreate-service: ОШИБКА: xdiary-api-gateway не поднялся`
- **Зависимости:** нет
- **Проверяет:** @TL
- **На проверке с:** 2026-11-13
- **Исполняет:** @DO (зона `7-deploy/`)

## Факт (замер на VPS-1, не догадка)

```
id -un                      -> deploy
podman ps -q | wc -l        -> 18          # контейнеры ROOTLESS
sudo -n podman ps -q | wc -l -> 0          # у root контейнеров нет
podman network ls           -> podman, apim, xdiary
sudo -n podman network ls   -> podman      # у root НЕТ сети xdiary
```

`update.sh` вызывал пересоздание как `sudo -n bash recreate-service.sh`, то есть в root-пространстве,
где сети `xdiary` нет: `podman run --network xdiary` падал, 3 попытки → «не поднялся», откат падал так же.
Поэтому прод оставался на контейнерах `Up 9–10 days`, а каждый прогон деплоя краснел на пересоздании.

## Правка

Режим выбирается по факту: если текущий пользователь видит контейнеры (`xdiary-pg`), sudo не нужен;
иначе — `sudo -n`. Все три вызова `recreate-service.sh` идут через `$PODMAN_SUDO`.

## Что это объясняет

Не сторож `DO-050` и не образы были конечной причиной: сторож пройден в #2048, образы собраны `release`
с одного коммита (lock с одним `commit=`). Последний барьер — выбор пользователя для podman.

## Результат

Прод пересоздаёт контейнеры в том же (rootless) пространстве, где они живут.
