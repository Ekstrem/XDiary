## Результат

Шаг добавлен в `ci-backend.yml` — «Run BC tests (Client, ApiGateway — DO-045)»:
`dotnet test` по `6-msa/BC-Client/src/Client.IntegrationTests` и `6-msa/ApiGateway.Tests`.
Отсутствующий проект — `::warning::` и пропуск; ни одного проекта — `::error` и код 1.

**Негативный контроль получен сам собой, на реальном падении, а не искусственно.**
Первый же прогон с шагом — `ci-backend` **#47** (`38ea111`) — дал **failure**:

| Проект | Итог |
|---|---|
| `9-tests/**` (6 проектов, старый шаг) | все `Passed!` (17, 8, 16, 23, 10, 16) |
| `6-msa/BC-Client/…/Client.IntegrationTests` | **`Failed! - Failed: 1, Passed: 8`** |
| `6-msa/ApiGateway.Tests` | не дошло: сработал `set -e` |

Упавший тест: **`ClientTokenServiceTests.TryValidateRefresh_Valid_Returns_ClientId`** —
`Assert.True() Failure`. То есть тесты @BE действительно не защищали контракт: гейт был зелёным,
а `refresh`-валидация падает.

По итогам первого прогона шаг переделан: `set -uo pipefail` + агрегированный код (`fail=1`),
чтобы падение `Client` **не скрывало** результаты шлюза, и прогонялись **все** проекты.

Локально негативный контроль невозможен (в песочнице `dotnet test` → `NU1301`, nuget недоступен;
`bash` → `couldn't create signal pipe`), поэтому доказательством служит прогон CI.
