## 🔍 Разбор кода `deploy.sh` (2026-11-18 16:42, @TL) — три конкретные причины, не одна

```
 52| sudo -n podman pull -q "$ref@$dig" …        ← sudo
 55| sudo -n podman pull -q "$ref:$tag" …        ← sudo
 66| for x in $(podman ps -aq); do [ "$x" = "$(podman ps -aq --filter name=xdiary-pg)" ] \
       || podman rm -f $x >/dev/null 2>&1; done  ← БЕЗ sudo, ошибки проглочены
 67| podman run -d --name xdiary-journal …       ← БЕЗ sudo
```

**Причина 1 — смешение store'ов.** `pull` идёт через `sudo`, а `rm`/`run` — без. Если в хранилище root'а или пользователя уже есть контейнеры с этими именами (например, `xdiary-catalog`, `xdiary-client` созданы другой командой/скриптом), `podman run` падает ровно с `container name … is already in use`.

**Причина 2 — ошибки удаления проглатываются.** `… >/dev/null 2>&1` скрывает и «cannot remove container … container is running/being removed», после чего скрипт идёт дальше и падает на `run` — с сообщением, которое **не указывает на настоящую причину**.

**Причина 3 — гонка.** `podman rm -f` асинхронный: имя может ещё числиться за удаляемым контейнером, когда через строку вызывается `podman run --name`. Именно так «`rm` вроде был, а имя занято».

**Минимальный набор правок (на выбор, в порядке предпочтения):**
1. **`podman run --replace`** в каждой из 12 строк — самый короткий и идемпотентный путь;
2. либо после цикла удаления — **дождаться** исчезновения имён: `for i in 1..10; do podman ps -a --format '{{.Names}}' | grep -q '^xdiary-' && sleep 1 || break; done`, и **не** глушить ошибки `rm`;
3. либо **единый store**: весь скрипт либо с `sudo`, либо без (сейчас `pull` с `sudo`, `run` без — это и есть источник расхождения).

**И обязательная проверка в конце `deploy-dev`** (сейчас её нет):
```bash
podman ps --format '{{.Names}} {{.Image}}' | grep -E 'xdiary-(partners|journal|catalog|client)'
# теги должны совпадать с images.lock; иначе — exit 1 с внятным текстом
```
Без неё джоб может быть зелёным при старом образе — что и случилось: `deploy-dev` failed, но никто не проверил, что контейнеры остались на `378a56c`.

## 🔴 Ревью PR `#2705` (@TL, 16:51): правка верная по сути, но **есть блокер — цикл удаления снесёт APIM**

**Что сделано хорошо:** `sudo -n` во всех вызовах (единый store), `--replace` на каждом `podman run`, ошибки `rm` больше не глушатся, добавлена сверка `podman ps` ↔ `images.lock` с `exit 1` и списком расхождений. Это ровно то, что просил.

**Блокер — строка:**

```bash
for x in $(sudo -n podman ps -aq 2>/dev/null); do [ "$x" = "$(sudo -n podman ps -aq --filter name=xdiary-pg)" ] \
    || sudo -n podman rm -f "$x" 2>&1 || true; done
```

Удаляются **ВСЕ** контейнеры, кроме `xdiary-pg`. А на том же хосте в podman живёт **APIM**:

```
7-deploy/apim/up.sh:24-29
  MONGO=xdiary-apim-mongo · UI=xdiary-apim-ui · PORTAL=xdiary-apim-portal-ui
  MGMT=xdiary-apim-management · GW=xdiary-apim-gateway
```

⇒ первый же `deploy-dev` после мержа **снесёт шлюз и всё APIM** (и `deploy.sh` их не поднимает — это отдельный `apim/up.sh`). До PR это «проносило», потому что `podman` вызывался **без `sudo`** (другой store) — то есть ровно тот дефект, который PR и лечит, только теперь blast radius стал реальным.

**Как закрыть (по возрастанию объёма):**
1. **Удалить цикл вообще** — он больше не нужен: `--replace` на каждом `podman run` сам заменяет контейнеры с этими именами, а `xdiary-pg` и APIM не трогаются по построению;
2. либо сузить фильтр: только `xdiary-<сервис>` из `SERVICES`/lock, явно исключив `xdiary-pg`, `xdiary-apim-*` и прочее инфраструктурное;
3. в любом случае — **не** `podman ps -aq` без фильтра: это «удалить всё, что не pg».

**Пока блокер не снят — PR не мержу:** риск тотального простоя стенда выше пользы от идемпотентности.
