## Задача (зона @DO, `7-deploy/`)

Перевести трафик через APIM так, чтобы **снаружи ничего не изменилось**, кроме пути внутри.
Порядок обязателен (после каждого шага — проверка, до следующего не идти):

1. **Пути в APIM:** listener-пути 12 API привести к реальным `/api/v1/<домен>` (правка `7-deploy/apim/import.sh`, повторный импорт). Проверка: `curl` через шлюз `127.0.0.1:18082` на `/api/v1/...` отвечает так же, как напрямую на `:8080`.
2. **`/health` через APIM:** сейчас на `18082` → `404`. Сделать так, чтобы smoke-гейт (`/health`) проходил через новый путь.
3. **Funnel → Caddy → APIM:** `Caddyfile.prod` `reverse_proxy 127.0.0.1:8080` → `127.0.0.1:18082`; Funnel переключить на Caddy `:443` (иначе Caddy снова вне пути, `DO-067` повторится).
4. **Жизненный цикл:** APIM-контейнеры включить в `deploy.sh`/`update.sh` + `images.lock` (сейчас поднимаются вручную `up.sh` — это дрейф, `check_env_drift` его видит).

## Причина блокера — найдена (2026-11-04 21:0x)

**Корень: сервисы публичны, авторизация живёт только в YARP.**

| проверка | результат |
|---|---|
| `xdiary-catalog:8080/api/v1/catalog` **напрямую** (без YARP и APIM) | **200** |
| APIM `18082` тот же путь, без токена | **200** |
| APIM с мусорным `Authorization: Bearer …` | **200** |
| YARP `8080` без токена / с мусорным | **401 / 401** |

Значит APIM ничего не «обходит» — он просто **не является** периметром, а сервис отдаёт данные без токена.
`[Authorize]` в коде есть не везде: в `BC-Client/src/Client.Api/Controllers/ClientsController.cs` — есть
(потому `clients` = 401 в обе стороны), в контроллерах `Catalog`/`Analytics`/`DailyMetrics`/`SomaticSeries` — **нет**.

**Матрица с правильными методами (по `api-index.yaml`):**

| путь | метод | APIM | YARP | вывод |
|---|---|---|---|---|
| `/api/v1/catalog` | GET | **200** | 401 | публичный сервис |
| `/api/v1/analytics/summary` | GET | **200** | 401 | публичный сервис |
| `/api/v1/daily-metrics/hrv` | POST | **400** | 401 | публичный (дошёл до валидации) |
| `/api/v1/somatic-series/points` | POST | **400** | 401 | публичный |
| `/api/v1/clients` | GET | 401 | 401 | `[Authorize]` есть ✔ |
| `/api/v1/privacy/pin/has` | GET | 401 | 401 | ✔ |

**Про «JWT-план»:** проверил тип ключа — `Jwt__SigningKey` = **64 символа, не PEM** (симметричный HMAC).
APIM `JWT`-план проверяет подпись по **публичному ключу/OAuth2**, то есть с текущим ключом вариант «(а) JWT-план»
**не заработает без смены типа подписи**. Остаются: `[Authorize]` в сервисах (@BE) или переход на RSA
+ JWT-план (решение @AR). Сам выбрал (б) «проброс заголовка» — недостаточно: проброс не создаёт проверку.

## JWT-план: проверка выполнимости (2026-11-04 21:1x)

Решение @AR `15:10` — вариант **(а) JWT-план**. Проверил создание плана на `Catalog.Api` (probe,
планы не публиковались) — API отвергает **все** значения `signature`:

```
HMAC  -> 400 "#/signature: HMAC is not a valid enum value"
RSA   -> 400 "#/signature: RSA is not a valid enum value"
ECDSA -> 400 "#/signature: ECDSA is not a valid enum value"
JWT   -> 400 "#/signature: JWT is not a valid enum value"
NONE  -> 400 "#/signature: NONE is not a valid enum value"
HS256 -> 400 "#/signature: HS256 is not a valid enum value"
```

То есть **схема V4-плана JWT в 4.4 отличается** от той, что я предполагал (`security.configuration.signature`).
Схему не удалось достать и из инстанса: `/management/v2/plugins*` → **500**, файла схемы на диске нет
(упакована в jar). **Вывод: создание JWT-плана блокировано несовпадением схемы, а не отказом платформы** —
нужен корректный V4-контракт плана (из документации APIM 4.4 или из UI владельца), после чего повторить пробу.

**Второй риск, независимый от схемы:** `Jwt__SigningKey` — 64 символа, не PEM (симметричный HMAC).
Если V4-план JWT принимает только асимметричную подпись, то для (а) нужен перевод подписи сервисов на
RSA/ECDSA (решение @AR + ротация ключа @DO). Пробу с HMAC-секретом проверить не удалось из-за схемы.

Unhandled exception. System.IO.IOException: The configured user limit (16384)

Замер на проде: **занято 24641 инстанс inotify при лимите 16384** — то есть лимит был съеден
целиком, и любой новый/перезапущенный .NET-сервис падал на старте, попадая в рестарт-петлю.
