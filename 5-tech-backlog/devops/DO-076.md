## Задача (зона @DO, `7-deploy/`)

Перевести трафик через APIM так, чтобы **снаружи ничего не изменилось**, кроме пути внутри.

2. **`/health` через APIM:** сейчас на `18082` → `404`. Сделать так, чтобы smoke-гейт (`/health`) проходил через новый путь.
3. **Funnel → Caddy → APIM:** `Caddyfile.prod` `reverse_proxy 127.0.0.1:8080` → `127.0.0.1:18082`; Funnel переключить на Caddy `:443` (иначе Caddy снова вне пути, `DO-067` повторится).

## JWT-план: проверка выполнимости (2026-11-04 21:1x)

Решение @AR `15:10` — вариант **(а) JWT-план**. Проверил создание плана на `Catalog.Api` (probe,
планы не публиковались) — API отвергает **все** значения `signature`:

```
HMAC  -> 400 "#/signature: HMAC is not a valid enum value"
RSA   -> 400 "#/signature: RSA is not a valid enum value"
ECDSA -> 400 "#/signature: ECDSA is not a valid enum value"
JWT   -> 400 "#/signature: JWT is not a valid enum value"
NONE  -> 400 "#/signature: NONE is not a valid enum value"
HS256 -> 400 "#/signature: HS256 is not a valid enum value"
```

То есть **схема V4-плана JWT в 4.4 отличается** от той, что я предполагал (`security.configuration.signature`).
Схему не удалось достать и из инстанса: `/management/v2/plugins*` → **500**, файла схемы на диске нет
(упакована в jar). **Вывод: создание JWT-плана блокировано несовпадением схемы, а не отказом платформы** —
нужен корректный V4-контракт плана (из документации APIM 4.4 или из UI владельца), после чего повторить пробу.

**Второй риск, независимый от схемы:** `Jwt__SigningKey` — 64 символа, не PEM (симметричный HMAC).
Если V4-план JWT принимает только асимметричную подпись, то для (а) нужен перевод подписи сервисов на
RSA/ECDSA (решение @AR + ротация ключа @DO). Пробу с HMAC-секретом проверить не удалось из-за схемы.
