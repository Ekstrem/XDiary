## Факты (по коду и по путям на VPS, не по догадке)

1. Миграции EF в коде **есть**: `6-msa/BC-*/src/*.Storage/Migrations/…` (InitialCreate + последующие, напр. `20261106150000_AddClientIdToCatalogItem.cs`).
2. **Применения миграций в деплое нет:** `git grep -i "dotnet ef|Database.Migrate|EnsureCreated"` по `6-msa` и `7-deploy` → **пусто**. Значит новые образы приезжают к **старой** схеме.
3. Гейт расхождения схемы существует — `tools/check_schema.py` («собирает ожидаемый список миграций из кода и фактический из `__EFMigrationsHistory`, rc=1 при расхождении»), и `update.sh` его вызывает по пути `/opt/xdiary/tools/check_schema.py`.

То есть: расхождение схемы не видно ни гейту (файла нет), ни людям (миграции не применяются) — а сервисы на новых образах падают `500`.

## Что нужно решить (задача)

1. **Применять миграции при выкатке**: шаг «migrate» до пересоздания сервисов (или контейнер-migrator, или `dotnet ef database update` из образа), с откатом при провале.
2. Пока миграций нет — **гейт должен быть жёстким**: если `check_schema.py` вернул `rc=1`, деплой останавливается **до** пересоздания (иначе получаем ровно текущее состояние: новые образы + старая схема = 500).
