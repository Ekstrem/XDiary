## Новые факты (2026-11-16 04:0x, прогон 43782330967 + пробы)

**Дамп APIM (104 API, все `contextPath` пустые):** маршруты задаются НЕ `contextPath`, а `listeners[].paths` (V4 PROXY). У каждого сервиса в APIM **по две записи**: старая `STARTED` и моя новая `STOPPED`:

```
73. a26f2441… cp="" state="STARTED" name="Journal Microservice API"
83. 82cfdc75… cp="" state="STARTED" name="Partners Microservice API"
72. 35dd10fc… cp="" state="STOPPED" name="Journal Microservice API"
27. 3ddf7886… cp="" state="STARTED" name="Catalog.Api"   ← каталог работает
```

**Пробы маршрутов на проде (это и есть ключ):**

| путь | ответ |
|---|---|
`/api/v1/catalog` | **401** (маршрут есть) |
`/api/v1/journal/records` | **404** (маршрута нет) |
`/journalmicroserviceapi/records` | 500 |
`/journalmicroserviceapi/api/v1/journal/records` | **500** ← маршрут ЕСТЬ, отдаёт Gravitee (`X-Gravitee-*`, тело APIM) |
`/partnersmicroserviceapi/api/v1/partners` | **500** (то же) |

**Вывод:** старые API (`STARTED`) живут по адресу `/<title>/`, а операции у них — абсолютные (`/api/v1/journal/records`). Отсюда двойной префикс: клиент зовёт `/api/v1/journal/records` → 404, а рабочий маршрут — `/journalmicroserviceapi/api/v1/journal/records` → 500 (битый backend, тот самый дефект `AR-160`).

**Что это значит для починки:** нужен API, у которого `listeners[].paths = /api/v1/journal/*`, а операции — относительные (`/records`), с корректным backend. Импорт через `_import/swagger` строит listener из названия спеки (`/journalmicroserviceapi/`) — поэтому и возникает `400 path.invalid` при повторных попытках.

**Проверено также:** `/fantasies`, `/records`, `/api/v1/journal/fantasies` → 404 (значит относительных маршрутов нет ни у одной записи).

**Точный следующий шаг для @DO (нужен management-API доступ):** либо (а) импортировать спеку с `servers: [{"url": "/api/v1/journal"}]` **и** относительными путями, предварительно сняв conflicting-запись, либо (б) у существующей `STARTED`-записи изменить `listeners[].paths` на `/api/v1/journal` (`PUT /apis/{id}`) и backend на `http://journal:8080`. После любого варианта критерий один: `/api/v1/journal/records` → **401**.

## Попытка правки маршрута (прогон 43784015816) — результат

Режим `APIM_FIX_ROUTES=1` нашёл `STARTED`-записи и сделал `PUT`:

```
journal: API a26f2441… name="Journal Microservice API" listener="/api/v1/journal/records/:id/when"
  PUT listener="/" → 200
partners: API 82cfdc75… name="Partners Microservice API" listener="/api/v1/partners/:id/unlink-client"
  PUT listener="/" → 200
```

**Важное открытие:** listener-путь «рабочей» записи — это **одна конкретная операция** (`/api/v1/journal/records/:id/when`), а не префикс. То есть `_import/swagger` создаёт API, у которого в listeners попал первый путь спеки, и остальные операции маршрута не получают.

**Эффекта на клиентские пути это не дало** (замер сразу после прогона):

| путь | ответ |
|---|---|
`/api/v1/journal/records` | **404** |
`/api/v1/journal/records/{id}/when` | 404 |
`/api/v1/partners` | 404 |
`/api/v1/partners/{id}/unlink-client` | 404 |
`/journalmicroserviceapi/api/v1/journal/records` | **500** (`X-Gravitee-*`) |
`/api/v1/catalog` | 401 |

Значит в APIM одновременно живут **несколько** определений на один сервис (в дампе — пары `STARTED`/`STOPPED`, плюс «призраки»), и трафик попадает в то, что развёрнуто на `/<title>/…`. Пока эти записи не сведены к одной, правка listener у одной из них ничего не меняет.

**Вывод (для @DO):** нужна чистка APIM до состояния «по одному API на сервис» с проверкой `state=STARTED` после каждого шага, затем один импорт и проба. Без доступа к management-API/Mongo изнутри это не сделать: `DELETE` по части id даёт `404 api.notFound`, а список содержит и «призраков», и дубли.
