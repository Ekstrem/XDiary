# DO-048: P0 — rootless-portmap: gateway пересоздаётся каждые ~90 с, фронт мигает

- **Статус:** В работе
- **В работе с:** 2026-11-08
- **Приоритет:** **P0** (прод нестабилен: `heal-network.sh` пересоздаёт gateway десятки раз в час)
- **Источник:** @DO 2026-11-08 05:40 — в `heal.log` пересоздание **каждые ~90 секунд**; остановка `heal-network.timer` стабилизировала gateway, но убила portmap (8080 → `refuse`), поэтому таймер вернули
- **Зависимости:** нет
- **Проверяет:** @TL (TechLead)

## Проблема
`heal-network.sh` лечит **симптом**: когда `/health` не отвечает, контейнер gateway пересоздаётся. Причина — **portmap в rootless-podman** отваливается регулярно. Итог: heal маскирует дефект, а прод мигает (пользователь видит периодические отказы/перезагрузки фронта).

## Задача (зона @DO)
1. Подтвердить причину: в логах podman/netavark найти ошибку portmap (`pasta`/`slirp4netns`/`rootlessport`).
2. Выбрать и применить один из путей: **rootful-podman** для gateway, либо `pasta` с корректной конфигурацией, либо systemd-юнит с `--network=host` для порта 8080 и внутренней сетью для сервисов.
3. После правки: **24 часа без пересозданий** и `heal.log` пуст по gateway; `curl /health` и фронт — стабильны.

## Критерии приёмки
- [ ] `heal.log` не содержит пересозданий gateway за сутки.
- [ ] Порт 8080 отвечает непрерывно (проверка раз в минуту, 0 отказов).
- [ ] `heal-network.sh` остаётся как аварийный инструмент, но **не срабатывает** в норме.

## Замер и сужение причины (@DO 2026-11-08 12:40)

**Что измерено:**
- **Быстрый замер с dev-VPS** (12 проб по 5 с на `https://xdiary-vps1.taile0b6ee.ts.net/health`): **12/12 OK, 0 отказов** — снаружи через Funnel API в этот момент отвечал.
- **Полный 10-минутный замер** запущен на dev-VPS в фоне (`/tmp/measure.sh` → `/tmp/health-10m.log`, 60 проб по 10 с), результат будет в этом файле; SSH-сессия на него больше не влияет.
- **`heal.log` на проде:** пересоздание gateway каждые **~60–90 с** (`10:25:50 gateway healed`, `10:27:20 gateway /health failed, recreating`, `10:27:30 gateway healed`). То есть **локальный** `curl 127.0.0.1:8080/health` падает почти сразу после пересоздания, а внешний путь при этом отвечает.

**Что это значит:** сервис живёт, а **публикация порта (rootlessport) деградирует в пределах минуты**. `heal` лечит симптом пересозданием контейнера, из-за чего каждые ~90 с есть окно недоступности — именно в него попал `fetch` владельца («Недоступен API (шлюз)»).

**Ограничение окружения:** `podman` на VPS-1 — **3.4.4**, поэтому `pasta` (появилась в podman 4.x) недоступна; `netavark`/`rootlessport` — старые. Значит варианты: (a) rootful-podman для gateway, (b) обновление podman до 4.x и перевод на `pasta`, (c) системный юнит с порт-хендлером. Все три меняют модель запуска → нужно решение координатора, а не тихая правка.

**Funnel на VPS-1:** включён, `https://xdiary-vps1.taile0b6ee.ts.net` → `http://127.0.0.1:8080`, то есть публичный адрес есть и **Tailscale на телефоне не обязателен**.

## Почему (a) rootful-gateway не решает задачу (@DO 2026-11-08 14:00)

Проверено на VPS-1, факты:

| Проверка | Результат |
|---|---|
| `sudo -n true` | OK (NOPASSWD есть) |
| `sudo podman ps` | **0 контейнеров** — rootful хранилище пустое |
| `sudo podman network ls` | только `podman`; сети `xdiary` **нет** |
| `podman network ls` (rootless) | `podman`, **`xdiary`**; gateway = `10.89.9.30` |
| версии | rootless 3.4.4, rootful 3.4.4, apt-кандидат тоже **3.4.4** (в Ubuntu 22.04 podman 4.x нет) |

**Вывод:** rootful-контейнер живёт в **другой сети** и не видит `10.89.9.0/24`, где находятся 12 бэкендов. Rootful-gateway без переноса всей сети просто не смог бы достучаться до сервисов — то есть «узкая правка одного сервиса» на деле требует **переноса всего стека в rootful**.

То же ограничение у варианта `--network=host` для rootless-контейнера: он выходит в netns хоста, а rootless-сеть бэкендов — отдельный netns, маршрута нет.

**Жизнеспособные пути:**
- **(b) podman 4.x + `pasta`** (rootless сохраняется, сеть одна, порт-форвардинг стабилен). Цена: внешний репозиторий (Ubuntu 22.04 даёт 3.4.4), обновление затрагивает рантайм всех контейнеров → нужен согласованный window и проверка после.
- **(a') полный перенос стека в rootful** — тот же результат, но больше работы и полный простой.
- **(c) системный юнит с порт-хендлером** — не отменяет деградацию rootlessport, только маскирует.

Рекомендую **(b)**; для неё нужен твой go на окно (все контейнеры будут пересозданы один раз) — это единственный путь, который убирает причину, а не симптом.
