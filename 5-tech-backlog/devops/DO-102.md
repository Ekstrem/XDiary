# DO-102: `images.lock` не проверяется против registry — деплой по lock невоспроизводим

- **Статус:** В работе
- **В работе с:** 2026-11-06
- **Приоритет:** **P1** (деплой «по lock» фактически не воспроизводим; гейт этого не видит)
- **Источник:** проверка @DO `2026-11-06 02:4x` при выкатке на dev (после закрытия `BE-086`)
- **Проверяет:** @TL

## Факт

`7-deploy/images.lock` называет по одному тегу на сервис — `single-<sha>` (13 сервисов).
Проверил на dev (`podman image exists` + `podman pull`):

| сервис | тег в lock | в образнице |
|---|---|---|
| journal | `single-1dde681` | **нет** (pull неуспешен) |
| partners | `single-2e0ad80` | **нет** |
| catalog / somatic-series / daily-metrics / garmin-gateway / apple-health-gateway / privacy | `single-6647cdc` | нет |
| analytics | `single-cf469e0` | нет |
| portability | `single-f4b2b19` | нет |
| client | `single-2339460` | нет |
| api-gateway | `single-5075ab5` | нет |
| front | `single-26b1258` | нет |

То есть **ни одного** тега из lock локально нет, а `deploy.sh` при этом отрабатывает `rc=0` и
поднимает сервисы. Значит деплой берёт образ не из lock (а из `single`/`latest`), и «выкатить ровно
то, что записано в lock» **невозможно** — lock в этой части декоративен.

Что при этом реально запущено (rev из метки образа) — **рассогласовано**:

```
partners 629cfbc8   journal 5e1c2f8a   analytics 042d24c1   api-gateway 5075ab50
client b9e18f8e     catalog/somatic-series/daily-metrics/garmin-gateway/
                    apple-health-gateway/privacy/portability 62cdcbd1
```

## Почему гейт молчит

`tools/gen_images_lock.py --check` сверяет **git ↔ lock** (`6-msa/BC-*` → sha), а не lock ↔ registry.
Поэтому `rc=0` («lock соответствует git») ничего не говорит о том, что образ с таким тегом
**опубликован**. Плюс `ci-partners`/`ci-journal` публикуют тег только когда их `docker`-джоб не
`skipped`, а `skipped` он при красных тестах (`BE-086`).

## Что сделать

1. добавить в `gen_images_lock.py` режим `--verify-registry` (или отдельный `check_lock_published.py`):
   для каждого сервиса из lock проверить, что `ghcr.io/ekstrem/xdiary-<svc>:single-<sha>` **существует**
   (pull/HEAD манифеста), и падать с `rc=1` и списком отсутствующих;
2. `rc=2`, если registry недоступен (не путать «нет образа» с «не смог проверить»);
3. выяснить, откуда `deploy.sh` реально берёт образ (прочитать скрипт, а не догадываться), и либо
   привести его к lock, либо честно переписать комментарий/док, что lock — это «что собрано», а не
   «что выкатывается»;
4. прогнать новый режим на **дефекте** (тег отсутствует → `rc=1`) и на **норме** (`rc=0`), по §5.4.

## Критерии приёмки

- `python tools/gen_images_lock.py --verify-registry` даёт `rc=0` на текущем lock **после** публикации
  недостающих тегов (или lock пересобран на опубликованные);
- на искусственно испорченном lock (несуществующий sha) — `rc=1` с именем сервиса и тега;
- в `## Результат` — номера прогонов/вывод команд.

## Уточнение причины (проверено по коду и по серверу, 2026-11-06 03:0x)

**1. `deploy.sh` в репозитории и `deploy.sh` на сервере — разные файлы.**

| что | факт |
|---|---|
| снимок в `7-deploy/deploy.sh` | `set -euo pipefail`; `LOCK_FILE=…/images.lock`; `TAG="$(awk '!/^#/ && NF>=2 {print $2; exit}')"` — **один** тег на все сервисы, берётся из первой строки lock |
| фактический `/opt/xdiary/7-deploy/deploy.sh` на dev | дата **Nov 2 12:59**, md5 `b66c6e3d…`; строка 3: **`TAG="${1:-single}"`**; `LOCK_FILE` в файле **нет** — lock не читается вообще |

То есть на dev серверный скрипт деплоит тег `single` (или переданный аргументом), а не то, что
записано в lock. Шаг CI «Tag из images.lock» делает `podman tag` перед вызовом — вот откуда берётся
иллюзия «деплой по lock». Ручной запуск `deploy.sh` (как в ранбуках и как делал я) lock **не учитывает**.

**2. Теги из lock действительно не опубликованы** — новый режим показывает это списком:

```
check_images_lock --verify-registry: сервисов 13 | опубликовано 1 | отсутствует 7 | не проверено 5
  ОТСУТСТВУЕТ: daily-metrics:single-6647cdc   … garmin-gateway, apple-health-gateway,
  ОТСУТСТВУЕТ: analytics:single-cf469e0        privacy, portability:single-f4b2b19,
  ОТСУТСТВУЕТ: client:single-2339460           front → 403 (не проверено)
```

Причина отсутствия — публикация условная: `docker`-джоб в `ci-partners`/`ci-journal`/… становится
`skipped` при красных тестах (так было весь вечер из-за `BE-086`), а lock генерируется из git и об этом
не знает.

## Результат (частично, инструмент готов)

**Сделано:** в `tools/gen_images_lock.py` добавлен режим `--verify-registry` (+ `--registry`, `--owner`):

- проверка через **HEAD манифеста** в registry анонимным pull-токеном (образы публичные);
- `rc=0` — все теги опубликованы; `rc=1` — есть отсутствующие (печатает `ОТСУТСТВУЕТ: service:tag`);
- `rc=2` — проверить не смогли (сеть/403) — «не измерено» не маскируется под «нет образа»;
- `--selftest` расширен до **7/7**: норма → `rc=0`, отсутствующий тег → `rc=1`, registry недоступен → `rc=2`.

**Доказано на обеих сторонах (§5.4):** на дефекте — `--verify-registry` даёт `rc=1` и перечисляет
7 отсутствующих тегов; на норме — `--selftest` `7/7 rc=0`, `--check` `rc=0`.

**Намеренно НЕ подключено в CI:** если добавить шаг сейчас, `ci-guards` станет красным на каждом пуше,
пока не починена публикация тегов. По §5.4 красный гейт не обходится — поэтому подключение идёт
вместе с починкой (пункт 3).

## Осталось

1. решить, что является источником правды: либо серверный `deploy.sh` приводится к чтению lock
   (и снимок в репозитории перестаёт расходиться с сервером), либо lock объявляется «что собрано»,
   а деплой официально идёт по `single` — и тогда `ADR-027`/`DO-066` нужно поправить, а не код;
2. пересобрать/опубликовать отсутствующие теги (`docker`-джоб не должен `skipped` при красных тестах —
   либо публикация отдельным workflow, не зависящим от тестов);
3. после этого добавить `--verify-registry` в `ci-guards` (с `--selftest` перед нормой) — по §5.4.

## Причина блокировки `deploy-prod` (проверено 2026-11-06 03:3x, read-only)

**Факт 1 — где какой `deploy.sh`:**

| контур | файл | дата | md5 | как выбирает тег |
|---|---|---|---|---|
| dev | `/home/ubuntu/XDiary/7-deploy/deploy.sh` | 2026-11-05 04:02 | `186b455b` | читает lock, `TAG` из **первой** строки |
| dev | `/opt/xdiary/7-deploy/deploy.sh` | 2026-11-02 12:59 | `b66c6e3d` | **`TAG="${1:-single}"`**, lock не читает |
| prod | `/home/deploy/XDiary/7-deploy/deploy.sh` | 2026-11-04 11:04 | `186b455b` | читает lock, `TAG` из **первой** строки |
| prod | `/opt/xdiary/7-deploy/deploy.sh` | 2026-11-04 11:04 | `186b455b` | то же |

То есть на **dev два разных скрипта** (в `/opt` — старый, от 2 ноября), а на **проде оба одинаковые** и читают lock.
Значит «какой скрипт исполнится» зависит от того, что вызывают: CI вызывает `/opt/xdiary/7-deploy/deploy.sh`
(старый на dev), а руками обычно `~/XDiary/7-deploy/deploy.sh` (новый).

**Факт 2 — `deploy.sh` берёт ОДИН тег на все 13 сервисов:**

```bash
TAG="$(awk '!/^#/ && NF>=2 {print $2; exit}' "$LOCK_FILE")"   # первая строка lock
... podman run … ghcr.io/ekstrem/xdiary-journal:$TAG
... podman run … ghcr.io/ekstrem/xdiary-partners:$TAG   # тот же $TAG
```

Первая строка lock — `journal single-1dde681`, то есть **все** сервисы будут тянуться как
`single-1dde681`. Режим `--verify-registry` показывает: **опубликован 1 тег из 13**, остальные
отсутствуют. При `set -euo pipefail` первый неудачный `podman run` **прерывает скрипт** — значит
`deploy-prod` с текущим lock **не может пройти**, даже если `smoke` станет зелёным.

**Факт 3 — что реально запущено (и насколько расходятся контуры):**

| сервис | dev (создан 23:55) | prod (создан) |

То есть прод — это **смесь шести разных сборок**, а не «одна версия».

## Минимальная правка (предложение, не применял)

Заменить в `deploy.sh` глобальный `TAG` на выбор по сервису из lock:

```bash
tag_of() { awk -v s="$1" '!/^#/ && NF>=2 && $1==s {print $2; exit}' "$LOCK_FILE"; }
# в каждом запуске: ghcr.io/ekstrem/xdiary-journal:$(tag_of journal)
```

Тогда lock перестаёт быть «первая строка решает всё» и становится тем, что написано в его шапке.
Проверяемо: `--verify-registry` даёт список отсутствующих, и деплой падает **на конкретном сервисе**,
а не «на всём подряд».
