# DO-129 — P0 ИНЦИДЕНТ: прод деградировал после неудачного деплоя (нет сети `xdiary`, контейнеры сняты)

- **Статус:** ToDo
- **Приоритет:** P0 (прод отвечает `500` на запись, часть сервисов отсутствует)
- **Источник:** прогон `deploy` `43461987716` (sha `3cddc1e0`), job `deploy-prod`; диагностика из патча №26 (`podman logs`/`exit` при провале) — она и назвала причину
- **Зависимости:** `DO-125` (release), `DO-128`
- **Проверяет:** @TL
- **Исполняет:** @DO (нужен доступ к VPS-1)

## Факт (дословно из лога)

```
run| Error: <sha256>: image not known
log| Error: no container with name or ID "xdiary-garmin-gateway" found: no such container
…
run| Error: unable to find network configuration for xdiary: network not found
log| Error: no container with name or ID "xdiary-api-gateway" found: no such container
recreate-service: ОШИБКА: xdiary-api-gateway не поднялся
```

**Две разные причины в одном прогоне:**
1. **сеть `xdiary` отсутствует** — `unable to find network configuration for xdiary: network not found`. Без неё не поднимется ни один сервис (все `--network xdiary --ip 10.89.9.x`).
2. **образы по digest не найдены локально** — `image not known` для перечисленных sha256: откат (и часть попыток) запускает `@sha256:…` (ADR-027/DO-113), но на VPS-1 этих образов нет — их надо `podman pull` по digest.

**Состояние прода на момент замера (внешние пробы @TL):**

```
/health              → 200   (Caddy жив)
/api/v1/catalog      → 401   (APIM жив)
/api/v1/clients/me   → 401   (APIM жив)
POST /api/v1/clients → 500   (сервис clients мёртв)
```

То есть прод **деградирован**: вход отвечает, но запись — `500`.

## Что нужно сделать (по порядку)

1. Восстановить сеть: `sudo podman network create xdiary` (подсеть как в `deploy.sh`: адреса `10.89.9.20…31`).
2. Подтянуть образы по digest: `sudo podman pull` для каждого `@sha256:` из `7-deploy/images.lock` (или тегом `single-c0552f2`).
3. Поднять сервисы `bash /opt/xdiary/7-deploy/deploy.sh single` (он создаёт контейнеры с `--network xdiary`, `--env-file secrets/.env`) — либо `recreate-service.sh` по одному.
4. Проверить: `GET /clients` 401, `POST /clients {}` 400, затем полный `deploy` — `deploy-prod` должен пройти.

## Почему это случилось (не «само»)

`recreate-service.sh` удаляет контейнер (`podman rm -f`) **до** успешного запуска нового и при провале пытается откатиться. Если провал вызван отсутствием сети/образа, откат тоже падает, и сервис остаётся снятым. Патч №26 добавил диагностику (она и сработала); **следующим шагом нужен безопасный порядок**: сначала `podman pull` + проверка сети, только потом `rm -f`.

## Критерии приёмки

- [ ] `POST /api/v1/clients` на проде отвечает `200`/`400` (не `500`);
- [ ] `podman network inspect xdiary` → сеть есть, адреса `10.89.9.20…31` заняты сервисами;
- [ ] `deploy` на `main` — `deploy-prod` зелёный;
- [ ] в `recreate-service.sh` порядок «pull → проверка сети → rm -f → run», а провал не оставляет сервис снятым.
