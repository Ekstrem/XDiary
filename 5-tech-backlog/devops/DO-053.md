## Факты по API (@DO 2026-11-08 12:20)

Три прогона на проде (синтетический номер, код не логируется):

| Прогон | Результат |
|---|---|
| `POST /api/v1/clients` **новый** номер | **HTTP 200**, `otpCode` в теле (код выдаётся) |
| повторный `POST` **тот же** номер | **HTTP 400**, тело `phone_taken: Телефон уже зарегистрирован` — **новый код не выпускается**, старый не аннулируется |
| `POST /api/v1/clients/{id}/verify` с **верным** кодом | **HTTP 200**, `result: "Verified"`, выдан `accessToken` |
| `POST /api/v1/clients/verify` (без id) | **HTTP 405** — маршрут требует id |

**Вывод:** серверная часть рабочая — регистрация выдаёт код, `verify` с верным кодом выдаёт токен. Поломка ровно в одном месте: **для существующего телефона нельзя получить новый код** (`phone_taken`), потому что `RegisterClientHandler` считает «телефон есть» ошибкой, а отдельного «выслать код повторно» нет. Если владелец нажимал «получить код» повторно, он получал 400, а вводить мог **старый** код — а он либо уже использован, либо клиент остался `Verified=false`.

Проверка состояния: в таблице `clients` сейчас **только одна запись `Verified=true`**, и это мой синтетический прогон; остальные — `Verified=false`, `OtpCode` заполнен. То есть владелец получил код, но подтверждение не завершилось.

**Что это значит для DO-053:** нужен серверный сценарий «существующий клиент → выслать новый код» (BE-047), после чего `verify` работает уже сегодня — я это проверил.

@TE поймал точнее меня, проверяю фактом:

| Факт | Значение |

| вывод | **образ старше фикса на 13 минут** → на проде `GET /partners` фильтрует, а `POST` по-прежнему оставляет `ClientId = NULL` |

**Следствие для владельца:** если он сейчас создаст «Это я», запись ляжет **без привязки** — и после фильтра по `sub` список снова окажется пустым. Это не регресс BE-048, а **недоехавший второй коммит**.

**Почему не доехал — три звена:**
1. На `b1878a1d` **не было ни одного CI-прогона**: это промежуточный коммит в пуше, GitHub запускает прогон только на head.
2. Прогоны, в которые он входит (`#99 6da6fe69`, `#100 781cff0e`, `#101 72ba46bb`), падают на **компиляции тестов**: `CS7036` — `9-tests/Partners.Catalog/PartnersCatalog.IntegrationTests/PartnerTests.cs(17,61)` и `(32,61)`: «no argument given that corresponds to the required parameter **`clientId`**». То есть BE-048 поменял сигнатуру, а тесты не обновлены → **образ не собирается**.
3. `deploy-prod` в `#817/#818` — `skipped` из-за `smoke-front`.

**Значит порядок такой:** починить два вызова в `PartnerTests.cs` (@TE/@BE) → `ci-backend` зелёный → образ с `b1878a1d` собирается → `smoke-front` уже зелёный после TE-047 (`4bcb24b9`, смержен `94a022a4`) → `deploy-prod` выполняется → прод получает фикс. После этого я могу **связать уже созданную запись** владельца (`UPDATE partners SET "ClientId"=… WHERE "Name"='Это я'`), чтобы ему не создавать заново.

**Проверено также, что «разных хранилищ» нет:** `ConnectionStrings__CommandDb` и `ReadDb` у `partners` совпадают (одинаковый `sha256[:8]`, одна БД `partners`); в схеме только таблица `partners` + `__EFMigrationsHistory`.
