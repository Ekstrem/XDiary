# DO-034: `heal-network.sh` не знает про `clients` — починка DO-033 откатится на следующем heal

- **Статус:** На проверке
- **Приоритет:** P1 (регрессия: 502 на `/api/v1/clients` вернётся сам, без участия людей)
- **Источник:** проверка TL 2026-11-06 после DO-033 (в `heal-network.sh` список `--add-host` из 11 сервисов без `clients`)
- **Зависимости:** DO-033 (сервис `clients` добавлен в `podman-compose.yml`), BE-031/BE-037
- **Проверяет:** @TL (TechLead) — §2.1 п.6, автор @DO

## Проблема
DO-033 восстановил маршрут `/api/v1/clients` на VPS-1: шлюз пересоздан по актуальному (серверному) `deploy.sh`, у него `ExtraHosts = clients:10.89.9.31`, `GET` = 200, `POST` = 400 «Phone is required».

Но в репозитории есть **`7-deploy/heal-network.sh`**, который вызывается после каждого цикла обновления и **пересоздаёт** шлюз при неудачном `/health`:

```
podman run -d --name xdiary-api-gateway --network xdiary --ip 10.89.9.30 ...
  --add-host journal:10.89.9.20 --add-host partners:10.89.9.21 --add-host catalog:10.89.9.22
  --add-host somatic-series:10.89.9.23 --add-host daily-metrics:10.89.9.24 --add-host garmin-gateway:10.89.9.25
  --add-host apple-health-gateway:10.89.9.26 --add-host analytics:10.89.9.27 --add-host privacy:10.89.9.28
  --add-host portability:10.89.9.29 --label io.containers.autoupdate=registry
```

**`clients` в списке нет.** Значит первый же heal (или пересоздание шлюза) соберёт шлюз без
`clients` → `POST /api/v1/clients` снова 502 → онбординг и OTP снова «не работают», и никто
не поймёт почему (сервис-то жив).

Тот же дрейф в провижининге: `provision-vps1.sh` и `provision-vps2.sh` про `clients` не знают.

## Задача
1. Добавить `--add-host clients:10.89.9.31` в `heal-network.sh` (и в провижининг-скрипты, если там есть аналогичный список).
2. **Убрать класс ошибки:** не держать список хостов руками в двух местах. Варианты:
   - генерировать `--add-host` из `podman-compose.yml` (источник правды уже там, 12 сервисов с `networks: ipv4_address`); или
   - вынести список в один файл/переменную и использовать и в `heal-network.sh`, и в `deploy.sh`.
3. **Серверный `deploy.sh`/`update.sh` — в репозиторий** (сейчас он живёт только на VPS, и именно из-за этого шлюз полдня ходил без `clients`). Если он генерируется — закоммитить генератор.
4. Проверка: после heal `curl` из шлюза до `clients:8080/health` = 200; и в `podman inspect xdiary-api-gateway` в `ExtraHosts` есть `clients`.

## Критерии приёмки
- [x] `heal-network.sh` пересоздаёт шлюз **со всеми 12** бэкендами, включая `clients`.
- [ ] Список хостов не дублируется руками: он берётся из compose (или единого файла).
- [ ] `deploy.sh`/генератор закоммичен в `7-deploy/`.
- [x] После прогона heal `GET`/`POST /api/v1/clients` не дают 502.

## Результат
- **Регрессия закрыта:** `--add-host clients:10.89.9.31` добавлен в `heal-network.sh` в репозитории **и** в живые копии на VPS-1 (`/home/deploy/heal-network.sh`, `/home/deploy/XDiary/7-deploy/heal-network.sh`) и VPS-2 (`/home/ubuntu/XDiary/7-deploy/heal-network.sh`). Первый heal больше не откатит DO-033.
- ⚠️ **Осталось (структурное):** список `--add-host` всё ещё руками в 2 местах (heal + серверный `deploy.sh`); генерация из `podman-compose.yml` — отдельным шагом.
- ⚠️ **Серверный `deploy.sh` в репозиторий не положен:** в нём **11 захардкоженных паролей БД** (в `.env` их нет), коммит = утечка. Нужно сначала вынести пароли в `secrets/.env` (`DB_PASS_*`) и заменить их на `${...}` — это следующий шаг.

## Подтверждено на практике (2026-11-02 17:40, @DO)
Гипотеза «дефект деплоя, не кода» подтвердилась полностью:
- на **VPS-2 (dev)** образ `ghcr.io/ekstrem/xdiary-client:single` был `created 2026-11-01 20:25` (~18 ч), `grep -ac AddJwtBearer /app/Client.Api.dll` = **0**, `UseAuthentication` = **0** → JWT-middleware BE-038 в образе **не было**;
- отсюда `401` на `/clients/me` (`sub` пуст) и **16/18 красных UI-спеков** — то есть `front-e2e` падал из-за устаревшего стенда, а не из-за фронта/бэка в коде;
- **корень:** в серверном `update.sh` список `SVCS` содержал **11 сервисов без `clients`** — образ клиента не тянулся никогда, а `deploy.sh` пересоздавал контейнер из локального (старого) образа;
- **починено** @DO: `update.sh` → `SVCS` + `clients`; `podman pull`; `bash deploy.sh single` (12 контейнеров), новый образ `created 2026-11-02 14:31`, `AddJwtBearer` = 1.

**Вывод для задачи:** ручное добавление `clients` в список — это лечение симптома. Требование «списки сервисов генерируются из compose» (п.2 задачи) становится **обязательным**: иначе третий сервис однажды снова выпадет, и мы опять будем искать «баг» в коде.

## Единый источник (07.11, по просьбе TL — «три места → один источник»)
- **	ools/gen-hosts.py** — единственное место, где живут IP-адреса (SERVICE_IPS) и откуда берётся список сервисов (podman-compose.yml → services:). Команды: --svcs, --add-host, --check.
- **7-deploy/update.sh** — в репозиторий, список сервисов больше **не хардкодится**: SVCS=""; если генератор недоступен — **выходит с ошибкой** (лучше не обновить, чем обновить неполный набор).
- **7-deploy/heal-network.sh** — --add-host берётся из gen-hosts.py --add-host; если генератор недоступен — шлюз **не пересоздаётся** (иначе потерял бы сервисы).
- gen-hosts.py --check — 12 сервисов, у всех есть IP (проверено).
- Осталось: deploy.sh пока живёт только на сервере (в нём 11 захардкоженных паролей БД — коммит = утечка); его --add-host тоже надо перевести на gen-hosts.py после выноса паролей в .env.
