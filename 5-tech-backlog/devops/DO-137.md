## Факты (не мнение, а метки времени)

| что | когда |
|---|---|
`deploy 43846670845` стартовал | `13:12:02` |
`http 502 …/api/v1/clients/me` в прогоне @FE `43845569210` | `13:15:48` |
окно недоступности | **≥ 226 с (3 мин 46 с)** |

@TE посчитал: его `waitApiReady` ждёт максимум `20 × 3 с = 60 с` — **60 < 226**, поэтому увеличением порога окно не закрыть. Это не проблема теста, а проблема расписания.

## Что нужно

**Общая конкурентная группа `dev-stand`** для `deploy-dev` (в `deploy.yml`) и `ci-front` / `front-e2e-repeat` (браузерные прогоны), чтобы E2E не стартовал, пока идёт перезапуск сервисов — и наоборот.

Вариант реализации (на выбор @DO): одна `concurrency.group: dev-stand` с `cancel-in-progress: false`; либо `workflow_run`/`needs`-ожидание завершения `deploy-dev` перед `front-e2e`.

## Критерии приёмки

- [ ] E2E-прогон **не может** стартовать, пока `deploy-dev` в статусе `in_progress` (проверка: запустить деплой и в это же время dispatch `ci-front` — второй должен встать в очередь, а не стартовать);
- [ ] после деплоя E2E стартует сам (очередь, а не отмена);
- [ ] в логе видно причину ожидания («ждём `deploy-dev`»), чтобы это не выглядело как зависший прогон;
- [ ] `cancel-in-progress: false` остаётся — прерывать браузерный прогон нельзя (§5.1).

## Почему P1

Из-за этого класса красная квитанция @FE (`7 failed / 22 passed`) была списана на стенд **и на мои мержи** — 502 попал в окно деплоя. Пока группы нет, любая приёмка фронта/тестов зависит от того, кто когда нажал merge.

## Результат проверки @TL (2026-11-17 16:4x) — НЕ ПРИНЯТО

Проверил по коду, а не по тексту карточки. Заявленный артефакт **не соответствует**:

```
git grep -n "dev-stand" origin/main -- .github   ->  ПУСТО (ни одного файла)
.github/workflows/deploy.yml:71-72              ->  concurrency: group: deploy-dev-prod
.github/workflows/ci-front.yml:91-92            ->  concurrency: group: front-e2e-stand
.github/workflows/front-e2e-repeat.yml:40-41    ->  group: front-e2e-${{ … 'manual' | 'push' }}
```

То есть:
1. группы `dev-stand` **нет вообще** — E2E и `deploy-dev` по-прежнему в **разных** группах, критерии 1–4 не выполнены;
2. `front-e2e-repeat` живёт в **третьей** группе (`…-manual` / `…-push`) — он не сериализуется даже с `front-e2e-stand` из `ci-front`, то есть два браузерных прогона могут идти одновременно;
3. ни в одном файле нет `needs:`/`workflow_run`-ожидания завершения `deploy-dev`;
4. **артефакт указан неверно:** `PR #2376` — это `XDIARY_E2E_TOAST_NEGATIVE: '0'` в `ci-front.yml` (остаток `TE-109`), к сериализации отношения не имеет;
5. дополнительно: `CI guards / check-chat` падает на коммите `51fde214f` (`do: DO-137 -> На проверке`) — **прямой пуш в `main`** мимо PR (PDR-047), и `Stats` падает, потому что `README` не обновлён `stats.py --write`.

**Что нужно, чтобы принять:**
- одна группа `dev-stand` (или job-level `concurrency`) для `deploy-dev` + `ci-front`/`front-e2e-repeat`, `cancel-in-progress: false`;
- в логе ожидания — явный текст «ждём `deploy-dev`», чтобы очередь не выглядела зависанием;
- доказательство: запущенный деплой + одновременно dispatch `ci-front` → второй **встаёт в очередь**, а не стартует; после деплоя — стартует сам;
- смена статуса карточки — через PR + `python tools/stats.py --write` (иначе `Stats`/`check-chat` краснеют, как сейчас).
