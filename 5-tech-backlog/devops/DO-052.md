## Задача (зона @DO)
1. **Хеш по каждому образу отдельно** вместо агрегатного (`update.sh:48`): для каждого сервиса — `image@digest`, сравнение с предыдущим состоянием, список «что изменилось».
2. **Пересоздавать только изменённые** контейнеры (compose `up -d <service>`), остальные не трогать; порядок — зависимости (БД → сервисы → шлюз → фронт).
3. **Пост-проверка:** для каждого пересозданного — `verify_running_images`, для всего стека — `/health`; при провале любого шага — **exit 1** и понятный откат.
4. **Миграции:** если изменился образ сервиса с миграциями — прогон миграций **до** пересоздания зависимых; частичный деплой не должен оставить схему и код в разных версиях.
5. **Откат по компоненту:** команда «вернуть предыдущий digest для N сервисов», проверенная один раз на стенде.

## Критерии приёмки
- [ ] Изменение **одного** сервиса пересоздаёт **только его** (подтверждено логом: список «изменено: 1 из 12»).
- [ ] Изменение в фронте не перезапускает бэкенд (негативный контроль: фронт-only коммит → бэкенд не тронут).
- [ ] Если поднялся не тот образ — `verify_running_images` валит деплой (уже есть, проверить в новой схеме).
- [ ] Откат одного сервиса на предыдущий digest выполнен на стенде и описан в `7-deploy/runbooks/`.

## Реализовано (@DO 2026-11-08 11:50)

**(1) По-образный хеш вместо агрегатного.** `update.sh` держит карту `service -> imageId` в `~/.xdiary-image-ids` и сравнивает **попарно**. Агрегатный sha256 (он и раньше был, но по всему набору) больше не решает, что деплоить.

**(2) Пересоздаются только изменённые.** Новый `7-deploy/recreate-service.sh <service>` собирает строку запуска из `deploy.sh`, валидирует её `bash -n`, и только затем удаляет/поднимает контейнер (3 попытки, при провале печатает готовую команду восстановления). `update.sh` проходит по порядку `сервисы → шлюз` и трогает **только** те, чей ID изменился.

**(3) Порядок:** EF-миграции выполняются при старте сервиса (они часть образа), поэтому порядок «сервисы → api-gateway» и есть «миграции → сервисы → шлюз»; фронт не в docker-наборе (GitHub Pages).

**(4) Пост-проверка:** `recreate-service` проверяет, что контейнер поднялся; `update.sh` в конце проверяет `/health` и при не-200 выходит с `exit 1`.

**(5) Откат по компоненту:** `update.sh --rollback <service> <image-id>` → `recreate-service <service> --image <image-id>` (подмена последнего аргумента строки запуска на конкретный ID). При провале деплоя `update.sh` сам откатывает все затронутые сервисы на предыдущие ID из сохранённого состояния.

**Негативные контроли (на проде, dry-run):**
- подменил ID одного образа (`privacy`) → `изменились: privacy` (только он, остальные 11 не тронуты);
- baseline без изменений → **`изменений нет: деплой не требуется`** — это и есть критерий «front-only коммит не перезапускает бэкенд»: изменения фронта не меняют ни один образ, значит пересозданий нет;
- baseline восстановлен: 12 строк, 13 контейнеров, `/health` 200.

**Ограничение, которое честно фиксирую:** полный прогон «изменился один образ → пересоздался ровно один контейнер» на живом проде ещё не выполнен (нужен реальный релиз); проверено dry-run'ом и `recreate-service --list`. Как только придёт следующий релиз — это и будет приёмочный прогон.
