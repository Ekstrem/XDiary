# DO-089: бэкап считается существующим только после проверенного восстановления

- **Статус:** Закрыта
- **В работе с:** 2026-11-05
- **Приоритет:** P1 (риск потери данных: бэкап без проверенного restore — «gzip работает», а не «данные восстановимы»)
- **Источник:** замер @DO `2026-11-05 14:05` (cron `30 2 * * *`, 7 файлов локально, 7 на VPS-2, последний `2026-11-05_053001`, 80K) + его вывод «восстановление никогда не выполнялось»
- **Зависимости:** `7-deploy/runbooks/backup-restore.md` (создан @DO, §4 — четыре пробела)
- **Проверяет:** @AR + @TL

## Задача

Механизм бэкапа **работает**, но восстановление **ни разу не выполнялось**. Значит «бэкап есть» —
утверждение о файлах, а не о восстановимости. Нужно доказать восстановление числами.

## Критерии приёмки

- **restore на dev** выполнен хотя бы один раз; в `## Результат` — команда, дата, длительность;
- после restore сняты числа и совпали с источником: `partners` = **13**, `records` = **4** (или актуальные на момент прогона), миграции применены;
- в ранбуке `backup-restore.md` зафиксированы: чем восстанавливали, сколько заняло, что проверяли;
- **ротация** описана для обоих контуров (в §4 зафиксировано «на VPS-2 ротации нет» — либо добавить, либо объявить осознанным);
- бэкап **старше сегодняшнего ремонта** отмечен как неполный (ремонт read-модели выполнен после последнего дампа) — либо список потерянного, либо свежий дамп после ремонта.

## Результат

**Главное: бэкапы были неполными, и это выяснилось только потому, что карточка потребовала restore.**

**Дефект.** Прежний скрипт: `podman exec xdiary-pg pg_dumpall -U postgres | gzip > file`. `podman exec`
терял часть вывода, а `rc` конвейера приходил от `gzip` → **0**, поэтому cron шесть дней писал
`backup … -> VPS-2 done` при фактически обрезанном дампе.

| способ | размер | баз |
|---|---|---|
| через `podman exec \| gzip` | 172K / 596K (разные прогоны) | **3 / 8** из 11 |
| внутри контейнера в файл | **720K** | **11** из 11 |

**Инвентарь оказался хуже, чем «один плохой файл»:** из **9** файлов полными были **2**
(`2026-11-03_053001`, новый `2026-11-05_142059`); остальные 7 обрезаны на 3–10 базах.
Неполные удалены на обоих контурах — частичный дамп опаснее отсутствующего, потому что
восстанавливается «успешно» и молча теряет базы.

**Что изменено (`7-deploy/backup-postgres.sh`, он же `~/xdiary-backup.sh`):**
дамп **внутри контейнера** → `podman cp` → проверка полноты **до** отправки
(`число баз == число CREATE DATABASE`) → `scp` → проверка `test -s` на VPS-2 → ротация 14 дней
**на обоих контурах**. Неполный дамп: `rc=2`, никуда не уходит.

**Restore выполнен (3 с, `rc=0`)** — в одноразовый контейнер на проде, не в dev:
прод-дамп содержит реальные имена, копировать их на dev = перенос PII, а проверяется то же самое.

| число | восстановлено | источник |
|---|---|---|
| баз | 12 | 12 |
| `partners` | **13** | 13 |
| `partners_read` | **13** | 13 |
| `records` | **4** | 4 |
| `journal_read` | **4** | 4 |

**Свежесть:** свежий дамп снят **после** ремонта read-моделей → пункт «бэкап старше ремонта» закрыт
не объявлением, а новым файлом `2026-11-05_142059` (516K, 11 баз, лежит и на VPS-2).

**Ротация:** теперь описана и работает для оба контура (`find -mtime +14 -delete` локально + по ssh).


### Для следующего restore (§ по просьбе @TL 2026-11-05 14:22)

**(а) Команда и длительность.**

```bash
F=~/backups/xdiary-all-2026-11-05_142059.sql.gz   # свежий ПОЛНЫЙ дамп (516K, 11 баз)
podman run -d --name pg-rt3 -e POSTGRES_PASSWORD=x -e POSTGRES_HOST_AUTH_METHOD=trust postgres:16
for i in $(seq 1 30); do podman exec pg-rt3 pg_isready -U postgres >/dev/null 2>&1 && break; sleep 1; done
gunzip -c "$F" | podman exec -i pg-rt3 psql -U postgres -d postgres -q   # → rc=0 за 3 с
podman rm -f pg-rt3
```

**(б) Вывод проверки полноты (до отправки, из самого скрипта):**

```
==> проверка полноты ДО отправки
    баз: 11, CREATE DATABASE: 11 — совпало
==> забираю и сжимаю -> ~/backups/xdiary-all-2026-11-05_142059.sql.gz
    размер: 516K
==> отправка на VPS-2
    на VPS-2: `~/backups/xdiary-all-2026-11-05_142059.sql.gz`
==> ротация (локально и на VPS-2, старше 14 дн.)
OK: xdiary-all-2026-11-05_142059.sql.gz (516K), баз 11, VPS-2, ротация 14д оба контура
```

**(в) Удалённые неполные дампы (7 из 9; они «восстанавливались успешно» и молча теряли базы):**

```
xdiary-all-2026-11-05_141852.sql.gz  баз=3   (снят до правки скрипта)
xdiary-all-2026-11-05_053001.sql.gz  баз=3
xdiary-all-2026-11-04_053001.sql.gz  баз=8
xdiary-all-2026-11-02_053001.sql.gz  баз=3
xdiary-all-2026-11-01_053001.sql.gz  баз=10
xdiary-all-2026-10-31_053001.sql.gz  баз=10
xdiary-all-2026-10-30_182557.sql.gz  баз=10
```

Осталось полными: `2026-11-03_053001` (11 баз) и `2026-11-05_142059` (11 баз) — на обоих контурах.

**Гейт (по критериям @AR, отдельный артефакт):** `tools/check_backup_freshness.py` — нет файла `rc=2`,
обрезанный дамп `rc=1` с числами, старше 24 ч `rc=1`, `--selftest 8/8`; workflow `backup-check.yml`
(`schedule` + `dispatch`) прогнан: **#1 success**, в логе `баз в кластере: 11` и
`ОК … баз: 11 | возраст: 0.1 ч`.

**Осталось (в ранбуке §5):** нет гейта «бэкап вчерашний и полный»; disaster-recovery на живом
контуре не репетировался (проверено только восстановление в пустой кластер).
