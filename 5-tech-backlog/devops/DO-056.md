# DO-056: APIM (Gravitee) как источник правды контрактов + drift-check — ADR-023 (решение B)

- **Статус:** В работе
- **Приоритет:** **P0 (владелец 2026-11-04: APIM — первый приоритет. Импорт реестра + drift-check; ждёт только покрытия реестра от BE-050)**
- **В работе с:** 2026-11-09
- **Источник:** ADR-023 пересмотрен **C → B** решением владельца (AR 2026-11-09 00:38: «владелец решил ADR-023 → B (полный APIM, Gravitee): OpenAPI-контракты импортируются в APIM, источник правды»); условие @LM 01:37 («repo → APIM»: спека в git, APIM — рантайм, иначе экспорт+drift-check)
- **Зависимости:** BE-050 (OpenAPI генерируется из кода и коммитится — **остаётся обязательным**, APIM потребляет эти спеки), DO-052 (path-based деплой), ADR-007 (YARP), ADR-013
- **Проверяет:** @TL (TechLead) — саморевью запрещено: автор @DO

## Задача (зона @DO, `.github/`, `7-deploy/`, `tools/`)

1. **Импорт вместо ручного авторинга:** OpenAPI-спеки из `openapi/*.json` (артефакт BE-050) импортируются в Gravitee **идемпотентно по тегу** (`single-<SHA>`), а не вручную в UI и не в `latest`.
2. **Drift-check (обязателен, это ядро решения):** ежедневная сверка «экспорт APIM ↔ git»; расхождение → **красный гейт/алерт**. Ручные правки в APIM запрещены, кроме аварийного хотфикса с обязательным обратным экспортом в git в тот же день.
3. **Локальная разработка без APIM:** профиль dev не требует APIM (сервисы поднимаются как сейчас) — иначе новый компонент остановит работу всех ролей.
4. **Breaking-change детектор** (перенос из прежней редакции): сравнение спеки с версией в `main` (`oasdiff`, версия пинована), нормализация формата, удаление поля/смена типа/новый обязательный параметр → failure с требованием `/v2`.
5. **Версия Gravitee пинована** и записана в задаче; **лицензия проверена** (LM назвал риск: лицензия Gravitee) и зафиксирована в ADR/ранбуке.
6. **Smoke через APIM:** отдельный прогон, который проверяет путь «клиент → APIM → сервис», а не только прямой порт.

## Критерии приёмки
- [ ] Спека из git импортируется в APIM по тегу; повторный импорт идемпотентен (не создаёт дублей).
- [ ] Ручная правка в APIM ловится drift-check в течение суток (негативный контроль: изменил в APIM → красный).
- [ ] Ломающее изменение спеки → failure с перечнем; аддитивное → success.
- [ ] `dev`-профиль поднимается **без** APIM (проверено прогоном).
- [ ] Версия Gravitee и решение по лицензии зафиксированы в ADR-023/ранбуке.
- [ ] Smoke «через APIM» зелёный и покрывает хотя бы один реальный маршрут (`/api/v1/clients`).

## Ресурсы и этапность (TL, решение 2026-11-09 05:40)

**Замер @DO 05:25 (VPS-1):** RAM 5904 МБ, свободно **4234 МБ**, 4 vCPU, диск 102 ГБ свободно; 13 контейнеров ≈ **990 МБ**. Gravitee CE + MongoDB + Elasticsearch ≈ **2.2–2.7 ГБ** → после внедрения остаётся **~1.5–2 ГБ**.

**Решение: два этапа, APIM вводим не сразу в трафик.**

1. **Этап 1 (сейчас, без риска доступности): APIM как control plane.** Gravitee CE поднимается **вне пути запросов**: импорт `openapi/*.json` (BE-050), жизненный цикл версий, портал, drift-check. Трафик идёт **Funnel → YARP → сервисы**, как сейчас. Это ровно то, что просил владелец («API помещать туда»), и при этом **падение APIM не влияет на продукт** — деградация по умолчанию, как и описал @DO.
2. **Этап 2 (после замера на dev): APIM в пути** — только если Caddy/edge умеет активные health-checks (`health_uri`, требует Caddy ≥ 2.5) и если замер RSS за 24 часа на dev показал запас **≥ 1 ГБ** на пике. **Обязательно:** Elasticsearch с ограниченным heap (`-Xms512m -Xmx512m`), иначе ES съест запас и уронит прод по памяти.
3. **Запрет:** поднимать ES/Mongo/Gravitee сразу на проде **без PoC на dev** и без суточного замера RSS. Причина — правило «< 500 МБ свободной RAM на пике → не вводим»: сейчас запас формально есть, но ES растёт с индексами, и оценка «2.2–2.7 ГБ» — это старт, а не пик.

**Негативный контроль (одинаков для этапов):** остановили APIM → `GET /api/v1/clients` отвечает **200** (на этапе 1 — через YARP, на этапе 2 — через переключение edge).

| Компонент | Состояние | RSS |
|---|---|---|

**Негативный контроль этапа 1 — ПРОЙДЕН:** при остановленном APIM `GET /api/v1/clients` через YARP = **200**, `/health` = 200; трафик не затронут. Свободно RAM ~3.8 ГБ.

**Найденные причины по ходу (обе — из сегодняшнего класса):**
1. **Конфликт портов**: `services.core.http.port` (node-management) совпадал с портом прокси `8082` → gateway падал с `Unable to start HTTP server`. Разведено: node-management `8072`/`8073`, прокси `8082`, management API `8083`.
2. **CNI-DNS не резолвит имена** в сети `xdiary-apim_apim`: `getent hosts xdiary-apim-mongo` → пусто, `nc: bad address` (та же болезнь, что днём в основной сети). Обход: `up.sh` поднимает mongo, берёт его IP из `podman inspect` и подставляет в `mongodb://<ip>:27017` — файл compose остаётся источником правды, IP подставляется при старте.

**Что осталось до критериев этапа 1:**
- **`management-api` не стартует** (exit 0, логи обрываются на bootstrap) — нужен полный лог и, вероятно, Elasticsearch или доп. память; без него нет импорта спек и drift-check.
- **`openapi/*.json` в репозитории НЕТ** (0 файлов), а **BE-050 «OpenAPI-реестр из сервисов» = `ToDo`** — то есть критерии «спека из git импортируется по тегу», «повторный импорт идемпотентен», «drift-check» **физически недостижимы** до BE-050. Swagger в сервисах есть (22 файла `AddSwaggerGen/UseSwagger`), так что спеки можно сгенерировать, но это BE-050, не этап 1 по APIM.
- `dev`-профиль без APIM — уже так (dev не содержит APIM).

## Этап 1 — состояние на 18:00 (точное, без «почти»)

**Работает (подтверждено):**
- `xdiary-apim-mongo` — Up, ~175 МБ.
- `xdiary-apim-gateway` — Up, ~482 МБ, прокси `127.0.0.1:18082` отвечает `404` (APIs нет).
- **`management-api` поднимается и доходит до инициализаторов** (dashboards, roles, themes) при **ручном** запуске: `podman run --network apim --memory=768m -e gravitee_management_mongodb_uri=… -e gravitee_analytics_type=none docker.io/graviteeio/apim-management-api:4.4` → статус **Up**, лог полный. Значит образ, сеть и Mongo-связность рабочие.
- **Негативный контроль пройден:** при остановленном APIM `GET /api/v1/clients` через YARP = **200**; трафик не затронут; свободно RAM ~3.8 ГБ.

**Не работает:** `management-api` **под compose** (`podman-compose up`) выходит сразу после старта, `18083/management/health` = `000`. Разница с рабочим ручным запуском остаётся в конфиге compose (env-набор и способ подключения сети) — это следующая точка, а не «необъяснимый сбой».

**Найденные и уже устранённые причины (все — реальные дефекты окружения):**
1. **Конфликт портов**: node-management API совпадал с прокси-портом `8082` → gateway падал `Unable to start HTTP server`. Разведено: `8072`/`8073`, прокси `8082`, management API `8083`.
2. **CNI-конфиг несовместим**: `podman network create` и `podman-compose` пишут `cniVersion: 1.0.0` с плагином `firewall`, а установленный плагин поддерживает только `0.4.0` → контейнеры создавались, но **не стартовали**. Рабочая сеть `xdiary` сделана на `0.4.0` без `firewall`. Исправлено: `~/.config/cni/net.d/apim.conflist` написан вручную по схеме `xdiary` (bridge `cni-podman10`, `10.89.10.0/24`, `portmap`, `tuning`, `dnsname`).
3. **CNI-DNS не резолвит имена** в этой сети (`getent hosts xdiary-apim-mongo` пусто) → `up.sh` подставляет IP mongo в URI.
4. **Память management**: на лимите 512 МБ RSS упирался в потолок (511/536) → поднято до **768 МБ** (ручной пробник на 768 МБ работает).

**Блокер критериев (не мой):** в репозитории **0 файлов `openapi/*.json`**, **BE-050 = ToDo** → «импорт по тегу», «идемпотентность», «drift-check» недостижимы до BE-050.

## Этап 1 — диагноз на 20:45: `podman-compose` не тот инструмент для этой сети

**Что доказано замерами (не догадками):**
1. **Контейнеры садятся в дефолтную сеть `podman`, а не в `apim`.** `podman inspect` → `сети mongo: podman`, `сети management: podman`. Top-level `networks: apim: external: true` в compose (podman-compose 1.6.0) **не применяется** — сервис-левел `networks: [apim]` игнорируется.
2. **IP mongo меняется при каждом `up`**, потому что compose пересоздаёт контейнер (мои же правки файла меняют хэш конфига). Замер: URI в compose `10.88.0.41`, фактический IP `10.88.0.44` → `MongoTimeoutException` → `Rest APIs stopped` → петля рестартов management.
3. **Mongo при этом живой:** `mongosh --eval 'db.runCommand({ping:1}).ok'` → `1`; связность `gateway → mongo:27017` по IP → **OK**.
4. **Ручной `podman run --network apim --memory=768m` с тем же URI доходил до инициализаторов** (dashboards, roles, themes) — то есть образ, Mongo и сеть рабочие; дело именно в том, как compose их соединяет.

**Вывод (решение, а не «ещё попробуем»):** для APIM этап 1 **уходим с `podman-compose` на явные `podman run`** в `up.sh` — ровно тот путь, который уже дал рабочий management. Причины: (а) полный контроль сети (`--network apim`), (б) IP не «переезжает», потому что mongo не пересоздаётся, (в) нет зависимости от того, как конкретная версия podman-compose трактует `external`.

**Остаток работы по этапу 1:** переписать `up.sh` на `podman run` (mongo + management + gateway), проверить `management/health` = 200, затем импорт/drift-check **после** появления `openapi/*.json` (BE-050 инкремент 1 делает @BE).
