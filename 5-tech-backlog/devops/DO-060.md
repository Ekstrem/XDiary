- **Статус:** Закрыта
- **Закрыта:** 2026-11-13 (по аудиту @TL 08:10)
- **В работе с:** 2026-11-10
- **Приоритет:** **P0** (владелец 2026-11-10: «15 секунд — неприемлемо; всё, что больше секунды для человека, слишком долго»)
- **Источник:** владелец 2026-11-10 (в чат @EX): «Нужен реестр API и скорость вызова через шлюзы и напрямую микросервисы. Всё что больше секунды для человека слишком долго»; факт @DO 2026-11-09 22:05 (B7): при остановленном апстриме шлюз отдаёт **504 через 15.01 c** (дважды), и только третья попытка — 502 за 3.08 c
- **Зависимости:** BE-050 (`openapi/index.json` — перечень операций для обхода), DO-056 (APIM: аналитика Gravitee — только этап 2, в тракте)
- **Проверяет:** @TL

## Проблема

1. **15 c до первой ошибки** — это таймаут YARP по умолчанию; пользователь 15 секунд смотрит в пустоту. Для интерактивных экранов это неприемлемо.
2. **Нет цифр**: мы не знаем p50/p95 ни «через шлюз», ни «напрямую в сервис», поэтому не можем ни поставить бюджет, ни доказать регресс.
3. **Gravitee даёт метрики отклика по API** (response time, latency, коды) — но **только для трафика, который через него идёт**. На этапе 1 (control plane вне трафика) его аналитика покажет **ноль** — значит замер нужен свой, сейчас, а не «когда-нибудь на этапе 2».

## Задача

1. **Бюджет двухуровневый (решение владельца 2026-11-10: «более чем приемлемо»):**
   - **интерактивные** (`clients`, `partners`, `journal`, `catalog`, `analytics/summary`) — **p95 ≤ 1000 мс**;
   - **тяжёлые** (экспорт всех записей, тренды за год, большие диапазоны `somatic-series`, портируемость) — **p95 ≤ 3000 мс** + **обязательный индикатор загрузки** в UI (FE-040);
   - **накладные шлюза** (разница «через шлюз минус напрямую») — ≤ 100 мс для интерактивных.
   Объём агрегации **не режем** — вместо этого даём тяжёлым запросам явный бюджет и видимую загрузку.
2. **Быстрый отказ апстрима:** `ActivityTimeout` **2 c** для интерактивных маршрутов (не 15); включить **пассивные health-checks** YARP (`Passive`, `ReactivationPeriod`), чтобы мёртвый апстрим давал **502 быстро**, а не 504 через таймаут. Проверить тем же приёмом, что B7 (остановить `xdiary-client`, замерить время до ошибки → должно быть ≤ 2–3 c, затем восстановление 200).
3. **Инструмент замера** (`tools/latency.py`, режим `--baseline`/`--check`): обход операций из `openapi/index.json` + список безопасных `GET`, для каждой — время **через шлюз** и **напрямую в сервис** (внутри сети), 20 повторов, вывод p50/p95/max + разница «шлюз минус напрямую» (накладные расходы шлюза).
4. **Гейт:** `--check` красный, если p95 интерактивной операции > 1000 мс или накладные шлюза > 100 мс. Подключение в CI — по §5.4: два прогона (дефект: искусственная задержка → красный; норма → зелёный) + `--selftest`.
5. **Артефакт:** `reports/latency-<дата>.json` коммитится, чтобы видеть тренд, а не одно число.

## Критерии приёмки

- [ ] p95 интерактивных операций ≤ 1000 мс на dev, цифры в `## Результат` (таблица: операция / через шлюз / напрямую / накладные).
- [ ] Мёртвый апстрим → **502 за ≤ 3 c**, восстановление → 200.
- [ ] `tools/latency.py --check` красный на искусственной задержке и зелёный на норме; `--selftest` внутри.
- [ ] В отчёте отдельная строка: «Gravitee-аналитика отклика появится на этапе 2 (в тракте); на этапе 1 источник цифр — этот инструмент».

4. **Пассивные health-checks YARP** (`Passive` + `ReactivationPeriod`): мёртвый апстрим → **502 за ≤ 3 c** (сейчас 504 через 15 c). Проверка — детерминированный контроль `7-deploy/flaky-gateway.sh` (502 за 0.026 c) плюс «живой» вариант.
5. **Два прогона по §5.4:** дефект (искусственная задержка 1200 мс → красный) и норма (зелёный), плюс `--selftest`.
