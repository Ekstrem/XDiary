## 1. Crash-loop `42P07` снят для `partners` — согласованием истории миграций

**Причина (найдена числами):** в `partners.__EFMigrationsHistory` **не было** строки
`20261105170447_AddReadStores`, при этом таблицы `partners_read` и `partners_directory` **уже
существовали** (их создаёт raw DDL `CREATE TABLE IF NOT EXISTS …` в `Program.cs`). EF считал
миграцию неприменённой → `CREATE TABLE partners_read` → `42P07` → контейнер в crash-loop
(`restarts` до **326**).

**Сделано (только данные, без удаления):**

1. бэкап обеих БД: `/tmp/pre-partners-20261105-205512.dump` (59 367 Б), `/tmp/pre-journal-20261105-205512.dump` (155 645 Б);
2. вставлена **одна** строка в историю — только там, где объекты уже есть:
   `partners` → `20261105170447_AddReadStores`, `journal` → `20261105170525_AddReadStores`;
3. выкатка штатным `deploy.sh`.

**Результат:** `partners` на свежем образе `640a9e20` — `running`, **`restarts=0`**, **`42P07 = 0`**,
`/health` **200**.

`journal` на свежем образе `5e1c2f8a` **всё ещё** падает: `42P07: relation "journal_defaults"
already exists`, хотя строка `AddReadStores` **есть** в его истории, а таблица существует.
Падение на `Program.cs:66` (`readDb.Database.Migrate()`). Пока journal запинен на рабочую сборку
`12365e54` (`restarts=0`, `/health` **200**) — стенд целый: **12 из 12 сервисов → 200**.

## 3. 🔴 Корень падений контрактных тестов (для @BE)

Перепрогон `PartnerSoftDelete` на **живом** стенде: `Failed: 3, Passed: 1, Total: 4`,

Все три падения — `Expected: OK, Actual: BadRequest` (`PartnerSoftDeleteTests.cs:71, 84, 101`), и
причина в теле ответа:

```
POST /api/v1/partners/{id}/remove  →  400  "Partner not found."
```

При этом партнёр **только что создан** (`POST /api/v1/partners` → 200) и виден в

`FullEventSourcing`: командный путь пишет только событие.

**Вывод:** обработчик `remove` ищет партнёра в **командной** таблице, которая пуста по дизайну,
поэтому «не находит» только что созданного партнёра. Лечение (зона @BE): читать агрегат из
read-модели или из event store, а не из `partners`.

## 5. `journal`: причина — образ собран ДО переименования миграции (@TL 2026-11-06 00:15)

@TL доказал по git: образ `journal 5e1c2f8a` собран из коммита **19:21**, а переименование
миграции `AddReadStores` сделано в `4332aa15` в **20:07**. То есть развёрнутый образ знает
**старый** `MigrationId` (`20261105161910_AddReadStores`), а база — новый (`20261105170525_…`):
EF видит «неприменённую» миграцию и делает `CREATE TABLE journal_defaults` → `42P07`.

**Важно (проверено):** образов, собранных **после** переименования, в registry **нет** —
`single-1dde681` (20:55) и `single-2339460` (20:17) отсутствуют, самый свежий — `single-5e1c2f8`.
Значит путь «(а) выкатить новый образ» сейчас **невозможен**, и остаётся «(б) согласовать историю
с тем ID, который знает развёрнутый образ».

**Сделано (с бэкапом `/tmp/pre-journal-hist-212657.dump`, 157 129 Б):**

```sql
delete from "__EFMigrationsHistory" where "MigrationId"='20261105170525_AddReadStores';
insert into "__EFMigrationsHistory" values ('20261105161910_AddReadStores','8.0.11');
```

**Результат:** `journal 5e1c2f8a` — `running`, **`restarts=0`**, **`42P07 = 0`**, `/health` **200**.

## 7. 🔁 Что сделать, когда появится образ после переименования

Порядок обязателен, иначе стенд снова упадёт:

1. выкатить образ, собранный **после** `4332aa15`;
2. **до** старта вернуть в историю новый id: `delete … '20261105161910_AddReadStores'` →
   `insert … '20261105170525_AddReadStores'`;
3. проверить `restarts=0` и `42P07 = 0` в логе.

Факт для `0-df-issue/migrations.md` (зона @BE): **переименование применённой миграции меняет
`MigrationId`**, и любой образ, собранный до переименования, конфликтует с базой.
