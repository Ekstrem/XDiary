## Почему это важно

Гейт, который не запускается, **не защищает**. Сейчас «CI зелёный» означает: 3 гейта из 11 + сборки. Остальные — ручная дисциплина,
которая уже подводила (правило трассировки выполнялось у 18/22, фиксированные паузы жили в спеках).

## Что сделать

1. Добавить в `ci-guards.yml` (или отдельный job) запуск **6 готовых** гейтов, у которых `rc=0` на `origin`:
   `check_adr028_move`, `check_read_paths`, `check_front_088`, `check_e2e_selectors`, `check_e2e_traceability`, `check_e2e_no_sleeps`
   — каждый **сначала `--selftest`**, затем реальный прогон (как сделано для остальных).
2. `check_swagger_perimeter` — в job, где есть базы: либо `--public-base` на прод/дев, либо `--internal-base` изнутри;
   иначе шаг будет **красным** (`rc=2` = «не измерено», а не зелено).
3. `e2e_receipt` — в job `front-e2e` **после** прогона: скормить вывод Playwright, получить одну строку-квитанцию
   (`passed/failed/skipped` + `REF`), и **`rc=2`** при неразобранном выводе (это уже реализовано в скрипте).

## Критерии приёмки

- в `.github/workflows` присутствуют **все 11** гейтов (grep по именам файлов);
- каждый шаг начинается с `--selftest` (иначе гейт может быть сломан и молча зелёный);
- в логе `front-e2e` есть **одна** квитанция с числами `passed/failed/skipped` + `REF`;
- `check_swagger_perimeter` либо получает базы, либо явно помечен как post-deploy (не «зелёный по умолчанию»).
