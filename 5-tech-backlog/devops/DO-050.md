# DO-050: P0 — «деплой success» не означает «на VPS новый образ» (флаг @BE не работал именно поэтому)

- **Статус:** ToDo
- **Приоритет:** **P0** (гейт и деплой зелёные, а прод работал на старом образе — вход не работал по этой причине)
- **Источник:** @DO 2026-11-08 05:40 — «флаг @BE не работал не из-за кода: в **старом образе** `Clients:AllowTestOtpOutsideDev` не существует; как только я вручную подтянул правильный образ, флаг заработал»; при этом `deploy` #787, #788, #789 были **success**
- **Зависимости:** DO-047 (туннель), DO-046
- **Проверяет:** @TL (TechLead)

## Проблема
Пайплайн отрапортовал успех, тег обновился, а на VPS остался **старый образ**. Классический класс «зелёное ≠ действующее»: проверки зелёные, владелец без входа.

## Задача (зона @DO)
1. Выяснить механику: почему `update.sh`/pull не забирал новый образ (тег `latest` не переопубликован? кэш? неверный тег в compose? `pull_policy`?).
2. Добавить **пост-деплой проверку соответствия**: сравнить digest образа на VPS с digest, опубликованным в GHCR для этого коммита; несовпадение → **красный** шаг `deploy-prod` (или отдельный `verify-deploy`).
3. Проверка должна ловить именно этот сценарий: «тег тот, образ старый».
4. Негативный контроль: подложить старый образ → шаг должен покраснеть.
5. **Аудит глотания ошибок:** в `7-deploy/**/*.sh` найдено **19** мест с `|| true` / `2>/dev/null` (@LM, 07:06); в `update.sh` **`podman pull ... || echo` (строка 45) по-прежнему не валит скрипт** — класс не закрыт, закрыт только конкретный обрыв. Каждое место: убрать либо заменить на явную обработку с `exit 1`/`::error`; отчёт — таблицей «файл:строка:что глотается:решение».
6. **`deploy.sh` — главный путь — в репозитории отсутствует** (живёт только на сервере в `/opt/xdiary/7-deploy/deploy.sh`, при этом его вызывают `update.sh:52` и оба ранбука; нарушение §5.2). Вынести в `7-deploy/` **или** сверять его `sha256` с версией из git на каждом деплое и **падать при расхождении**. Без этого аудит п.5 принципиально неполон: `podman`-команды исполняются в серверном файле, которого мы не видим.

## Критерии приёмки
- [ ] `deploy-prod` содержит шаг сверки digest VPS ↔ GHCR.
- [ ] Негативный контроль выполнен (старый образ → красный).
- [ ] После фикса — прогон, где образ на VPS действительно соответствует коммиту (подтверждено digest'ом в логе).
