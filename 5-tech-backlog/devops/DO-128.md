## Анализ @TL (2026-11-18 00:1x): `recreate-service.sh` **уже** удаляет контейнер — значит проблема в правах/владельце

Проверил скрипт в `main` (`7-deploy/recreate-service.sh`, 340 строк): удаление **есть** —

```
297| podman rm -f "$CONTAINER" >/dev/null 2>&1 || true
299|   sudo -n podman rm -f "$CONTAINER" >/dev/null 2>&1 || true
```

и в самом файле (строки 292-294) уже описан ровно наш случай:

```
# (rootless vs root) от прошлых прогонов. Тогда `podman run` падает не на сети, а на имени:
#    is already in use by "<id>". You have to remove that container to be able to reuse that name
```

**Что это значит:** `rm -f` в CI **не сработал молча** (`|| true` скрыл причину), а `sudo -n` в этом окружении недоступен → контейнер остался, и `podman run` упал на имени. То есть дефект не в отсутствии `rm`, а в том, что ошибка удаления **проглатывается** и владелец контейнера не проверяется.

**Что нужно (зона @DO):**
1. не скрывать ошибку `rm`: если `podman rm -f` вернул не 0 и контейнер всё ещё существует (`podman ps -a --filter name=…`) — печатать **владельца** (`podman inspect --format '{{.Config.User}} {{.State.Status}}'`) и падать с внятным сообщением, а не идти дальше в `podman run`;
2. выровнять контекст: либо всё rootless под одним пользователем, либо всё через `sudo -n` (и тогда `sudo -n true` проверять в pre-flight, чтобы «нет sudo» было видно **до** выкатки);
3. диагностическая команда для VPS (приложить в ранбук): `podman ps -a --filter name=xdiary-client --format '{{.Names}} {{.Image}} {{.Status}}'` и `podman inspect xdiary-client --format '{{.Config.User}}'`.

**Критерий:** `deploy-dev` проходит, `xdiary-client` пересоздаётся; если контейнер занят — в логе видно **кто** им владеет, а не «already in use» без контекста.
