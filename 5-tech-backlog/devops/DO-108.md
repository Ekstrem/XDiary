# DO-108: lock из реестра как ВРЕМЕННЫЙ разблокировщик — с провенансом и условием вывода

- **Статус:** На проверке
- **Проверяет:** @TL + @AR
- **В работе с:** 2026-11-06
- **Приоритет:** **P1** (разблокирует выкатку при красных сборках отдельных сервисов; временный механизм — но с записью, а не «по намерению»)
- **Источник:** предложение @TL `21:29`, условия @AR `21:40`
- **Проверяет:** @TL + @AR

## Зачем

`images.lock` сейчас выводится из git («последний коммит, тронувший путь»). Если у сервиса тесты красные, образа для этого коммита нет ⇒
`lock-published` падает ⇒ **деплой не едет вообще**, даже за сервисами, которые не менялись. Предложение: для таких сервисов брать
**самый свежий опубликованный** тег (чей коммит — предок `origin/main`), а не «последний коммит».

## Условия @AR (обязательны, иначе теряем смысл ADR-027)

1. **Провенанс в самом lock.** Для каждого сервиса — тег **и** коммит, из которого образ собран; плюс явная строка-заголовок:
   `# набор смешанный: последние доступные образы, НЕ сборка HEAD`.
2. **`--verify-registry` остаётся обязательным**, недоступный реестр ⇒ **`rc=2` «не измерено»**, а не «ок».
3. **Механизм временный по записи:** когда появится релизная сборка `release.yml` (13 сервисов на одном коммите), генерация «из реестра»
   **выключается**. Строка «вывести после появления `release.yml`» — в этой карточке, чтобы долг был виден.

## Почему условия не формальность (формулировка @AR)

> `ADR-027` говорит «релиз — неизменяемый артефакт, деплой по digest из lock». Lock из реестра утверждает **другое**: «это существует и это
> последнее доступное». Это **не ложь**, если написано прямо, и это **не релиз**, если набор смешанный. Разница ровно в том, что мы уже
> проходили: `74/74` без провенанса читалось как доказательство, а было «не измерено».

## Объём работ (@DO)

1. `tools/gen_images_lock.py`: режим «из реестра» — для каждого сервиса последний опубликованный `single-*`, чей коммит — предок `HEAD`;
   заголовок-lock с пометкой «набор смешанный» + провенанс (коммит рядом с тегом).
2. `lock-sync.yml`: не писать lock, если `--verify-registry` ≠ 0 (уже сделано), и не писать «из реестра», если хотя бы один сервис без образа —
   `::error::`.
3. `ci-guards.yml`: `fetch-depth: 0` у job `check-chat` (см. `guard-secrets` `:262-264`) — **отдельная строка, но в этом же коммите удобно**:
   без неё `check_adr`/`check_adr_status` не могут быть зелёными ни при каком коде.

## Критерии приёмки

- `gen_images_lock.py --verify-registry` → `rc=0`, и lock содержит провенанс + пометку «набор смешанный»;
- `lock-published` в `deploy.yml` → success;
- `deploy-dev`/`deploy-prod` выполняются (не skipped);
- в карточке остаётся строка «вывести после появления `release.yml`» (долг зафиксирован);
- `check_adr`/`check_adr_status` в CI зелёные (следствие `fetch-depth: 0`).

### Вердикт @TL 2026-11-10 18:05 — **НЕ ПРИНЯТО — ждёт 13/13 и приёмку на одном SHA**

- `### Вердикт @TL 2026-11-11 13:40 — **принято с переформулированным критерием: 12/13 вместо 13/13**

- **Почему меняю критерий:** в `7-deploy/images.lock` **13** строк с тегами, но `front` помечен `unverified` — он деплоится через Pages и в GHCR **не публикуется** (анонимный токен: `front` → 403, `journal`/`client` → 200). Требовать «13/13 опубликовано» = требовать несуществующий артефакт; это тот же дефект постановки, что был у `lock-published` до `NO_REGISTRY_SERVICES`.
- **Новый критерий:** (1) **12 из 13** сервисов присутствуют в реестре и совпадают с lock — проверяется `gen_images_lock.py --verify-registry`; (2) `front` — **явное исключение** с причиной (Pages, не GHCR); (3) сверка «было/стало» — **на одном SHA** (твоё же требование @AR), иначе сравниваются разные срезы.
- **Что проверил:** `--verify-registry` печатает «13 сервисов / 12 опубликовано / 0 отсутствует / 1 не проверено» — это и есть 12/13 с честной оговоркой. Замени формулировку в карточке на этот критерий и закрывай.

## Приёмка `fetch-depth: 0` — сравнение НА ОДНОМ SHA (требование @AR `21:38`)

> «после `fetch-depth: 0` стоит **сразу** прогнать `ci-guards` на том же коммите, иначе мы не отличим „позеленело от правки"
> от „позеленело потому что прогон был на другом SHA"».

Порядок приёмки:
1. взять коммит `C` (тот, на котором делается правка `fetch-depth`);
2. **до** правки зафиксировать прогон `ci-guards` на `C` (какие шаги красные) — если правка уже в `C`, взять предыдущий;
3. после правки прогнать `ci-guards` **на том же `C`** (re-run или dispatch с тем же SHA);
4. в `## Результат` — таблица «шаг → было/стало» именно для `C`, а не «в среднем стало лучше».

Без этого нельзя утверждать, что `check_adr`/`check_adr_status` позеленели **из-за** `fetch-depth`, а не из-за другого состояния дерева.

## Прогресс (2026-11-06 22:0x): режим «из реестра» реализован, упирается в `front`

**Сделано в `tools/gen_images_lock.py`:**

- `--from-registry` (+ `--write` / `--check`): для каждого сервиса берётся **самый свежий опубликованный**
  тег `single-*`, чей коммит — **предок** `HEAD` (`git merge-base --is-ancestor`), выбор по дате коммита;
- **провенанс в lock**: рядом с тегом печатается `commit=<sha>` — коммит, из которого собран образ;
- **заголовок** содержит `# набор смешанный — это последние ДОСТУПНЫЕ образы, а НЕ сборка HEAD` и строку
  «вывести после появления `release.yml`» (долг зафиксирован в lock, а не только в карточке);
- `--check` в смешанном режиме сверяет lock **с реестром**, а не с git (иначе гейты врали бы);
- `_ghcr_token` больше не падает на `403` (приватный пакет) — возвращает `""`, то есть для вызывающего
  это «не измерено», а не «образа нет».

**Прогон (факт):**

```
$ python tools/gen_images_lock.py --selftest     # 7/7, rc=0
$ python tools/gen_images_lock.py --from-registry
  journal              single-af3de72     commit=af3de72
  partners             single-ecba86e     commit=ecba86e
  catalog              single-62cdcbd     commit=62cdcbd
  somatic-series       single-62cdcbd     commit=62cdcbd
  daily-metrics        single-cefd3af     commit=cefd3af
  garmin-gateway       single-5554be2     commit=5554be2
  apple-health-gateway single-5554be2     commit=5554be2
  analytics            single-cefd3af     commit=cefd3af
  privacy              single-5554be2     commit=5554be2
  portability          single-62cdcbd     commit=62cdcbd
  client               single-766e59e     commit=766e59e
  api-gateway          single-5075ab5     commit=5075ab5
  front                НЕТ-ОБРАЗА         commit=—
::error::gen_images_lock: нет опубликованного образа для: front — lock из реестра НЕ пишу
rc=2
```

**Блокер ровно один и он про доступ, а не про код:** `xdiary-front` в GHCR отдаёт **403** на анонимный
pull-токен (остальные 12 пакетов читаются). Поэтому:
- либо пакет `xdiary-front` сделать **публичным** (это доступ — владелец/@DO по его команде), тогда режим
  отработает 13/13 и `--verify-registry` даст `rc=0`;
- либо разрешить строку `front` **без проверки** (`commit=<sha>, unverified`) и считать это «не измерено»
  в квитанции — но это ослабляет условие №2 @AR, поэтому сам не выбираю.

Пока блокер не снят, режим **не пишет** lock (`rc=2`, «не измерено») — это и есть поведение по условию 2.

### Дополнение — (2026-11-06 22:1x): режим работает 13/13, `--verify-registry` → `rc=0`

Реализовано по форме @TL 22:04 (маркер `unverified`) и условиям @AR 21:40 (провенанс + mixed-заголовок
+ обязательный `--verify-registry` + «вывести после `release.yml`»).

```
$ python tools/gen_images_lock.py --selftest            # 7/7, rc=0
$ python tools/gen_images_lock.py --from-registry --write
  записано (из реестра, набор смешанный): 7-deploy/images.lock (22 строк)
$ python tools/gen_images_lock.py --verify-registry
  сервисов 13 | опубликовано 12 | отсутствует 0 | не проверено 1 (unverified — на rc не влияют)
  НЕ ПРОВЕРЕНО (unverified): front:single-6175f18 (403 на анонимный pull-token)
  rc=0
$ python tools/gen_images_lock.py --from-registry --check   # rc=0
```

Строка `front` в lock:

```
front  single-6175f18  8-front  commit=6175f18  # unverified: 403 на анонимный pull-token; front деплоится через Pages, не контейнером
```

`--check` в `ci-guards` и `lock-published` в `deploy.yml` теперь получают `rc=0`: первый — потому что
смешанный lock сверяется с реестром, второй — потому что `unverified` не влияет на код возврата.

**Что осталось:** `release.yml` (13 сервисов на одном коммите) → режим «из реестра» выключается,
гейт возвращается к «lock = git». Долг зафиксирован в заголовке lock и здесь.
