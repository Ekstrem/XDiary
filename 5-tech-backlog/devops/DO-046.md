## Факты
- Отправитель: `6-msa/BC-Client/src/Client.Application/Security/TelegramOtpSender.cs`; ключи: `Otp:Telegram:BotToken`, `Otp:Telegram:AdminChatId` (или `ChatId`), опционально `Otp:Telegram:ChatIdMap`.
- В коде явные отказы: нет `BotToken` → `InvalidOperationException`; нет `chatId` → «номер не в ChatIdMap и нет AdminChatId — OTP не отправлен».
- На dev работает `CLIENTS__TESTOTP`, на проде его нет (правильно) — значит прод-путь упирается именно в Telegram.

## Диагностика (зона @DO, по порядку)
1. **Env контейнера:** `docker exec <client-api> env | grep -i '^Otp'` — проверить наличие и **непустоту** `Otp__Channel=telegram`, `Otp__Telegram__BotToken`, `Otp__Telegram__AdminChatId`. Имена с двойным подчёркиванием соответствуют `Otp:Telegram:...`.
2. **Логи API** по вызову `POST /api/v1/clients`: есть ли исключение `BotToken не задан` / `OTP не отправлен`, и **код ответа Telegram** (`401` — токен неверен, `400 chat not found` / `403 bot can't initiate` — пользователь не нажимал `/start` или `chat_id` не тот).
3. **Проверка бота напрямую** (без приложения): `curl -s "https://api.telegram.org/bot<TOKEN>/getMe"` → `ok:true`; затем `sendMessage` в `chat_id` из env тем же токеном. Токен **не печатать** в чат (правило §6).
4. **Сверка id:** `AdminChatId` должен быть **id пользователя** (личный чат) или группы, где бот участник. Если владелец не нажимал `/start` у бота — Telegram физически не даст боту написать первым.
5. **Сеть:** доступ VPS-1 → `api.telegram.org` (на dev работало, но проверить именно прод-контейнер).

## Обходной путь (только по решению владельца)
Временный тестовый код на проде (`Clients__TestOtp=000000`) — даёт войти и проверить остальное, но **ослабляет прод**; включать только с явного разрешения владельца и снять сразу после проверки.

## Результат диагностики (@DO 2026-11-08 04:05)

**Причина названа: сеть, а не код и не токен. TCP-доступ к Telegram с обеих VPS заблокирован на уровне провайдера.**

Проверено по шагам (контейнер `xdiary-client` на VPS-1, rootless `podman`):

1. **Env — в порядке.** `Otp__Channel` задано (длина 8 = `telegram`), `Otp__Telegram__BotToken` задано (46 симв.), `Otp__Telegram__AdminChatId` = `211320390`. Значения не печатались, только длина/наличие (§6).
2. **Прямая проверка бота невозможна: `api.telegram.org` не отвечает.**
   - `curl -v https://api.telegram.org` → `Trying 149.154.166.110:443… connect … Connection timed out` (и то же для IPv6 `2001:67c:4e8:f004::9`);
   - `TCP 443` до `149.154.166.110`, `149.154.167.220`, `91.108.56.130` — **нет соединения**; `TCP 80` туда же — тоже нет;
   - **ICMP при этом проходит:** `ping 149.154.166.110` → **0% потерь, 43 мс**. Маршрут есть, режется именно TCP 80/443;
   - контроль того же хоста: `github.com` → **200**, `api.telegram.org` → **000**.
3. **Не только прод: VPS-2 (dev) ведёт себя так же** — все три Telegram-адреса по 443 недоступны.
4. **Обходных сетевых путей нет:** прокси-переменных в контейнере нет, локальных прокси-портов (1080/3128/9050) нет, в Tailscale только два узла (`xdiary-vps1`, `xdiary-vps2`) — **exit node отсутствует**, поэтому завернуть трафик «через другую сеть» из существующей инфраструктуры нечем.
5. **Dev не показателен:** `POST /api/v1/clients` на dev → `200` и `"otpCode":"000000"` — dev идёт по `CLIENTS__TESTOTP`, Telegram там не задействован вообще.

**Следствие:** `AdminChatId` и `/start` нельзя ни проверить, ни исключить, пока нет TCP-связности: `TelegramOtpSender` падает на connect-таймауте до любого ответа Telegram. Это объясняет и «гейты зелёные, а продукт недоступен»: `smoke-api` не проверяет доставку OTP.

**Варианты (нужно решение владельца — доступы и деньги):**
- (A) Тикет провайдеру на разблокировку Telegram-подсетей (ICMP проходит → это фильтр, а не отсутствие маршрута). Самый дешёвый по работе, зависит от хостера.
- (B) Прокси-релей на хосте, откуда Telegram доступен (отдельный VPS у другого провайдера либо Cloudflare Worker), и `TelegramOtpSender` ходит через него: нужна правка @BE (адрес API/прокси) + конфиг.
- (C) SMS-канал по ADR-021 — требует доступов к SMS-провайдеру.
- (D) Временный `Clients__TestOtp` на проде — **ослабление прода**, только по явному разрешению владельца (@TL 03:30/03:40 просил не включать до починки доставки).

**Критерий «точная причина» выполнен; критерий «владелец входит» — нет**, поэтому задача остаётся `В работе`.

### Дополнение (@DO 2026-11-08 04:30): почему «временный TESTOTP» на проде не сработает

`6-msa/BC-Client/src/Client.Application/Commands/ClientHandlers.cs:18`:

```
_testOtp = isDev ? config["Clients:TestOtp"] : null;
```

где `isDev` = `ASPNETCORE_ENVIRONMENT == "Development"`. На проде `ASPNETCORE_ENVIRONMENT` = **`Single`** (проверено в контейнере), поэтому `_testOtp` **всегда `null`**, и код уходит в `_sender.SendAsync` → падает на connect-таймауте.

**Вывод:** включение `Clients__TestOtp` на проде — **no-op**, оно не даёт входа и создаёт ложное впечатление временной меры. Механизм для обхода нужно сначала построить (правка @BE, ~1 строка): разрешать `Clients:TestOtp` вне Development по отдельному явному флагу (например `Clients:AllowTestOtpOutsideDev=true`), который затем снимается вместе с кодом. Только после этого «временная мера» станет реальной.

### Почему в логах нет строки `Telegram OTP отправлен` / `Telegram <код>`

Логи `xdiary-client` за 8 часов работы содержат **ноль** строк про Telegram/OTP (только SQL-запросы). Причина в коде: успешная отправка не логируется, а ошибка не пишется в лог, а **возвращается клиенту**: `TelegramOtpSender` бросает `Telegram <код>: <тело>`, `RegisterClientHandler` ловит и делает `ClientResults.Fail(ex.Message)` → текст уходит в ответ `POST /api/v1/clients`. То есть искать надо не в логе, а в **ответе API**, которого у нас нет (владелец делал вход из UI).

### Распоряжение @TL 04:25 и почему оно пока невыполнимо (@DO 04:50)

@TL распорядился: включить `Clients__TestOtp` на проде, максимум 60 минут, с записью в задаче и сообщением владельцу (`000000`).

**Выполнить буквально нельзя:** `ClientHandlers.cs:18` читает `Clients:TestOtp` **только** при `ASPNETCORE_ENVIRONMENT="Development"`; на проде он `Single`, значит `_testOtp` = `null` и код всегда идёт в `TelegramOtpSender`. Включение переменной даст **ложное впечатление меры** (и потребует перезапуска контейнера без пользы).

**Почему не обойти сменой окружения на `Development`:** `Client.Api/Program.cs:52` — в Development включается **Swagger UI**, а прод торчит в публичный интернет. Это шире, чем «временный тестовый код»: вместо одного фиксированного кода мы открыли бы документацию API всему интернету на 60 минут. Не делаю.

**Нужная правка (@BE, ~1 строка + тест):** разрешать тестовый код вне Development по отдельному явному флагу, по умолчанию выключенному:

```
var allowTestOtp = string.Equals(config["Clients:AllowTestOtpOutsideDev"], "true", OrdinalIgnoreCase);
_testOtp = (isDev || allowTestOtp) ? config["Clients:TestOtp"] : null;
```

После этого порядок становится безопасным и быстрым: деплой → включить `Clients__AllowTestOtpOutsideDev=true` + `Clients__TestOtp=000000` → запись в задаче «временная мера, включена HH:MM» → сообщение владельцу → снять оба сразу после входа (и записать «снят HH:MM, проверено: `POST /api/v1/clients` больше не возвращает `otpCode`»).
