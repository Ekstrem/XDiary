# DO-037: Caddy-конфиги стендов — в репозиторий (снимок, а не «на сервере»)

- **Статус:** На проверке
- **Приоритет:** P2
- **Источник:** @TL 2026-11-02 18:34 («@DO — … DO-036 (Caddy в репозиторий)»), §5.2 воспроизводимость
- **Зависимости:** нет
- **Проверяет:** @TL (автор @DO — саморевью запрещено, §2.1 п.6)

## Задача

`/etc/caddy/Caddyfile` жил только на двух машинах: при пересоздании VPS или ручной
правке конфиг некуда было сверить, а «починил на сервере» — новый дрейф (§5.2).
Нужен снимок конфигов обоих стендов в репозитории + инструкция применения.

## Сделано

- `7-deploy/caddy/Caddyfile.dev` — dev (VPS-2), вариант **API-only** по вердикту @AR (DO-036):
  `@api path /api/* /health` → `reverse_proxy`, корень → `respond` 200 вместо 502.
- `7-deploy/caddy/Caddyfile.prod` — прод (VPS-1), снят с машины как есть: `tls` + `reverse_proxy 127.0.0.1:8080`.
- `7-deploy/caddy/README.md` — таблица «файл → машина → роль», команды применения
  (`cp` + `caddy validate` + `systemctl reload`), таблица ожидаемых кодов и правило
  «файл = снимок работающего, а не пожелание».

## Критерии приёмки

- [x] Оба конфига в репозитории; `Caddyfile.dev` соответствует работающему dev (проверено по `/` `/health` `/api/v1/clients` `/api/v1/partners`).
- [x] `Caddyfile.prod` — байт-в-байт снимок с VPS-1 (без «улучшений»).
- [x] Секретов нет: только домены, пути к сертификатам (сами сертификаты вне репозитория), локальные адреса.
- [x] `python tools/check_rule_docs.py` — без предупреждений.

## Результат

Caddy-конфиги обоих стендов в `7-deploy/caddy/`; применение и проверка описаны в
`7-deploy/caddy/README.md`. Прод-конфиг зафиксирован **как есть**, включая известное
поведение `GET /` → 502 (у YARP нет маршрута на `/`); менять прод — отдельное решение @TL/@AR.
