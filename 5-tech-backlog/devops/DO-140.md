# DO-140 — P1: сверка digest `catalog` (lock ↔ dev ↔ prod) — условие закрытия `FE-054`

- **Статус:** На проверке
- **Приоритет:** P1 (единственное, что отделяет `FE-054` от корректного закрытия; включает прод-проверку **без** ослабления прода)
- **Источник:** @TE 2026-11-18 00:50 («закрывать только после сверки digest»), принято @TL; @FE закрывает `FE-054` по более раннему вердикту
- **Зависимости:** нет (read-only)
- **На проверке с:** 2026-11-18
- **Проверяет:** @TL
- **Исполняет:** @DO

## Зачем

`FE-054` (идемпотентность `POST /catalog`) подтверждена **на dev** четырьмя независимыми прогонами (`00:09` @FE, `00:14` @TE, `00:35` @TE, `00:42` @FE). Но `deploy-prod` **ни разу не выполнялся** (`DO-139`/`BE-126`/`DO-128`), поэтому на `vps1` может стоять образ от **2026-11-13**. Включать тестовый OTP на проде ради замера мы **сознательно не будем** (@TE: «удобно для теста» не должно ослаблять прод).

Значит единственный корректный способ подтвердить, что контракт есть и в проде — **сверить digest образа**.

## Что нужно (2 команды на каждой машине, read-only)

```bash
podman inspect xdiary-catalog --format "{{.ImageDigest}}"
# либо, если поле пустое:
podman image inspect "$(podman inspect xdiary-catalog --format '{{.ImageName}}')" --format "{{.Id}}"
```

на **dev** (`vps2`) и на **prod** (`vps1`), и сравнить с `7-deploy/images.lock`:

```
catalog  single-b536455  6-msa/BC-Catalog  commit=b536455  digest=sha256:d5544df7…
```

## Решение по результату

| результат | действие |
|---|---|
digest(prod) == digest(lock) == digest(dev) | критерий `FE-054` закрыт для прода: контракт в прод-образе есть. `FE-054` остаётся `Закрыта` (граница «живой замер на проде не прогонялся» уже записана в карточке) |
digest(prod) != digest(lock) | на проде **старый образ** ⇒ `FE-054` **переоткрыть** (`На проверке`) до `deploy-prod`; в карточке сослаться на этот пункт |
digest недоступен (нет доступа/контейнера) | вернуть карточку в чат с точной причиной, не выдумывать вывод |

## Критерий

В `FE-054` (или в этой карточке, если `FE-054` уже закрыта) появилась строка с тремя digest-ами и выводом «совпали/нет» + дата. Это и есть квитанция прод-доставки без включения тестового OTP.

### Доказательство по графу коммитов (@TE, 01:18) — не «возможно отстал», а доказано

```
prod-образ собран из   c0552f2f816f728a0a0494de2f5f91c683088d50  (2026-11-13 18:18:22)
контракт идемпотентности 4f49b47f1                               (2026-11-17 20:43:27)

git merge-base --is-ancestor 4f49b47f1 <prod-sha>  → НЕТ
git merge-base --is-ancestor <prod-sha> 4f49b47f1  → ДА
```

То есть **prod-образ физически старше контракта** — `#2429` в нём отсутствовать обязан. Это сильнее сверки тегов: даже если бы тег выглядел подозрительно, граф коммитов не оставляет вариантов.

## Вывод (по правилу, записанному в карточке)

- **dev:** контракт `#2429` в образе есть, поведение подтверждено живым замером (четыре прогона).
- **prod:** образ **старше lock** ⇒ пользователь в проде фичу **не получил** ⇒ `FE-054` **остаётся `На проверке`** до зелёного `deploy-prod`. Закрывать «по dev» нельзя — это была бы ложная квитанция.

## ⚠️ ЦЕЛЬ ПО DIGEST ОБНОВЛЕНА (@FE поймал устаревшее число, @TL подтвердил в `origin/main`)

`7-deploy/images.lock` больше **не** `single-b536455`. Актуально (проверено @TL 2026-11-18 09:09, `main` = `628834339`):

```
journal   single-378a56c  commit=378a56c  digest=sha256:512f923d…
partners  single-378a56c  commit=378a56c  digest=sha256:8fe6a725…
catalog   single-378a56c  commit=378a56c  digest=sha256:cfb0e0de…
```

⇒ **цель для прода — `sha256:cfb0e0de…` (catalog, тег `single-378a56c`)**, а не `d5544df7…` (это был `single-b536455`).

**Правило проверки после выкатки:** сравнивать digest контейнера **с текущим `images.lock` в `main`**, а не с числом из старого обсуждения. Если прод окажется на `d5544df7…` — это значит «прод на предыдущем теге», и такой результат фиксируется отдельной пометкой, но **не** считается успехом.
