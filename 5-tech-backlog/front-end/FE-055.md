# FE-055 — P1: акт не должен теряться при обрыве/5xx — черновик + один повтор

- **Статус:** ToDo
- **Приоритет:** P1 (основной сценарий владельца: «добавить акт»; любой сбой сети сейчас = потерянный текст)
- **Источник:** владелец 2026-11-16 «сделать возможным добавление акта» + наблюдение: `POST /api/v1/journal/records` в проде был `500` несколько суток
- **Зависимости:** нет (не зависит от `BE-122`: это про журнал, не про каталог)
- **Проверяет:** @TL
- **Исполняет:** @FE (`8-front/`)

## Проблема

Прод отдавал `500` на `/api/v1/journal/records` несколько суток. В приложении отправка акта при ошибке сети/`5xx`:
- не сохраняет введённый текст — пользователь теряет то, что набрал;
- не показывает, что запись **не** сохранена, если экран успел уйти вперёд.

Класс тот же, что `FE-051` (молчаливый пустой экран) и `FE-054` (дубль при повторе), но здесь цена выше: теряется **содержание**, а не отображение.

## Что нужно

1. **Черновик акта** сохраняется локально (тот же механизм, что у каталога/партнёров — `repository.js` + `localStorage`) **до** отправки и очищается только после `2xx`.
2. При сетевой ошибке/`5xx`: текст остаётся в форме (или восстанавливается из черновика при повторном открытии), видимый тост/блок с причиной и кнопкой «Повторить».
3. При `4xx` (валидация): черновик **не** удаляется, ошибка показывается как есть (не маскируем).
4. Идемпотентность повтора: если `POST` уже прошёл, а ответ потерялся — повтор не должен создавать вторую запись (тот же подход, что `FE-054`: клиентский `id`, если сервер его примет; иначе — явно отметить как ограничение).

## Критерии приёмки

- [ ] runtime-тест (как `FE-054-…-test.js`): обрыв сети → черновик сохранён, `POST` повторён один раз, после `2xx` черновик удалён;
- [ ] `5xx` → черновик сохранён, видимый текст причины;
- [ ] `4xx` → черновик сохранён, ошибка видна, повторов нет;
- [ ] открытие заново после обрыва восстанавливает текст;
- [ ] негативный контроль: без сохранения черновика тест падает;
- [ ] `node --check` rc=0, версия в паре (`0.12x` ↔ `xdiary-v12x`).

## Граница

Бэкенд/маршруты не трогаем (зона @BE/@DO). Если сервер не принимает клиентский `id` — фиксируем это в карточке как известное ограничение и не выдаём за идемпотентность.
