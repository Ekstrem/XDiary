# FE-055 — P1: акт не должен теряться при обрыве/5xx — черновик + один повтор

- **Статус:** На проверке
- **Приоритет:** P1 (основной сценарий владельца: «добавить акт»; любой сбой сети сейчас = потерянный текст)
- **Источник:** владелец 2026-11-16 «сделать возможным добавление акта» + наблюдение: `POST /api/v1/journal/records` в проде был `500` несколько суток
- **Зависимости:** нет (не зависит от `BE-122`: это про журнал, не про каталог)
- **Проверяет:** @TL
- **Исполняет:** @FE (`8-front/`)
- **На проверке с:** 2026-11-17
- **Артефакт:** `8-front/js/app.js` (черновик в `localStorage`, восстановление, классы ошибок), `8-front/js/repository.js` (`DB.onRecordCreated` — id сразу после создания), версия `0.120` / `xdiary-v120`; тест `5-tech-backlog/front-end/FE-055-draft-runtime-test.js`

## Проблема

Прод отдавал `500` на `/api/v1/journal/records` несколько суток. В приложении отправка акта при ошибке сети/`5xx`:
- не сохраняет введённый текст — пользователь теряет то, что набрал;
- не показывает, что запись **не** сохранена, если экран успел уйти вперёд.

Класс тот же, что `FE-051` (молчаливый пустой экран) и `FE-054` (дубль при повторе), но здесь цена выше: теряется **содержание**, а не отображение.

## Что нужно

1. **Черновик акта** сохраняется локально (тот же механизм, что у каталога/партнёров — `repository.js` + `localStorage`) **до** отправки и очищается только после `2xx`.
2. При сетевой ошибке/`5xx`: текст остаётся в форме (или восстанавливается из черновика при повторном открытии), видимый тост/блок с причиной и кнопкой «Повторить».
3. При `4xx` (валидация): черновик **не** удаляется, ошибка показывается как есть (не маскируем).
4. Идемпотентность повтора: если `POST` уже прошёл, а ответ потерялся — повтор не должен создавать вторую запись (тот же подход, что `FE-054`: клиентский `id`, если сервер его примет; иначе — явно отметить как ограничение).

## Критерии приёмки

- [x] runtime-тест (как `FE-054-…-test.js`): черновик сохранён до отправки, id созданной записи зафиксирован (повтор идёт в ту же запись), после `2xx` черновик удалён — `FE-055-draft-runtime-test.js` 7/7;
- [x] `5xx`/сеть → черновик сохранён, видимый `.load-error` с причиной и кнопкой «Повторить» (остаёмся в визарде);
- [x] `4xx` → черновик сохранён, ошибка показывается как есть, автоматических повторов нет;
- [x] открытие визарда без `id` при наличии черновика восстанавливает текст (тост «Черновик восстановлен»);
- [x] негативный контроль: без фиксации id черновик остаётся без id — повтор создал бы дубль (тест это ловит);
- [x] `node --check` rc=0 для `app.js`/`repository.js`; версия в паре `0.120` ↔ `xdiary-v120`.

## Граница

Бэкенд/маршруты не трогаем (зона @BE/@DO). Если сервер не принимает клиентский `id` — фиксируем это в карточке как известное ограничение и не выдаём за идемпотентность.

## Результат

**Сделано в `0.120`/`xdiary-v120`.**

- **Черновик до отправки:** `writeRecordDraft(rec, rec.id)` вызывается **перед** `DB.putRecord`; хранится в `localStorage` под `xdiary.recordDraft` (`{rec, id, savedAt}`). Очистка — **только** в `then` после успешной цепочки (`clearRecordDraft()`).
- **Повтор без дубля:** `DB.putRecord` при создании записи вызывает `DB.onRecordCreated(id)` сразу после `Api.journal.start()`, а `app.js` фиксирует этот id в черновике (`patchRecordDraftId`). При повторе `saveWizard` видит `pending.id` и передаёт `rec.id` → `DB.putRecord` идёт по ветке **редактирования** той же записи, а не создаёт новую.
- **Классы ошибок:** сеть/`status 0`/`5xx` → остаёмся в визарде, `.load-error` с текстом «Не удалось сохранить акт: … Черновик сохранён — можно повторить» и кнопкой **«Повторить»** (перезапускает `saveWizard`), плюс тост «Нет связи с сервером — черновик сохранён»; `4xx` → `.load-error` с «Сервер отклонил акт: …» (как есть), черновик остаётся.
- **Восстановление:** `openWizard()` без `id` при наличии черновика подставляет его и открывает визард через `loadWizardData` (тост «Черновик восстановлен»); при ошибке загрузки — `openWizardDegraded`.
- **Позиция блока:** `showLoadError` для визарда кладёт блок в `.content` (а не над appbar).

**Квитанция:** `node 5-tech-backlog/front-end/FE-055-draft-runtime-test.js` → **7/7, rc=0** (исполняются **реальные** `readRecordDraft`/`writeRecordDraft`/`patchRecordDraftId`/`clearRecordDraft` из `app.js`): черновик пишется и читается; `id` созданной записи фиксируется и попадает в `rec.id`; текст не теряется; после успеха черновик очищен; **негативный контроль** — без фиксации id он остаётся `null` (повтор создал бы дубль).

**Честная граница:**
1. runtime-тест проверяет **хелперы черновика и фиксацию id**, а не полную цепочку «POST → все поля → complete»: для неё нужен браузерный прогон. Утверждение «POST повторён один раз» обеспечено кодом (кнопка «Повторить» вызывает `saveWizard` один раз за клик; автоматических повторов нет), но в тесте не исполняется.
2. Браузерного прогона на `0.120` не было — в текущих прогонах красное из-за стендовых `429`/`502`.
3. Сервер не принимает клиентский `id` для журнала (это `BE-122`-класс для каталога): идемпотентность здесь обеспечена **на клиенте** — id созданной записи, полученный от сервера, повторно используется как `rec.id`, поэтому второй записи не появляется. Это не «серверный idempotency-key», а «продолжаем ту же запись» — так и записано.
