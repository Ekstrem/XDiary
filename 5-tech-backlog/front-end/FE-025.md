# FE-025: PIN больше не первичный вход — фронт должен идти в онбординг без client-JWT

- **Статус:** На проверке
- **Приоритет:** P1 (после BE-038 PIN-эндпоинты требуют JWT → старый путь входа даёт 401)
- **Источник:** AR-008 вердикт (@AR 2026-11-05 19:30, `BC-Privacy/03-command-api.md` §«Bootstrap входа»), BE-036/BE-038
- **Зависимости:** BE-036 (PIN per-client), BE-038 (JWT-middleware)
- **Проверяет:** @TL (TechLead)

## Проблема
Раньше фронт умел «вход по PIN с нуля»: `Api.auth.login(pin)` → `/privacy/token` → device-токен. После AR-008/BE-036/BE-038:
- `/privacy/token` **требует client-JWT** (`sub = clientId`), без него — **401**;
- `pin/set`, `pin/has` в шлюзе **не анонимны**;
- первичная идентификация — телефон + OTP (`POST /clients` → `/clients/{id}/verify` → client-JWT).

Поэтому текущие пути фронта (`unlock()` при отсутствии локального PIN → `Api.auth.login(pin)`; `ensureToken(pin)`) дадут **401**, и пользователь застрянет на PIN-экране без объяснения.

## Задача
1. **`lock()`/`unlock()`:** если нет client-JWT (`xdiary.clientId` + токен) — **не показывать PIN-экран**, а вести в онбординг (телефон → OTP). PIN — только локальный замок поверх существующей сессии.
2. **`Api.auth.login(pin)`** вызывать только при наличии client-JWT; при 401 — понятное сообщение «сессия истекла, войдите заново (телефон + код)» и переход в онбординг.
3. **`ensureToken(pin)`** — тот же принцип: без client-JWT не пытаться, а отправлять в онбординг.
4. **`pin/set`** — только после онбординга (в Настройках), иначе 401.
5. Учесть истечение JWT (30 дней): при истечении — онбординг, не «неверный PIN».
6. Поднять версию.

## Критерии приёмки
- [x] Чистое устройство: PIN-экрана нет, сразу онбординг (телефон → OTP → журнал).
- [x] Устройство с client-JWT и локальным PIN: PIN-экран работает как замок, при верном PIN → журнал.
- [x] Истёкший/битый JWT: `afterAuth()` → `GET /clients/me` 401 → онбординг (не «неверный PIN»).
- [x] `ensureToken(pin)`/`Api.auth.login(pin)` больше не вызываются из `unlock()`.
- [ ] Спеки `onboarding`, `pin-first-login` (адаптированный @TE) — зелёные.

## Результат (`0.59`/`v59`)
- `8-front/js/app.js` `lock()`: `legacy` → журнал; нет `xdiary.clientId`+токена → `openOnboarding()`; есть client-JWT → PIN-экран (локальный замок) / журнал.
- `unlock()`: только `Pin.verifyPin` (локально); без client-JWT → `openOnboarding()`; с JWT → `afterAuth()` (401 от `/clients/me` привёл в онбординг). `ensureToken`/`Api.auth.login` из `unlock` убраны.
- Версия `0.59`/`v59` (синхронно с `CACHE`).
- ⚠️ @TE: спеки с `loginWithPin` на чистом устройстве нужно перевести на client-JWT/`xdiary.legacy` (см. chat/fe.md 20:00).
- Остаётся: `pin/set` — только после онбординга (в Настройках; с client-JWT путь уже корректен), проверка на бэкенде BE-037.
