# FE-032: P0 — экран PIN без PIN: `ensureView` оставляет замок, если `Pin.hasPin()` не ответил

- **Статус:** В работе
- **В работе с:** 2026-11-08
- **Приоритет:** **P0** (владелец после перезагрузки видит «Введите PIN-код», которого не ставил, и не может пройти дальше)
- **Источник:** владелец 2026-11-08 ~16:00: «после обновления страницы снова увидел PIN, который я не ставил — суперкритичный баг»
- **Зависимости:** FE-027/FE-029 (починка lock-гейта), ADR-021/AR-009 (PIN локальный)
- **Проверяет:** @TL (TechLead)

## Причина (по коду `8-front/js/app.js`)
`ensureView()`: если ни одно view не видно → `showView("lock"); lock();`. Далее, если `view-lock` виден, вызывается `withTimeout(Pin.hasPin(), 5000, false)`; при **ошибке/таймауте** промис уходит в `function (e) { console.error("ensureView/hasPin:", e); }` — **и экран остаётся замком**. То есть любой сбой IndexedDB/таймаут = **вечный PIN-экран у пользователя без PIN** (тупик, без выхода).

## Задача (зона @FE, `8-front/`)
1. **Никогда не оставлять замок при неизвестном `hasPin`:** при ошибке/таймауте считать «PIN нет» и переходить по состоянию токена: есть `accessToken` → `afterAuth()`, нет → `openOnboarding()`.
2. **Явный выход с экрана блокировки:** ссылка/кнопка «Забыли PIN? Войти по телефону» → очищает локальный PIN и ведёт в онбординг (это локальный контур, серверный PIN не нужен).
3. **Диагностика в консоли:** `ensureView: hasPin=unknown (err) → fallback to <afterAuth|onboarding>`.
4. Проверить, что после входа (verify) **PIN не создаётся сам** и замок не показывается, если `hasPin=false`.

## Критерии приёмки
- [ ] Симуляция ошибки `Pin.hasPin()` (например, через отключение IndexedDB/искусственный throw) → приложение уходит в журнал (или онбординг), **не висит на PIN**.
- [ ] На экране PIN есть путь выхода без знания PIN.
- [ ] Владелец после перезагрузки попадает в журнал (подтверждено им).
