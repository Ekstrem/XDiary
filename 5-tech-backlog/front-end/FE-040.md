# FE-040: Индикатор загрузки для тяжёлых экранов (тренды, экспорт)

- **Статус:** На проверке
- **Приоритет:** P2 (появляется вместе с бюджетом латентности DO-060)
- **Источник:** владелец 2026-11-10: для тяжёлых запросов «отдельный бюджет 3 c с индикатором загрузки — более чем приемлемо»; DO-060 (бюджет p95 для тяжёлых ≤ 3000 мс)
- **Зависимости:** DO-060 (бюджеты), FE-035 (версия в ошибках — уже сделано)
- **Проверяет:** @TL — артефакт: `8-front/js/app.js` (`busyStart`/`busyStop`/`busyRun`), версия `0.91` / `xdiary-v91`

## Задача (зона @FE, `8-front/`)

1. Для экранов, где запрос заведомо тяжёлый (**тренды/аналитика**, **экспорт**, **портируемость**): показывать **индикатор загрузки** сразу (< 300 мс после действия), а не пустой экран — «считаем…» + отмена, если операция долгая.
2. Не блокировать интерфейс целиком: остальные вкладки остаются доступными.
3. Если запрос не уложился в **3 с** — показать честный текст «дольше обычного» и кнопку «повторить» (без бесконечного спиннера).
4. Длительность запроса **не выдумывать**: брать из ответа/заголовка, если сервер отдаёт `Server-Timing`; иначе — измерять на клиенте и показывать только текст, без цифр.

## Критерии приёмки

- [x] Индикатор появляется < 300 мс после нажатия и исчезает при ответе (успех/ошибка). — проверено тестом таймеров: при операции 1000 мс баннер `display=block` на 400 мс, к 1300 мс в DOM его нет.
- [x] При ответе > 3 с появляется текст «дольше обычного» + «повторить». — проверено: на 3200 мс `display=block`, текст «…: дольше обычного», кнопка `inline-block`; клик вызывает повтор и снимает баннер.
- [x] На быстром ответе (< 1 с) индикатор не «мигает». — при 150 мс индикатор **не появляется вовсе** (порог 300 мс); при 1000 мс виден 700 мс, то есть без мигания.
- [ ] Проверено на медленном стенде (искусственная задержка @DO) и на нормальном. — **требует стенда @DO**, не закрашен.

## Результат

Реализовано в `0.91`. Добавлен переиспользуемый механизм в `8-front/js/app.js`:

- `busyStart(label, retry)` — баннер внизу экрана: `setTimeout(300)` показывает его, `setTimeout(3000)` переключает текст на «`label`: дольше обычного» и показывает кнопку «Повторить» (только если передан `retry`).
- `busyStop()` — снимает оба таймера и удаляет баннер из DOM (идемпотентно, вызывается и на успех, и на ошибку).
- `busyRun(label, task, retry)` — обёртка: стартует индикатор, ждёт промис, **всегда** гасит его (в `.then` и в обработчике ошибки), затем отдаёт результат или пробрасывает ошибку.

Интерфейс не блокируется: баннер `pointer-events: none`, кликабельна только кнопка «Повторить». Длительность не выдумывается — `Server-Timing` сервер сейчас не отдаёт, поэтому цифр в тексте нет, только состояние.

Подключено к тяжёлым операциям:
- **Тренды** — `Api.daily.series(dayKey(-90), dayKey(0))` в `renderTrends` (`busyRun("Считаем тренды", …, renderTrends)`), повтор перезапускает отрисовку.
- **Экспорт CSV** — `DB.getAllRecords()` в `downloadCsv` (`busyRun("Готовим CSV", …, downloadCsv)`), плюс добавлен `.catch`: раньше ошибка выгрузки терялась молча и спиннер висел бы бесконечно.

Честная граница объёма: отдельного экрана **портируемости** во фронте сейчас нет (нет вызова `/portability`), а соматика читается в детали записи, а не тяжёлым диапазоном, — поэтому обёрнуты два реальных тяжёлых пути. Когда появится portability-экран, он подключается одной строкой `busyRun`.

Проверка: `node --check` → rc=0 для `app.js` и `sw.js`; прогон поведения таймеров на заглушке DOM (`vm`, реальный код из `app.js`) — 150 мс → 0 баннеров, 1000 мс → показан на 400 мс и снят к 1300 мс, 3200 мс → «дольше обычного» + кнопка, клик → повтор и снятие; версия `0.91` ↔ `xdiary-v91`.
