# P0: приложение остаётся на заставке — «не показывает ни одного экрана»

- **Статус:** На проверке
- **Приоритет:** **P0** (базовый сценарий недоступен: ни онбординга, ни замка, ни журнала)
- **Источник:** прогоны `front-e2e` #765/#766/#770/#774 + `9-tests/reports/front-e2e-run-765-triage.md` §6 (@TE, 2026-11-06 04:32–05:07)
- **Зависимости:** `TE-068` (фикстура `syncAt` давала `NaN`), `DO-079` (прогон)
- **Проверяет:** @TL — артефакт: `8-front/js/app.js`, версия `0.96` / `xdiary-v96`

## Факт (из снимков прогонов, а не из рассуждения)

В снимках устойчиво `view-splash: visible`, остальные `hidden`; восемь UI-действий не завершались за 80–90 с.
Цитата @TE: «**сплэш не разрешается, когда API отвечает ошибкой**».

## Причины (две, обе механические)

1. **`ensureView()` считал заставку экраном.** Обход `VIEWS` видел видимый `#view-splash` и выходил с `any = true`, поэтому страховка «через 2 с покажи хоть что-то» **никогда не срабатывала**, если приложение застряло на заставке. Отсюда «все три hidden» в отчётах: они indeed hidden, а видим сплэш.
2. **`Pin.pinInfo()` вызывался без таймаута.** В `lock()` таймаут был только у `Pin.hasPin()` (1.5 с), а `pinInfo` шёл за ним напрямую: при молчащем IndexedDB промис не резолвился — заставка оставалась навсегда, без ошибки в консоли.

## Критерии приёмки

- [x] `splash` исключён из проверки «есть видимый экран» в `ensureView()` — страховка срабатывает;
- [x] `Pin.pinInfo()` под `withTimeout(…, 2000, null)`, при истечении — `showLockScreen()`;
- [x] `node --check` rc=0; версия `0.96` ↔ `xdiary-v96`;
- [ ] прогон `front-e2e` на `0.96`: `view-splash` не застревает, в снимках появляется один из `#view-onboarding`/`#view-lock`/`#view-journal` — **за @TE/@DO (`DO-079`)**, не закрашен.

## Результат

Исправлено в `0.96`.

- `app.js` (`ensureView`, строки ~170–172): в цикле по `VIEWS` добавлено `if (VIEWS[i] === "splash") continue;` с комментарием, зачем это нужно. Теперь `ensureView` при застрявшей заставке переходит в `showView("lock")` / `lock()` и далее — в штатную ветку (`openOnboarding` или `afterAuth`).
- `app.js` (`lock`, ~446): `Pin.pinInfo()` обёрнут в `withTimeout(Pin.pinInfo(), 2000, null)`; при `null` срабатывает существующая ветка `showLockScreen()`, то есть экран появляется вместо вечной заставки.

Проверено @TE по `origin`: «`ensureView()` больше не считает `splash` экраном (`app.js:170-172`), `Pin.pinInfo()` — под `withTimeout(…, 2000, null)` (`app.js:446`). Это ровно тот механизм, который я видел в снимках».

**Связанное, что НЕ является этим дефектом** (зафиксировано, чтобы не чинили дважды):
- `partner-edit`: `POST /partners/{id}/name` → `400 Partner not found` — партнёра удалил **другой параллельный прогон** между шагами (гонка тестовой среды, вывод @TE 04:57), код фронта тут ни при чём;
- `stale-note`: причина была в фикстуре — `syncAt.partners: NaN → NaN`, свежесть считалась неопределённой; исправлено в `TE-068`;
- `catalog-archive` (модалка `#confirm-modal` не появлялась) — проверено: `#btn-catalog-delete` показывается только при непустом `id`, и `editingCatalogId` ставится из того же `id`, поэтому ранний `return` в `deleteCatalogEdit()` при видимой кнопке недостижим; наиболее вероятно это тот же симптом зависания, а не отдельный дефект состояния — окончательно решает прогон на `0.96`.
