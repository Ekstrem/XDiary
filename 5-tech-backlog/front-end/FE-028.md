# FE-028: Обновление client-JWT по refresh-токену вместо выброса в онбординг

- **Статус:** ToDo
- **Приоритет:** P1 (после BE-041; сейчас через 15 минут пользователь теряет сессию)
- **Источник:** @AR 2026-11-02 17:26 (access 15 мин + refresh 30 дней, `POST /clients/refresh`), FE-025/FE-027
- **Зависимости:** BE-041 (эндпоинт refresh), BE-040 (401 на `/clients/me`)
- **Проверяет:** @TL (TechLead)

## Проблема
Сейчас на любой 401 фронт уходит в онбординг (`afterAuth().catch → openOnboarding()`, `withTimeout` из `0.61`). При access-токене в 15 минут это означает: **каждые 15 минут пользователь «вылетает»** и должен заново вводить телефон и код.

## Задача
1. **Хранить refresh**: при `/verify` сохранять `xdiary.refreshToken` (+ `expiresAt`), access — как сейчас.
2. **Обновление вместо выброса:** при 401 от API — **одна** попытка `POST /api/v1/clients/refresh` с refresh-токеном; при успехе — сохранить новую пару и **повторить исходный запрос**; при неудаче — онбординг (как сейчас).
3. **Однократность:** параллельные 401 не должны запускать несколько refresh — один «inflight» промис, остальные ждут его.
4. **Не зациклиться:** если refresh вернул 401 — больше не пробовать, уходить в онбординг.
5. **Онбординг после успеха** — не показывать, если сессия восстановлена.
6. Версия/кэш: поднять `APP_VERSION` и `CACHE` (`sw.js`) синхронно.

## Критерии приёмки
- [ ] Через 15+ минут (или при принудительно истёкшем access) приложение **не показывает онбординг**, а обновляет токен и продолжает работу.
- [ ] При истёкшем/битом refresh — онбординг с понятным сообщением.
- [ ] Параллельные 401 не дают шторма refresh-запросов (проверяется в E2E: счётчик вызовов).
- [ ] `front-e2e` зелёный; `seedSession` в тестах кладёт и refresh (по согласованию с @TE).
