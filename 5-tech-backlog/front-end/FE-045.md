## Факт (из прогона, не из рассуждения)

Шаги спеки (`add-partner.spec.js:10-22`): вход по PIN → `#tab-partners` → `#btn-partner-add` → заполнить `#pe-name` → **`#btn-partner-save`** → ожидание `#view-partners` (5 с) → `#partners-list` содержит имя.


Снимок в момент падения: пользователь **на экране `#view-partner-edit`**, заголовок «Новый партнёр», поле `Имя` заполнено `TE-1793906639517`, кнопка «Сохранить» на месте — то есть нажатие **не привело ни к возврату в список, ни к видимой ошибке**.

## Где смотреть в коде (`8-front/js/app.js`, `savePartnerEdit()` 1287-1344)

- `1305` → `DB.putPartner(...)` (POST создания), `1308` → `.then(created => ...)`;
- `1311-1319` → после создания вызывается `linkClient(pid, cid)`; при ошибке ставится `partnerLinkWarning`, промис **резолвится**;
- `1322-1332` → если `partnerLinkWarning` непустой: `toast(warn)` и **`return`** ⇒ **навигации нет** (ровно наблюдаемое);
- `1343` → `.catch` → `toast(текст ошибки сохранения)` ⇒ при отказе POST тоже **остаёмся на форме**.

**Гипотеза для проверки:** `PartnersController.Register` (`:24-27`) **уже** проставляет `ClientId` из `sub`, поэтому `linkClient` после создания может быть **избыточным** — и тогда ветка (а) срабатывает без реальной причины.

## Задача

1. Снять точный статус и тело ответов на `POST /api/v1/partners` и `POST /api/v1/partners/{id}/link-client` при этом клике (DevTools/Network или Playwright trace).
2. Если 4xx — показывать понятную ошибку и **не терять** введённые данные; если 2xx — исправить навигацию.
3. Проверить избыточность `linkClient` после `Register` (см. гипотезу) и сделать путь терпимым к 200/204, если связь уже есть.

## Критерии приёмки

- `npx playwright test tests/add-partner.spec.js` → **1 passed**, созданный партнёр есть в списке;
- при искусственной ошибке API — **видимый** текст ошибки, введённое имя сохранено в форме;
- `check_front_readpath` и `check_front_specs_base` остаются `rc=0`.
