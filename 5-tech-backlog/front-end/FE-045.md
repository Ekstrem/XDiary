## Результат

**Исправлено в `0.95` (коммит `26b12587`); причин было две.**

1. **Навигация зависела от предупреждения (главная).** В `savePartnerEdit()` ветка `if (partnerLinkWarning) { toast(warn); … return; }` прерывала обработчик **до** перехода в список. Теперь предупреждение показывается тостом, а `showView("partners")` + `renderPartners()` выполняются **всегда** (ветки `wizard`/`onboarding` — по `partnerEditReturn`).
2. **Лишний `profile` в цепочке создания.** `needProfile(p)` — вызов только если `photo` непустой, `gender ≠ female` или `notes` непустые; плюс `retryOnce()` — один повтор через 200 мс на `400`/`404` для `profile` и `linkClient` с логом `retry after lag`. На `register`/`remove` повтор не распространяется.

**Как проверялось (артефакты, не слова):**

## Минимальная правка, снимающая гонку для базового сценария (@TL 2026-11-05 22:4x)

Проверено по коду: при открытии формы «Новый партнёр» **дефолты пустые** —
`partnerEditPhotoData = ""` (`app.js:1265`), `partnerEditGender = "female"` (`:1266`), `notes` пусто (`:1262`).

Значит для сценария «ввёл имя → Сохранить» вызов `profile` **ничего не меняет по смыслу**
(кроме приведения `gender` из `""` в `"female"`, что фронт и так подставляет при чтении: `p.gender || "female"`).

**Предложение (уменьшает и число запросов, и окно гонки):**

```js
// DB.putPartner (repository.js:182-186): после register
var id = m.id;
var needProfile = !!p.photo || (p.gender && p.gender !== "female") || !!p.notes;
if (!needProfile) { p.id = id; return p; }
return Api.partners.profile(id, {...}).then(...)
```

и, на случай проекционной задержки, **один retry** для идемпотентных вызовов `profile`/`link-client`
(400/404 → пауза 200 мс → повтор один раз), с логом «retry after lag», чтобы это не превратилось в
молчаливое скрытие настоящей 400.

**Важно:** retry **не** должен применяться к `register` (создание второй сущности) и к `remove` без id-проверки.
