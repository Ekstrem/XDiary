# FE-047: ветка «номер уже зарегистрирован» в онбординге — приведена к контракту `409`, ждёт `BE-092`

- **Статус:** В паузе
- **Приоритет:** P2 (не блокирует вход: путь «новый номер» работает; повторный вход на новом устройстве упирался в тупик)
- **Источник:** @TL `2026-11-06 21:42`/`21:44`; @AR `22:24` (финал: `409` + структура, `api-index.yaml:177–184`, `edm-canon` §17); мой разбор `fe.md 21:42`/`22:21`
- **Зависимости:** `BE-092` (`delivery` в `200`, `409` со структурой), `BE-090` (не отдавать `otpCode`)
- **Проверяет:** @TL
- **Пауза:** фронтовая часть готова (`0.101`), проверять нечем — сервер пока отдаёт `400` строкой и `409` не возвращает
- **Разблокирует:** @BE (выкатка `BE-092`) + решение по каналу OTP (@EX)

## Действующий контракт (единственный, финал)

`api-index.yaml` стр.177–184 + `edm-canon` §17:

| Код | Когда | Тело |
|---|---|---|
| `200` | новый номер | `id, version, phone, otpExpiresAt, verified, delivery` |
| `409` | номер уже зарегистрирован | **структурированное** `{error, clientId, delivery}`, код переотправлен |
| `400` | неверный телефон/OTP | строка |
| `429` | лимит переотправки | 1/60с на клиента, 5/час на номер |

Отдельной операции переотправки **нет**: её роль выполняет повторный `POST /clients` → `409`.

## Факт (проверено по коду в `origin`)

- Фронт до `0.100`, `app.js:391-399`: на `400`/`409` брал `clientId` из тела ошибки, которого сервер не отдавал → ветка не срабатывала, при пустом `storedClientId()` пользователь застревал на форме.
- Сервер, `ClientsController.cs:29`: `return BadRequest(result.ErrorMessage())` — плоская строка, `409` не возвращается. Это то, что закрывает `BE-092`.

## Что уже сделано во фронте

- `0.98`: текст ветки перестал обещать повторную отправку, пока её не подтверждает сервер.
- `0.99`: кнопка «Запросить код заново» — `disabled` + `aria-disabled` + честная подсказка (операции переотправки в API нет: `git grep -i resend` по `6-msa` → пусто).
- `0.100`: ветка `409` читает `clientId` и `delivery`; `429` вынесен отдельной веткой.
- `0.101`: `delivery` читается **и в `200`, и в `409`** через общий `deliveryHint()`, поэтому UI не зависит от того, какая ветка вернёт код.

## Критерии приёмки

- [x] контракт зафиксирован в файле (`api-index.yaml:177–184`) и в каноне (§17), а не только в чате;
- [x] фронт читает `409` (`clientId`) и `delivery` в трёх состояниях (`ok=true` / `ok=false` / поля нет);
- [x] `429` не путается с «код неверный»;
- [x] `node --check` rc=0, версия в паре (`APP_VERSION` ↔ `CACHE`);
- [ ] на стенде после `BE-092`: `POST /clients` на занятом номере → `409` с реальным `clientId` и `delivery`; кнопка переотправки включается, тест «новое устройство + занятый номер» проходит.

## Результат

Контракт доведён до одного состояния; из карточки убраны промежуточные варианты, которые контрактом **не стали** — идемпотентный `200` (@TL `21:44`), строка `400` с признаком (@AR `21:45`, коммит `47d1f920`), `POST /clients/verify` (@TL `21:49`): все три отклонены, `verify` остаётся кандидатом на будущее и в контракте его нет.

Фронт приведён к финалу в `0.101`/`xdiary-v101`. Осталось внешнее: выкатка `BE-092` (форма ответа) и канал OTP (@EX) — без канала `delivery.ok` будет честным, но `false`.
