- **Статус:** В паузе
- **Приоритет:** P2 (не блокирует вход: путь «новый номер» работает; но повторный вход на новом устройстве упирается в тупик)
- **Источник:** @TL `2026-11-06 21:42`/`21:44`; @AR `21:42` (решение «`delivery` только в 200»); мой разбор `fe.md 21:42`
- **Зависимости:** `BE-092` (`delivery` в `POST /clients`), `BE-090` (не отдавать `otpCode`)
- **Проверяет:** @TL
- **Пауза:** нет решения по операции входа для занятого номера. Контракт `POST /clients` окончателен (`21:49`, @TL/@AR): `delivery` только в `200`, тело `400` — строка, `409` и структурированный конверт **отменены**. Открыт вопрос @TL: вводить ли новую операцию `POST /api/v1/clients/verify` с телом `{phone, code}` (проверка по номеру, без `id`) — если да, мёртвая ветка **удаляется** целиком
- **Разблокирует:** @AR (контракт) + @BE (реализация)

## Факт (проверено по коду в `origin`, не по пересказу)

- Фронт, `8-front/js/app.js:391-399`: на `400`/`409` от `POST /clients` пытается взять `clientId` из **тела ошибки** (`e.data.clientId || d.aggregateId || d.id`), иначе — из `storedClientId()`.
- Сервер, `6-msa/BC-Client/src/Client.Api/Controllers/ClientsController.cs:29`: на любом отказе `return BadRequest(result.ErrorMessage())` — тело **плоская строка**, `clientId`/`aggregateId`/`delivery` в нём нет; `409` не возвращается вовсе.
- Следствие: ветка «номер уже зарегистрирован → сразу к вводу кода» **не срабатывает**; при пустом `storedClientId()` пользователь видит текст и остаётся на форме — показать экран ввода кода нечем.

Дополнительно в `0.99`: кнопка «Запросить код заново» (`#btn-onb-resend`) — `disabled` + `aria-disabled` с подсказкой, потому что операции переотправки в API нет вовсе (`contract_gap` в `api-index.yaml`, проверка `git grep -i resend` по `6-msa` → пусто).

Обновлено в `0.98`: текст ветки больше не обещает повторную отправку («Если код приходил ранее — введите его; если нет — нажмите „Запросить код заново“»), потому что доставку сервер не подтверждает.

## Возможные решения (одно из них снимет эту карточку)

1. **Идемпотентный `200`** (предложение @TL `21:44`): для существующего номера — тот же успешный ответ, что и для нового, включая `delivery`. Тогда ветка **удаляется**, у фронта один путь. **Статус: не принято.**
2. **Строка `400` с явным признаком повторной отправки** — текущее решение @AR (откат `47d1f920`, 21:46): тело ошибки остаётся строкой, `409` не вводится. Тогда ветка **не удаляется**, а ждёт от @BE признака в тексте; фронт опознаёт его и поднимает формулировку до «код отправлен повторно», иначе оставляет текст `0.98`. **Статус: действующее.**
3. ~~Структурированный отказ `409` / конверт `{reasons, aggregateId, delivery}`~~ — **отклонено** @AR (`47d1f920`) и подтверждено @TL (`21:49`): error-envelope для всех операций не меняется.
4. **Новая операция `POST /api/v1/clients/verify` с телом `{phone, code}`** (предложение @TL `21:49`): проверка кода **по номеру**, без `id`. Закрывает дыру, которую откат не закрывает: при занятом номере `clientId` из `400` не приходит, `storedClientId()` пуст — показать экран кода нечем. Тогда фронт **перестаёт зависеть от `clientId`**, и мёртвая ветка исчезает. **Статус: ждёт решения** (вопрос продуктовый: можно ли проверять код по номеру без входа).
