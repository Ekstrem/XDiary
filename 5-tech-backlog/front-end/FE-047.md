# FE-047: ветка «номер уже зарегистрирован» в онбординге — мертва, ждёт решения по `POST /clients`

- **Статус:** В паузе
- **Приоритет:** P2 (не блокирует вход: путь «новый номер» работает; но повторный вход на новом устройстве упирается в тупик)
- **Источник:** @TL `2026-11-06 21:42`/`21:44`; @AR `21:42` (решение «`delivery` только в 200»); мой разбор `fe.md 21:42`
- **Зависимости:** `BE-092` (`delivery` в `POST /clients`), `BE-090` (не отдавать `otpCode`)
- **Проверяет:** @TL
- **Пауза:** нет решения @AR/@BE по форме ответа для существующего номера — **идемпотентный `200`** против **`409`/`400`**; без него непонятно, удалять ветку или переписывать
- **Разблокирует:** @AR (контракт) + @BE (реализация)

## Факт (проверено по коду в `origin`, не по пересказу)

- Фронт, `8-front/js/app.js:391-399`: на `400`/`409` от `POST /clients` пытается взять `clientId` из **тела ошибки** (`e.data.clientId || d.aggregateId || d.id`), иначе — из `storedClientId()`.
- Сервер, `6-msa/BC-Client/src/Client.Api/Controllers/ClientsController.cs:29`: на любом отказе `return BadRequest(result.ErrorMessage())` — тело **плоская строка**, `clientId`/`aggregateId`/`delivery` в нём нет; `409` не возвращается вовсе.
- Следствие: ветка «номер уже зарегистрирован → сразу к вводу кода» **не срабатывает**; при пустом `storedClientId()` пользователь видит текст и остаётся на форме — показать экран ввода кода нечем.

Обновлено в `0.98`: текст ветки больше не обещает повторную отправку («Если код приходил ранее — введите его; если нет — нажмите „Запросить код заново“»), потому что доставку сервер не подтверждает.

## Два возможных решения (одно из них снимет эту карточку)

1. **Идемпотентный `200`** (предложение @TL `21:44`): для существующего номера — тот же успешный ответ, что и для нового, включая `delivery`. Тогда ветка **удаляется**, у фронта один путь.
2. **Структурированный отказ** (`409` или `400` с конвертом `{reasons, aggregateId, delivery}`): тогда ветка **переписывается** под него (и `delivery.ok=false` тоже даёт честный экран).

## Критерии приёмки

- [ ] зафиксировано решение: идемпотентный `200` **или** структурированный отказ (`409`/`400` с полями);
- [ ] реализовано соответствующее поведение фронта: при (1) — ветка `400`/`409` удалена, код идёт по `200`; при (2) — ветка читает `aggregateId`/`delivery` и показывает три состояния;
- [ ] проверено на сценарии «номер уже есть, новое устройство» (пустой `storedClientId`): пользователь либо попадает на ввод кода, либо видит честный отказ — без «застрял на форме»;
- [ ] `node --check` rc=0, версия в паре (`APP_VERSION` ↔ `CACHE`).

## Результат

Не начато — карточка на паузе до решения (см. `Пауза:` / `Разблокирует:`). Заведена по прямой просьбе @TL `21:44`: «зафиксируй в карточке, что ветка `app.js:391-399` мертва и её надо либо удалить (при идемпотентности), либо переписать (при 409)».
