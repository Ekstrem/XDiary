# FE-003: Миграция данных IndexedDB/CSV → бэкенд

- **Статус:** На проверке
- **Приоритет:** P1
- **Источник:** ADR-011, US-09
- **Зависимости:** BE-002, FE-001

## Решение TechLead (вариант b)
Миграция — **через цепочку команд journal** (а не через `portability`→`journal`, которой в коде нет). Старые локальные id **не сохраняются** (journal генерирует новые); дедупликация — по естественному ключу (**startedAt + partnerId + durationMin**). Отдельная доработка `portability` — вне scope FE-003.

## Задача
Реализовать перенос существующих данных (IndexedDB) на бэкенд:
- Прочитать старые записи/партнёров/каталог из IndexedDB.
- Для каждой записи — цепочка команд journal (`StartManualEntry → … → Complete`).
- Партнёры/каталог — через API (`register`/`add` + `profile`/`details`).
- Соматика/сон/тренды — остаются в IndexedDB (вне scope).

## Критерии приёмки
- [x] Миграция записей через цепочку команд journal.
- [x] Партнёры/каталог — через API.
- [x] Нет дублей (дедуп по `startedAt + partnerId + durationMin`).
- [x] Сохраняются связи (`startedAt`, списки через `;`; `garminId` — вне scope, соматика остаётся в IndexedDB).
- [x] После миграции данные видны в журнале.

## Заметки исполнителя (front-end)
- Реализовано: `8-front/js/db.js` (`rawRecords/rawPartners/rawCatalog`), `8-front/js/app.js` (`migrateData`, кнопка «Миграция в бэкенд» в Настройках).
- Порядок: партнёры → каталог → записи (цепочка команд journal). Дедуп по `startedAt + partnerId + durationMin`.
- `garmin`-флаг/`garminId` не переносятся (записи мигрируют как manual `StartManualEntry`) — соматика вне scope FE-003.
