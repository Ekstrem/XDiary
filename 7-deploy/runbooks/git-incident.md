# Ранбук: git-инцидент (повреждённые метаданные, «не могу запушить»)

> Норма процесса — `AGENTS.md` §5.3 (STOP и один восстановитель) и §5.5 (пуш одной командой).
> Инструмент синхронизации — `tools/git_sync.py`; «почему так» — там же в шапке файла.

- **Класс:** повреждённые метаданные git (`.git/rebase-merge` без `head-name`), «роль не может запушить», потеря работы в общем дереве
- **Владелец:** `@DO` (инструмент), **восстанавливает один — координатор** (`@TL`)
- **Когда применять:** `git_sync` печатает «найден незавершённый rebase»; `git rebase` не стартует с «could not read head-name»; коммиты «исчезли» из `origin`; несколько ролей одновременно чинят дерево
- **История:** инциденты 2026-11-02 (`51315b5`) и 2026-11-02 (`21f50145`) — одинаковая подпись: в `.git/rebase-merge` **только** `autostash`

## 1. Диагностика — только чтением

```bash
# 1) какие маркеры есть (ничего не удалять!)
for p in .git/rebase-merge .git/rebase-apply .git/MERGE_HEAD .git/index.lock; do
  printf '%-24s %s\n' "$p" "$(test -e "$p" && echo ЕСТЬ || echo нет)"
done
# 2) что внутри rebase-каталога
ls -la .git/rebase-merge 2>/dev/null
# 3) SHA автостэша — записать ДО любых действий
cat .git/rebase-merge/autostash 2>/dev/null
# 4) git вообще работоспособен?
git branch --show-current; git rev-parse --short HEAD; git status --porcelain | head
```

**Правило:** SHA автостэша записывается в чат **короткой формой** (полный — в файле). Полный 40-символьный хеш ловится гейтом `guard-secrets` как `hex-long`, поэтому в чат — 8 символов и пометка «полный в `.git/rebase-merge/autostash`».

## 2. Объявление, потом действия

Одна строка `→ всем` в свой outbox: что найдено, что записано, что **не трогал**. Пока не прозвучало «работа возвращена» — `.git/` не трогает никто, кроме координатора. Параллельные восстановители опаснее повреждения.

## 3. Восстановление (делает координатор)

```bash
git rebase --abort                  # если метаданные целы
git stash apply <SHA автостэша>     # если работа была в стэше
git stash list                      # проверить, что стэш не потерян
```

Если `--abort` не работает («could not read head-name») — метаданные повреждены: объявить `→ всем`, восстановление за координатором, автостэш спасать через `git stash apply <SHA>`.

## 3a. Если состояние «пустое» — его можно снять одной командой

Пустое состояние = `.git/rebase-merge` **без** `head-name`/`onto`, внутри **только** `autostash`.
Именно так остаётся после `rebase --autostash` на грязном дереве (три инцидента 02.11).

```bash
python tools/git_sync.py --role <роль> --fix-state
```

Что он делает и чего не делает:

- печатает **SHA автостэша** (короткой формой) до удаления;
- **отказывается**, если этого автостэша нет в `git stash list` (иначе работа пропадёт);
- удаляет **только** пустой `rebase-merge` и печатает, что именно удалил;
- живой rebase (`head-name`/`onto` на месте) **не трогает** — возвращает код 2 и просит §5.3;
- после успеха просит повторить обычный запуск (сам не пушит).

Corner-case (@TL 10:10): если пустое состояние осталось после того, как автостэш **уже применили**
и запись из stash убрали, предохранитель не должен отказывать навсегда. Проверка:

    git diff --quiet <SHA автостэша>   # код 0 = изменения уже в дереве
    python tools/git_sync.py --role <роль> --fix-state --force-drop-autostash

Без --force-drop-autostash снятие **не** произойдёт, а команда объяснит, чего не хватает.
Если же изменения **не** в дереве — отказ при любом флаге: сначала git stash apply <SHA>.

Решение о «пустоте» проверяется тестом `tools/test_git_sync_state.py` в `ci-guards`.

## 3b. Стеши после инцидента — разобрать, а не забыть

После нескольких инцидентов в дереве копятся записи вида `autostash` / `lm-docs`. Они **не пустые**:
в каждом лежит чья-то работа. Порядок:

```bash
git stash list                                   # список + короткие SHA
git stash show --name-only stash@{0}             # чьи файлы
# решение по файлам, затем:
git stash apply stash@{0}                        # восстановить
git stash drop  stash@{0}                        # или объявить мусором, ЗАПИСАВ SHA в чат
```

Правило: `git stash clear` **не применяем** — он сносит всё без разбора.

## 3c. Правило, обязательное для всех ролей

**Ручной `rebase`/`rebase --autostash` в общем дереве не запускаем.** Только:

- `python tools/git_sync.py --role XX` (сам откажет на untracked и на пустом rebase-состоянии);
- либо ветка `hold/<role>` (`git_sync --hold`), если очередь занята.

Причина: три инцидента подряд (02.11 — трижды) имели **одну подпись** — `.git/rebase-merge`
только с `autostash`. Пока `rebase` запускают руками, подпись повторится.

**Один восстановитель.** Пока координатор не сказал «работа возвращена», `.git/` не трогает никто.

### Разбор стешей — как это делается на практике (02.11)

После инцидентов накопилось четыре записи. Снимали **не «как мусор»**, а по содержимому:

```bash
git stash show --name-only stash@{N}      # какие файлы
git show stash@{N}:8-front/js/app.js      # что именно внутри
```

Что показала проверка: `autostash` — старые версии (фронт `0.66` при текущем `0.69`,
`chat_lint.py` без `find_multiline`), `lm-docs` — «0 строк, которых нет в HEAD», а две строки чата,
которых нет в файлах ролей, **сохранились в архиве `_dialogue.md`**. Потери нет — поэтому удаление
было законным. Вывод: SHA писать в чат **до** любых действий (мы так и делали — все четыре
восстановимы до `gc`).

## 4. Проверить, что работа не потеряна

```bash
git fetch origin
git merge-base --is-ancestor <мой SHA> origin/main && echo "в origin"
git log --oneline origin/main..HEAD        # что ещё не доехало
```

Если ветка содержит **удаления** чужих строк относительно `main` — её **нельзя** мержить (критерий D-08: diff ветки — только добавления; удаление чужих строк — стоп). Такую ветку удаляют, а её содержимое переносят обычным коммитом.

## 5. Профилактика (уже в репозитории)

| Что | Где | Что делает |
|---|---|---|
| Предохранитель untracked | `tools/git_sync.py` | при `??`-файлах и без `-u` **отказывает до** `fetch`/`rebase` (код 1) — путь «`rebase --autostash` на грязном дереве» недостижим |
| Регресс-тест предохранителя | `tools/test_git_sync.py` | требует код 1, «ВНИМАНИЕ», имя файла и **отсутствие `TypeError`** |
| Шаг теста в CI | `.github/workflows/ci-guards.yml` | правку предохранителя нельзя влить без проверки предохранителя |

Альтернатива пушу при занятой очереди — ветка `hold/<role>` (`git_sync --role XX --hold`): `main` не трогается, тяжёлые workflow слушают только `main`.

## 6. Негативный тест (проверка, что предохранитель жив)

## 7. Грабли

- `rebase --autostash` в цикле с `push` оставляет `.git/rebase-merge` без `head-name` — не запускать вручную в общем дереве.
- В `git_sync.py` был `say("   ?", name)` при `def say(text="")` → `TypeError` **до** пуша; чинилось `say("   ? " + name)`. Урок: предохранитель тоже нуждается в тесте.
- Копия инструмента — в `LoopMaker/tools/`: правку делать **в обоих местах**, иначе `sync_tools --pull` откатит фикс.
- Ссылаться на SHA можно только после `git merge-base --is-ancestor`: `rebase` переписывает коммиты.
