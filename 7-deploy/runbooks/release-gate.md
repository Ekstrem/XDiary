## 1. Проверка перед началом (Definition of Ready-to-ship)

Проверять **по API/логам, а не по памяти**:

```bash
# 1) гейт: прогон завершился САМ и зелёный (не cancelled, шагов не 0)
gh run view <run> --json status,conclusion,jobs
# 2) образ на проде — тот ли, что ждём
ssh <прод> "sudo podman inspect ghcr.io/ekstrem/xdiary-client:single --format '{{.Created}}'"
# 3) ключи OTP на проде на месте (без печати значений)
ssh <прод> "sudo grep -c '^Otp__' /opt/xdiary/7-deploy/secrets/.env"
# 4) очередь CI пуста
gh run list --workflow deploy.yml --limit 5
```

Готово к релизу, только если: `test` зелёный **и** `front-e2e` зелёный **и** завершились сами.

## 2. Шаги

1. **Смержить/дождаться `deploy-dev`** — прод идёт только после dev.
2. **`smoke-api`** (health + API-E2E) и **`smoke-front`** (Playwright) — это **два разных гейта**;
   `deploy-prod` требует `smoke-api=success` **и** (`smoke-front=success` **или** фронт не менялся).
3. **`deploy-prod` запускается автоматически** — руками не деплоить.
4. **Проверить, что на проде доехал именно новый образ** (не «контейнер Up»):
   ```bash
   ssh <прод> "sudo podman inspect xdiary-client --format 'created={{.Created}}'"
   ssh <прод> "sudo podman exec xdiary-client sh -c 'grep -ac TelegramOtpSender /app/Client.Application.dll'"
   ssh <прод> "sudo podman exec xdiary-client sh -c 'grep -ac AddJwtBearer /app/Client.Api.dll'"
   ```
   Ожидание: дата сегодняшняя, оба `grep` = `1`. `0` = старая версия, и релиз не состоялся.
5. **Проверить API прода:** `/health` = 200; `GET /api/v1/clients` = **401**
   (ADR-026: список закрыт, 200 здесь — дефект!), `POST /api/v1/clients` с пустым телом = **400**
   (онбординг жив), `GET /clients/me` = **401**.
6. **Отдать владельцу на вход по коду** — это единственная настоящая проверка OTP.

## 4. Грабли (из реальных случаев)

- **`cancelled` ≠ зелёный.** За 2026-11-02 пять пушей вытеснили друг друга (`#977`–`#983`,
  у всех 0 шагов), и версия 0.65 **ни разу не проверялась**. Гейт — лотерея, если пушить чаще,
  чем прогон успевает стартовать: нужно окно тишины.
- **Один гейт на всё = блокировка не того.** Пока `smoke` был общий, фронтовый баг держал
  доставку бэкенда; отсюда `diff-paths` и два `smoke`-джоба (DO-035).
- **«Контейнер Up» не значит «образ новый».** Единственная проверка — `grep` по содержимому
  dll (или дата `created` у образа).
- **Ручной `podman pull` на проде как «быстрый обход»** — запрещён: он скрывает дефект гейта
  и делает доставку невоспроизводимой (`AGENTS.md` §5.4).
- **OTP не заработает без нового образа.** Ключи в `.env` есть, а `TelegramOtpSender` в старом
  образе отсутствует — и «OTP не приходит» ищут в ключах.
- **Прод-`/` отдаёт 502** — это известное состояние (фронт на Pages), не дефект релиза.

## 7. «Код в образе» и откат — только с контрольной строкой (P0 2026-11-10)

Инцидент `INCIDENT-2026-11-10-PII`: прод 30 минут отдавал `GET /api/v1/clients` = **200
со списком клиентов и телефонами**, при `/health` = 200. Два «разумных» способа проверки
показали «всё в порядке».

**Почему HTTP не доказывает ничего:** на проде **все** неанонимные пути отдают `401`
(ставит шлюз до маршрутизации), и **выдуманный путь тоже 401**. По коду ответа нельзя
отличить «маршрута нет» от «нужен токен».

Проверять только по содержимому сборки, **с контрольной строкой**:

```bash
IMG=ghcr.io/ekstrem/xdiary-client:single
ssh <прод> "sudo podman pull -q $IMG"

# КОНТРОЛЬ: grep вообще работает. Без этой строки «0 находок» ничего не значит.
ssh <прод> "sudo podman run --rm --entrypoint sh $IMG -c \"grep -ac 'api/v1/clients' /app/Client.Api.dll\""

# что проверяем: шим и профиль
ssh <прод> "sudo podman run --rm --entrypoint sh $IMG -c \"grep -ac 'link-partner' /app/Client.Api.dll\""
ssh <прод> "sudo podman run --rm --entrypoint sh $IMG -c \"grep -ac 'me/profile'   /app/Client.Api.dll\""
```

`--entrypoint sh` обязателен: приложение падает на старте на guard'е `Otp:Channel=log`
и не даёт посмотреть файлы.

**Гейт в CI:** в `deploy.yml`, job `deploy-prod`, перед `update.sh` стоит `GUARD`:
тянет образ, проверяет контрольную строку и обе ключевые; при отсутствии любой —
`GUARD_FAIL` и выкатка не начинается. Условие снятия guard'а: в `main` есть шим + профиль,
и первый корректный билд прошёл (дальше это дублирует `smoke-api`).

**Откат образа — проверять три поля, иначе откат фиктивный:**

```bash
podman inspect xdiary-<svc> --format '{{.Image}}'                       # тот ли образ
podman inspect xdiary-<svc> --format '{{len .HostConfig.ExtraHosts}}'   # ожидаемое число адресов
podman inspect xdiary-<svc> --format '{{.Config.Cmd}}'                  # ДОЛЖНО быть [] / Entrypoint-дефолт
```

Реальный случай: `recreate-service.sh --image` подменял хвостовой `>/dev/null` вместо
образа; флаги `--add-host` уходили **после** образа → попадали в `Cmd`; контейнер
создавался на **старом** образе, а скрипт печатал «OK». Спасли только пост-проверки
(`ExtraHosts=0, ожидалось 10`). **Инструмент, который печатает OK, не проверив результат,
опаснее отсутствия инструмента.**

**Псевдоним `clients` — отдельная проверка.** Маршруты шлюза ходят на имя **`clients`**
(множественное), контейнер называется `xdiary-client`. Список `--add-host` нельзя собирать
«по именам контейнеров»: псевдоним берётся из `gen-hosts.py`/`SERVICE_IPS`.

```bash
podman exec xdiary-api-gateway grep -c ' clients$' /etc/hosts   # >= 1
```

Иначе `GET/POST /api/v1/clients` → **502** при живом `/health`.

### После `podman restart` шлюза — сразу проверять `/health` до 200

`restart` шлюза — это не «мгновенно»: пока приложение поднимается, внешний вход отдаёт
**502 на всё**, включая `/health` (Caddy: `dial tcp 127.0.0.1:8080: connection refused`).
Реальный случай 2026-11-10: после `podman restart` я увидел 502 на всех путях и почти
принял это за дефект — это было окно пересоздания.

Правило: после `restart`/пересоздания шлюза **дождаться `/health` = 200 в цикле** и только
потом мерить внешние коды. Иначе «restart» означает «сколько-то минут недоступности, о
которой никто не знает».

```bash
for i in $(seq 1 18); do
  code=$(curl -s -o /dev/null -w '%{http_code}' -m 6 http://127.0.0.1:8080/health)
  [ "$code" = "200" ] && break; sleep 5
done
echo "health: $code"
```

### Литералы в .NET-сборке — только UTF-16, иначе «0» врёт

`grep -a 'male' Client.Domain.dll` даёт **0** даже когда литерал есть: в .NET строки
хранятся в **UTF-16LE** (`m\0a\0l\0e\0`), а `grep` ищет ASCII. Второй капкан: `strings`
в runtime-образе **нет** — команда не найдена, вывод пустой, и это легко прочитать как
«совпадений нет».

Правильный способ — UTF-16-паттерн в `grep -P`, **всегда с контрольной строкой**:

```bash
podman exec xdiary-client sh -c 'grep -acP "m\x00a\x00l\x00e\x00" /app/Client.Domain.dll'   # ожидание 1
podman exec xdiary-client sh -c 'grep -ac "UpdateProfile" /app/Client.Domain.dll'               # КОНТРОЛЬ: 1
```

Контроль обязателен: без него «0» не отличает «нет литерала» от «команда не сработала» —
это тот же класс ошибки, что «вердикт по тексту вместо `rc`».

### Пересоздание шлюза: `Jwt__SigningKey` — обязательный env

Шлюз **сам валидирует** access-токен. Если при пересоздании потерять `Jwt__SigningKey`,
он поднимается, `/health` = 200, `GET /clients` = 401 (выглядит «правильно»), но
**все авторизованные вызовы дают 401** — потому что токен, выданный `client`, шлюз
считать не может.

Как отличить от дефекта сервиса за один шаг: тот же токен **напрямую в контейнер**
(мимо шлюза) даёт 200, а через шлюз — 401. Значит виноват шлюз, а не сервис.

Проверка после пересоздания (обязательна, вместе с `ExtraHosts` и функциональным пробником):

```bash
podman inspect xdiary-api-gateway --format '{{range .Config.Env}}{{println .}}{{end}}' | grep -c '^Jwt__'
# ожидание: >= 1 (на проде/деве обычно 1 — Jwt__SigningKey)
```

Env брать не «по памяти», а из живого `client` (или из `.env`), и **не печатать значение**:

```bash
podman inspect xdiary-client --format '{{range .Config.Env}}{{println .}}{{end}}' | grep '^Jwt__' > /tmp/gw_jwt.env
# затем передать эти строки в --env при podman run
```

### Auto-update и ручное пересоздание не работают одновременно

`podman-auto-update.timer` + label `io.containers.autoupdate=registry` — это **вторая
система пересоздания**. Пока она включена, ручной `update.sh`/`recreate-service.sh`
конкурирует с ней: контейнер может быть пересоздан между «я выкатил» и «я проверил»,
и проверка увидит то старое, то новое состояние.

Реальный след 2026-11-10/11: несколько «внезапных» 502 и тихих 401 на dev, которые я
принимал за дефекты сервисов.

Правила:

1. На стенде, где идёт ручная работа, таймер **выключен**:
   `sudo systemctl disable --now podman-auto-update.timer`, затем
   `systemctl is-enabled podman-auto-update.timer` → `disabled`.
2. Ярлык с контейнера снять нельзя без пересоздания — при следующем плановом
   `update.sh` его либо оставить осознанно (и не работать руками), либо убрать из
   команды `podman run`.
3. После **любого** пересоздания — функциональный пробник (`GET`/`POST` рабочего входа),
   а не только `/health`: окно, в котором `/health` уже 200, а upstream ещё нет,
   длится десятки секунд.

Состояние 2026-11-11: таймер выключен на dev и на prod; на проде ярлык
`io.containers.autoupdate=registry` остаётся у 12 контейнеров (снимется при следующем
плановом пересоздании), поэтому **ручные пересоздания на проде теперь единственный путь**.

## Исключение DO-035 (`always()` в `deploy-prod`) — оформлено по §8

Почему существует: до 2026-11-05 бэкенд-пуш не доезжал до прода, если красный фронтовый
гейт, хотя фронт в пуше не менялся. EXCEPTION живёт в `.github/workflows/deploy.yml`
(`deploy-prod.if: always() && …`).

- **Владелец:** @TL (координатор релиза), исполнение — @DO.
- **Условие существования:** `needs.smoke-api.result == 'success'`
  И (`smoke-front` зелёный ИЛИ фронт не менялся — `diff-paths.outputs.front != 'true'`).
- **Условие снятия (когда убираем `always()`):** когда `smoke-front` перестанет быть
  обязательным для бэкенд-изменений на уровне `paths` (то есть фронт-гейт не запускается
  на бэкенд-пуше и его `skipped` не блокирует прод).
- **Правило:** новое исключение в `deploy.yml` — только через ADR (ADR-027 §3.3), не
  добавлением `always()` по месту. Проверка: `python tools/check_lock.py` (правило 4).
