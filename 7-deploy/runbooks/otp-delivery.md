# Runbook — доставка OTP (Telegram)

Как устроено сейчас и что считается **ожидаемым** поведением, чтобы это не выглядело багом.

## Канал
- `Otp__Channel=telegram` — обязателен на проде: `OtpChannelGuard` при старте валит сервис, если вне dev выбран `log`.
- Отправитель: `6-msa/BC-Client/src/Client.Application/Security/TelegramOtpSender.cs` → Bot API `sendMessage`.
- Токен и чат: `Otp__Telegram__BotToken`, `Otp__Telegram__AdminChatId` (значения — только в `secrets/.env`, режим 600).

## Почему через прокси
С VPS-1 и VPS-2 **TCP к `api.telegram.org` заблокирован провайдером** (ICMP проходит, TCP 80/443 — таймаут; 12 адресов Telegram проверены). Рабочий путь:
- `xray` (systemd --user, `Restart=always`) с VLESS+REALITY из ссылки владельца, HTTP-инбаунд на `127.0.0.1:1081` и `100.88.114.23:1081` (tailscale, **не** в интернет);
- в `secrets/.env`: `HTTPS_PROXY=http://100.88.114.23:1081`, `NO_PROXY` с перечнем внутренних сервисов;
- проверка канала: `curl -x http://127.0.0.1:1081 https://api.telegram.org` → 302, `getMe` → `ok:true`.

## `ChatIdMap` не задан — и это ожидаемо
`Otp__Telegram__ChatIdMap` в проде **пуст**. Следствие: **любой** OTP уходит в `AdminChatId`, то есть в личный чат владельца, независимо от того, на какой телефон запрошен код.

Это штатно для «пары» на MVP, но означает:
1. **Любая тестовая регистрация присылает сообщение владельцу.** Перед прогоном — предупредить `→ @EX`: «сейчас придёт тестовый код, не используйте его».
2. Если владелец вводит в приложении код, пришедший ему для **другого** номера, он получит «Неверный код» — это не дефект, а следствие общего чата.
3. Хочешь раздельные чаты — заполнить `ChatIdMap` формата `+79991234567:123456789,+79997654321:987654321` и пересоздать контейнер `client` (env читается только при `podman run`).

## Поведение кода (проверено на проде)
| Свойство | Значение | Как проверено |
|---|---|---|
| TTL | 5 минут | поле `OtpExpiresAt` (миграция `AddOtpSecurity`) |
| Одноразовость | код гасится после успешного `verify` | повторный `verify` → `400 «Код уже использован.»` |
| Лимит попыток | 5 | 6-й неверный ввод → `400 «Слишком много попыток, попробуйте позже.»` |
| Перевыпуск | `POST /clients` для существующего номера → **200 + новый код** (BE-047) | проверено на проде |

## Дерево решений, если «код не приходит»
1. `getUpdates` ботом (через прокси) — если пусто, владелец не нажимал `/start` у **нашего** бота (`@xdayry_bot`); бот не может писать первым.
2. `sendMessage` вручную → если `400 chat not found`, `AdminChatId` не тот чат.
3. `curl -x http://127.0.0.1:1081 https://api.telegram.org` → если 000, туннель лёг: `systemctl --user status xray`, `journalctl --user -u xray`.
4. Логи `xdiary-client` про OTP: ошибка отправки возвращается **в ответ API** (`Fail(ex.Message)`), а не всегда пишется в лог.

## Тестовый OTP на dev: почему `000000` иногда не работает

`TestOtpPolicy` (`6-msa/BC-Client/src/Client.Application/TestOtpPolicy.cs:8`) отдаёт тестовый код только если:

1. окружение — **`Development`** (без флага), **или**
2. задан **`Clients__AllowTestOtpOutsideDev=true`** (тогда код отдаётся с предупреждением в лог).

Dev работает в **`ASPNETCORE_ENVIRONMENT=Single`** (так его поднимает `deploy.sh`), поэтому **одного
`CLIENTS__TESTOTP` недостаточно**: `verify` с `000000` вернёт **400 «Неверный код»**, хотя тестовый код
формально включён. Лечение (только dev, на прод не ставится):

```bash
# в secrets/.env на dev
CLIENTS__TESTOTP=000000
Clients__AllowTestOtpOutsideDev=true
```

Затем пересоздать сервис: `sudo -n bash recreate-service.sh client`.

**Замер 2026-11-07 (dev, `Single`):** без флага `verify(000000)` → **400**; после флага → **200**, токен
236 символов, `GET /journal/records` с ним → **200**. `POST /clients` в первые секунды после пересоздания
отдаёт **502** (`Connection refused (clients:8080)` — гейтвэй стучится раньше, чем сервис начал слушать);
это тёплое окно, а не дефект — повтор через 10–15 с даёт 200.

**Прод:** флаг никогда не выставляется автоматически (@BE 11:13: `AllowTestOtpOutsideDev` есть только в
`test-otp-toggle.sh`, ручной путь с `--reason … --confirm` по `DO-046`). В обычном режиме у прода `delivery`
в ответе **есть**, на dev при `TESTOTP` — **нет** (это проверяет `receipt-be092`).
